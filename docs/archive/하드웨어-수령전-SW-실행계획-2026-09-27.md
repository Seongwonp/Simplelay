# 하드웨어 수령 전 SW 실행 계획 — 2026-09-27

사용자 요청: 팀원이 하드웨어를 제작하는 동안 SW를 최대한 준비하고, 수령 후 RPi5·RPi4에 배포해 실물 통합한다. **이번 문서는 계획이며 구현·배포 완료 기록이 아니다.** 기존 노트북 작업목록의 세부 항목을 아래 우선순위에 맞춰 진행한다. 실기기 자료가 필요한 항목 때문에 나머지 SW 작업을 멈추지 않는다.

## 목표와 범위

수령 전 목표는 ‘PC에서 모의 기기로 앱·키오스크·서버·실행기 흐름을 완주하고, 보드별 배포와 교체 지점이 준비된 상태’다. 모의 결과를 실제 가전 검증으로 기록하지 않는다. ThinQ 전체 기종 지원을 완료 목표로 삼지 않고, 공통 구조와 지원 기능별 검사를 마련한 뒤 실제 모델별 검증을 늘린다.

주요 기존 기반: 제안 생명주기·학습 근거·실행 ID 추적·제어 중재·UART 계약·센서 검증 인터페이스. 재작성보다 기존 흐름에 작은 단위로 연결한다. 하드웨어가 도착하면 기존 H0~H1 검증을 최우선으로 전환한다. 전문가 자료·보유 가전 모델·최종 OS가 없으면 해당 의존 항목만 보류한다.

## 우선순위별 작업과 완료 조건

| 순서 | 작업 | 눈으로 확인하거나 테스트할 완료 조건 |
| --- | --- | --- |
| S0 | 현재 기준선 및 실행 환경 정리 | 실제 테스트 결과를 범위별로 기록. 앱/키오스크/서버 시작 명령, 보드 역할, 선택된 모의 설정을 재현 가능하게 정리 |
| S1 | 명령·승인·결과의 독립 계약 | 승인 후 대상·경로·동작·인자 변경 차단, 변경 불가능한 인자 스냅샷, 중복 승인 1회 처리, 만료/철회 차단. 기존 물리 경로는 우선 유지 |
| S2 | 모의 클라우드 기기 한 동작을 끝까지 연결 | 모의 공기청정기 풍량 변경을 제안→승인→실행→결과 표시까지 앱·키오스크에서 완주. 계정/PAT·인터넷 없이 재현 |
| S3 | 장애·정지·중복 실행 검증 | 접수 응답 유실·상태 지연·동시 승인·연결 복구·서버 재시작에서도 거짓 성공·자동 재전송 없음. 조회 복구와 재실행을 구분 |
| S4 | RPi5↔RPi4 모의 통신과 HW 교체 경계 정리 | 프로토콜의 분할/잘못된/늦은 메시지, 단절, 실행 중 정지에 대한 회귀. 모의 모션/센서를 주입해서 보드 간 역할을 재현하며 물리 UART 성공과 구분 |
| S5 | 설치·배포·롤백 패키지 준비 | 보드별 시작/종료/로그/설정/버전 확인 절차. 모의 모드 기본값. 새 파일 전송 실패 시 기존 키오스크 보존. 산출물과 커밋 연결 |
| S6 | 대표 시나리오와 인수 리허설 | 승인·거절·직접 완료·부재·실패·복구를 하나의 사용자 이야기로 보여주고, 합성 데이터와 실물 증거를 구분해 기록 |

실행 순서의 기본은 S0→S1→S2→S3다. S4·S5는 계약이 안정되는 대로 진행하고 하드웨어 수령이 가까우면 S2 확장보다 앞당긴다. S6 시나리오 초안은 S0에서 작성하되 완주 검증은 마지막에 한다. 이 순서는 병렬 에이전트 실행 지시가 아니다.

## S1에서 먼저 바로잡을 계약

기존 [U1-a](../ThinQ-U1a-명령-결과-승인-계약-2026-09-22.md)는 아래 사항을 보완한 뒤 구현한다.

- `ExecutionMode`(real/mock/unknown)·제어 경로·실행 결과/근거는 독립이다. cloud 모드를 추가하지 않는다.
- L1 눌림 확인과 가전 상태 확인을 같은 사실로 취급하지 않는다. 물리 결과의 기존 L1/L2/L3 근거를 보존하고 UI는 확인한 범위만 표시한다.
- 확인 불가에는 ‘접수 확인 뒤 결과 불명’과 ‘접수 여부 자체가 불명’이 있다. 후자에 ‘보냈어요/접수됐어요’를 단정하지 않는다. `stopped`는 확인 수준이 아니라 결과/중단 상태다.
- `frozen` 자료형 안에 변경 가능한 dict를 그대로 넣지 않는다. 정규화·타입/크기 제한·비유한 수치 거절 및 불변 스냅샷을 정하고 fingerprint를 계산한다. fingerprint는 동일 내용 확인용이며 사용자 인증이나 일회성 승인 토큰을 대신하지 않는다.
- 승인 ID는 서버에서 명령과 연결하고 중복 사용을 원자적으로 차단한다. 같은 내용에 대한 새로운 사용자 요청과 동일 승인 재전송은 구분한다.
- 승인 후 목적을 다시 해석해서 다른 명령을 실행하지 않는다. 현재 대상·프로필·지원 동작·상황을 실행 직전에 재검사하되 내용이 달라지면 재승인한다. 만료·부재·무효 카드를 기존 pending으로 되살리지 않는다.
- 결과 미확인으로 전체 실행 잠금을 풀어도 해당 대상의 미해결 명령 추적은 유지하는 정책을 정한다. 새 요청으로 중복 실행되는 경로와 재시작 후 복구도 검증한다. 가전 운전 전체 동안 서버 전역 잠금을 유지하는 방식은 피한다.

기존 물리 승인 고정·이력 마이그레이션·학습 조건·앱 문구를 동시에 바꾸지 않는다. 계약 테스트 → 모의 흐름 연결 → 기존 물리 경로 이전 → DB/학습 호환 검증으로 나눈다. 자연 사용 습관과 제안 수락 선호도는 계속 분리하며, 새 선호도 모델은 이번 필수 범위가 아니다.

## S2·S3: 사용자 흐름을 먼저 완주

첫 모의 동작은 ‘공기청정기 풍량 설정’ 하나다. 공통 구조에는 대상·지원 기능·인자 범위가 있으나 모든 가전의 UI와 제어를 한 번에 만들지 않는다. 미지원 동작·읽기 전용·인증 불가·기기 오프라인·오래된 상태는 각각 차단 사유를 표시한다. 경로별 준비 상태를 적용하고 로컬 물리 예외가 클라우드 실행으로 새지 않게 한다.

필수 장애 사례:

1. 앱·키오스크가 같은 승인을 동시에 전송한다.
2. 기기는 요청을 받았지만 응답이 사라진다. 자동 재전송하지 않는다.
3. 상태 이벤트가 늦거나 중복·역순으로 온다. 과거 이벤트로 새 요청을 성공 처리하지 않는다.
4. 명령 전에 이미 목표 상태다. 명령이 원인이 되어 상태가 변했다고 지어내지 않는다.
5. 승인 후 가전 등록·프로필·상황이 달라진다. 잘못된 대상으로 보내지 않는다.
6. 미전송 취소와 전송 후 결과 불명을 구분한다. API 명령 취소를 가전 정지로 표시하지 않는다.
7. 서버 재시작·앱 복귀 뒤 미해결 결과를 다시 확인한다. 성공이나 정지를 추정하지 않는다.

모의 테스트 도구는 일반 사용자 화면에 섞지 않는다. 합성 기록은 시연 출처로 구분하고 자연 습관 데이터에 넣지 않는다. 모의 API가 성공했다고 실제 ThinQ 호환이 증명된 것은 아니다.

## S4·S5: 실제 보드에 옮기기 위한 준비

현재 소스 기준 실제 Act 진입점은 `python -m rpi4.act_main`이다. `rpi4.main`은 이름과 달리 RPi5 쪽 브릿지 역할이라는 주석이 있으므로 실행 안내에서 혼동을 없앤다. 실제 모션은 여전히 모의 클라이언트 구성이고 하드웨어 사양 확인 후 어댑터를 연결해야 한다.

- RPi5: API·상황/습관·제안·앱/키오스크 연결·선택적 ThinQ 어댑터.
- RPi4: 실행 수신·모션 어댑터·센서 근거·정지 처리. 핀·좌표·힘·속도·임계값은 미확정 상태에서 실제 값으로 고정하지 않는다.
- 보드별 환경변수 예제에 비밀값을 넣지 않고 모의/실제 활성화 조건을 구분한다. 실물 장치가 준비되지 않았는데 REAL로 보고하지 않는다.
- 최종 RPi5 OS/컨테이너 구성과 현재 성공한 키오스크 실행 방식을 확인한다. 웹·네이티브 설정 저장/TTS 차이를 점검하고 한 배포 경로부터 검증한다. 소스 빌드 성공과 실제 RPi5 실행 성공은 별개다.
- 현재 `deploy_kiosk.ps1`은 원격 기존 디렉터리를 먼저 지운다. 임시 위치 전송→검사→교체 및 이전 버전 복구 방식으로 개선할 계획이다. 백엔드 코드와 정적 화면의 버전도 맞춘다.
- DB 백업/마이그레이션·데이터 디렉터리·권한·서비스 재시작·종료·로그·헬스 확인을 설치 절차에 포함한다. 서비스 자동 시작만으로 가전 동작을 자동 재개하지 않는다.
- RPi4 모의 서비스 실행 설정과 RPi5 연결 설정을 준비한다. PC에서 모의 전송을 검증하고 실제 UART 핀·포트·전기 연결은 팀원과 확인한 뒤 실물 검증한다.

## 하드웨어가 도착하면

기존 [하드웨어 연결 설계](../하드웨어-연결-설계.md)의 H0~H1 순서를 따른다. 전원·부팅·로그 → 두 보드 통신 → 가전 없이 모션/정지 → 센서 원시값 → 한 버튼 → 한 시퀀스 → 앱·키오스크 실제 흐름 순이다. 실제 ThinQ 검증은 지원 기기와 소유자 현장 확인이 가능할 때 추가한다. 구현된 모의 어댑터를 실제 어댑터로 교체하되, 실물에서 드러난 동작 차이는 테스트와 문서에 되돌려 반영한다.

## 진행·완료 기록

작업마다 문제→재현→작은 수정→관련 테스트→사용자 흐름 확인을 남긴다. 공통 실행 계약·DB·정지 경로를 바꾸면 관련 전체 회귀를 수행한다. UI 문구/배치 변경은 일반·큰 글씨에서 확인하며 골든은 검토 후 갱신한다. 커밋 단위는 되돌릴 수 있는 작업 묶음으로 나누고, 테스트 수와 미검증 범위를 개발 로그에 남긴다.

이번 요청에서 먼저 착수할 구현 후보는 **S0 기준선 점검 후 S1 독립 명령·승인 계약**이다. 실제 ThinQ 호출·계정 설정·기기 실행은 이번 계획 작성에 포함되지 않는다.
