### 유지할 강점

- 제안의 `appliance_id`가 사용 이력 → 패턴 후보 → 승인 실행까지 이어진다. 기존 DB를 위한 열 추가 마이그레이션도 준비했다.
- 앱 재시작 후 pending job을 복원하며, 통신 유실을 물리 실행 실패로 단정하지 않고 `unknown`으로 구분한다.
- 음성 실패 이유와 대체 조작 동선을 화면에 남긴다.
- 성공 문구를 “버튼 조작을 마쳤어요”로 표현해 조리 완료와 구분한다.
- 폰/키오스크의 골드 강조색, 주요 행동 문구, 접근성 개선 방향이 일관된다.
- 키오스크는 800×480 설계 캔버스를 큰 화면에서 비율 확대한다. 큰 화면에 정보를 더 넣는 부담을 피한다.

## 4. 우선 결함 목록과 완료 기준

### R1 · P0 · 제안 승인까지 실행 대상 검증 통합

**심각도: 치명.** 직접 실행 라우트의 가전 존재 검사가 제안 승인 경로에는 없다.

근거: [router.py](../../rpi/api/router.py):81,330 · [suggestions.py](../../rpi/intent/suggestions.py):250 · [service.py](../../rpi/api/service.py):426.

실패 경로: A 가전 제안 생성 → A 삭제와 노드 해제 → 남은 제안 승인 → `submit_purpose()` → 노드 없음 → 기본 로컬 컨트롤러 반환. 삭제되지 않았더라도 노드가 없는 커스텀 가전의 무조건적인 로컬 폴백은 대상 가전을 보장하지 않는다.

- [ ] 공통 서비스에서 가전 존재·명시적 실행 대상·설치 상태를 검증한다. 라우터 하나에만 검사를 추가하지 않는다.
- [ ] 존재하지 않거나 준비되지 않은 대상은 분류된 오류로 거부한다. 클라이언트가 모두 “다른 작업 실행 중”으로 표현하지 않게 한다.
- [ ] 삭제 시 pending 제안을 무효화하고, 승인과 삭제가 겹치는 경우의 규칙을 정한다. 권장: 실행 접수와 대상 확정을 원자적으로 처리하고 활성 작업의 삭제는 거부한다.
- [ ] 폰 제안 화면에서 알 수 없는 ID를 현재 선택 가전으로 바꿔 보여주지 않는다. “대상 가전 정보를 확인해 주세요”로 안내하고 승인을 막는다. 현재 폴백: `app/lib/screens/suggestion_screen.dart`:114–121.
- [ ] 일반 실행·수동 실행·제안 승인·삭제/승인 동시 요청 모두 검증한다. 거부한 경우 mock 컨트롤러 호출 횟수가 **0**이어야 한다.

완료 기준: 삭제/미설치 가전을 어떤 진입점에서도 다른 액추에이터로 실행하지 않는다. 테스트·응답 코드·양쪽 화면 안내가 일치한다.

예상: SW 1~2일. 데이터 모델·기존 내장 가전의 명시적 로컬 매핑에 따라 늘어날 수 있다.

### R2 · P0 · 실제 실행과 모의 실행의 의미 일치

**심각도: 중요, 물리 연결 전에 완료.** 데모 토글이 켜지면 화면은 “실제 조작이 아닙니다”라고 표시하지만 HTTP 실행은 실제 서버로 전송된다.

근거: [status_screen.dart](../../app/lib/screens/status_screen.dart):102 · [voice_screen.dart](../../app/lib/screens/voice_screen.dart):149 · [suggestion_screen.dart](../../app/lib/screens/suggestion_screen.dart):213,260 · [demo_provider.dart](../../app/lib/providers/demo_provider.dart).

- [ ] 두 의미를 구분한다: **모의 실행 = 실제 전송 없음**, **실기기 리허설 = 실제로 움직임**.
- [ ] 권장 구현은 모의 실행에 별도 fake 서비스/전송 경로를 주입하는 것이다. 화면 배너만 바꾸어 전송 차단을 대신하지 않는다.
- [ ] 실행별 `execution_mode` 또는 출처를 상태와 이력에 보존한다. 진행 중 전역 토글 변경으로 현재 작업의 표시가 바뀌지 않게 한다.
- [ ] 모의 실행 상태의 음성·수동·제안 승인에서 실제 HTTP/BLE execute 호출이 0인지 검증한다. 기존 실제 작업의 정지 기능은 유지한다.
- [ ] 지연된 데모 타이머 결과가 다음 실제 job을 덮지 못하게 취소/세션 식별을 적용한다.

완료 기준: 화면의 실제/모의 표시가 해당 job의 전송·결과 출처와 항상 일치한다.

예상: SW 1~2일. R1과 함께 최우선이며 UI 개편보다 먼저 진행한다.

### R3 · P0 · 다중 폰 동기화에서 명시적인 삭제만 전파

**심각도: 중요.** 현재 폰에 없는 모든 서버 가전을 유령으로 간주해 삭제한다.

근거: [settings_screen.dart](../../app/lib/screens/settings_screen.dart):383,402–440 · [appliance_provider.dart](../../app/lib/providers/appliance_provider.dart).

실패 경로: 보호자 폰 A에 선풍기, 폰 B에 다른 가전 등록 → A가 “다시 동기화” → A 로컬에 없는 B 가전과 해당 노드 등록 삭제. 마지막 로컬 커스텀 가전 삭제가 실패하면 동기화 버튼 조건까지 사라진다.

- [ ] 서버 목록에만 존재한다는 이유로 삭제하지 않는다. 서버 가전은 내려받아 병합한다.
- [ ] 이 폰에서 명시적으로 수행한 삭제만 tombstone/outbox에 기록하고 재전송한다. 성공한 항목만 대기열에서 제거한다.
- [ ] pending upsert/delete·실패 상태를 재시작 후에도 유지한다. 같은 ID의 upsert/delete 순서를 보존한다.
- [ ] 서버 ID를 기준으로 병합하며 로컬 사진 경로는 해당 폰의 로컬 데이터로 유지한다.
- [ ] 마지막 가전이 없어도 미완료 동기화가 있으면 재시도할 수 있게 한다.
- [ ] 두 폰, 오프라인 등록·삭제, 재시작, 서버 오류, 부분 성공을 테스트한다. 동시 편집 충돌은 조용한 덮어쓰기 대신 버전 충돌 안내 등 명시적 규칙으로 처리한다.

완료 기준: A 폰의 동기화가 B 폰의 가전을 임의 삭제하지 않고, 삭제 실패 데이터도 사용자가 재입력하지 않고 복구한다.

예상: SW 2~3일. 일정이 부족하면 먼저 무차별 삭제를 제거하고, 수동 재시도부터 제공한다.

### R4 · P1 · 알림함의 미확인과 빈 목록 분리

**심각도: 중요.** 기존 목록은 통신 실패 시 유지되지만 최초 조회 실패는 “아직 알림이 없어요”로 보인다.

근거: [care_events_screen.dart](../../app/lib/screens/care_events_screen.dart):42,73 · [care_events_provider.dart](../../app/lib/providers/care_events_provider.dart):76.

- [ ] loading/error/empty/data와 마지막 성공 확인 시각을 모델링한다.
- [ ] 실패 시 기존 목록 유지 + “새 알림을 확인하지 못했어요” + 재시도. 빈 목록에서도 재시도 가능하게 한다.

완료된 과거 devlog는 지우지 않고 새 기록을 추가한다. 테스트 개수에 골든을 포함했는지 명시한다. 완료 체크에는 검증 결과와 커밋을 연결한다. UI 변경은 전후 캡처와 시나리오를 남긴다.

## 9. 일정이 부족할 때

- 유지: R1/R2/R3, 실제 한 가전 폐루프, 물리 정지 확인, 일치하는 실행 결과, 기본 조작 접근성.
- 축소: D4 전면 관리 화면은 최소 가전 상세로, D5 안내는 짧은 문구/동선 개선으로.
- 보류: 새 모델, 카메라 버튼 자동 인식, 복잡한 보호자 플랫폼, 추가 차트·애니메이션, 가전 종류 확대.
- 제출 전 새 기능을 추가하지 않는다. 결함 수정은 회귀 테스트와 시연 재확인 후 반영한다.
- 목표 날짜가 밀리면 “mock E2E 완료 / 실제 기기 완료 / 사용자 확인 완료” 중 어느 단계인지 기록한다. 일부 성공을 전체 완료로 바꾸지 않는다.

## 10. 기존 문서와의 관계

- **이 문서:** 9/9 교차 평가 후 실행 우선순위·인계의 시작점.
- **결선로드맵:** 기존 일정·주차 목표·역사적 완료 기록. 날짜가 충돌하면 조정 근거를 양쪽에 기록한다.
- **앱 개선 백로그:** 기존 A/B 항목의 상세 근거. D1↔A1, D2/D3/D4/D5/D6↔A2, R4↔A4 잔여, D4↔B2, H2↔B5, H1의 디스플레이 점검↔B6.
- **개발현황:** 현재 무엇이 코드/실기기에서 완료됐는지의 요약. 이 계획을 만들었다는 이유로 상태를 완료로 바꾸지 않는다.
- **디자인 시스템·접근성 체크리스트:** 구현과 어긋난 예전 지침(파형/차트 확대 권고 등)은 D 작업 완료 시 갱신한다. 체크박스만 보고 구현을 추정하지 않는다.
