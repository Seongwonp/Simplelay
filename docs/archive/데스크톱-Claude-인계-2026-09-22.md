# 데스크톱 Claude 인계 — 컨설팅 반영과 소프트웨어 가전 제어

> **독립 평가 추가:** [Claude 평가 원문 및 Codex 검토](Claude-계획평가-2026-09-22.md). HA 경유 우선안은 확정하지 않고 시나리오·보유 기기·일정부터 확인하는 방향으로 재검토한다. 평가 의견과 수용/보완 사항을 구분했으며 코드 변경은 없다.

## 최신 논의 — LG 가전 지원 범위와 실기기 확보

- 사용자는 LG 가전을 최대한 폭넓게 지원하는 방향을 원한다. 목표는 **ThinQ API가 공개한 기능을 수용할 수 있는 공통 구조**이며, 모든 LG 모델·모든 원격 기능을 지원한다고 보증하는 것은 아니다.
- 제안 구조: 계정의 지원 기기 조회 → 모델별 제공 기능 확인 → 앱/키오스크에 가능한 조회·제어만 표시 → 사용자 허용 정책 안에서 제안/실행. 기능 자동 발견·매핑이 어디까지 가능한지는 실제 API 프로필과 HA 엔티티를 조사한 뒤 확정한다. 아직 구현되지 않았다.
- 첫 실기기 검증을 한 대로 시작하는 것은 지원 범위를 한 대로 제한하려는 뜻이 아니다. 실제 확인한 모델·기능부터 검증 목록을 늘린다. 상태 조회만 되는 기기를 원격 실행 가능한 것으로 표시하지 않는다.
- 실제 연동 증거를 확보하려면 지원되는 실제 가전에 접근해야 하지만, 새로 구매하거나 사용자 집으로 옮겨야 하는 것은 아니다. 집·팀원·지인의 보유 가전을 소유자 동의 아래 활용할 수 있는지 먼저 확인한다. 소유자가 현장에서 결과를 확인할 수 있어야 한다.
- 전문가에게 테스트용 가전 또는 개발용 테스트 환경 제공 여부를 문의하는 방안도 있다. 제공되는 환경이 실제로 존재하거나 사용할 수 있다고 확인한 것은 아니다.
- 기기 확보 전에는 모의 응답으로 목록·기능별 UI·인증 오류·통신 오류 처리를 개발할 수 있다. 모의 검증과 실제 가전 연동 검증은 분리해 기록한다. 현재 보유 모델·테스트 계정·실행 가능한 기능은 미확정이다.
- 다음 자료는 **ThinQ 앱에 등록해 사용하는 가전의 종류·모델명·테스트 가능 여부**다. HA 경유/직접 ThinQ 선택과 구현 범위는 이 자료를 바탕으로 판단한다. 무승인 기기 실행이나 구매는 이번 논의에서 요청되지 않았다.

작성일: 2026-09-22. **다음 세션은 이 문서부터 읽는다.** 사용자는 데스크톱 Claude가 이미 알고 있는 LG 기술문서 맥락과 이번 컨설팅 내용을 합쳐 후속 방향을 검토하려 한다. 이번 인계는 계획과 조사 결과이며, ThinQ/Home Assistant 연동이 구현됐다는 뜻은 아니다.

## 4. ThinQ 조사 결과 — 공개 문서로 확인한 범위

정확한 명칭은 **LG ThinQ / ThinQ Connect API**다. Home Assistant 공식 문서는 ThinQ Connect API를 이용한 LG 가전 제어와 LG 계정 기반 PAT 발급 절차를 안내한다. LG 클라우드를 이용하므로 해당 연동은 인터넷이 필요하다.

공식 연동 문서의 기능 예시:

| 종류 | 문서에 기재된 기능 예시 |
| --- | --- |
| 에어컨 | 전원·온도·운전 모드·풍량 |
| 공기청정기 | 전원·모드·풍량 |
| 세탁기/건조기 | 시작·일시정지·상태 조회 |
| 냉장고 | 온도·급속 냉각 등 |
| 전자레인지 | 상태·팬·조명 등. 가열 시작을 지원한다고 가정하지 않는다. |

이는 전체 지원 범위의 예시다. **ThinQ 앱 등록 가능 여부, API 조회 가능 여부, 원하는 기능의 제어 가능 여부는 각각 확인해야 한다.** 특정 한국 모델의 기능·원격 시작 조건·지원 지역은 이번 조사로 확정하지 않았다. 구형 모델은 상태 갱신이 느릴 수 있으므로 즉시 상태 피드백이 온다고 가정하지 않는다.

출처(2026-09-22 확인):

- [Home Assistant 공식 LG ThinQ 연동 문서](https://www.home-assistant.io/integrations/lg_thinq/) — 인증, 클라우드 의존, 기기/기능 목록, 업데이트 특성.
- [LG 공식 PAT 발급 페이지](https://connect-pat.lgthinq.com/) — 로그인 후 발급. 이 세션에서는 로그인·토큰 발급을 하지 않았다.
- [LG ThinQ Connect 개발자 페이지](https://smartsolution.developer.lge.com/en/apiManage/thinq_connect) — 참조 주소. 이번 브라우징 도구로 본문 접근에 실패했으므로 상세 API 계약·요금·이용 조건을 확인했다고 쓰지 않는다.

Home Assistant에 보이는 ‘소프트웨어 버튼 맵’은 물리 화면의 좌표일 필요가 없다. 엔티티·지원 속성·호출 가능한 동작을 가리키는 것으로 해석할 수 있지만, 전문가가 약속한 실제 자료를 받은 뒤 용어를 확정한다.

## 5. Codex 제안 — 먼저 작은 협력 시나리오를 증명

### 단계 A: 시나리오와 실제 보유 기기 확인

‘저녁 귀가’ 같은 상황 하나를 고른다. 예시로 상황/시간/사용 이력을 보고 연결 가능한 공기청정기를 준비하고, 식사 시간에는 기존 전자레인지 사용을 제안한다. 이는 후보 시나리오이며 보유 기기와 감지 수단에 맞춰 바꾼다. 귀가 인지나 다중 사용자 식별이 이미 되는 것처럼 설명하지 않는다.

성공 조건: 왜 필요한지, 어떤 신호가 들어오는지, 가전 두 대가 각각 무엇을 하는지, 어떤 행동에 승인이 필요한지, 부재/거절/실패 시 어떻게 달라지는지 한 장으로 설명할 수 있다.

### 단계 B: 연동 방식 선택

| 후보 | 장점 | 비용/제약 |
| --- | --- | --- |
| SimpleLay → ThinQ 직접 | LG 기기 하나에 집중하고 중간 서비스를 줄일 수 있음 | 인증·기기 프로필·제어·상태 이벤트·호출 제한 처리를 직접 담당 |
| SimpleLay → Home Assistant → ThinQ | 기존 ThinQ 연동을 사용하고 이후 다른 연동도 검토하기 쉬움 | HA 설치/운영과 별도 인증·장애 지점 추가. ThinQ의 클라우드 의존은 그대로 |

**초기 검토 우선안은 Home Assistant 경유**다. 전문가가 제안한 자료와 맞고, 우리 개발 시간을 상황 판단·기존 물리 가전과의 협력에 집중할 수 있다는 판단이다. 단, HA 실행 환경과 실제 기기 지원 여부를 확인한 뒤 결정한다. HA 도입을 이유로 기존 RPi5 OS를 재설치하지 않는다.

### 단계 C: 읽기부터, 기기 하나씩

1. 소유자가 계정/토큰을 로컬에 설정하고 기기 목록과 지원 동작을 조회한다.
2. 목표 기능과 상태 반환이 실제 모델에서 가능한지 확인한다. 지원 안 되는 가전이면 시나리오를 바꾸고 모델명을 문서에 남긴다.
3. 사용자와 확인한 동작 하나를 실행하고 요청 접수·상태 변경·실제 결과를 구분해 기록한다. 처음부터 여러 기기를 자동 실행하지 않는다.

### 단계 D: 기존 제어 구조에 최소 어댑터 추가

구현 전 `rpi/api/service.py`, `rpi/intent/`, `rpi/services/controller_factory.py`와 가전 등록 모델을 읽는다. 물리 버튼 좌표와 API 동작을 억지로 같은 값으로 저장하지 않는다. 공통의 목적·대상·허용 정책 아래 실행 수단을 선택하고, 기기별 지원 동작을 검사하는 구조를 제안한다.

연동 실패를 감지했다고 물리 버튼으로 자동 전환하면 중복 실행할 수 있다. 접수 여부가 모호하면 확인 불가로 남겨 재조회/사용자 확인을 거친다. 기존 잠금·정지·학습 출처 구분을 우회하는 별도 실행 경로를 만들지 않는다.

### 단계 E: 자동화 정책과 고장 시 동작 확정

- 행동마다 사전 허용 자동 실행 / 실행 전 승인 / 수동 전용을 정한다. 가열 기기의 무승인 자동 실행은 현재 구현 범위에 없다.
- RPi 측은 상황·습관·정책·실행 게이트를 담당하고, ThinQ 클라우드는 지원 가전 명령/상태 연결을 담당하도록 제안한다. 로컬 판단이 가능해도 클라우드 가전 제어까지 오프라인으로 된다는 뜻은 아니다.
- 명시적 부재·센서 unknown·인터넷 단절·API 응답 유실·서버 재시작·부분 성공을 각각 정의한다. 한 기기 성공 후 다른 기기 실패 시 되돌림이 항상 가능한 것은 아니다.
- 물리 정지 경로와 가전 자체 운전 정지는 HW 담당과 별도로 검증한다. API/키오스크만을 독립 비상정지 수단으로 취급하지 않는다.

### 단계 F: 시연과 증거

물리 가전 1대와 소프트웨어 제어 기기 1대의 협력을 우선 증명한다. 직접 조작 대비 사용자 행동 감소, 상황이 달라졌을 때 제안 변화, 승인/취소, 끊김 후 복구 시간, 중복 실행 여부를 기록한다. 수치 목표는 실제 기기 특성을 확인한 뒤 정하며 아직 측정값은 없다.

## 7. 데스크톱 Claude에게 요청할 첫 결과물

1. 알고 있는 LG 기술문서 요구와 본 문서를 대조해 확정 사실·추정·빠진 내용을 구분해 달라.
2. 보유 기기/자료가 없는 상태에서 연동 가능하다고 단정하지 말고 필요한 질문부터 추려 달라.
3. 생활 시나리오 후보 2개 중 하나를 추천하고 이유를 설명해 달라.
4. 직접 ThinQ와 HA 경유 중 최소 구현 경로를 검토하고, 실제 조회→단일 제어→물리 가전 협력 순서의 작업 단위를 제안해 달라.
5. 기존 공감지능/제어 코드를 재사용할 지점과 새로 필요한 부분, 자동화 정책·정지 경계·검증 기준을 정리해 달라. 현재 요청 범위를 넘어 바로 대규모 구현하지 않는다.
