## 1. RPi5 — 백엔드 + 키오스크

### 1-1. 첫 설치

Pi에 SSH로 붙어서:

```bash
curl -sSL https://raw.githubusercontent.com/Seongwonp/Simplelay/main/scripts/setup_rpi.sh -o setup_rpi.sh
chmod +x setup_rpi.sh && sudo ./setup_rpi.sh
```

스크립트가 하는 일: hostname → 패키지 → git clone → venv → systemd 유닛 →
logrotate → cage+Chromium 키오스크 → 동작 확인.

**확인**: 마지막에 `/health`가 JSON을 돌려주면 백엔드는 산 것이다.
키오스크 화면에는 "키오스크 화면이 아직 없어요"가 뜬다 — 정상이다(다음 단계에서 넣는다).

### 1-2. 키오스크 화면 넣기

PC에서:

```powershell
.\scripts\deploy_kiosk.ps1 -PiHost simplelay.local
```

`simplelay.local`이 안 잡히면 `-PiHost <IP>`로. 그다음 Pi에서:

```bash
sudo systemctl restart simplelay simplelay-kiosk
```

키오스크 패널은 **15.8형 터치 패널**이다(2026-09-14, 7인치에서 변경). 제품 사양표·사용설명서
기준 1920x1080 @60Hz, 10점 터치, Type-C PD 전원(8.5 W)이다(`docs/하드웨어-연결-설계.md` §0-1).
아래는 RPi5에 물렸을 때의 실제 동작 확인이다.

- [ ] **케이블 세 가닥** — ① RPi5 micro-HDMI ↔ 모니터 HDMI(**동봉 케이블은 HDMI–mini HDMI라
      맞지 않는다**, micro-HDMI–HDMI 케이블 준비) ② RPi5 USB-A ↔ 모니터 **Type-C 데이터 포트**
      (터치) ③ 제조사 PD 어댑터 ↔ 모니터 **Type-C 전원 포트**. 두 Type-C 포트를 바꿔 꽂지 않는다
- [ ] **터치가 안 되면 HDMI만 연결했는지 먼저 본다** — 설명서상 HDMI만으로는 터치가 되지 않는다
- [ ] **사양표·설명서에 없는 것** — 화면 방향 설정, RPi5 실제 출력 모드, 데이터 포트 연결의
      RPi5 전원 영향. 결과는 설계 문서 §0-1과 `docs/전력버짓.md` §2-3에 적는다
- [ ] **음성 안내 출력** — 키오스크 음성 안내가 HDMI로 모니터 스피커에서 나오는가(음량 기록)
- [ ] **기본 해상도** — 실제 출력 모드가 패널 기본 해상도와 같은가
      (`cat /sys/class/drm/card*-HDMI-A-*/modes`의 첫 줄). 1920x1080이 아니면 15인치
      테스트의 수치를 실제 값으로 바꾼다
- [ ] **화면 방향** — 가로로 뜨고 회전·뒤집힘이 없는가
- [ ] **전체 화면 표시** — 상하좌우가 잘리지 않고(오버스캔 없음), 남는 쪽은 배경색 여백뿐인가
- [ ] **부팅 자동실행** — 전원만 넣고 손대지 않아도 키오스크 대기 화면까지 뜨는가
- [ ] 대기 화면을 누르면 가전 선택으로 들어가는가
- [ ] **터치 인식** — 마우스 없이 터치만으로 조작되는가
      (`libinput list-devices`가 있으면 터치 장치로 잡혔는지도 본다)
- [ ] **터치 좌표** — 중앙과 네 모서리 가까운 버튼을 눌러 손끝 위치와 반응 위치가 맞는가
- [ ] **화면 가장자리 터치** — 가장자리 가까운 조작(정지 버튼, 오른쪽 아래 톱니 2초 길게)이
      한 번에 되는가
- [ ] **큰 글씨** — 설정 → 큰 글씨 모드에서도 잘림·겹침이 없는가
- [ ] **1.5~2m 거리 가독성** — 서서 보는 거리에서 가전 이름·조작 가능 여부·버튼 이름이
      읽히는가 ← 크기는 권고값으로 정했지 실측이 아니다. 안 되면
      `rpi5-touchscreen-app/lib/widgets/kiosk/*.dart`의 fontSize를 올리고
      `deploy_kiosk.ps1` 다시 실행 (정보를 더 넣지 않는다)
- [ ] **너무 크거나 비어 보이지 않는가** — 판단과 사진만 남긴다. 레이아웃 재설계는 하지 않는다(백로그 B6)
- [ ] **밝기** — 실내 조명·시연장 조명에서 읽히는가(사양 250 cd/m²). 쓴 밝기 설정값을 기록
- [ ] **장시간 구동** — 30분 이상, 리허설 길이 이상 켜 두어도 화면 꺼짐·깜박임(설명서상 전원
      부족 증상)·절전 진입·터치 끊김·과열이 없는가. 구동 시간을 기록

**느리면 즉시 후퇴:**

```bash
sudo systemctl edit simplelay-kiosk    # ExecStart 의 /kiosk/ → /ui
sudo systemctl restart simplelay-kiosk
```

구형 HTML 키오스크는 백엔드에 딸려 있어 항상 뜬다. 대신 오늘 한 접근성·카피 개편은
그쪽에 없다(`rpi/touchscreen/index.html`에 아직 `✦ AI 제안`이 있다).

### 1-3. 재부팅 내성

- [ ] `sudo reboot` 후 전원만으로 키오스크가 다시 뜨는가
- [ ] `sudo systemctl kill -s SIGKILL simplelay` 후 되살아나는가 (Restart=always)

**재부팅 뒤에 남는 것과 없어지는 것이 다르다.** 잃었을 때 어느 쪽으로
틀리는지가 기준이라 일부러 갈라 놓았다:

| | 재부팅 뒤 |
|---|---|
| 가전 준비 상태(F1) | **없어진다** — 그 사이 선이 빠졌는지 아무도 확인하지 않았다 |
| 안부 확인 쉬기(F5) | **남는다** — 여행 이틀째의 재부팅이 남은 닷새의 알림을 되살리면 안 된다 |
| 사용 이력·알림·가전 등록 | 남는다 (SQLite) |

- [ ] `SIMPLELAY_DB_PATH`가 설정돼 있는가 — **없으면 F5의 쉬기도 재부팅에
      사라진다**(개발 PC와 같은 인메모리 동작)

### 1-4. 가전을 '조작 가능'으로 만들기 (F1 — 새 단계, 빠뜨리기 쉽다)

**노드를 등록했다고 실행되지 않는다.** 주소를 적어 넣은 것은 "연결됐다"가
아니라서, 서버는 준비 상태를 보고받기 전까지 그 가전의 실행을 **412로
거절한다**(컨트롤러를 아예 부르지 않는다). 폰·키오스크에는 `아직 연결되지
않았어요`가 뜨고 버튼이 비활성이다.

네 축을 전부 보고해야 `조작 가능`이 된다:

```bash
curl -X POST http://simplelay.local:8000/readiness/<가전id> \
  -H 'Content-Type: application/json' \
  -d '{"transport":true,"motion":true,"sensor":true,"calibration":true,
       "calibration_profile_version":"fan-cal-1"}'
```

- [ ] 보고 전에는 실행이 412로 거절되고 화면이 이유를 보여주는가
- [ ] 네 축을 보고한 뒤 그 가전만 실행되는가
- [ ] **서버를 재시작하면 다시 '준비 안 됨'으로 돌아가는가** (설계다 — 그
      사이 선이 빠졌는지 아무도 확인하지 않았으므로)
- [ ] 10분(TTL)이 지나면 다시 보고를 요구하는가

> `calibration_profile_version`은 실행 이력·CSV에 스냅샷으로 함께 남는다.
> 좌표를 다시 맞추면 성공률이 통째로 달라지므로, **버전을 바꿔 가며 실험할
> 때는 매번 새 값으로 보고**해야 나중에 그 숫자를 해석할 수 있다.

**노드가 없는 커스텀 가전은 실행할 수 없다.** 로컬 컨트롤러는 내장 가전 위에
얹힌 갠트리이지 아무 가전이나 되는 실행기가 아니다. 데모용으로 로컬 갠트리에
물렸다면 그렇게 밝혀야 한다:

```bash
SIMPLELAY_LOCAL_APPLIANCES=aircon   # 쉼표로 여러 개
```

## 5. 검증 우선순위 — 여기가 진짜 목적

**컴파일과 렌더는 PC에서 다 확인했다. 아래는 실기기에서만 알 수 있는 것들이고,
위에서부터 위험한 순서다.**

### 1순위 — 정지가 실제로 통하는가

이 프로젝트에서 정지 관련 결함이 **네 번** 나왔다. 매번 다른 이유였다.

- [ ] 실행 중 키오스크 **긴급 정지** → 실물이 즉시 멈추는가
- [ ] 실행 중 폰 **긴급 정지** → 같은가
- [ ] 게이트웨이 보드의 **물리 E-STOP 버튼** → 전체 노드가 멈추는가
      (8/29에 배선했다. 그 전에는 RPi5에 그 신호를 읽는 코드가 아예 없었다)
- [ ] 유휴 상태에서 정지를 눌러도 다음 실행이 정상 시작되는가
- [ ] **승인 직후~시작 직전**에 정지 → 실행이 아예 시작되지 않는가
      (여기가 마지막으로 막은 구멍이다)

**세 시각을 구분해 잰다.** "눌렀더니 멈췄다"는 측정이 아니다:

| | 어디서 나오나 |
|---|---|
| ① 소프트웨어 정지 접수 | `GET /history.csv`의 `stop_requested_at` |
| ② 실행 루프 종료 | 같은 CSV의 `stop_latency_seconds`(② − ①) |
| ③ **물리 동작 중단** | **아직 없다** — 눈·영상으로 재고 따로 적는다 |

③이 CSV에 없는 것은 장치가 스스로 보고해야 알 수 있기 때문이다.
**`stop_latency_seconds`를 "물리 정지 지연"으로 발표하면 안 된다** —
그 숫자는 서버가 접수한 뒤 실행 루프가 멈추기까지이고, 모터가 실제로
서는 시간은 그 뒤에 더 붙는다.

### 2순위 — ESP-NOW 왕복

- [ ] BLE 광고와 ESP-NOW가 **동시에** 도는가 (겸용의 유일한 진짜 위험)
- [ ] 버튼 20개 × 긴 라벨로 250바이트를 넘겨 **조각 분할 왕복**이 되는가
- [ ] 노드 전원을 끈 채 실행 → 25초 기다리지 않고 **즉시** 오류가 올라오는가
      (송신 콜백 기반으로 바꿨다)
- [ ] 대기 중인 `rid`와 다른 응답이 버려지는가 (로그 `dropping node response`)

### 3순위 — 크로스코어 동기화 (펌웨어)

- [ ] 실행이 블로킹하는 동안 도착한 프레임이 버려지는가
      (로그 `frame dropped -- still handling`)
- [ ] `esp_now_register_recv_cb` 콜백이 ISR이 아니라 Wi-Fi 태스크에서 불리는가
      — `portENTER_CRITICAL`(비-ISR판)을 쓴 전제다

### 4순위 — 폐루프

- [ ] 센서 캘리브레이션 (전류·음향 임계값)
- [ ] 버튼 1개 소요 시간 p95 측정 → `SIMPLELAY_UART_*_TIMEOUT` 조정
- [ ] 재시도가 실제로 좌표를 보정하는가

## 알아둘 함정 (이미 겪은 것들)

- **`install.platformio.org`는 죽었다.** DNS 레코드가 없다. PyPI로 받아야 한다
- **PlatformIO는 Python 3.14를 지원하지 않는다.** 3.11 전용 venv를 썼다
  (`%USERPROFILE%\.pio-venv`)
- **`SIMPLELAY_ACT_MODE`를 안 켜면 실물이 안 움직인다.** 기본값이 mock이라 화면상으로는
  전부 성공한 것처럼 보인다 — 가장 헷갈리는 실패 모드다.
  실행 이력의 `execution_mode`로 구분된다(`GET /history.csv`). **원격 노드로 나간
  실행은 노드가 자기 모드를 보고하기 전까지 `unknown`이다** — 원격이라는 사실만으로
  real이라고 추측하지 않기 때문이다(저쪽 보드가 mock일 수 있다)
- **노드를 등록해도 준비 상태를 보고하기 전에는 실행이 412로 거절된다** (1-4 참고).
  하드웨어를 붙인 첫날 "아무것도 안 된다"의 1순위 원인이다
- **백엔드에 CORS 미들웨어가 없다.** 키오스크를 다른 포트로 띄우면 `/status`·`/events`가
  전부 막힌다. `/kiosk`로 같은 오리진에서 서빙하는 이유가 이것이다
