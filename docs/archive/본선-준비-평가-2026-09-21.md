# 본선 준비 평가 — 2026-09-21

## 평가 범위와 결론

**사용자 확인 반영(9/21): RPi5에서 키오스크 화면을 실제로 띄우는 데 성공했다.** 터치패널을 사용하는 구성이며, 현재 화면이 실행되지 않는다고 평가하지 않는다. 아래 웹 배포 관련 사항은 저장소의 배포 스크립트와 소스 사이의 정적 검토 결과다. 실제 성공한 실행 방식·산출물과 대조하기 전 현재 장치에서 재현된 장애로 취급하지 않는다. 설정 보존·음성 안내·터치 완주는 화면 표시 성공과 별도 검증 항목이다.

현재 체크아웃의 공개 문서, 앱·키오스크·서버·Act 진입점·배포 코드와 저장된 골든 화면을 검토했다. 비공개 LG 원문 자료는 열거나 외부로 전송하지 않았다. 실제 폰·RPi·모터 동작은 이번 평가에서 확인하지 않았다.

**기능 폭과 SW 구조는 충분히 갖췄으나, 배포 완성도와 실물 증거가 부족하다.** 신규 기능 추가보다 기존 기능이 최종 배포 환경에서 끝까지 동작하도록 마감하는 것이 우선이다. 앱과 키오스크의 하드웨어 독립 영역을 먼저 완성하고, 하드웨어 수령 후 통합 검증으로 제품 완성을 판정한다.

공식 심사점수나 수상 확률을 산출할 근거는 없다. 아래 평가는 준비도에 대한 판단이다.

## 대회 방향과 연결

- 저장소의 LG OT 요약: 공감지능, 공간 이해·초개인화, 온디바이스·클라우드 추론 경계.
- 저장소의 예선 피드백: 구동 전력·전원 관리, 버튼맵 일반화, 장착 안정성, 누름·다이얼 오차 보정.
- 공개 제24회 안내의 스마트가전 방향은 사용자를 이해하고 먼저 행동하는 개인 맞춤형 AI 가전 서비스다.
  출처: https://www.newswire.co.kr/newsRead.php?no=1033827 및 해당 발표의 첨부 개요.
- 검색된 완성도 60·독창성 20·활용성 20 배점 문서는 제23회 표기이므로 **올해 확정 배점으로 사용하지 않는다**. 이번 확인에서는 제24회 상세 배점을 확정하지 못했다.

발표의 중심은 ‘기존 물리 버튼 가전을 사용자의 생활 맥락에 연결하고, 승인받아 조작하며, 결과까지 확인한다’가 적합하다. 패턴 빈도 통계를 개인 식별 기반 초개인화로, 모의 관측 API를 실제 공간 인지로 발표하지 않는다. LG 플랫폼 연계는 실제 서비스 호출·결과 활용을 확인한 범위만 주장한다.

## 현재 강점

- 앱: 음성·수동 제어, 대상 가전 선택, 제안 승인·거절, 실행 이력, 등록·편집·동기화, 큰 글씨·음성 안내까지 사용자 흐름이 있다.
- 작업 ID 추적, 미완료 작업 복원, 결과 불명 상태, 동기화 충돌 방지 등 정상 화면 밖의 상태도 다룬다.
- 키오스크: 대상·현재 누르는 버튼·검증·진행·정지 동작을 큰 화면에 보여준다. 저장된 1920×1080 골든은 시연 가독성이 좋다.
- 서버: 비동기 실행, 제어권 중재, 준비 상태 차단, 이력 영속화, 테스트 가능한 어댑터 분리가 장점이다.
- 모의 구현과 실기기 검증을 구분하는 최신 개발현황 문서는 정직하다.

## 먼저 해결할 코드·배포 문제

### P0 — Flutter 웹 배포와 네이티브 설정/TTS 코드 충돌

근거:

- `scripts/simplelay-kiosk.service`는 Chromium에서 `/kiosk/`를 연다.
- `rpi5-touchscreen-app/lib/main.dart:26`은 시작 화면 생성 때 `KioskSettingsStore()`를 직접 만든다.
- `services/kiosk_settings_store.dart:72,87`은 생성 과정에서 `File`과 `Platform.environment`를 사용한다. `load()`의 예외 처리보다 먼저 실행된다.
- `services/kiosk_tts_service.dart:43`은 `Process.run`으로 espeak-ng를 실행한다.

웹은 이러한 호스트 OS 입출력 경로를 지원하지 않는다. 시작 실패와 음성 안내 무동작을 유발하는 배포 계약 불일치다. 정적 코드로 확인했으며 실제 브라우저 재현은 미실행이다.

대응: 웹용 설정 저장과 음성 구현을 분리하거나 네이티브 배포로 일원화한다. 웹을 유지한다면 브라우저 저장소와 음성 API 또는 제한된 서버 기능을 선택한다. 현재 Chromium은 `--incognito`이므로 브라우저 저장소로 바꾸기만 해서는 재시작 후 설정 보존이 해결되지 않는다.

완료 조건: 릴리즈 `/kiosk/` 최초 진입, 큰 글씨·음성 설정 변경, 브라우저 재시작 후 복원, 실제 한국어 발화 확인.

기술 근거: https://docs.flutter.dev/resources/faq 및 https://docs.flutter.dev/platform-integration/web/faq

### P0 — 하위 경로 배포의 base href 누락

`scripts/deploy_kiosk.ps1:32`는 `flutter build web --release`만 실행한다. `web/index.html`은 기본 `$FLUTTER_BASE_HREF`를 사용하지만 서버는 산출물을 `/kiosk`에만 마운트한다. 해당 스크립트로 만든 기본 빌드는 루트 자산 경로와 맞지 않을 수 있다.

대응: `/kiosk/` base href를 명시하고 실제 서버 마운트에서 검증한다. 기존에 수동 수정한 배포 산출물의 정상 동작은 스크립트 재현성의 증거가 아니다.

완료 조건: 새 빌드 복사 후 `/kiosk/`와 새로고침에서 부트스트랩·JS·폰트·이미지 404 없이 첫 화면 표시.

### P1 — 키오스크 연결 유실을 정지로 단정

`screens/kiosk_screen.dart`는 상태 조회 유실 시 `serverLost`로 실패 화면에 들어간다. 그런데 `widgets/kiosk/done_view.dart`의 큰 제목은 모든 실패에 ‘실행을 멈췄어요’를 표시한다. 작은 설명에 직접 확인 안내가 있어도 제목의 정지 단정은 잘못이다. 앱은 `ExecutionPhase.unknown`으로 분리되어 있다.

대응: 성공·실패·정지 확인·결과 불명을 각각 표현하고, 결과 불명에는 재확인과 정지 요청 경로를 제공한다. 작업 ID로 기존 결과를 확인하기 전 새 실행을 유도하지 않는다.

완료 조건: 실행 중 서버 연결 차단 시 양쪽 화면 모두 정지·성공을 단정하지 않으며, 복구 후 같은 작업의 실제 결과로 수렴한다.

### P1 — 배포 인증을 선택 설정으로 남겨 둠

`rpi/api/auth.py`는 API 키 미설정 시 요청을 허용한다. 서버는 `0.0.0.0`에 바인딩되고 `scripts/setup_rpi.sh`의 키 템플릿은 주석 상태다. 별도 설정이 없다면 같은 네트워크에서 실행·설정 변경 API에 접근할 수 있다. 현재 실제 보드가 무인증이라는 뜻은 아니다.

대응: 개발과 시연 설정을 분리하고, 시연/실물 모드에는 키 없을 때 기동 또는 원격 실행을 차단한다. 리허설 주입 API도 시연 준비용 권한·활성화 범위를 정한다.

완료 조건: 원격 무키 요청 거절, 정상 앱 요청 허용, 로컬 키오스크 동작, 실물 모드의 리허설 권한 검증.

## 구현되어도 아직 제품 기능이라고 말할 수 없는 부분

- `rpi4/act_main.py:84,87`: 모션과 안전 제어는 MockGrblClient·MockSafetyController로 고정. UART 연결 성공만으로 실모터 성공이 되지 않는다.
- 최신 개발현황 §3: L3 전력 판정기는 실행 진입점 미연결, 저장된 mm 좌표를 읽는 실행 경로 없음, 공간 상태의 전원·실행 연계 미연결.
- 사진 버튼 인식: 폰 편집기와 검증 코드는 있지만 실제 서비스 응답·실폰 검증은 남아 있다.
- 음성 STT: 폰 OS에 위임하므로 시스템 전체의 오프라인 음성 인식을 보장할 수 없다. 수동 입력을 포함한 핵심 제어 경로와 구분한다.
- `docs/roadmap.md`의 ‘다이얼 오차 보정을 폐루프가 커버’라는 오래된 문구는 최신 현황의 ‘다이얼 실행 거절’과 불일치한다. 발표 근거는 최신 구현에 맞춰 정리해야 한다.

## SW 선행 마감 순서와 합격 조건

아래 횟수는 공식 기준이 아닌 팀 내부 마감 기준 제안이다.

1. 키오스크 웹 배포 P0 수리 → 새 빌드의 첫 실행·설정 보존·TTS를 실제 배포 방식으로 확인.
2. 앱·키오스크 상태 일치 → 정상, 검증 실패, 정지, 연결 유실, 서버 재시작, 앱 재실행을 양쪽에서 확인.
3. 동시 조작·접수 응답 유실 → 폰과 키오스크 동시 제출, 연속 탭, 접수 후 응답 손실에서 중복 실행 여부 확인. 해결 전에는 접수 실패와 실제 실행 실패를 같은 상태로 취급하지 않는다.
4. 시연 설정 마감 → 인증, mock/real 표시, 리허설 API, 선택 가전·사용자 설정 보존 점검.
5. 모의 백엔드와 릴리즈 앱·키오스크로 대표 흐름 20회 연속 수행. 오대상 실행·중복 실행·거짓 성공·거짓 정지 0건을 요구한다. 통과해도 실물 완료는 아니다.
6. 처음 쓰는 사람 3~5명에게 연결, 가전 선택, 수동/음성 조작, 결과 확인, 오류 회복을 맡겨 도움 횟수와 막힌 지점을 기록한다. 탐색적 사용성 평가이며 통계적 일반화는 하지 않는다.

시각 디자인의 대대적 개편은 우선순위가 낮다. 센서 점수 93% 같은 수치는 성공 확률로 오해할 수 있으므로 사용자 화면의 뜻을 명확히 하고, 발표의 상세 수치는 실제 측정 근거와 함께 제시한다.

## 하드웨어 수령 후 수상 경쟁력을 높일 증거

1. 한 가전의 대표 시퀀스를 끝까지 완성한다. 원점·이동·누름·센서 판정·정지까지 연결한다.
2. 반복 시험에서 첫 누름 성공률, 복구 후 성공률, 누르지 못했는데 성공으로 판정한 비율, 실행 시간, 물리 정지 시간을 각각 기록한다.
3. 동일 조건에서 개방루프와 폐루프를 비교한다. 단순 성공 장면보다 ‘검증 덕분에 실제 실패를 발견·회복했다’는 근거가 차별점을 설명한다.
4. 설치 시간·다시 부착했을 때 보정 시간·원가·소비전력을 채운다. 이미 있는 `실측-기록표.md`를 사용한다.
5. 패턴 제안은 실제 이력에서 생성하고, 거절·부재·방해금지로 제안을 억제하는 장면도 보여준다. 데모 주입은 주입이라고 밝힌다.
6. 1대가 안정화된 다음 두 번째 가전으로 일반화와 LG 서비스 연계 가능성을 증명한다.

## 이번 검증의 한계

- Flutter 실행 파일은 PATH와 배포 스크립트 기본 경로에서 찾지 못했다. Flutter 테스트·분석·릴리즈 빌드를 실행하지 못했다.
- 저장소 `.venv`가 없다. 번들 Python으로 pytest를 시도했으나 `No module named pytest`로 테스트 수집 전에 종료했다. 제품 테스트 실패로 집계하지 않는다.
- 개발현황의 9/17 기록은 백엔드 1,252·폰 373·키오스크 120(골든 제외), 골든 51·26장이다. **이번 재실행 결과가 아니다.**
- 화면 평가는 저장된 골든 4장 기준이며 실제 손가락 조작·음질·프레임 속도는 평가하지 않았다.
- 이번 변경은 평가 문서 추가뿐이다. 위 결함은 아직 수정하지 않았다.
