# 공감지능 중심 기능·UI 실행 계획

작성: 2026-09-21. 사용자와 합의한 디자인 방향을 기능·사용 흐름으로 구체화한 계획이다. 구현 착수·완료 기록이 아니다.

**진행 갱신(9/21):** 첫 구현 묶음인 넘김/승인 뒤 자동 재제안 제한·시간대 만료·키오스크 반복 안내 방지를 반영했다. 상세 검증과 한계는 [개발 로그](../devlog/devlog_2026-09-21.md) 참조. 아래 전체 계획이 완료된 것은 아니다.

## 확정 전제

- 사용자가 RPi5에서 키오스크 화면 표시 성공을 확인했다. 이를 미구현으로 취급하지 않는다.
- 앱·키오스크의 하드웨어 독립 기능을 먼저 마감하고, 장치 수령 후 모터·센서·통신을 실제로 검증한다.
- 디자인은 기존 색·큰 글씨·명확한 조작 방식을 유지하면서, 제안이 있을 때 ‘왜 지금 도와주는지’를 먼저 보여준다.
- 공감지능은 기록 → 반복 발견 → 맥락 확인 → 제안 → 사용자 반응 → 다음 제안 조정의 순환으로 구현한다.
- 먼저 알아차려 제안하는 기능을 우선한다. 가열 가전의 승인 없는 자동 실행은 이번 범위에 넣지 않는다.
- 기존 기능 동결 기록보다 이번 사용자의 검토·계획 요청을 우선한다. 신규 모델 개발·다중 사용자 식별까지 승인받은 것으로 확대 해석하지 않는다.

| 흐름 | 현재 | 남은 문제 / 방향 |

| 사진 추가 | 홈의 사진 추가가 설정 탭으로 이동 | 해당 가전 사진 편집으로 연결되지 않음. 실제 편집 경로를 만들거나 문구를 ‘가전 관리’로 정직하게 변경 |

| 제안 설명 | 시간대·횟수와 실행할 버튼 표시 | 설명은 사실에 맞음. 자연스러운 질문, 근거 기간, 대상, 동작 요약 순서로 정리 |

| 기록 | 실행 이력과 usage 학습 기록 존재 | usage에는 사용자·입력 출처·실제/모의 구분 없음. 직접 버튼 조작은 purpose 없으면 학습 제외 |

### 이번에 직접 재현한 세 가지

번들 Python으로 기존 `PatternDetector`와 `ProactiveSuggestionService`를 직접 호출했다. 고정 시계·메모리 이력·모의 실행기를 사용했고 물리 실행과 네트워크 호출은 하지 않았다.

입력: 현재 2026-09-21 08:00 +09:00, 90일 전 같은 날 아침 성공 기록 3건, 두 가전에 같은 목적 문자열, 최소 횟수 3.

1. 후보가 생성되며 횟수는 3, 대상은 마지막 사용 가전으로 나온다. 가전별 3일 반복을 의미하지 않는다.
2. `reject()` 후 `create_suggestions()`를 다시 호출하면 새 ID의 동일 제안이 생성된다.
3. 시계를 오후 16시로 바꾸어도 아침 제안이 `pending()`에 남는다.

이것은 기존 단위 로직에 대한 재현 결과다. Flutter·전체 백엔드 테스트 및 실기기 재현을 대신하지 않는다.

## 실행 순서

### 1단계 — 제안이 사용자를 귀찮게 하지 않도록 수리

기능:

- 루틴 식별자를 가전 + 정규화한 목적 중심으로 정의한다. 원래 발화와 실행 목적은 구분한다.
- 제안 유효시간, 같은 시간대 재제안 제한, 완료 직후 재제안 제한을 서버에서 판정한다.
- 승인·넘김·영구 숨김·만료·노출을 구분한다. 무응답은 거절로 학습하지 않는다.
- 상태를 재시작 후에도 유지한다. 클라이언트 시계가 아니라 서버 시계로 판정한다.
- 키오스크에서는 같은 제안으로 화면과 TTS가 반복되지 않게 한다.
- 유효시간과 대상/맥락은 승인 시에도 재검사한다. 만료된 카드는 실행하지 않는다.

UI:

- 넘김 성공은 실제 제한 범위에 맞게 알린다. 예: 같은 시간대 제한이면 ‘오늘 아침에는 다시 묻지 않을게요’.
- 전달 실패는 ‘넘겼어요’로 표시하지 않는다.
- 앱과 키오스크에서 이미 처리된 카드가 다시 실행 버튼을 내걸지 않게 한다.

완료 조건: 넘김→다음 생성 주기, 승인→완료→다음 주기, 시간대 종료, 서버 재시작, 양쪽 동시 승인에서 중복 제안·이중 실행이 없다. 무응답 카드가 반복 발화하지 않는다.

### 2단계 — 최근 생활을 반영하는 학습 기반

기능:

- 초기 설계안은 최근 28일, 서로 다른 3일 이상의 사용을 후보 조건으로 삼는다. 팀의 제품 기본값 제안이며 효과가 검증된 수치가 아니다.
- 횟수와 사용일 수를 별도로 저장·표시한다. 하루 10회가 10일 습관이 되지 않게 한다.
- 최근 기록에 더 무게를 주고, 근거가 부족하면 정밀 시각·요일별 습관을 주장하지 않는다.
- 학습 기록에 실제/모의 및 사용자 직접 실행/제안 승인 출처를 남긴다. 기존 기록에서 출처를 복원할 수 없으면 unknown으로 둔다.
- 실제 모드 학습에서 모의·리허설 데이터를 제외한다. 데모 학습은 분리된 데이터로 재생한다.
- 제안 승인 성공을 직접 사용과 무조건 동등하게 세지 않는다. 시스템의 제안이 자신의 확신을 계속 키우는 현상을 막는다.
- 수동 버튼 실행은 실제 시퀀스가 저장된 루틴과 일치할 때만 목적과 연결한다. 임의 버튼을 AI가 추측해 습관으로 만들지 않는다.
- 반복 거절은 ‘앞으로 싫다’와 구분해 빈도 감소 근거로 활용한다. 사용자가 통제할 수 있는 초기화·일시정지 범위를 정의한다.

UI:

- ‘최근 4주 동안 아침에 5일 사용했어요’처럼 집계 범위와 단위가 명확한 근거를 표시한다.
- 새 사용자는 ‘사용 기록이 쌓이면 자주 하시는 일을 제안해요’ 정도로 안내한다. 허구의 학습률은 넣지 않는다.
- 단일 사용자/가구 기준을 우선한다. 현재 사람 식별 데이터가 없으므로 개인별 기억을 구현했다고 말하지 않는다. 다중 사용자 프로필은 별도 후속 범위다.

완료 조건: 오래된 습관, 최근 시간 변경, 같은 날 반복, 가전 2대의 같은 명령, 별칭, 모의 이력, 제안 승인 이력을 고정 시계 시나리오로 검증한다.

### 3단계 — 합의한 홈·제안 UI 적용

- 앱 홈: 유효 제안이 있으면 대상·자연스러운 질문·근거를 위에 두고 수동 조작을 유지한다. 연결 경고와 결과 불명 작업은 제안보다 우선한다.
- 제안 화면: 질문 → 근거 → 가전/실행 요약 → 선택. 전체 버튼판은 필요할 때 펼친다.
- 질문 문구는 등록된 목적의 표시용 문장으로 만든다. 명령문에 ‘지금 할까요?’를 단순 연결하지 않는다. 자유 문구는 인용형 질문으로 안전하게 폴백한다.
- 키오스크: 같은 제안 내용·행동 의미를 앱과 공유하고, 큰 실행 버튼과 대상 식별을 유지한다.
- 초 단위 카운트다운은 사용자 조작을 재촉하지 않게 조정한다. 숨김과 만료를 구분하고 접근성 시간 설정을 보존한다.
- 실행/완료: 버튼 조작 완료와 가전 작업 완료를 구분한다. 성공·실패·정지 확인·결과 불명을 각각 표시한다.
- 기존에 충분한 탭 구조는 유지한다. 학습 대시보드·AI 점수·새 관리자 화면은 추가하지 않는다.

완료 조건: 작은 폰·큰 글씨·키오스크 1920×1080에서 정보가 잘리지 않고, 실행/넘김/취소가 찾기 쉬우며, 화면과 TTS가 같은 의미를 말한다. 골든과 실제 손가락 조작을 각각 확인한다.

### 4단계 — 공간·추론 경계와 SW 통합 마감

- presence의 재실/부재/모름에 대해 생성·노출·발화 정책을 각각 정한다. 모름을 재실로 설명하지 않는다.
- 부재와 방해금지 중 자동 발화를 막고, 복귀 시 만료된 제안을 몰아서 보여주지 않는다. 수동 제어는 별도 흐름으로 유지한다.
- 온습도 제안은 정보의 최신성·대상 가전 준비 상태를 확인한다. 습도만 높은데 ‘더워요’라고 설명하지 않는다.
- 이력 집계·제안 결정·승인·실행 검증은 로컬에서 수행한다. 외부 해석을 사용했다면 설정과 필요한 안내에 그 경계를 표시한다.
- 사진 외부 전송 동의는 유지한다. STT의 OS 의존성은 로컬 제어 가능 여부와 구분한다.
- RPi5에서 이미 성공한 실행 방식과 저장소 배포 스크립트를 대조한다. 화면 표시와 별개로 설정 보존·음성·재부팅 자동실행을 검증한다.
- 인증, 동시 제출, 접수 응답 유실, 서버 재시작, 연결 복구를 릴리즈 앱·실행 중인 키오스크·모의 백엔드 조합으로 검증한다.

완료 조건: 대표 흐름 20회 연속에서 잘못된 대상·중복 실행·거짓 성공·거짓 정지 0건. 연결 장애와 서버 재시작은 별도 포함한다. 이 횟수는 내부 마감 기준 제안이다.

### 5단계 — 하드웨어 통합 및 본선 증거

- 한 가전에 대해 원점·이동·누름·센서 판정·재시도·물리 정지를 연결한다.
- 앱·키오스크의 표시를 실제 센서·실행 결과로 검증한다.
- 센서 판단 없는 실행과 폐루프 실행의 성공률·복구율·오판정·시간을 같은 조건에서 비교한다.
- 실제 사용 기록에서 제안이 생성되고 거절/시간 변화에 따라 달라지는 과정을 시연한다. 날짜를 압축한 리플레이는 실제 생활 실험과 구분한다.
- 설치 시간·원가·전력을 기존 실측 기록표에 채운다. 한 대가 안정된 뒤 두 번째 가전으로 일반화를 검증한다.

## 이번 계획에서 보류

새 AI 모델 훈련, 얼굴로 개인 식별, 무승인 가열 실행, 새 클라우드 서비스, 다이얼 구동 확장, 개발자 도구 확장, 전면 디자인 교체는 넣지 않는다. 최근 기록·피드백을 반영하는 통계 기반 적응은 먼저 구현하고 모델 기반 기능과 구분해 설명한다.

## 작업·검증 방식

- 첫 구현 단위는 1단계의 ‘넘김 뒤 재제안 / 시간대 지난 pending / 키오스크 반복 발화’다.
- 기능 계약 → 재현 테스트 → 서버 수정 → 앱·키오스크 반영 → 실제 흐름 확인 순서로 진행한다.
- 전체 테스트 도구는 현재 환경에서 미준비다. 기존 통과 개수는 신규 작업 검증으로 재사용하지 않는다.
