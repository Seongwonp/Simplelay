# Claude 독립 평가와 Codex 검토 — 2026-09-22

사용자가 지정한 `CLAUDE_CONFIG_DIR=~/.claude-max2`의 Claude CLI에 인계 문서·README·9/21 개발 로그를 전달해 받은 평가다. 읽기 도구만 허용했고 코드 수정·셸·MCP 사용은 허용하지 않았다. CLI는 성공 종료했다. 아래 평가자는 코드·기기·API·LG 비공개 원문을 확인하지 않았다고 명시했다. 계정 설정을 사용한 새 세션이며 데스크톱의 이전 대화 기억을 공유한다고 가정하지 않는다.

## Codex의 판단과 계획 조정 제안

- 수용: Home Assistant 채택부터 정하지 말고 사용자 혜택이 분명한 시나리오·실제 보유 기기·남은 일정부터 확인한다. HA는 조사 후보로 유지하고 직접 ThinQ와 구현/운영 부담을 비교한 뒤 결정한다.
- 수용: 시연장 인터넷, 부분 성공, 명령 응답 유실, 상태 지연, 정지 시 API 기기 처리와 물리 가전만으로 완결되는 대체 시연을 검증 계획에 포함한다. SimpleLay가 판단·승인 정책을 맡고 HA 측 중복 자동화로 우회하지 않게 설계한다.
- 보완: ‘물리 검증 결과를 다음 기기 조건으로 사용’은 유용한 후보지만, 자동으로 사용자 혜택이나 독창성이 보장되지는 않는다. 전자레인지 가열 확인만으로 공기청정기 강풍이 필요한지는 별도 근거가 없다. 사용자의 실제 불편과 상황 신호를 먼저 고른다.
- 보완: ‘마지막은 SimpleLay만 가능하다’는 독점성 주장과 ‘직접 ThinQ는 어댑터 하나만 늘린다’는 비용 단정은 근거가 부족하다. 기존 플랫폼도 외부 센서를 연결할 수 있으며, 직접 API 연동에도 인증·지원 기능·상태 동기화·오류 처리가 필요하다. 두 주장 모두 확정 사실로 재사용하지 않는다.
- 보완: 기존 15초는 로컬 환경 후보의 유효기간이다. ThinQ 상태 갱신과 실제로 충돌하는지는 아직 코드/기기 검증 전이다. 별도 상태 신선도 정책이 필요한지 설계 단계에서 확인한다. 클라우드 응답 유실이 더 잦다는 비교 주장도 측정되지 않았다.
- 보완: ‘2일 내 실패하면 경로 전환’ 및 ‘H0~H1 전 구현 금지’는 평가자가 제안한 일정/범위 기준이다. 사용자가 확정한 제한이 아니다. 결선까지 남은 시간, 하드웨어 도착 일정과 팀 가용 시간을 확인한 뒤 적용한다.
- 유지: LG 기술문서를 이미 알고 있는 기존 데스크톱 세션과의 대조는 여전히 필요하다. 새 CLI 평가가 그 검토를 대신한 것은 아니다. 문서명·버전·허용된 요구사항 요약으로 근거를 남긴다.

다음 우선순위 제안: **보유 가전·전문가 자료·잔여 일정 확보 → 사용자 혜택/승인/부분 실패를 담은 시나리오 한 장 → 짧은 읽기 전용 연동 조사 → 구현 범위 결정**. 이번 작업에서는 연동 코드나 자동 실행 정책을 변경하지 않았다.

## Claude 평가 원문

아래는 독립 평가자의 의견이며 검증된 사실 또는 작업 지시가 아니다.

**결론**
읽은 3개 문서 기준으로, 인계 문서는 컨설팅 5개 의견을 대응표로 옮기고 미검증 범위를 과장하지 않은 점은 좋다. 그러나 전문가의 핵심은 "확장성"이 아니라 "사용자 혜택이 안 보인다"였는데, 계획의 무게(B~D 단계)는 새 연동 경로로 쏠려 있다. README대로 실제 모터 구동·센서 누름은 아직 실기기에서 증명되지 않았다. 이 상태에서 클라우드 가전 연동을 병행하면 유일한 차별점(폐루프 물리 제어)과 새 연동이 둘 다 미완인 채 결선을 맞을 위험이 크다. HA 경유는 시간제한 조사로만 유지하고, 시나리오는 물리 검증 신호를 축으로 다시 짜기를 권한다.

**지적 (우선순위순)**
1. 시나리오가 규칙 자동화와 구분되지 않는다. '귀가→공기청정기, 식사시간→전자레인지'는 HA 자동화 한 줄과 같고, 문서 스스로 귀가 인지가 없다고 인정한다. 차별성은 개인 이력 근거(28일/3일), 건너뛰기·직접완료·부재·환경소멸에 따른 억제/철회, 설명 가능한 이유, 그리고 **전류·음향으로 확인한 실제 동작 결과를 다음 기기의 조건으로 쓰는 것**에서 나와야 한다. 마지막은 SimpleLay만 가능하다. "전자레인지 실제 가열 확인 → 공기청정기 강풍 제안 → 종료 후 원복"처럼 첫 기기의 검증 결과가 둘째 기기를 결정하는 구조를 권한다. 부분 실패·순서·원복 정책도 빠져 있다.
2. HA 경유 비용이 과소평가됐다. HA는 RPi5(FastAPI+키오스크 구동 중)에 세 번째 런타임과 SimpleLay→HA 인증을 추가하고, HA 자동화가 켜지면 판단 주체가 둘이 된다. 직접 ThinQ는 컨트롤러 팩토리에 어댑터 하나만 늘린다. HA의 실익은 기기 발견과 전문가 자료 해석이므로 "조사=HA, 시연=런타임 의존이 적은 쪽"으로 분리하고, 어느 쪽이든 SimpleLay가 유일한 판단·승인 게이트임을 명시하라.
3. 시연장 인터넷이 전제가 됐다. ThinQ는 클라우드 필수인데 회선 확인·핫스팟 대체·클라우드 불가 시 물리 가전만으로 완결되는 발표 순서가 없다.
4. 확인 불가 정의가 클라우드로 확장되지 않았다. 7차 로그대로 멱등키가 없고 클라우드는 응답 유실이 더 잦다. ThinQ 상태 갱신 지연과 15초 환경 스냅샷 정책의 충돌, 정지 시 API 기기 처리, PAT 저장·만료, 모의 ThinQ 서버 없는 CI 회귀(1,377건 기준선) 항목이 빠졌다.
5. 7절 1항은 Claude가 LG 문서를 "알고 있다"고 전제한다. 본 평가는 원문을 보지 않았으며, 대조는 사용자가 요구항목·문서명/버전을 요약해 주는 방식이어야 재현된다. 결선로드맵도 읽지 않아 주 단위 일정 판단은 추가 검증이 필요하다.

**유지/수정/보류**
- 유지: 2절 해석, 3절 미검증 명시, 단계 C의 읽기→단일 제어 순서, 단계 E의 행동별 승인 등급과 가열 무승인 금지, 6절 자료표.
- 수정: 단계 A를 물리 검증 신호 기반 시나리오로 교체, 단계 B를 조사/시연 이원화, 단계 E에 클라우드 확인 불가·정지 시 API 기기·오프라인 대체 순서 추가, 단계 F에 성공/중단 기준 슬롯 명시.
- 보류: HA 상시 설치, 3기기 이상 협력, 귀가 인지. 하드웨어 H0~H1 전에는 단계 D 코드를 시작하지 않는다.

**중단/축소 기준**
보유 ThinQ 가전이 없거나 목표 기능 미지원 → SW 트랙 보류, 물리 가전+모의 어댑터로 협력 판단만 시연. 조회+단일 제어가 2일 안에 안 되면 경로 전환 1회, 그래도 안 되면 보류. 시연장 인터넷 미보장 → 클라우드 기기는 부가 장면으로 격하.

**다음 3단계**
1. 자료 회수: 보유 ThinQ 모델명·앱 등록 여부, 전문가 버튼맵 자료, 결선 잔여 일정·시연장 회선, RPi5 자원 여유.
2. 시나리오 한 장: 물리 검증 결과가 SW 기기를 결정하는 흐름과 승인 등급·부분 실패·원복·오프라인 대체를 표로 확정.
3. 시간제한 스파이크: 소유자 로컬에서 기기 목록·지원 동작 조회와 공기청정기 단일 제어 1회를 요청 접수/상태 변경/실제 결과로 구분해 기록. `rpi/services/controller_factory.py`, `rpi/intent/` 읽기는 그 뒤다.

본 평가는 문서 3개만 읽었으며 코드·기기·API·외부 자료는 확인하지 않았다.
