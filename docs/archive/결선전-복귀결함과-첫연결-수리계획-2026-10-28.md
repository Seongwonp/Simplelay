# 결선 전 복귀 결함과 첫 연결 수리 계획

작성일: 2026-10-28. 목표: 기능 추가 없이 실제 누름 뒤 복귀와 결과 표시를 바로잡고 설치 과정의 막힘을 줄인다.

## 범위와 현재 근거

- 사용자 실물 관찰: 버튼을 누른 뒤 좌표가 0,0이 되고 돌아오지 않았다. 복귀가 잠겨 키오스크에는 실패로 표시됐다. 원인과 정확한 실패 단계는 아직 코드·송수신 기록으로 재현하지 않았다.
- 코드 확인 기준: 로컬 및 원격 `72e7adbc`. 실제 촬영 빌드와 일치하는지는 확인 필요.
- `rpi/controller/touchbridge_motion.py:426`의 `home()`은 설정에 따라 `:434`의 현재 위치 원점 설정(`Z`)을 호출한다. 이는 대기 위치로 이동하는 기능이 아니다.
- 같은 파일 `:494`의 `press()`는 좌표 이동 후 누름 응답을 기다린다. 이 함수 자체에는 누른 뒤 XY 대기 자리로 이동하는 명령이 없다.
- `rpi4/services/act_executor.py:915`의 정지 대기 경로는 실행 성공과 가전 동작 확인 등의 조건에 따라 시작한다. 실제 실행에 이 경로가 붙었는지는 확인 필요.
- `rpi/services/controller_factory.py:53`은 설정된 실행기 주소로 연결한다. 가전 추가의 사진 매핑과 RPi4 설치 연결을 구분해야 한다.

줄 번호는 위 기준 트리에서 확인한 값이며 실제 수정 전 재확인한다. 과거 devlog의 다른 펌웨어·규약을 현재 동작으로 가정하지 않는다.

## 작업 원칙

1. 새 기능, UI 전면 개편, 모델 학습·최적화, RPi4 자동 탐색 신설은 하지 않는다.
2. HW 담당 펌웨어·핀·PID·기구 설정은 수정하지 않는다. 펌웨어 원인이 확인되면 증거와 필요한 계약을 HW 담당에게 전달한다.
3. 복귀 실패를 숨기지 않으며, 복귀를 위해 버튼을 다시 누르지 않는다. 자동 재누름 정책을 확대하지 않는다.
4. 정지·비상정지 뒤 자동 파킹을 일괄 추가하지 않는다. 좌표와 장치 상태를 신뢰할 수 없는 상태에서는 이동을 새로 시작하지 않는다.
5. 기존 잠금을 통째로 제거하거나 원점 설정을 우회하지 않는다. 누가 어떤 잠금을 언제 해제해야 하는지 재현으로 확인한다.
6. 다른 작업의 미커밋 변경을 보존한다. stash·강제 push·공유 작업 트리의 임의 초기화 금지. 커밋·push는 사용자 요청에 따른다.

## 2단계 내일 실물 원인 확인

시험 종료 후 사용자와 함께 진행한다. 날짜는 2026-10-29 예정이며 시각은 정하지 않는다.

### 시작 전 확보

- RPi5·RPi4·폰·키오스크 배포 SHA, 모션 펌웨어 식별 정보. 제출 영상 당시 것과 현재 것을 나눠 기록한다.
- 현재 환경 설정과 매핑의 로컬 백업. 주소·키·USB 식별 정보·원문 로그는 저장소 밖에 보관한다.
- 실행에 쓰인 어댑터 종류, 원점 설정 방식, 복귀 위치·설정, 실행 시작 경로를 확인한다.
- HW 담당이 정한 중단 수단과 작업 가능 범위를 확인한다. CT가 없으면 가전 반응을 CT로 확인했다고 말하지 않는다.

### 재현 순서

1. 움직이기 전 현재 좌표·원점 상태·연결 상태를 읽고 저장한다. 상태 조회만으로 좌표가 바뀌는지 본다.
2. 이미 검증된 범위에서 누르지 않는 이동과 복귀를 각각 확인한다. 현재 위치를 원점으로 덮어쓰는 동작과 구별한다.
3. 사용자와 HW 담당이 허용한 버튼으로 누름을 한 번만 실행한다. 누름 직전·응답 직후·복귀 요청 직전·실패 직후의 좌표와 명령 순서를 남긴다.
4. 일반 승인 실행과 개발자 조작을 별도로 시험한다. 한 경로의 성공을 다른 경로의 성공으로 쓰지 않는다.
5. 좌표가 0,0이 되는 최초 시점을 찾는다. `Z`/home 전송, MCU 재부팅, 좌표 응답 변화, 앱 기본값 표시를 구분한다.
6. 복귀가 거절된 정확한 이유와 보유 중인 제어권·정지 상태를 확인한다. ‘잠겼다’만으로 락 교착이라고 단정하지 않는다.

### 원인별 처리

| 확인 결과 | 수리 방향 | 하지 않을 것 |
|---|---|---|
| 호스트가 복귀 대신 원점 설정을 호출 | 그 호출부만 분리·수리하고 기존 좌표계의 이동으로 복귀 | 누름마다 새 원점 설정 |

| 호스트 표시만 0,0이고 보드는 좌표 유지 | 누락/실패 응답을 0으로 대체하는 지점 수리 | 표시를 실제 원점으로 취급 |

## 3단계 원인 확정 후 최소 수리

수정할 행동을 실제로 재현하는 회귀 시험을 먼저 작성하고, 수정 전 실패를 확인한 뒤 수정한다. 실제 동작이 재현되지 않은 시험은 원인 입증이 아닌 방어 시험으로 분류한다.

| 시험 조건 | 확인할 결과 |
|---|---|
| 누름 완료 응답 뒤 정상 복귀 | 좌표 기준이 바뀌지 않고 지정 위치로 이동. 실제 복귀 성공 응답 전 ‘돌아왔어요’ 금지 |
| 누름 뒤 복귀 거절·시간 초과 | 기존 버튼 결과 보존, 복귀 실패 원인 표시, 추가 누름 0회 |
| 복귀 중 사용자 정지 | 중단 처리, 정지 뒤 자동 복귀 재시작 0회 |
| 누름 뒤 MCU 재부팅·연결 끊김 | 좌표를 0,0으로 단정하지 않음. 성공·자동 재전송 금지 |
| 누름 응답 미확인 | 실제 버튼이 눌렸다고 단정하지 않음. 미확인 안내 유지 |
| 다음 실행·동시 요청 | 복귀가 진행 중이면 기존 정책에 맞게 차단. 다른 실행의 좌표·결과를 섞지 않음 |

RPi4 → RPi5 → 폰·키오스크를 같은 결과 데이터로 연결해 시험한다. 결과 문구는 현재 데이터가 아는 수준만 표현한다. 예를 들어 누름 요청 응답만 있는 경우 ‘실제 버튼 누름 성공’으로 바꾸지 않는다. 필요한 결과 구분이 기존 필드로 불가능하면 선택 필드와 구버전 표시를 함께 설계하고 변경 범위를 보고한다.

검증: 변경 관련 회귀 시험 → 백엔드·RPi4 전체 시험 → 폰·키오스크 변경 시 해당 Flutter 시험·analyze·관련 골든 비교 → 저장소 가드·문서 링크 검사. 원인·수정 전 실패·시험 수·종료 코드·미검증 범위를 devlog에 기록한다.

## 4단계 첫 연결 동선 수리

모터 복귀 수리 뒤 진행한다. 자동 탐색 신설 없이 기존 설치 과정의 안내·상태·순서만 다룬다.

1. 폰에서 연결하는 대상은 본체(RPi5), 본체가 연결하는 실행기는 RPi4임을 설치 안내에서 구별한다. 일반 사용자에게 보드 이름을 모두 외우게 하지 않는다.
2. 본체 연결 성공을 누름 장치 준비 완료로 표시하지 않는다. 실행기 미연결·좌표 기준 없음·매핑 없음·확인 주행 미완료를 구별한다.
3. 사진 매핑에 들어가기 전에 필요한 연결·범위 정보를 받지 못했다면 그 이유와 설치자가 할 일을 보여 준다. 현재 서버 계약으로 가능한 범위에서만 수정한다.
4. 주소 변경·인증 실패는 설치자 안내로 연결한다. 원격 주소 변경 API나 인증 없는 자동 탐색을 추가하지 않는다.
5. 처음 쓰는 사람이 연결 실패 뒤 어디로 돌아가야 하는지 확인한다. 팀원이 설명한 뒤 성공한 것을 독립 성공으로 기록하지 않는다.

## 5단계 결선 전 종료 기준

- 동일 빌드의 정상 실행에서 이동 → 한 번 누름 → 지정 위치 복귀 → 결과 표시를 연속 확인한다. 목표는 우선 10회 반복 기록이며, 이것만으로 가정용 안전 인증·전체 성공률을 주장하지 않는다.
- 중간 실패에서 재누름이 없고 누름 결과와 복귀 결과를 혼동하지 않는다.
- 실제 이동 중 정지와 복귀 중 정지를 별도로 확인한다. 과거 모터 축 응답 시간을 현재 기구 정지 시간으로 사용하지 않는다.
- 첫 연결 실패를 의도적으로 한 번 만들고 상태 설명·복구 동선을 확인한다.
- 실측 결과로 발표의 가능·미확인 범위를 갱신한다. 제출 원본을 몰래 바꾸지 않고 결선 시점의 추가 검증으로 구분한다.

## 보류할 작업

SLM 최적화·습관 알고리즘 확대·CT 신규 통합·RPi4 자동 발견·새 파킹 상태 머신·UI 전면 개편·HW 펌웨어 수정은 이번 수리 묶음에서 제외한다. 기존 기능의 결함이 확인된 부분만 수정한다.

## 추가 계획: 시연 데이터 모드

2026-10-28 사용자 요청. 아래는 계획이며 이번 모션 수리에서 구현하지 않는다.
기존 사용 기록과 루틴을 촬영용으로 직접 바꾸는 대신 별도 시연 데이터 공간을 선택하는 방식으로 한다.

### 권장 동작

- 기본값은 일반 모드다. 환경변수로 시작 모드를 선택하고, 실행 중 데이터 공간을 바꾸는 스위치는 두지 않는다.
  변수명은 구현 때 확정한다. 기존 `SIMPLELAY_DB_PATH`를 재사용할 수 있지만 DB 외 저장 경로도 먼저 조사한다.
- 시연 모드는 일반 DB·기록·루틴·맡기기 허용과 다른 저장소를 사용한다. 일반 저장소와 경로가 같으면 기동을 거절한다.
  끄고 다시 시작하면 원래 데이터로 돌아온다. 실제 데이터의 삭제·덮어쓰기·자동 복원으로 모드를 구현하지 않는다.
- 시연용 가전 표시·루틴·사용 기록·알림 등 필요한 표본을 버전 있는 묶음으로 넣는다.
  모드 첫 시작에 한 번만 넣고, 재시작·재접속으로 중복 생성하거나 사용자가 수정한 시연 데이터를 덮지 않는다.
  초기화는 별도 명시적 작업이며 시연 저장소만 대상으로 한다.
- 실물 설치 정보(기기 연결·버튼 좌표·좌표계·확인 주행)는 가짜 값으로 만들지 않는다.
  재사용이 필요하면 가져올 설정의 범위를 명시하고 현재 장치와 맞는지 확인한다. 키·토큰은 표본에 넣지 않는다.
- 화면에서 **시연 데이터**와 **모의 실행**을 구별한다. 시연 데이터를 쓴다고 자동으로 모의 실행이 되거나
  실제 장치 제어가 허용되는 것이 아니다. 실제 제어 여부는 기존 실행 모드·승인·장치 준비 상태가 결정한다.
- 합성 기록에는 시연 출처를 남긴다. 일반 습관 학습·실제 사용 통계·실측 증거에 섞지 않는다.
  시연용 제안이 실제 사용에서 학습된 것처럼 보이지 않게 하고, 합성 사건이 실제 자동 실행의 확인 근거가 되지 않도록 한다.
- 승인·맡기기 허용·정지·비상정지·조용한 시간·중복 전송 방지 규칙은 그대로 둔다.
  시연 모드를 이유로 승인 완료나 검증 성공을 자동 입력하지 않는다. 실제 제어의 안전 시계도 바꾸지 않는다.

### 구현 순서와 시험

1. DB·파일·메모리별 저장 위치, 기존 모의/시연 API를 조사해 격리할 대상을 확정한다.
2. 시작 모드와 경로 분리를 먼저 구현한다. 일반 데이터의 내용·해시가 전후 동일한지 시험한다.
3. 표본 삽입을 트랜잭션과 고정 식별자로 묶는다. 두 번 시작·중간 실패·버전 변경·초기화를 시험한다.
4. 폰·키오스크의 시연 데이터 표시와 실물/모의 실행 표시를 함께 시험한다.
5. 일반 모드 복귀, 모드별 허용 기록 분리, 합성 사건의 실가전 자동 실행 차단을 확인한다.

모션 복귀의 실물 원인 확인을 우선한다. 이후 시연에 필요한 최소 데이터 묶음만 구현하며 별도의 시연용 실행 엔진은 만들지 않는다.

이 계획 작성 시 실물 시험·회귀 시험 실행·동작 수리·보드 배포는 하지 않았다. 현재 원인 미확정이며, 사용자가 내일 실물 확인에 참여한 뒤 수리 방향을 확정한다.
