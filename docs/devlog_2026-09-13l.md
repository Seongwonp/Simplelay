## 결함: "명령 완료"와 "안전 정리 완료"를 섞었다

settle이 초입에서 `_inflight=False`를 내린 뒤 복구 정지(`command_error`)를
호출했다. 어댑터의 복구 정지가 지연되는 동안:

1. 별도 긴급 정지가 들어오면 "진행 중 명령 없음"으로 판단해 정지 성공 후
   **제어권을 반납**한다 → 새 실행/세션 B가 시작될 수 있다.
2. 그 뒤 A의 오래된 복구 정지가 **실패**로 끝나면, 세대 확인 없이
   `self._session`(이제 B다)을 닫고 제어권을 벗겨냈다.
3. 덤으로 `_try_stop_confirm` 성공이 현재 fault를 무조건 해제해서, 오래된
   정리의 성공이 **그 사이 다른 주체가 건 fault**를 풀 수 있었다.

## 수리

- **점유 단위 = 명령 + 그 명령의 안전 정리.** `_inflight`는 settle의 단일
  출구(`_finish_settle`)에서만 내려간다. 정리 중에 온 정지는 여전히
  반납을 위임하고(stopping 상태 지속), 반납은 위임받았거나 자기 세션을
  직접 닫았을 때만 나간다.
- **세대(epoch) 확인 후 자기 세션만 닫는다.** 지연된 정리의 실패는 잠금
  (fault)은 걸어도 — 기계 상태 불명이므로 잠그는 게 맞다 — 남의 세션은
  건드리지 않는다.
- **settle의 정지는 fault를 해제하지 않는다.** 해제는 사용자의 긴급 정지가
  확인되는 경로(`_send_stop`) 하나뿐이다.

## 검증 방식 (리뷰 권고 그대로)

반복 횟수를 늘리는 대신 **복구 정지를 원하는 지점에서 멈추는 fake**
(`_BlockedRecoveryAdapter`)로 조합을 결정적으로 재현했다:
press 예외 → 복구 정지 게이트 대기 → 별도 긴급 정지 → 새 실행·새 세션
시도(둘 다 거절돼야 함) → 게이트 해제 후 복구의 성공/실패 각각. 성공이면
fault 없이 재개, 실패면 fault 잠금 + 남의 세션 무사 + 긴급 정지 확인으로
복구. 별도로, 오래된 정리의 성공이 남의 fault를 보존하는 것도 고정했다.
