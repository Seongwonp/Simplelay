- 지금 위젯 시험의 200% 장면은 대부분 `360×2400`이라 화면 밖으로 밀리는 문제를 잘 못 잡는다. 예외는 홈 `360×780`·200% 한 장면(`home_verify_note_test.dart`) — 루틴 1개·가전 2개·보조 줄만, AppShell·탭바·RunningStopStrip 없음, 버튼 가운데 hitTest까지(실제 탭 동작은 아님). 루틴 행 200% 시험은 아직 `360×2400`이다.
- 일반 폰 높이(예: 360×780, 412×915)와 에뮬레이터의 글꼴 크기 최대 설정에서 아래를 본다.
  - 홈 큰 루틴 카드·실행하기·가전 타일 상태 줄이 잘리지 않는지
  - 루틴 행의 편집/실행하기가 겹치지 않고 줄바꿈되는지(둘 다 48 이상)
  - 기록 행의 제목 → 결과 → 다음 행동이 읽히는지
  - **실행 중 정지 줄(RunningStopStrip)이 스크롤·확대에서도 항상 보이고 눌리는지**
- 문제가 있으면 위젯 시험에 그 크기 장면을 더해 고정한다.
- 홈 타일 최신성(검토 M1·M3)도 에뮬레이터에서 본다: 연결을 유지한 채 비상정지를 걸면 타일이 "확인하는 중이에요" → "준비가 필요해요"로 바뀌는지(5초 조회 주기만큼 늦다), 서버 재시작 뒤 확인 주행 보조 줄이 "확인 주행 기록이 없어요"로 바뀌는지(폰이 끊김을 본 경우만 — b6d1634부터 5초 조회가 연속 2번 실패하면 같은 주소·키여도 끊김으로 본다). 원격 노드 준비 변화는 연결이 유지되면 다시 받지 않는다(남은 한계).

## 4. TalkBack

에뮬레이터에서 TalkBack을 켜고 다음을 확인한다.
- **홈 읽는 순서:** 제목·허브 상태 → (장애 안내) → 제안 또는 첫 루틴(이름·대상·실행) → 나머지 루틴 → 가전 타일(이름·상태·확인 주행 보조 줄) → 가전 추가 → 탭바.
- **설정 탭:** "설정, 읽지 않은 알림 N건"으로 읽히는지. 조회 실패일 때 0건처럼 읽히지 않는지.
- **실행하기 버튼:** 루틴 이름이 포함돼 서로 구별되는지.
- **실행 중:** 정지 버튼에 바로 닿는지. 정지 뒤 단계 문구(보냈어요 / 모션 보드가 확인했어요 / 멈춘 것을 확인했어요(모션 보드 응답 n ms))가 읽히는지.
  마이크 권한이 없는 새 설치에서 첫 실행 중 권한 창이 뜨지 않는지(M3 규칙), '말로 조작하기'에서 허용한 뒤 다음 실행에 "듣는 중"이 보이는지.
- 결과는 표로 남긴다. 막힌 곳은 고칠 것과 당사자 시험 항목으로 나눈다.
- 위젯 시험의 기록 '시각적 배치 순서'·홈 '가전 목록 아래 배치' 시험은 화면 좌표만 본다 — 낭독 순서는 여기서만 확인된다.

**10/13 이후 커밋(10/14 수리·3차 평가 수리)은 보드에 올리지 않았다 — 실물 미검증 항목과 순서는 §8.** 아래는 10/13 당일 계획(기록)이다.

  - 정지 보고 규약이 바뀌었다. 새 RPi5에 옛 RPi4가 붙으면 화면이 늘 "보냈어요"로 나온다.
  - 옛 폰은 새 서버의 `stop_job_id`·`last_stop_job_id`를 무시해 다른 실행의 정지 단계를 실을 수 있고, 옛 키오스크는 ms 문구가 다르다 —
    서버 필드만으로 화면 결속 보장이 생기지 않는다. 새 폰 + 옛 서버(필드 없음)는 호환으로 단계를 싣지만 그 출처가 그 job인지 증명하지 못한다.
  - `SIMPLELAY_LINK_KEY`는 두 보드에 이미 있다. 저장소에는 넣지 않는다.
- 폰에서 정지를 누르고 다음을 확인한다.
  - 줄 기록(`SIMPLELAY_MOTION_LOG_PATH`)에 `>> stop`과 `<< {"id":…,"ok":true}`가 둘 다 남는지
  - 화면의 ms가 기록의 `>> stop`→`<< ok` 간격(ack_ms, sent→MCU 응답)과 맞는지 — verified까지의 시간은 G3 B 구간으로 따로 잰다
  - 멈춤 확인(`verified`)이 나오는지
- 기한 값(0.3 s·0.1 s·1.5 s)은 자리표시자다. 실측해서 정하고 [실측 계획](실측-계획-결선.md) G3 두 구간에 기록한다.
- (10/13 결과) 모터 축에서 위 세 항목을 확인했다. 캐리지가 실제로 움직이는 구성·실제 버튼 누름·키오스크 정지 줄 문구는 아직이다 —
  발표에서는 "정지 확인 단계는 시험대 모터 축에서 확인, 캐리지·버튼 누름은 미검증"으로 말한다.

## 8. 다음 보드 날 (10/14 수리·3차·4차 평가 수리 뒤 — 전부 실물 미검증)

> **10/14 데스크톱에서 1~5·7을 실행했다(모터 축·리허설) — [결과](devlog/devlog_2026-10-14-desktop-board.md).** 같은 커밋 배포, M1 자동 실행 `sent`(`rpi4_uart`+`clock_ref`), 걸림 알람, 키오스크 짧은 정지, USB 재열거(`ce37b81` 배포 스크립트 수리 뒤)를 확인했다. 6(데이터 정리)은 사용자 확인 대기, 실제 TalkBack 낭독은 미확인이다.

[10/14 수리 기록](devlog/devlog_2026-10-14-fixes.md) · [3차 평가 수리 기록](devlog/devlog_2026-10-14-eval3-fix.md)(`8756f4b`…`e693e26`) · [4차 평가 수리 기록](devlog/devlog_2026-10-14-eval4-fix.md)(`8f3ece7`…`8b3c365`). 순서대로 한다.

1. **같은 커밋 4종 배포** — RPi5 백엔드·RPi4 실행기·폰 APK·키오스크를 **같은 커밋**으로(각 빌드 SHA 기록). 모션 중단 원인(`abort_reason`)·키오스크 결과 잡기·자동 실행 한 줄·포트 다시 열기가 함께 들어가야 화면에 보인다. 섞으면 원인이 안 나온다.
   - **3차 M1:** 새 RPi4만 `act_info.clock_protocol: 1`을 알리고 `clock_probe`에 `clock_ref`로 답한다. 옛 RPi4면 그 링크의 가열 종료 사건은 신선도 근거가 없어 자동 실행이 **늘 보류**("…근거가 없어…")다.
     배포 뒤 링크 기록(`SIMPLELAY_SESSION_LOG_PATH`)에 `clock_probe`→`clock_ref`가 오가는지, UART 리허설 가열 종료(`POST /demo/appliance-done`, 허용한 규칙)로 자동 실행이 `sent`가 되는지 본다.
     **두 가지를 함께 확인해야 두 보드 기준점의 증거다(4차 평가 L-N1):** 응답의 `injected_in`이 **`rpi4_uart`**이고, 같은 때 링크 기록에 `clock_ref`가 있다.
     `injected_in=rpi5_mock`(기본 mock)은 RPi5 안 로컬 시계 경로라 기준점 교환을 거치지 않는다 — 이 결과로 M1을 확인했다고 적지 않는다.
     RPi4 실행기를 다시 띄우면 새 `clock_id`라 다음 `act_info`·`clock_ref` 전까지는 보류가 정상이다.
   - **3차 H2·M3:** approve-and-allow 응답에 `auto_allow`, `/thinq/devices`는 `device_id` 대신 `key`·`device_key` — 옛 폰은 `auto_allow`를 무시한다(규칙이 안 켜진 것을 따로 알리지 않음).
   - **4차 M-N1:** RPi5는 연결이 유지되는 동안 60초마다 `clock_probe`를 다시 보낸다(링크 기록에 주기적으로 보여야 정상). 기준점이 600초를 넘게 갱신되지 않으면 자동 실행은 보류다. 두 보드 사이 `clock_probe`→`clock_ref` 왕복 시간을 링크 기록에서 몇 번 적어 둔다(드리프트 500ppm·유효 기간 600초는 설계값).
   - **4차 M-N3:** 서버 DB에 `auto_rules_session` 표시가 생긴다. **전원을 뽑거나 강제 종료한 뒤에는 자동 실행이 꺼진 채 시작한다**(루틴 탭 "허브가 정상 종료되지 않아…" → 다시 허용). `systemctl restart`·재부팅은 유지. 배포 직후 첫 기동은 표시가 없어 그대로 믿는다.
   - **4차 H-N1:** 자동 실행 끄기·값 바꾸기·삭제 응답에 `in_flight_notice`(이미 보내기 시작한 명령은 취소되지 않음) — 폰은 아직 이 문장을 띄우지 않는다.
2. **걸림 알람 실물 재현** — 시험용 좌표에서 일부러 걸리게(엔코더 선 하나 빼기 등, 안전한 방법만) 한 번 실행한다.
   - 줄 기록: `move` 1회 뒤 알람, 같은 실행에서 재이동·재누름이 **없어야** 한다.
   - `/status`: `last_abort_reason=motion_alarm: stall`, `last_retry_count=0`, 기록 `termination=motion_aborted`.
   - 폰·키오스크: "모터가 걸려 멈췄어요. 다시 누르지 않았어요" 계열, '다시 시도' 버튼 없음.
3. **키오스크 짧은 실행·정지 확인** — 폰에서 짧은 실행(0.45 s 정도)을 시작하고 바로 정지한다. 키오스크가 그 결과(정지 줄 "멈춘 것을 확인했어요 (모션 보드 응답 n ms)")를 띄우는지, 실패 화면에 머무는 동안 폰이 시작한 다음 실행·정지를 이어 보이는지 실패널로 본다(10/13 k02에서 놓친 장면).
   - 자동 실행 한 줄(C2): 모의 가열 종료 사건으로 자동 실행을 한 번 돌려, 키오스크 평소 화면 위 한 줄이 실제 결과대로 나오고 실행 중 화면에는 그려지지 않는지 본다.
4. **USB 재열거 재현** — 먼저 RPi4 env `SIMPLELAY_MOTION_PORT`가 `/dev/serial/by-id/…`인지 본다([런북](결선-운영-런북.md) §3-4). 그다음 ESP32 USB를 뽑았다 꽂거나 모터 전원을 넣어 재열거를 일으킨다.
   - `docker logs simplelay-act`에 `motion port lost` → `motion port reopened` → `reconnected`가 나오고, **실행기를 다시 띄우지 않고** 붙는지.
   - 그동안 폰·키오스크는 준비 안 됨, 다시 붙은 뒤 원점 전이면 누르지 않는지.
   - RPi4 전원(5 V 3 A)과 모터 전원 분리, `dmesg`의 `Undervoltage detected`.
5. **골든 갱신 목록(데스크톱에서 눈 검토 뒤)** — 폰 10장: `home_dark`·`home_light`·`home_empty`·`lt_home_empty`·`home_unknown_category`·`home_two_appliances`·`home_demo`·`home_large`(타일 상태 줄 낱말 경계 줄바꿈), `suggestion_large`·`suggestion_long_large`(큰 글씨 승인 화면 고정 영역). 키오스크 42장은 그대로. `screenshot_test.dart`의 아이콘 글꼴 경로가 `C:\flutter\flutter`로 고정돼 있어 지금 데스크톱(`C:\src\flutter`)에서는 그대로 돌지 않는다 — 갱신 전에 경로부터 정한다.
6. **시연 데이터 정리(사용자 확인 뒤)** — **지울 항목의 이름·ID 목록부터 만든다**(`GET /appliances`·`/routines`·`/routines/auto-rules`·`/suggestions`). 시연용으로 만든 데이터(시험 가전·시험 루틴·시험 제안)만 지운다. **실제 가전 등록·버튼 위치(보정)·확인 주행 기록·자동 실행 허용 기록·ThinQ 추가 가전은 건드리지 않는다.** 목록을 사용자에게 보여 주고 확인받은 뒤 지운다.
7. 큰 글꼴 승인 화면(글꼴 2.0)·홈 루틴 낭독을 에뮬레이터에서 다시 찍고, 가능하면 실제 TalkBack으로 루틴마다 따로 읽히는지와 "아침 데우기 실행하기"를 듣는다.
