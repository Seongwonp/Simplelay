## F4 이음매. 모드는 실제 실행 대상이 말한다 (`9fbb990`)

교차 평가가 잡아준 결함이다. 첫 구현은 서비스 생성 시 `SIMPLELAY_ACT_MODE`
하나로 모드를 정해 두고 모든 이력에 그 값을 찍었는데, 실행 대상은
`_controller_for()`에서 가전별 원격 노드로 바뀐다.

    ACT_MODE 미설정(=mock) + 선풍기는 원격 노드에 등록
    → 실제 원격 액추에이터가 버튼을 누름 → CSV에는 mock 으로 기록

반대로 "원격이니까 real"도 똑같이 틀렸다. **전송이 원격이라는 사실은 저쪽이
실제로 눌렀는지에 대해 아무것도 말해주지 않는다** — 원격 RPi4가 자기 안에서
`MockGrblClient`를 돌리고 있을 수 있다.

- `ExecutionMode`를 controller 계층으로 옮겼다(실행 경로의 성질이다)
- `MockGrblClient`=mock / `DbusGpioClient`=real, `ClosedLoopController`는 자기가
  쥔 클라이언트에게 묻는다
- **원격 3종(ESP HTTP·ESP-NOW·UART)은 `unknown`.** 노드가 스스로 보고하게

- 모드를 밝히지 않는 컨트롤러도 `unknown` — 기본값을 real/mock 어느 쪽으로

(`controller`와 `history`) `is` 비교가 조용히 어긋났고, **`execute_buttons`가
`appliance_id`를 `_run_buttons`로 안 넘겨** 수동 버튼 실행 이력이 대상 가전을
잃고 있었다(커스텀 가전은 대부분 이 경로다 — 실험 표본이 통째로 비는 자리).

## F1. 등록 상태와 조작 가능 상태 (`560c2c8`)

`NodeRegistry`는 **주소만** 안다. 주소가 등록돼 있으면 실행이 그 노드로 가고
끝이라, 구조가 사실상 `registered == operable`로 읽힌다. 실기기가 붙는 순간
그 등식이 깨진다 — 주소는 맞는데 선이 안 꽂혀 있고, 전송은 되는데 모터가 홈을
안 잡았고, 모터는 도는데 센서가 기준값을 안 잡았다.

**heartbeat가 온다는 것은 전송이 살아 있다는 뜻일 뿐이다.**

- 내부 네 축: `transport` · `motion` · `sensor` · `calibration` + 사유 + 확인 시각
- 사용자에게는 셋: **미연결 / 준비 필요 / 조작 가능**
- 게이트는 `_controller_for`(모든 진입점의 합류점) 안. 거절의 기준은
  **컨트롤러 호출 0회**
- **412**로 거절한다. 404는 '없는 가전'이고(이건 있다), 409는 이 API에서
  '다른 작업 실행 중'이라 "잠시 후 다시"로 안내된다 — 여기서 필요한 것은
  기다림이 아니라 **설치를 마치는 일**이다. `detail`은 화면에 그대로 실을 수
  있는 문장이다
- `ReadinessRegistry`는 **메모리에만** 산다. 주소와 보정 프로파일 버전은
  남기지만 살아 있는 준비 상태는 남기지 않는다 — 재시작 후에도 '조작 가능'이면
  그 사이 선이 빠졌는지 아무도 확인하지 않은 채로 물리 조작을 받는다. 오래된
  판정(TTL)도 같은 이유로 거절한다
- `calibration_profile_version`을 history·CSV에 스냅샷. 좌표를 다시 맞추면
  성공률이 통째로 달라진다

폰·키오스크는 `GET /appliances`에서 **같은 상태·같은 사유**를 받아 실행을 막고
무엇이 남았는지 보여준다.

## F1 마감 감사 (`bb5a339`)

교차 평가가 F1에서 두 개를 더 잡아줬다. 둘 다 실제 오작동·데이터 오염으로
이어지는 것이라 F2 전에 닫았다.

**① 노드 없는 커스텀 가전이 로컬 갠트리로 흘렀다.** `_require_ready`가
"로컬 컨트롤러면 검사 대상 아님"으로 빠져나갔는데, 노드 없는 커스텀 가전도
그 로컬 폴백으로 간다. 로컬 컨트롤러는 **내장 가전 위에 얹힌 갠트리**라,
선풍기 시퀀스가 전자레인지의 엉뚱한 버튼을 누른다 — R1이 막았던 물리
오라우팅이 다른 문으로 되돌아온 것이다.

로컬 실행이 정당한 경우를 둘로 못 박았다: **내장 가전**(그 갠트리가 곧 자기
액추에이터다), 또는 `SIMPLELAY_LOCAL_APPLIANCES`에 명시적으로 밝힌 커스텀
가전(데모 배선). `/appliances`의 `can_execute`도 같은 규칙을 쓴다 — 어긋나면
누를 수 있는데 안 되는 버튼이 생긴다.

8/31 에어컨 데모 경로를 검증하던 기존 테스트 2건은 새 계약으로 갱신했다.
**옛 동작이 곧 이 결함이었다.**

**② 보정 버전을 실행 종료 시점에 읽고 있었다.** 20초짜리 실행 도중 노드가
`cal-v1 → cal-v2`를 보고하면, 끝나고 읽은 값은 그 실행이 실제로 쓴 좌표가
아니다. v1로 돌린 결과가 v2의 성적표에 들어간다. 대상을 확정하는 시점에
캡처해 실행 컨텍스트(비동기 job 스레드 포함)로 넘긴다.

**③ 클라이언트 fail-open 범위.** readiness 필드가 없는 응답을 `operable`로
보고 있었다. 안전한지는 **서버 게이트가 반드시 걸리는 경로인가**로 갈린다:

- HTTP 실행 → 서버가 412로 막는다. 화면이 느슨해도 물리 조작은 못 나간다
- **BLE 폴백 → 서버를 거치지 않는다.** ESP32로 바로 나가므로 게이트가 없다

그래서 규칙을 갈랐다. 필드가 없으면 `unknown`(확인된 `operable`과 구분),
서버가 "안 된다"고 말한 가전은 **BLE로도 내보내지 않는다**, 서버 얘기를 들은
적이 없으면 막지 않는다 — 막으면 서버가 죽었을 때 조작 수단이 통째로 사라진다.
