# 인계 2026-10-18 — 처음 보는 심사위원 시각의 평가

노트북 세션이 **프로젝트 맥락 없는 평가자**에게 심사위원이 받는 자료만 주고 채점하게 한 결과다(10/18 저녁 기준 저장소).
평가자가 본 것: README, [개발완료보고서 초안](submission/개발완료보고서-초안.md), [작품소개서 초안](submission/작품소개서-초안.md), 골든 화면 10여 장, 펌웨어·서버 코드 일부.
보지 않은 것: CLAUDE.md, devlog, 내부 평가·계획 문서. 배점은 [본선 실행 계획](본선-실행계획-2026-09-30.md) §6(완성도 60·독창성 20·활용성 20·가산점 10).
**데스크톱 세션은 이 문서를 읽고 §5 순서대로 반영한다.** 같은 날 [정합 점검 목록](submission/정합-점검-2026-10-18.md)과 겹치는 곳은 그 목록을 따른다.

## 1. 점수 — 59/100

| 항목 | 점수 | 평가자 근거 |
|---|---|---|
| 완성도 /60 | 32 | 핵심 장면(갠트리 실제 누름·캐리지 이동, CT 판정, 콘센트 회로)이 실물로 하나도 성공하지 않음. SW 안전 설계·정지 3단계 실측·ThinQ 실가전은 탄탄 |
| 독창성 /20 | 13 | 승인 결속(명령 지문), 단계별 확인, '확인 불가는 재전송 안 함', 물리 가전 사건 → ThinQ 가전 흐름은 신선. 누름 기구·모션 제어 핵심은 Touch Bridge와 같음 |
| 활용성 /20 | 11 | 대상·문제 정의는 좋음. 가전 한 대에 RPi5+RPi4+ESP32×2+CoreXY, 원가·설치 시간 공란 → 보급 가능성 판단 불가 |
| 가산점 /10 | +3 | 보드 3종 연동은 조건부, 시연 흐름 안 증거 미측정. L2(소리)는 실행 경로에 미연결 |

참고: 같은 날 코드·문서까지 본 평가는 72, 화면만 본 처음 보는 평가자 UI 평가는 84였다. 이번 59는 **제출 서류만 받은 심사위원** 시각이라 더 낮다. 평가자 판단: 실물 E2E 1회 성공이면 70점대 중반 가능.

## 2. 강점

1. **검증 수준을 정직하게 나눔** — README 검증 표의 실물/모의/예정, 보고서 '【기입】을 옛 수치로 채우지 않는다', 상용품은 설계 차이로만 비교.
2. **안전·실패 처리 설계가 깊음** — 정지 보냄 → MCU 응답 → 엔코더 멈춤 3단계, 걸림 시 재시도 없이 정지, 토글 버튼 재누름 금지, 결과를 잃으면 재전송 안 함, 펌웨어 워치독·명령 기한·소프트 리밋.
3. **확인 수준에 맞는 화면 문구** — '눌렸는지 몰라요'와 다음 행동, '켜졌는지는 아직 몰라요', 비상 상태 안내.

## 3. 약점

1. **시연 핵심 미검증** — 승인 → 실제 누름 → CT 가열 시작(README 시연 ②, 보고서 §3-3 장면 2). 벨트·솔레노이드·콘센트 회로가 없는 상태.
2. **문서끼리 모순** — 안전 수리 배포(README '배포됨' vs 보고서 §6-1a·소개서 '미배포'), 시험 수(README vs 보고서 §6-2), 구성도 설명(소개서 '초록 실선=실물 확인' vs 보고서 그림 1 '구버전, 선 색을 증거로 쓰지 않음'), **`firmware-motion-corexy/README.md`의 '보드에 올리지 않았고 실물 검증 0건'**(10/12~14 실물과 모순 — 정합 점검 목록에 없던 곳).
3. **보고서 가독성** — 커밋 SHA·devlog 링크·'실측 실행 SHA 【기입】'이 본문을 덮음. 【기입】 20곳 이상, 구버전 그림·'그림 자리' 5곳. 책자로 인쇄되면 미완성 서류로 보인다.
4. **HW 독자 기여가 약해 보임** — 기구·모션 펌웨어 핵심은 원작, 고유 HW인 콘센트 모듈은 펌웨어 컴파일까지(`firmware-outlet/README.md`). L1 전류센서 미배선·L2 미연결이라 '단계별 확인'의 실물 근거는 사실상 L3 하나.
5. **화면이 실제보다 앞섬** — 키오스크 대기 화면 골든에 세탁기·선풍기·인덕션 '준비됐어요'(실물은 전자레인지 1대 — 골든 예시 데이터지만 제출 그림으로 쓰면 그대로 지적받음), 완료 '가전이 켜졌어요'(CT 미측정), 폰 상태 '센서로 눌림 확인'(L1 미배선), 자동 규칙 '데우기가 끝나면'(문서는 '가열 종료, 조리 완료가 아닐 수 있음'보다 단정적).

## 4. 질의응답 예상 질문 (답을 미리 준비)

1. 오늘 갠트리가 실제 버튼을 몇 번 눌렀고 첫 시도 성공률은 n/N인가? 펌웨어 README '실물 검증 0건'과 10/12 실물 중 어느 쪽이 현재인가?
2. '즉석밥'은 눌러도 전력 변화가 없다. L1 센서 없이 첫 버튼이 눌렸는지 어떻게 아나? 첫 누름을 놓친 채 '시작'을 누르면 다른 모드로 가열될 위험은?
3. 인버터 전자레인지는 출력을 주기적으로 끈다. CT 2채널 교대 샘플링(채널당 250 Hz)으로 RMS·종료 판정을 믿을 수 있나? 임계값 근거는?
4. Touch Bridge(한이음, 진행 중)와 같은 기계·모션 펌웨어 — 같은 장비가 두 대회에 나가는 것 아닌가? 이 작품만의 HW 산출물은?
5. 가전 한 대당 BOM·설치 시간은? 사진 4점 보정만으로 작은 버튼에 맞는 mm 정확도가 나오나? 버튼 푸셔 대비 비용을 정당화하는 근거는?

## 5. 반영 순서 (10/28 제출 · 11/6 시연)

1. **실물 E2E 1회 성공·촬영** — 승인 → 갠트리 실제 누름 → CT 시작·종료 → 공기청정기. README 첫 화면에 사진 1장·30초 영상, 제출 영상 URL로도 사용. (ESP32·솔레노이드·콘센트 회로 필요 — HW 담당 일정에 맞춰 SW는 시험 절차·촬영 대본을 미리 준비)
2. **콘센트 모듈 회로 + CT 파형 그래프 1장** — 정상·취소·팬만 도는 조건의 판정 시점. 고유 HW와 L3 근거가 동시에 생긴다.
3. **문서 정합** — [정합 점검 목록](submission/정합-점검-2026-10-18.md) §2·§3 + 위 §3-2의 펌웨어 README '0건'. SHA·devlog 나열은 보고서 부록으로 옮기고 본문은 '무엇을 어떤 수준으로 확인했나'만. 구버전 그림·【기입】을 없애고 못 잰 항목은 '미측정' 한 줄로.
4. **활용성 숫자** — 비교 조건 실험(축소판이라도 n 명시), BOM 원가, 설치 시간, 팀 밖 1~2명 사용성. 숫자 3개만 있어도 오른다.
5. **시연 축소·백업** — 5장면을 실물 3장면(거절 → 승인·누름·CT → ThinQ 자동)으로. 모의 장면은 '연습' 표시, 공유기·백업 영상·모의 클라우드 전환 리허설. **화면이 실제보다 앞서는 문구 정리**(§3-5 — 등록 안 된 가전 '준비됐어요', CT 미측정에서 '가전이 켜졌어요', L1 없이 '센서로 눌림 확인', '데우기가 끝나면'). 제출 그림에는 실제 구성(전자레인지·공기청정기)으로 만든 화면을 쓴다.

UI는 동결 유지([노트북 검토 인계](인계-2026-10-18-노트북-검토.md) §2-1). 위 §3-5는 정직성 문제라 예외로 고친다.
