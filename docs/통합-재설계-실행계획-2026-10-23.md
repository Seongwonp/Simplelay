## 1. 목표와 사용자가 정한 작업 순서

첫 목표는 **담당자가 검증한 ESP32 코드로 두 모터를 조작하고, 앱에서 저장한 버튼 위치로 다시 이동하는 것**이다. 그다음 사진 매핑·일반 실행·화면을 연결한다.

**사용자 확정 원칙(2026-10-23): HW 코드는 SW 담당이 수정하지 않는다.** ESP32 스케치·헤더·핀·PID·모터 제어식과 HW 담당이 관리하는 코드는 읽기 전용으로 참고한다. 앱·RPi5·RPi4의 SimpleLay 통신 어댑터가 담당자의 기존 규약을 따른다. HW 코드 변경이 필요해 보이면 근거를 인계 기록에 남기고 담당자가 수정한 버전을 받는다. SW 작업으로 펌웨어를 임의 수정·재업로드하지 않는다.

사용자 결정: **운영용 안전 정책의 설계·추가 적용·종합 검증은 매핑 완료 뒤 마지막 개발 단계에서 한다.** 조정 중 매 동작마다 홈을 요구하거나, 측정하지 않은 작은 작업 범위를 먼저 강제해 좌표 탐색을 막지 않는다. 원본에 있는 정지 명령은 조작 도구에서 계속 사용할 수 있게 연결한다.

개발 순서는 다음과 같다.

1. RPi4·ESP32·기구를 하드웨어 담당자에게 인계하고 사용할 원본 파일 묶음을 확정한다.
2. RPi4가 그 원본 프로토콜을 이해하도록 어댑터와 연결 상태를 맞춘다.
3. 개발자 도구를 조이스틱·좌표·상태·센서·로그 중심으로 정리한다.
4. 수동 위치 등록 → 다른 곳으로 이동 → 등록 위치 재방문을 완성한다.
5. 사진 매핑으로 얻은 좌표를 같은 이동 경로에 연결한다.
6. 일반 앱·키오스크·루틴과 연결하고, 받아 둔 UI 마감 계획을 처리한다.
7. 매핑 결과를 바탕으로 운영용 안전 정책을 마지막으로 적용·검증한다.
8. 확정 빌드로 실제 시연·촬영·제출 자료를 마감한다.

하드웨어 담당자가 기구를 조정하는 동안 SW 담당자는 2·3단계의 모의 통신 시험과 UI 수정을 진행할 수 있다. 기구가 없다고 전체 작업을 멈출 필요는 없다.

## 3. P0 — 하드웨어 담당자 인계부터 마감

**담당:** HW 담당은 기구·펌웨어 기준 확정, SW 담당은 RPi4 접근·도구·기록 준비.

### 넘길 구성과 정보

- RPi4, 실제 사용하는 ESP32 모션 보드, USB 케이블, 기구·모터·드라이버·엔코더·SwitchBot 연결 구성을 함께 넘긴다. 전원 구성은 HW 담당이 관리한다.
- 현재 올라간 바이너리의 이름·해시·빌드 입력 파일 목록을 남기고, HW 담당이 쓰는 기준 스케치 전체와 비교한다.
- HW 담당에게 받을 파일: 스케치·설정·모션/모터/엔코더 헤더·SwitchBot 헤더·라이브러리/보드 버전. 바뀐 파일만 전달해 파일 조합이 흔들리지 않게 한다.
- RPi4 접속 방법, Docker 시작 방법, USB 장치 경로, 시리얼 속도, 실행기 중지/복귀 방법을 한 장에 적는다. 주소·키·기기 식별값은 로컬 전용 인계 메모에 둔다.
- `?`·`P`로 확인하는 읽기 도구와, 담당자가 직접 사용할 수 있는 시리얼 명령 입력·수신 로그 도구를 준비한다. 자동 연결 시 모터 명령이 실행되지 않게 한다.
- 인계 도구는 **RPi4 + ESP32만으로** 동작하게 한다. HW 담당의 모터·SwitchBot 시험에 RPi5·우리 앱·에뮬레이터가 필수로 끼지 않게 하고, SimpleLay 전체 경로는 복귀 뒤 연결한다. 담당자의 BLE 앱과 USB 도구는 어느 쪽으로 제어 중인지 정해 번갈아 사용한다.
- 기존 동작 영상과 안 움직였던 명령·관찰 결과를 함께 전달한다. 추측 원인과 관찰 사실을 분리한다.

### 담당자가 확정해 줄 결과

| 확인할 결과 | 남길 정보 |
| --- | --- |
| 기준 펌웨어 | 전체 소스 묶음 버전·파일 해시·빌드 환경 |
| 조이스틱의 실제 방향 | 사진 기준 좌/우/위/아래와 명령의 대응 |
| 두 모터·엔코더 | 명령·A/B 계수 변화·눈으로 확인한 캐리지 이동 |
| 물리 이동과 계산 좌표 | 풀리·환산값·가용 이동 범위. 설정값과 실측값 구분 |
| Z 누름 | SwitchBot 장착·단발 누름 결과·응답 의미 |
| 기준점 설정 | 수동 `Z`와 자동 `H`의 실제 동작 및 위치 기준 |

**완료 조건:** HW 담당이 RPi4에서 자신이 검증한 펌웨어를 직접 제어할 수 있고, SW 담당이 같은 파일 묶음·명령·응답 로그를 받았다. RPi4의 전체 앱 연동을 끝낼 때까지 인계를 미루지 않는다.

## 4. P1 — 제어 책임과 원본 프로토콜 맞추기

### 책임을 한 곳씩 둔다

| 계층 | 맡을 일 |
| --- | --- |
| 폰·키오스크 | 방향·좌표 이동·위치 등록 의도를 전달하고 현재 결과를 표시 |
| RPi5 | 가전·버튼·보정 버전·실행 번호를 결속하고 RPi4에 전달 |
| RPi4 | 원본 ESP32 규약으로 전송·응답 분류·실행 상태 변환·기록 |
| ESP32 | CoreXY 모터 조합·엔코더·PID·궤적·SwitchBot BLE 처리 |

원본이 mm 목표 좌표를 받는 경로에서는 RPi4가 mm를 모터 카운트로 바꿔 다시 보내지 않는다. **사진 좌표 변환과 모터 A/B 변환을 서로 다른 단계로 유지해 중복 변환을 없앤다.**

### 사용할 두 조작 경로

| 용도 | 원본 명령 | 완료를 판단할 근거 |
| --- | --- | --- |
| 개발자 방향·시간 조정 | `M a b ms` | `OK`는 접수 근거만. 이후 상태·계수·실제 이동을 구분 |
| 현재 자리를 좌표 기준으로 설정 | `Z` | 이동 없이 좌표 기준을 바꾸는 원본 동작 확인 후 상태 조회 |
| 개발자 진단 | `P`, `?` | 해당 펌웨어의 실제 원문 |
| 일반 목표 이동 | v2 `move_only` | 같은 `commandId`의 `POSITIONED`·위치·`positionToken`·최종 상태 |
| 목표 도착 뒤 누름 | v2 `press` + 토큰 | 해당 명령의 완료/오류. Bot 응답과 실제 버튼 눌림은 별도 |
| 상태 조회 | v2 `status` | 같은 `commandId`의 위치·기준 설정 여부 |
| 중단 | v2 `stop` 또는 원본 `S/!` | 실제 받은 응답까지만 기록 |
| 자동 원점 복귀 | `H`/v2 `home` | 매핑 초기 작업의 필수 선행으로 두지 않음. 마지막 운영 정책 단계에서 적용 범위 결정 |

### 구현할 파일과 계약

- 새 Touch Bridge 어댑터를 만들고 [act_main.py](../rpi4/act_main.py)에 명시적 프로토콜 선택을 추가한다. 설정 이름·허용값은 구현 첫 커밋에서 확정하고 잘못된 선택을 조용히 다른 모드로 바꾸지 않는다.
- 기존 `SerialMotionClient` 구체 클래스 검사에 의존한 개발자 연결·준비 판정을 공통 모션 인터페이스와 기능 정보로 바꾼다. 필요한 기능만 추출한다.
- [dev_motion.py](../rpi4/services/dev_motion.py)·[dev_real_motion.py](../rpi/services/dev_real_motion.py)·[dev_router.py](../rpi/api/dev_router.py) 사이의 기능 정보와 결과 모델도 함께 맞춘다. 새 모드인데 앱이 실물 조작을 못 찾는 이음매를 시험한다.
- 시리얼은 **한 리더가 읽는다.** 로그·텍스트 진단·v2 JSON을 분류하고 다른 요청의 줄을 소비해 버리지 않는다. 상태 조회가 이동 응답을 먹거나 이동 대기가 정지 전송을 잠그지 않게 한다.
- 원본의 `CMD_LINE_MAX=256`, command ID 길이·허용문자, 출력 정밀도를 기준으로 인코딩·파싱을 설계한다. 긴 요청은 보내기 전에 검출한다.
- `RECEIVED`·`MOVING`·`POSITIONED`·`COMPLETED`와 오류를 분리한다. `COMPLETED`만 보고 위치 토큰이 있다고 가정하지 않는다.
- 텍스트 명령은 요청 ID가 없으므로 개발자 조작이 포트를 독점하는 동안만 처리한다. 개발자 입력과 일반 실행의 충돌을 요청 단계에서 설명한다.
- 원본 v2 `status`에는 기존 어댑터의 엔코더 필드가 없다. 없는 필드를 합성하지 않고 지원 여부를 표시한다. 진단용 `P` 파서는 실제 로그로 확정한다.

**완료 조건:** 실제 받은 프로토콜 모양을 사용하는 가짜 시리얼로 연결·이동·도착·누름·오류·중단이 이어진다. 모의 장치가 기존 SimpleLay 규약으로 답해 시험만 통과하는 형태를 금지한다.

## 5. P2 — 개발자 도구를 위치 조정에 맞게 정리

**첫 화면:** 연결된 장치와 현재 좌표 → 큰 방향 패드 → 파워·지속시간 → 현재 위치 저장. 상태·센서 읽기는 유지하고 원문 명령·로그는 펼쳐 볼 수 있게 둔다.

- 한 번의 개발자 진입 뒤 조작할 수 있게 연결 이유를 표시한다. 개발자 화면이 사라지거나 `mock`과 실물이 바뀌는 문제부터 확인한다.
- 사용자가 요청한 대로 조작 화면에서 매번 누르는 `홈` 버튼·홈 강제 안내를 제거한다. `현재 위치를 기준점으로`는 위치 등록 도구에 별도로 둔다.
- **시간 조그와 좌표 이동을 구분**한다. `M 0.5 0.5 300`의 0.5는 PWM 비율, 300은 ms이며 0.5 mm·300 mm가 아니다. 시간 조그의 실제 거리를 mm처럼 표시하지 않는다.
- 방향 패드는 X/Y 의도를 A/B 동시 명령으로 변환한다. 원본 기준 식 `A=X+Y`, `B=X-Y`를 출발점으로, 최대 절댓값을 기준으로 함께 정규화해 의도한 파워를 유지한다. 사진 기준 위/아래와 펌웨어 Y 부호는 P0 결과로 확정한다.
- 파워·지속시간 초기 후보는 담당자의 `0.5`, `300 ms`이고 `500 ms`도 조정 후보로 둔다. 원본 허용 범위·담당자 최종 설정을 확인해 적용한다. 임의의 좁은 mm 범위로 시간 조그를 차단하지 않는다.
- 1차는 한 번 누르면 설정 시간 동안 움직이는 방식으로 검증한다. 길게 누르기 반복은 기본 조작이 확인된 뒤 추가하고, 명령을 무한히 쌓는 타이머 구조는 사용하지 않는다.
- 터치 뒤 전송·접수·동작 중·완료를 구분하고 현재 좌표를 갱신한다. 이동 대기가 화면 전체의 상태·중단 버튼을 막지 않게 한다.
- 중단 버튼은 바로 보이는 고정 위치에 둔다. `M`의 정상 시간 종료마다 앱이 불필요한 별도 정지를 보내 기준점을 계속 잃게 만드는지 확인한다.
- 원문 명령 입력은 실제 지원 명령과 응답 로그를 보여 준다. 지원하지 않는 채팅 문장을 모터 명령으로 추론하는 기능은 추가하지 않는다.
- 재연결 때 모터를 자동으로 움직이지 않고 상태부터 읽는다. 기존 세션·응답 세대 처리가 조작마다 초기화되는지 확인한다.

**완료 조건:** 화면 진입 → X/Y 네 방향 조정 → 현재 좌표·상태 확인 → 위치 저장이 반복된다. 매 방향 조작 뒤 기준점을 다시 잡게 되면 미완료다.

## 6. P3 — 사진보다 먼저 수동 좌표 등록·재방문

### 좌표 기준을 먼저 하나로 맞춘다

1. 기구를 보는 방향을 사진 한 장으로 고정하고 A/B, 좌/우/위/아래를 표시한다.
2. 개발자 시간 조그로 네 구석의 **도달 가능한 위치**와 가운데를 확인하고 좌표·원시 계수를 기록한다. 물리 끝점을 찾기 위해 벽을 계속 미는 방식을 기준으로 삼지 않는다.
3. 원본의 현재 위치 기준 설정 방식으로 좌표 기준을 한 번 정한다. 시간 조그 탐색 뒤 절대좌표 시험을 시작할 때 기준을 확정한다.
4. 손으로 캐리지를 옮기거나 설정을 바꾼 뒤에는 이전 기록과 같은 좌표 기준인지 표시한다. 앱 접속만으로 좌표를 0으로 덮어쓰지 않는다.
5. 펌웨어 계산 mm와 실제 이동량을 구분해 기록하고, 필요한 환산 확인은 HW 담당의 실측값을 받는다.

### 버튼 등록과 재방문 순서

1. 더미 패널을 고정하고 버튼마다 변하지 않는 ID와 표시 이름을 준다. 위쪽 작은 두 버튼 이름은 사용자 확인대로 `10초`, `20초`다.
2. 조이스틱으로 버튼 중심에 맞춘 뒤 **현재 위치 읽기 → 해당 버튼에 저장**한다. 누르고 있는 동안 읽은 중간 위치를 저장하지 않는다.
3. 버튼 위치와 함께 가전 ID·기준 버전·펌웨어/기구 설정 버전을 남긴다. 버튼 이름을 바꿔도 ID와 좌표의 연결이 유지돼야 한다.
4. 다른 위치로 옮겨 대기한다. 저장한 버튼을 선택해 누름 없이 이동하고 눈으로 중심을 확인한다.
5. 가운데·모서리 가까운 버튼을 섞어서 각 3회 이상 재방문해 오차와 출발 방향의 영향을 기록한다. 3회는 개발 확인 기준이며 성능 통계가 아니다.
6. 여러 버튼을 번갈아 이동한 뒤 첫 버튼으로 돌아가 누적 오차를 확인한다.

**완료 조건:** 적어도 더미 버튼 3곳을 저장하고, 다른 출발점에서 각 버튼으로 재방문할 수 있다. 반복 오차 허용값은 실제 버튼 면적·누름 팁 크기로 정하며 문서에서 임의 mm를 실측값으로 선언하지 않는다.

## 7. P4 — 사진 매핑을 동일한 좌표 이동에 연결

기존 [panel_mapping.py](../rpi/services/panel_mapping.py)·[transform.py](../rpi/calibration/transform.py)와 가전 추가 흐름을 활용한다.

1. 등록할 사진과 기구를 고정한다. 프레임 네 모서리, 버튼 중심, 대기 위치, 실제 취소 버튼을 서로 다른 항목으로 저장한다.
2. **사진 원본 픽셀 → 화면에서 보이는 사진 → 프레임 평면 → 모션 좌표**의 각 변환을 표로 만든다. `BoxFit`의 여백·잘림·축소·이미지 회전 때문에 탭 위치가 달라지는지 확인한다.
3. 사진 좌상단 기준 Y 증가와 원본 모션 좌하단 기준 Y 증가를 명시적으로 변환한다. 가로/세로로 기구를 놓았을 때 회전·반사·원점 오프셋도 같은 변환에서 처리한다.
4. 기구 치수·좌표 기준은 P3에서 확정한 값으로 전달한다. 화면 격자 칸 번호를 mm로 해석하지 않는다.
5. 사진으로 계산한 버튼 좌표와 P3의 수동 등록 좌표를 비교한다. 계산이 맞아 보이는 점 외에 변환 맞춤에 쓰지 않은 점도 확인한다.
6. 사진에서 버튼을 탭 → 목표 좌표 확인 → **이동만** → 현재 좌표·실물 위치 비교를 먼저 마친다.
7. 저장 후 앱 재시작·서버 재조회에도 같은 가전·버튼·좌표 버전이 유지되는지 확인한다. 다른 폰에 로컬 사진이 없을 때 좌표와 사진 표시가 어떻게 되는지도 확인한다.
8. 기구·패널·기준점이 바뀌었을 때 어떤 매핑을 다시 해야 하는지 표시한다. 단순 재연결과 실제 설치 변경을 같은 사건으로 취급하지 않는다.

**완료 조건:** 동일 버튼에서 수동 좌표와 사진 좌표의 차이를 기록했고, 사진 기반 재방문이 반복된다. 버튼을 인식한 화면이나 저장 성공만으로 매핑 완료라고 쓰지 않는다.

## 8. P5 — 일반 앱·키오스크·루틴 연결

- 개발자 이동과 일반 실행이 같은 Touch Bridge 어댑터를 사용한다. 화면마다 다른 A/B 조합·좌표 변환을 두지 않는다.
- 저장한 `appliance_id`·버튼 ID·보정 버전·job 대상을 실행 시작부터 기록 종료까지 유지한다. 실행 중 다른 가전을 선택해도 대상이 바뀌지 않아야 한다.
- 원본 v2 이동의 도착 토큰을 같은 이동에 이어지는 한 번의 누름에만 사용한다. 이전 버튼·정지 전 이동의 토큰을 재사용하지 않는다.
- SwitchBot 응답은 누름 장치의 처리 결과로 기록한다. 그 응답만으로 전자레인지가 가열 중이거나 실제 버튼이 눌렸다고 표시하지 않는다.
- 센서가 아직 없으면 해당 검증은 미확인으로 남긴다. 모의 판정의 성공을 실물 실행의 근거로 섞지 않는다.
- 더미 패널에서 선택 → 승인 → 이동 → 누름 명령 → 결과 → 기록을 먼저 잇는다. 실제 가전의 동작을 포함한 최종 시험은 P7 이후에 한다.
- 루틴은 버튼별 목표를 순서대로 전달한다. 대상 도착 실패 후 다음 누름으로 넘어가지 않는지 확인한다.
- 개발자 모드에서 등록한 가전이 모드를 끄면 사라지는 기존 기록을 재확인한다. 설치 가전 목록과 개발자 화면 노출 조건을 분리한다.
- 키오스크·폰이 같은 job의 대상·단계·결과를 표시하는지 확인한다. 완료 뒤 이전 승인 카드로 돌아가는 경로도 재현되면 함께 수리한다.

**완료 조건:** 더미 기준 전체 경로가 연결되고, 개발자 전용 화면을 닫아도 등록 가전·매핑·정상 조작 경로가 유지된다.

## 10. P7 — 매핑 완료 후 마지막 개발 단계: 운영 안전 정책

**시작 조건:** P3 수동 재방문과 P4 사진 재방문이 확인됐고 실제 좌표 기준·이동 범위가 기록돼 있다. 이 단계에 앞서 임의의 제한값·홈 강제 흐름을 계속 추가하지 않는다.

| 작업 | 매핑 결과를 어떻게 사용할지 | 확인할 결과 |
| --- | --- | --- |
| 작업 영역 | 실제 측정한 범위와 버튼·대기 위치를 기준으로 운영 범위 결정 | 안쪽 목표 허용, 범위 밖 목표는 이동 전 거절 |
| 기준점 수명 | `Z`·`H`·수동 이동·USB 재연결·보드 재부팅을 구분 | 기준이 유지되는 조작에는 반복 홈 없음. 잃었을 때만 구체적인 복구 안내 |
| 이동 중 정지 | 원본 정지 명령을 RPi4·RPi5·앱까지 연결 | 요청·보드 응답·실제 정지를 구분해 실측 |
| 연결 끊김·기한 | 원본의 호스트 단절 대응 유무부터 확인 후 필요한 보완 결정 | 실행 결과를 꾸미지 않고 미확인/중단으로 기록. 자동 재누름 없음 |
| 누름·재시도 | 위치 토큰과 실제 확인 수단의 의미에 맞게 정책 적용 | 전송 후 결과 미확인을 같은 버튼 재누름으로 바로 처리하지 않음 |
| 개발자/일반 실행 | 조정 상태와 일반 실행 상태의 전환 확인 | 서로의 작업을 끼워 넣지 않음 |
| 배포·시연 설정 | 실제 빌드와 개발자 기능·접근 설정 점검 | 재부팅 뒤 예상한 서비스·프로토콜·실행 모드로 복구 |

기존 원본에서 지원하지 않는 확인 수준을 SW만으로 있다고 표시하지 않는다. 특히 원본 v2 `status`의 정보만으로 기존 `verified` 정지 판정을 그대로 유지할 수 있는지 다시 결정한다.

**완료 조건:** 정상 이동·누름과 이동 중 중단·통신 단절·재시작을 실제 기구에서 확인했고, 폰·키오스크·이력의 표현이 관찰 결과와 맞는다. 전자레인지 정지 버튼 누름과 갠트리 모터 정지는 다른 동작으로 기록한다.

## 11. CT·콘센트 모듈 작업의 위치

- 기존 사용자 결정인 **10/28 제출 영상에서 CT 제외, 11/6 결선 목표**를 유지한다. CT를 기다리느라 모터·사진 매핑을 막지 않는다.
- HW 담당은 센서·콘센트 모듈을 준비하고 SW 담당은 받은 실제 입력 형식에 맞춰 기존 기록·판정 경로를 연결한다. 임의 임계값으로 실측 성공을 선언하지 않는다.
- CT 조립·센서 기록 도구 점검은 P0~P6와 병행할 수 있다. 실제 가전 가열을 포함한 통합 시험은 P7 이후 진행한다.
- 가열 시작·종료 파형과 판정 근거를 남긴다. 가열 종료를 정상 조리 완료로 단정하지 않는다.
- CT가 늦으면 기계의 이동·누름 장면과 센서 검증 장면의 완료 범위를 분리해 발표한다.

## 12. 시험은 이음매와 실제 응답을 우선

| 번호 | 지나가야 하는 이음매 | 확인할 사례 |
| --- | --- | --- |
| T1 | 앱 방향 → RPi5 → RPi4 → `M` | 네 방향 A/B 조합·파워·시간·전송 횟수 |
| T2 | 원본 텍스트와 JSON → 단일 리더 | 부트 로그·진단 응답이 이동/정지 응답을 소비하지 않음 |
| T3 | 이동 → 도착 → 토큰 → 누름 | 다른 command ID·토큰 없음·이전 토큰·늦은 응답 |
| T4 | 조그 → 좌표 읽기 → 저장 → 재방문 | 마지막 중간 응답이 저장 좌표를 덮지 않음 |
| T5 | 사진 탭 → 변환 → 실행 목표 | 사진 회전·여백·Y축 방향·원점 오프셋 |
| T6 | 새 모션 모드 → 기능 정보 → 앱 | 실물 연결 인식·개발자 진입·상태/센서 읽기 |
| T7 | 가전/버튼/기준 버전 → job → 기록 | 선택 가전 변경·이름 변경·다른 가전의 같은 버튼 이름 |
| T8 | 기준 유지 → 다음 조그 | 정상 반복 조작마다 원점 요구가 되살아나지 않음 |
| T9 | UI 상태 → 사용자 문구 | 로딩/빈 기록/실패·모의/실물/미확인 구분 |
| T10 마지막 단계 | 이동 중 정지·단절·재시작 | P7에서 실제 응답과 물리 결과를 함께 확인 |

가짜 MCU는 **원본 응답 로그를 fixture로** 사용한다. 파서 시험은 원문을 읽고, 서비스 시험이 파서를 우회한 가짜 객체만 넣는 형태로 끝내지 않는다. 새 프로토콜에는 소프트웨어 계약 시험과 실제 기구 확인이 모두 필요하다.

## 14. 변경·커밋·배포 기준

- 지금은 계획 작성 단계다. 문서 검토 뒤 P0부터 실행하고 작업마다 담당·결과·미완 항목을 갱신한다.
- 사용자가 지정한 main에서 작게 커밋한다. 프로토콜 어댑터, 개발자 화면, 수동 등록, 사진 연결, 일반 실행, UI, 마지막 운영 정책을 섞지 않는다.
- 기존 미커밋 파일 5개는 새 방향과 대조한다. 임시 bench 자동 홈·에뮬레이터 노출 플래그는 그대로 정식 동작에 편입하지 않고 목적에 맞춰 정리한다.
- SW 변경은 관련 시험 → 해당 영역 회귀 → 변경된 화면 골든 순서로 확인한다. 모션 연결 변경은 RPi4·백엔드 이음매 시험을 함께 돌린다.
- 회귀 시험은 실제 결함이 있는 이전 코드에서 실패하는지 확인한다. 순수 문구·문서 편집에 동작과 같은 시험을 중복 작성하지 않는다.
- 배포 때 PC HEAD·RPi4/RPi5 이미지·APK·키오스크 버전을 기록하고, 프로토콜이 이어지는 조합으로 배포한다. 펌웨어는 담당자의 확정본과 합의한 변경만 올린다.
- 통과/실패/건너뜀, 골든 포함 여부, 실제 기구 확인 여부를 따로 적는다. 테스트 수나 빌드 성공을 기구 이동 성공으로 대신하지 않는다.
- 외부 평가 점수를 올리기 위한 반복 개편은 하지 않는다. 막힌 사용자 과업과 실패한 실제 경로를 수정 근거로 삼는다.

## 15. 공개 문서와 로컬 전용 기록

공개 저장소에는 역할·프로토콜 모양·재현 절차·확인된 결과·미검증 범위만 적는다.

`dev-docs/` 등 gitignore가 적용된 로컬 전용 위치에는 다음을 둔다.

- RPi4/RPi5 접속 주소·장치 경로·계정 접근 안내·env 백업 위치.
- 담당자가 준 원본 파일과 해시 대응표, 실제 업로드한 바이너리·빌드 입력 목록.
- 원문 시리얼 로그·모터 영상·매핑 사진·실측 좌표표·배포 당시 상태.
- SwitchBot 식별값·페어링 정보·API/링크 키 등 기기별 값. 공개 문서로 복사하지 않는다.
- 대회 플랫폼의 비공개 제공 자료·빌드 환경. 외부 평가나 공개 리포에 전송하지 않는다.

이 파일들이 gitignore된 것과 추적되지 않는 것을 확인하고, 인계 자료는 필요한 팀원에게 직접 전달한다. 공개 문서에 로컬 파일 내용을 인용할 때도 식별값·개인정보·비공개 플랫폼 내용은 제외한다.
