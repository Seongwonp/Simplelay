# ThinQ 연동 검토 — 데스크톱 답변 (2026-09-22)

[데스크톱 Claude 인계](데스크톱-Claude-인계-2026-09-22.md) 7절의 요청에 대한 답이다.
**코드는 바꾸지 않았다.** 비공개 플랫폼 자료는 로컬에서만 대조했고, 여기에는 인터페이스
이름·메시지 형식을 적지 않는다. 공개 API 사실은 아래 출처에서 2026-09-22에 확인했다.

## 0. 결정 사항 (사용자 확인)

| 항목 | 결정 |
|---|---|
| 저장소 가드 | 제품명 ThinQ는 금지어에서 뺐다(공개 제품명, 공식 공개 API 연동 대상). 플랫폼 내부 인터페이스·버스 이름은 계속 막는다 |
| 연동 경로 | **직접 ThinQ Connect(공식 파이썬 SDK)**. Home Assistant는 상시 설치하지 않고, 전문가 자료를 읽는 조사용으로만 노트북에서 |
| 대표 시나리오 | **조리 확인 → 공기 관리**: 물리 폐루프의 가열 확인 결과가 클라우드 가전(공기청정기) 제안을 만든다 |
| 우선순위 | 하드웨어 H0~H1이 여전히 1번. ThinQ는 U0·U1(모의)까지만 병렬, 실기기 제어(U2~)는 보유 가전 모델명 확정 뒤 |

## 1. 비공개 플랫폼 자료와의 대조

확정:
- 비공개 자료(D-Bus 명세·가이드·샘플)에서 ThinQ가 나오는 명세는 **하나**뿐이고, 그것은 **이 기기 자신을
  ThinQ 기기로 등록·프로비저닝하고 클라우드와 원시 패킷을 주고받는 통로**다. 다른 LG 가전을 조회·제어하는
  API가 아니다. 대부분 특권 권한이 필요하고 패킷 형식은 문서에 없다.
- 따라서 인계 7절 1항의 전제("데스크톱이 아는 LG 문서로 가전 제어 요구를 대조")는 성립하지 않는다.
  **가전 제어 경로는 공개 ThinQ Connect API 또는 HA 경유뿐**이다.
- 플랫폼 에이전트 명세는 날씨·일정·제안 메시지를 읽을 수 있고, 감지 인원·사용자 목록은 우리가 써 넣는
  속성이다. 심사 키워드(공간 이해·온디바이스/클라우드 경계)와 닿는 것은 이쪽이다.
- 플랫폼 이미지에는 파이썬이 없고 우리 백엔드는 컨테이너로 올린다(8/31 실증). 공식 파이썬 SDK는 이 구성
  그대로 쓸 수 있다.

추정(확인 필요):
- 플랫폼 에이전트가 "기기 제어를 다룬다"는 문구가 있으나 방법이 없다. 내부 도구로 보이며 우리가 부를 수
  있다고 가정하지 않는다.

## 2. 공개 API로 확인한 사실

- 인증: PAT + 기기별 고유 클라이언트 ID(UUID4 권장) + 국가 코드. 클라우드 필수.
- 상태: 푸시(AWS IoT MQTT)로 온다. **구형 기기는 5분 주기**. 에너지는 하루 1회.
- 기기 종류: HA 문서 30종, SDK 27종(전자레인지·오븐·공기청정기 포함). **디바이스 프로필**이 종류별
  속성과 읽기/쓰기를 표준화한다 — "폭넓은 공통 구조"의 근거.
- 과다 호출·클라이언트 남발은 차단된다. 요금·정확한 한도·약관은 개발자 사이트가 열리지 않아 **미확인**.
- 원격 시작은 "지원 모델에서 가능"이라고만 적혀 있다. 전자레인지 가열 시작은 가정하지 않는다.

빠진 것(아래 U4로): 클라우드 쪽 확인 불가 정의(응답 유실·상태 지연·부분 성공), PAT 보관·만료, 모의 서버
없는 CI 회귀, `/stop` 시 클라우드 기기 처리.

| 2 | RPi5 최종 구성(플랫폼 이미지+컨테이너 vs 라즈비안) |

| 2 | 하드웨어 도착일 |

## 4. 대표 시나리오 — 조리 확인 → 공기 관리

"즉석밥 데워줘" → 갠트리가 누름 → **전류로 가열 확인(설계 목표, 실물 센서 드라이버 미구현 — 9/29 기준 L3 real 기동 거절)** → 공기청정기(ThinQ) 강풍을 **승인 받고** 실행 →
전자레인지 종료 감지 후 몇 분 뒤 원복 제안.

- 트리거가 우리에게 없는 기능(귀가 인지)이 아니라 이미 만든 폐루프 검증 결과다. "귀가→공기청정기"는
  HA 자동화 한 줄과 구분되지 않는다.
- 물리 1대 + 클라우드 1대, 승인 게이트, 오프라인 대체(물리만으로 완결)가 한 장면에 들어간다.
- 가열 확인만으로 강풍이 필요하다고 단정하지 않는다. **제안**하고 승인을 받는다. 승인 이력은 자연 사용
  습관(28일/3일)에 넣지 않고 **제안 수락 선호도로 따로 집계**한다(§7).

## 5. 직접 ThinQ vs HA 경유

| | 직접(공식 파이썬 SDK) | HA 경유 |
|---|---|---|
| 런타임 | 컨테이너 안 라이브러리 1개 | RPi5에 세 번째 런타임 + 자원 + 유지 |
| 판단 주체 | SimpleLay | HA를 연결 중계로만 쓰면 SimpleLay 하나로 유지 가능. 별도 HA 자동화가 제어하면 정책 충돌 관리 필요 |
| 인증 | PAT 1개 | PAT + HA 토큰 |
| 기기 발견·프로필 | SDK가 그대로 줌 | 엔티티로 가공돼 옴 |
| 실익 | 시연 의존성 최소 | 전문가 자료 해석, 타 브랜드 확장 |

"직접은 어댑터 하나만 늘린다"는 과장이다. 명령·결과 계약과 경로별 준비 상태를 설계해야 한다(§6). 직접 SDK도 인증·연결 수명·MQTT 재연결·비동기 계약 연결을 관리해야 한다. `ExecutionMode`에 cloud를 추가하지 않고 제어 경로를 별도로 표현한다.

## 6. 최소 구현 순서

| 단위 | 내용 | 조건 |
|---|---|---|
| U0 스파이크 | 저장소 밖 로컬 스크립트로 기기 목록·프로필·상태 덤프 → 모델별 지원 속성 표(모델명·날짜) | PAT·보유 기기 확보 후 |
| U1 어댑터(모의) | U1-a: 대상·제어 경로·동작·인자와 결과 확인 수준 계약, 승인 내용 고정. U1-b: 선택한 경로·동작별 준비 상태 및 실행 직전 재검사. U1-c: 모의 어댑터. 실제/모의와 제어 경로는 별도 축이며 cloud 실행 모드는 추가하지 않는다 | 하드웨어 전 가능 |
| U2 단일 제어 실기기 | 동작 1개를 요청 접수 / 상태 변경 / 실제 결과로 나눠 기록 | 소유자 현장 |
| U3 협력 | 물리 실행 결과 → 제안 → 승인 → 클라우드 실행. 종료 지속 감지는 별도 미구현 기능. 원복은 이전 설정 저장·사용자 변경 여부 확인 후 제안하며 무조건 타이머로 덮어쓰지 않는다 | U2 후 |
| U4 정책·정지 | 행동별 등급(자동/승인/수동). 정지는 로컬 미전송 명령 취소 / 전송 후 접수·결과 불명 / 가전 운전 정지로 구분. 이미 전송한 명령의 취소를 보장하지 않는다. 어댑터의 request_stop 의미·확인 범위를 정의한다. 인터넷 없으면 클라우드 가전 격하 | U1과 함께 |
| U5 시연·증거 | 성공 3연속, 끊김 후 복구, 중복 실행 0 | 리허설 |

재사용: 실행 깔때기(`rpi/api/service.py`), 승인 게이트, 습관 근거, 제어권 중재. `NodeRegistry`는 가전별 컨트롤러 선택 개념을 참고하되 현재 주소 기반 등록 구조를 그대로 재사용한다고 가정하지 않는다. 신규: 클라우드 명령·결과 계약, 경로별 준비 상태, 클라우드 등록/어댑터, PAT 보관(환경 변수), 모의 서버. 승인 후 재해석으로 명령을 바꾸지 않으며 대상·경로·동작·인자가 달라지면 재승인한다.

멈출 것: 보유 기기 확인 전 U2 착수, HA 상시 설치, 3기기 협력, 귀가 인지.

## 7. 노트북 세션 검토 반영 (2026-09-22, 코드 대조 후 합의)

노트북 세션이 `4400cd8`과 현재 코드를 대조해 낸 지적을 데스크톱에서 코드로 재확인했고, 아래처럼 합쳤다.
직접 ThinQ 선택은 양쪽 동의. **U1은 다시 나눈다.**

| 지적 | 판단 | 반영 |
|---|---|---|
| `ExecutionMode`에 `cloud` 추가 반대 — 실행 환경(real/mock/unknown)과 제어 경로는 다른 축 | **수용.** `rpi/controller/models.py`의 모드는 "실제 하드웨어를 움직였나"다 | 축 셋으로 분리: 실행 환경 / 제어 경로(physical·thinq) / 확인 수준(접수·상태 확인·실제 동작 확인). 실제/모의 여부와 성공·확인 수준을 독립적으로 기록한다. 실제 기기 대상도 실패/확인 불가일 수 있고 모의 서버도 상태 변경을 반환할 수 있다. 학습 허용 조건에서 실행 환경·출처·결과 근거를 함께 검사한다 |
| "클라우드는 전송·인증만" 반대 — 기기 오프라인·읽기 전용·현재 상태 불가가 있다 | **수용.** `_require_ready()`의 로컬 예외 경로(`runs_locally`)도 있어 준비 상태 클래스만 고쳐서는 부족 | 준비 상태를 **선택한 제어 경로·요청 동작 기준**으로 검사: 물리는 기존 4축, 클라우드는 인증·대상 접근·기능 지원·인자 범위·동작별 실행 조건. 확인 못 한 필수 조건은 조작 가능으로 두지 않는다 |
| `execute(buttons)`에 동작명 문자열은 확장성 부족 — 온도·풍량엔 인자와 허용값이 필요 | **수용** | 명령 계약을 `대상 + 동작 + 인자`로. 기존 잠금·승인 흐름은 재사용하되 결과 표시를 분리한다 — 클라우드 성공을 "버튼 눌림을 모두 확인했어요"로 보이지 않게 |
| `NodeRegistry`는 가전 ID → 노드 주소 → 팩토리 구조라 ThinQ 계정·기기 ID를 그대로 못 담는다 | **수용** | 재사용은 "가전별 컨트롤러 선택" 개념까지. 클라우드 등록은 별도 등록소 또는 확장 |
| 승인 이력을 28일/3일 습관에 편입하면 추천의 자기 강화 방지 정책과 충돌 | **수용.** `patterns.py`는 REAL+DIRECT+성공만 학습 | §4 문장 정정: 승인 기록은 DIRECT로 바꾸지 않는다. **자연 사용 습관과 제안 수락 선호도는 별도 집계** |
| U3·U4가 없는 기능을 전제 — 종료 지속 감지, 원복 시 사용자 변경 확인, 클라우드 명령 취소 불가 가정, `request_stop()` 의미 | **수용.** `/stop`은 등록 노드에 `request_stop`을 전파한다(`rpi/api/service.py`) | U3에 "종료 감지는 별도 기능(미구현)" 명시. 원복은 이전 설정 저장 + 사용자 변경 여부 확인. 정지는 로컬 대기 명령 취소 / 접수 불명 / 가전 운전 정지로 구분하고, 클라우드 어댑터의 `request_stop()` 의미를 먼저 정한다 |
| HA 비교표 편향 — HA도 자동화를 끄면 판단 주체는 하나, 직접 SDK도 인증·연결 수명·MQTT 재연결·비동기↔동기 연결이 필요 | **부분 수용.** 판단 주체 행은 정정. 다만 세 번째 런타임·RPi5 자원·유지 부담은 그대로라 결론은 유지 | §5에 "직접 SDK 운영 부담: 인증·연결 수명·MQTT 재연결·비동기 계약 연결"을 명시 |

**U1 재분할(합의):** U1-a 명령·결과 계약(대상+동작+인자, 확인 수준 포함) → U1-b 제어 경로별 준비 상태 → U1-c 모의 어댑터.
`cloud` enum 추가와 승인 이력의 자연 학습 편입은 이번 안에서 뺀다.

**한계:** 노트북은 비공개 원문을 열지 않았고 §1의 대조 결론을 독립 검증하지 않았다. 가드는 단어 검사라
§1이 일반 용어라는 것만으로 공개 가능성을 보증하지 않는다 — §1은 데스크톱이 원문을 읽고 요약한 것이며,
인터페이스 이름·메시지 형식은 적지 않았다.

## 8. 후속 검토 반영 — 본문 일치와 승인 계약

2026-09-22 노트북 Codex 검토로 §5·6의 이전 문구를 §7 방향에 맞춰 교체했다. 이전에는 §7에서 제외한 cloud 모드·전송/인증만의 준비 상태·문자열 동작명 계약이 §6에 남아 있었다. 이 변경은 문서 설계 정리이며 구현 완료가 아니다.

- 실행 환경(real/mock/unknown), 제어 경로, 결과/확인 수준은 독립적으로 유지한다. 상태 변경 확인 여부로 실행 환경을 정하지 않는다. 실제 클라우드 실행의 학습 허용 기준은 U1-a에서 별도로 정의한다.
- U1-a 승인 계약: 사용자가 승인한 가전·제어 경로·동작·인자를 실제 실행 명령과 대조한다. 예를 들어 ‘풍량 약’ 승인 후 재해석된 ‘풍량 강’을 실행하지 않는다. 승인 내용이 달라지면 재승인이 필요하다.
- 승인 명령이 같아도 실행 직전 권한·지원 기능·준비 상태·상황 유효성을 재검사한다. 변경된 프로필이나 오래된 상태를 승인만으로 우회하지 않는다.
- 직접 ThinQ 선택과 U1-a → U1-b → U1-c 순서는 유지한다. 다음은 계약 설계이며 실제 제어는 보유 모델과 지원 기능 확인 뒤 진행한다.
