# 하드웨어 방향 확정 — 2026-09-30 (피드백 반영 계획 자료 기준)

팀의 "컨설팅 피드백 반영 계획"(9/22 컨설팅 후속, 로컬 발표 자료 — 저장소에 넣지 않음)을 기준으로 하드웨어와 시연 방향을 다시 정했다.
9/29에 저장소에 반영한 설계([motion-mcu devlog](devlog_2026-09-29-motion-mcu.md))와 다른 부분은 **이 문서가 우선**이다.
이날 RPi4·RPi5·ESP32를 수령했다. 모터·드라이버·갠트리 수령 여부는 아직 확인하지 않았다.

## 2. 코드에 미치는 영향

1. **RPi4 ↔ 모션 MCU 규약은 유지한다.** 줄 단위 JSON 규약(`docs/protocol.md` "모션 MCU 링크", `firmware-motion/protocol_table.json`)과
   호스트 쪽 `SerialMotionClient`·`python -m rpi.tools.jog`·`rpi4/act_main.py`는 MCU 종류와 무관하다. **Arduino 펌웨어가 같은 규약을 말하게** 만든다.
   `firmware-motion/`의 ESP32 전용 부분(FreeRTOS 태스크·ESP32 PWM·워치독)은 AVR 단일 루프로 옮겨야 한다. 보드 모델에 따라 메모리 한계가 다르다.
2. **Z 누름은 시간 기반이 될 가능성이 크다.** 스위치봇 모듈에 엔코더가 없다면 `press --depth`는 쓸 수 없고 `--duration`만 남는다.
   구동 방식(모듈 모터를 Arduino가 H브리지로 직접 구동하는지)에 따라 규약의 `press` 필드와 기구 값(`SIMPLELAY_MOTION_*`)을 조정한다.
3. **ESP32 콘센트 모듈 펌웨어는 새로 만든다.** 지금 `firmware-node/`는 가전 노드(HTTP/ESP-NOW 중계)이고 CT 계측이 없다.
   필요한 것: CT 샘플링 → 유효 전력 계산 → 서버로 전송, 대기 전력 관리 출력.
   서버 쪽은 `SIMPLELAY_L3_MODE=real`이 기동을 거절하던 자리에 **원격 전력 공급원**을 붙인다(`rpi/controller/power_operation.py`).
4. **잔여 전류 기록(피드백 ③).** 완료 뒤 대기 전력까지 내려가는 시간·꼬리 평균·최대·사용 전후 기준선을 원시 기록기·실험 CSV에 열로 추가한다.
5. **시나리오(피드백 ②).** 기존 `cook_then_air`·`evening_rest`·`wash_then_dry`에 더해 아침 루틴(즉석밥 완료 → 복약 안내 음성 → 확인 없으면 보호자 알림함)과
   귀가(지오펜싱 → 실내 28°C 이상 또는 습도 70% → ThinQ 에어컨 → 저녁 제안)를 추가한다. 복약 안내는 시간 알림·확인 수준이며 의료 판단을 하지 않는다.
6. **자료와 현재 구현이 다른 규칙 — 결정 대기.**
   - 자료는 제어 경로 `physical · api · both`(both면 API 실패 시 물리로 대체)를 쓴다. 저장소는 `physical | thinq`이고 대체 실행이 없다.
   - 자료는 "API 응답 뒤에도 CT로 동작을 확인해야 완료"라고 한다. 저장소는 ThinQ 상태 조회 확인(`state_confirmed`)을 성공으로 본다.
     콘센트 모듈이 붙는 가전에 한해 CT 확인을 더하는 방향이 자료와 맞는다.
   - 자료의 긴급 제어 트리거 4종(사용자 정지·위험 신호음·전력 이상·확인 두절) 중 "음성 '멈춰'"와 "전력 이상 → 중단"은 아직 없다.
7. **자료의 구현 현황 숫자(9/15 기준)는 낡았다.** 9/30 데스크톱 검증: 백엔드+rpi4 1,905 · 폰 441 · 키오스크 168(골든 제외), 골든 폰 53·키오스크 32.

## 3. 팀원에게 받아야 할 값

- Arduino 보드 모델(Uno·Nano·Mega 등)과 RPi4 연결 방식(USB 시리얼 가정), 모터 드라이버 핀맵.
- 스위치봇 모듈 구동 방식(모터 전압·H브리지·리밋 유무)과 누름 시간 범위.
- CT 센서 종류(분할형 CT 모델·부담 저항)와 ESP32 ADC 직결인지 외부 ADC인지.
- ESP32 개수. 콘센트 모듈과 서버 사이 통신을 ESP-NOW 게이트웨이로 할지, 같은 공유기 Wi-Fi(HTTP)로 할지.

## 4. 오늘 저녁 순서 (보드만 도착한 상태)

1. **RPi5(192.168.0.178)** — root SSH 키 접속 확인됨. 백엔드는 8/31 빌드 컨테이너(`simplelay-backend`)라 최신 코드로 다시 배포한다.
   이 PC에 도커가 없어서 기기 안에서 빌드한다(기기 도커·인터넷 확인됨, `python:3.12-slim` 이미지 있음). 되돌릴 수 있게 옛 이미지에 태그를 남긴다.
   최신 코드는 API 키가 없으면 LAN을 401로 막으므로 `SIMPLELAY_API_KEY`를 정해 폰 설정에도 넣는다.
2. **RPi4** — 랜선 연결 후 IP 확보 → 같은 방식으로 `rpi4.act_main` 배포 → RPi5 `SIMPLELAY_ACT_MODE=uart`로 두 보드 통신 확인(모션은 mock).
3. **ESP32** — USB로 이 PC에 연결해 보드·COM 확인까지. 콘센트 모듈 펌웨어는 아직 없으므로 **`firmware-motion`은 올리지 않는다.**
4. 시연 v2 §3 모의 리허설을 실제 RPi5·RPi4·키오스크 화면 위에서 한 번 완주한다.
