# 개발 로그 — 2026-08-29

## ESP-NOW 전송 구현 + 교차 리뷰 치명 5건 수리

본선 데모용 ESP-NOW를 노드·게이트웨이·RPi5 세 쪽에 구현하고, 곧바로 교차 리뷰를
받아 치명 5건을 수리했다. 백엔드 테스트 **490 → 527**.

리뷰 결론이 정확했다: **"단편화 알고리즘보다 앞뒤 연결부에서 먼저 깨질 가능성이
크다."** 실제로 조각 분할·재조립 자체보다 그 바깥이 문제였다.

### 왜 게이트웨이가 필요했나

ESP-NOW는 ESP32 라디오끼리만 통한다. RPi5에는 그 라디오가 없다. 문서에는
"ESP-NOW (무선, RPi5 ↔ 노드의 ESP32)"라고 적혀 있었는데 **물리적으로 성립하지 않는
문장**이었다. 실제 경로는 이렇게 된다:

```
RPi5 --UART--> 게이트웨이 ESP32 --ESP-NOW--> 노드 ESP32 --UART--> RPi4
```

전용 보드를 추가하지 않고 **폰 BLE 폴백 브릿지가 겸하기로** 했다(팀 결정). 처음엔
"데모 조건에서 BLE와 ESP-NOW가 겹친다"고 반대했는데, 전용 공유기를 지참하는 계획이라
BLE 폴백은 그것마저 실패했을 때의 2차 방어다 — 겹칠 확률이 낮다는 지적이 맞았다.
되돌릴 수 있게 `ESPNOW_GATEWAY_ENABLED` 하나로 분리했다.

## 수리한 것

### 치명 — 한글을 글자 수로 세어 버퍼가 3배 모자랐다

`버튼 20개 × 라벨 40자 = 800`이라고 근거를 적어놓고 **바이트로 취급**했다. 한글은
UTF-8 3바이트라 실제 최악값은 약 2,500바이트다. 512바이트 UART와 1,280바이트 재조립
버퍼를 모두 넘긴다 — **분할·재조립을 만든 이유였던 그 요청이 정작 UART에서 먼저
잘리고 있었다.**

- `MAX_EXECUTE_PAYLOAD_BYTES`를 스키마에 단일 기준값으로 두고 **직렬화 바이트로** 검증
- 펌웨어 버퍼 4곳(양쪽 UART·양쪽 재조립)을 그 값에 맞춤
- 예산이 파이썬 1 + 펌웨어 4로 흩어져 있고 언어가 달라 상수를 공유할 수 없어서,
  **그 관계 자체를 회귀 테스트로 고정**했다(버퍼를 되돌리면 실패하는 것을 확인)

UART가 잘림을 조용히 넘기던 두 지점도 함께 막았다. 송신은 `measureJson()`으로 먼저 재고
안 들어가면 **자르지 않고 보내지 않으며** 실패를 반환한다(잘린 JSON은 받는 쪽이 버릴
뿐이라 "보낸 쪽은 성공으로 아는데 받는 쪽은 아무것도 못 받는" 상태가 된다). 수신은
overflow 상태를 두어 개행까지 통째로 버린다 — 잘린 JSON이 우연히 유효해 보이는 것이
최악이다.

### 치명 — 실행 중 긴급 정지가 자기 락에 막혀 있었다

`execute()`가 응답 대기 내내 락을 쥐고 `request_stop()`이 같은 락을 요구해서,
**실행 중에는 정지가 아예 나가지 않았다.** 실행이 끝나거나 타임아웃된 뒤에야 전송된다.
화면은 정지됐다는데 실물은 계속 누르는, 이 프로젝트에서 가장 위험한 실패 모드다.

정지를 확실히 보내려고 여기저기 배선해놓고 정작 그 정지를 자기 락으로 막고 있었다.
쓰기 락(한 줄 쓰는 동안만)과 실행 락(응답 대기 직렬화)을 분리하고, 정지는 실행 락을
건드리지 않게 했다.

기존 테스트가 못 잡은 이유도 같은 계열이다 — execute가 타임아웃으로 락을 놓은 *뒤에*
`node_stop`이 기록됐는지만 봤다. "정지가 언젠가 나갔다"는 확인했지만 "실행 중에
나갔다"는 확인하지 않았다. 실제 스레드로 실행을 띄우고 그 도중에 정지를 거는 테스트를
추가했다.

### 치명 — 신규 전송이 프로덕션에 배선돼 있지 않았다

`get_node_registry()`가 기본 HTTP 컨트롤러를 그대로 써서, 펌웨어에서 ESP-NOW를 켜고
MAC을 등록해도 RPi5는 그 MAC을 HTTP 주소로 취급했다. **단위 테스트에만 존재하고
프로덕션 요청은 지나가지 않는 상태.** `SIMPLELAY_NODE_TRANSPORT`로 명시 선택하게 했다
(주소 모양으로 자동 감지하지 않는다 — 오타 하나가 조용히 다른 전송을 타면 시연장에서
원인을 좁힐 수 없다).

### 중요 — 정지 플래그가 소거되지 않아 abort 무한 반복

`poll()`이 플래그를 보고 콜백만 부르고 지우지 않아서, 실행 중이 아닐 때 정지 프레임이
한 번 오면 매 loop마다 UART로 abort를 계속 보냈다. 확인과 소거를 하나의 연산으로 합쳤다.

정지 하나를 두고 **한쪽(실행 중)에서는 아예 안 나가고 다른 쪽(유휴)에서는 무한히
나가는** 두 결함이 동시에 있었다.

### 중요 — 게이트웨이가 pending을 전송 뒤에 세움

노드가 아주 빨리 응답하면 마지막 조각을 보내는 사이에 답이 도착하고, 수신 콜백이
`_pending == false`를 보고 그것을 버린 뒤 타임아웃까지 기다렸다. pending을 먼저 세우고
전송 실패 시 되돌린다.

## 이번에도 이음매였다

8/26에 "각 계층은 테스트되는데 둘을 잇는 경로를 지나는 테스트가 없다"는 교훈을 적었는데,
같은 패턴이 다시 나왔다.

- **테스트가 데이터 손실을 정답으로 고정**했다. 공유 UART에서 남의 줄을 "무시한다"고
  검증한 테스트가, 실은 그 줄을 **소비하고 버리는** 동작을 명세로 굳힌 것이었다
- **정지 테스트가 시점을 확인하지 않았다.** 결과만 보고 타이밍을 안 봤다
- **전송 배선이 없는데 단위 테스트는 전부 통과**했다. 조립 지점을 지나는 테스트가 없었다

테스트 개수(527개)는 정확성의 근거가 아니다. 이번 리뷰 프롬프트에 "테스트 통과 개수는
믿지 말고 조각 사이를 봐달라"고 적어 보낸 것이 그대로 값어치를 했다.
