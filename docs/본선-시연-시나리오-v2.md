## §0. 한 장 요약

**시연 목표.** 9/29 전문가 의견의 두 요구를 **한 흐름 안에서** 보인다.

1. **소프트웨어 가전 제어 포함** — 물리 버튼 경로(갠트리) 옆에 ThinQ Connect 경로를 두고, 같은 승인·실행·결과 확인 흐름에 태운다(장면 ③·④).
2. **상황 시나리오·다가전 공조** — 한 가전의 실행 결과가 다른 가전의 제안이 되고(③ 조리 확인 → 공기 관리), 한 상황이 두 가전의 단계로 묶인다(④ 저녁 휴식).

이를 받치는 기존 강점 — 학습 근거가 있는 선제 제안(①), 폐루프 보정 재시도(②), 화면과 독립된 정지와 "정지됨/실패" 구분(⑤), 사용자 통제(⑥) — 을 같은 흐름에 넣는다.

**총 시간: 7분 00초**(도입 30초 + 장면 6개 6분 + 마무리 30초). 발표 심사 시간이 6분 이하로 정해지면 §1 끝의 "줄이는 순서"를 따른다.

**무대 배치.**

### ② 조리 확인 → 공기청정기(ThinQ) 제안 → 승인 → 확인 수준 (1:50–2:50, 60초)

| 항목 | 내용 |
|---|---|
| 화면 | K 시나리오 카드("시나리오 · 조리 확인 → 공기 관리", 질문, 근거, "승인하면 할 일: 공기청정기(모의) 풍량 강 · ThinQ") → 승인 → K 완료 "가전 상태를 확인했어요 · ThinQ · 상태 확인됨" |
| 사용자 행동 | 카드의 근거 줄을 가리킨 뒤 "지금 실행" |
| 시스템 동작 | 전자레인지 job 완료 이벤트 → 엔진이 카드 생성(모의 성공이면 시연 제안, 근거 "시연: 모의 실행이 성공으로 끝났어요 — 실제 가열을 확인한 것은 아니에요") → 승인 시 지문 대조 → ThinQ `set_wind_strength HIGH` → 상한 3초 안에 상태 재조회 → `last_route=thinq`, `last_confirmation=state_confirmed` |
| 말할 문장 | *"전자레인지가 돌았다는 결과가 공기청정기 제안으로 이어졌고, ThinQ 명령은 보낸 것과 상태가 바뀐 것을 구분해 '상태 확인됨'일 때만 성공으로 적습니다."* |
| 심사 포인트 | **요구 1(SW 가전 제어)**, **요구 2(가전 간 연쇄)**, 확인 수준(접수됨/접수 불명/상태 확인됨) |

| 항목 | 내용 |
|---|---|
| 화면 | (실물) 갠트리 측면 — 첫 누름 뒤 다시 누름 / (모의) T 단계 목록 "검증 불합격 추정 → 재시도 1회째", 누름 기록 "즉석밥 2회", 보정 요청 표시 → K 완료 |
| 사용자 행동 | 발표자가 "일부러 첫 버튼 검증을 실패시키겠습니다"라고 말하고 운영자가 주입, 폰에서 "즉석밥 데워줘" |

이 실행도 성공이므로 `cook_then_air` 카드가 다시 생길 수 있다 — ⑥의 "건너뛰기" 소재로 쓴다.

### ⑥ 사용자 통제 — 건너뛰기·부재·환경 철회 (5:50–6:30, 40초)

| 항목 | 내용 |
|---|---|
| 화면 | K에 남은 카드 "넘기기"(이번만) → 운영자가 부재 보고 → 남은 시나리오/환경 카드가 사라짐 → (여유 있으면) 운영 노트북의 `/suggestions/events` 에서 `dismissed/user_skip`, `withdrawn/presence_absent` 두 줄 |
| 사용자 행동 | 카드 넘기기 1회 |
| 시스템 동작 | `POST /suggestions/{id}/reject {"mute":false}` → `user_skip`. `POST /presence {"present":false}`(서버가 `SIMPLELAY_PRESENCE_GATING=true`일 때만) → 시나리오·환경 카드 `withdrawn/presence_absent`. 온도를 내리면 환경 카드 `withdrawn/environment_unavailable` |
| 말할 문장 | *"거절과 '이유가 사라져 시스템이 거둔 것'을 따로 기록해, 사용자가 싫다고 하지 않은 것을 싫어한다고 배우지 않습니다."* |
| 심사 포인트 | 9/22 C3(개입 지점), 오학습 방지, 공감지능의 절제 |

## §2. 장면별 실행 조건 3단계

| 등급 | 정의 | 서버 구성 |
|---|---|---|
| **실물** | 하드웨어 + ThinQ 등록 가전·PAT·인터넷 확보 | `SIMPLELAY_ACT_MODE=uart`, RPi4 `SIMPLELAY_MOTION_MODE=serial`, `SIMPLELAY_THINQ_MODE=real`(**`RealThinqClient` 미구현 — 지금은 이 등급 자체가 불가**) |

| **전부 모의** | 오늘 가능 | `SIMPLELAY_THINQ_MODE=mock python -m rpi.simulator_main` |

화면 표시 원칙: 서버가 보고하지 않은 성공을 화면·말로 만들지 않는다. 모의 부분은 기존 표시(키오스크 상단 "모의 실행 · 실제 조작 아님", 폰 모드 배너, 가전 이름의 "(모의)", 근거의 "시연:")를 가리지 않는다.

|---|---|---|---|---|
| ① 선제 제안 → 물리 실행 | 갠트리가 실제로 누름. 셋업 때 같은 시간대 3일 이상 실제 이력이 있으면 근거 문장("…3번 하셨어요") 표시 가능 — 없으면 `/demo/suggest` | 좌동 | 시뮬레이터가 누름 기록을 만들고 T가 개념 모션으로 따라 그림 | 실물·부분: 실행 환경 real. 모의: "모의 실행 · 실제 조작 아님", T 상단 "개념 모션 · 실제 동역학 아님". `/demo/suggest` 카드는 근거 없음 |

| ③ 실패 주입 → 재시도 | RPi4로 주입 전달(UART), 갠트리가 실제로 다시 누름. 센서 판정은 실측 임계값 확정 후 | 좌동 | T에 재시도·보정 요청 표시 | 주입은 **리허설 장치**라고 말한다. 폰 재시도 배지는 모든 등급에서 안 뜬다(G1) |
| ④ 저녁 휴식 | 공기청정기 실물 ThinQ + 선풍기 노드 실물 | 공기청정기 모의 + 선풍기: 노드 조립됐으면 실물, 아니면 서버 구성 모의 선풍기 | 둘 다 모의 | "(모의)" 이름, 근거 "시연: 합성 이력 … 실제 사용 기록이 아니에요". 선풍기 확인 근거는 `reported`(가전 동작 미확인) |

## §4. "조용히 실패하는 것" 점검표

화면은 정상처럼 보이는데 장면이 무너지는 것들이다. 무대에 서기 전 위에서부터 확인한다. 1~4는 v1에서 가져왔다.

| # | 항목 | 증상 | 확인·해결 |
|---|---|---|---|
| 1 | 폰 데모 모드 켜짐(설정 › 고급) | 실행이 서버로 안 나감, 상단 "데모 모드 — 실제 조작이 아닙니다" | 끈다 |
| 2 | 노드 가전이 조작 가능 아님 | 412 "아직 연결되지 않았어요". 서버 재시작 시 다시 준비 안 됨(설계) | `GET /readiness/<id>`의 `state`·`reasons`. 물리는 `POST /readiness/<id>`로 4축 보고. **내장 전자레인지는 `state:"disconnected"`여도 `runs_locally`라 실행된다** — 헷갈리지 말 것 |
| 3 | `SIMPLELAY_ACT_MODE` | 기본 mock이면 갠트리 안 움직여도 성공 표시 | 실물·부분 실물은 `uart`. `/health.act_mode`, `/history.csv`의 `execution_mode` |
