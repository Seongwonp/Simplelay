# 가전 그림 통일 실행계획

작성: 2026-10-23. **계획만 저장, 이 작업의 코드 수정 없음.** 사용자는 다음 작업일에 진행한다.

## 목표와 원칙

승인된 폰 메인 화면의 `ApplianceArtwork` 스타일을 가전이 등장하는 모든 화면에 사용한다. 현재 등록된 몇 대만 바꾸지 않고 **등록 전 종류 선택부터 앞으로 추가할 가전까지** 일관되게 확장한다. 상태·경고·정지·설정·음성·알림·출처 아이콘은 가전 그림과 구별하여 유지한다.

그림을 추가했다고 실제 제어를 지원하는 것은 아니다. 종류의 표시 지원, 사진/버튼 매핑 가능 여부, ThinQ/API 제어 지원 여부는 각각 구분한다. 이름으로 종류를 추측하지 않는다. 기존 category 문자열·기기 id·사용자 버튼 데이터는 유지한다.

## 우선 적용 화면과 코드 조사 지점

1. **기기 추가 최우선:** `add_appliance_wizard_screen.dart` 종류 선택, `appliance_editor_screen.dart` 종류 선택/수정. 메인과 같은 그림+한글 이름, 선택 상태를 테두리·표시·낭독으로 표현한다.
2. **기기 사용:** 상세, 수동 조작, 사진 매핑 진입, 음성 대상, 제안 대상, 실행 상태의 가전 표시. 사진 자체·버튼 번호·상태표시는 교체 대상이 아니다.
3. **저장 동작:** `routine_icon.dart`, 저장 목록, 자동 실행, 새 동작 대상 선택, 편집 토큰과 선택 목록. 다중 가전은 기존 겹침 표현을 유지하되 두 대상 모두 같은 그림 계열로 바꾼다. 알림만 동작은 종, 삭제된 대상은 대체 그림을 유지한다.
4. **관리·이력:** 설정 가전 목록, 노드 연결 화면, 기기 발견 목록, 기록의 대상 그림. 기록의 손/반복/마이크 등 ‘누가 실행했나’ 표시는 그대로 둔다.
5. **키오스크:** 아래 별도 계획과 같은 그림 원본·종류 키를 사용한다.

확인된 기존 사용 지점: `home/suggestion.dart`, `manual_control_screen.dart`, `status_screen.dart`, `voice_screen.dart`, `suggestion_screen.dart`, `history_screen.dart`, `routine_editor_screen.dart`, `settings/appliance_section.dart`, `settings/node_section.dart`. 구현 시작 때 전체 `.icon`, 고정 가전 `Icons.*`, 가전 portrait 렌더를 다시 검색하여 누락 목록을 만든다.

## 가전 종류 카탈로그

현재 코드 종류는 전자레인지·에어컨·세탁기·인덕션·밥솥·인터폰·공기청정기·기타다. 아래는 **추가 후보 목록이며 지원 확정이나 실제 등록 목록이 아니다.**

| 묶음 | 준비할 후보 그림 |
|---|---|
| 주방 | 냉장고, 김치냉장고, 전자레인지, 오븐, 에어프라이어, 인덕션/전기레인지, 가스레인지, 밥솥, 식기세척기, 정수기, 커피머신, 전기포트, 토스터, 음식물처리기, 레인지후드 |
| 세탁·의류 | 세탁기, 건조기, 의류관리기 |
| 냉난방·공기 | 에어컨, 공기청정기, 선풍기/서큘레이터, 제습기, 가습기, 히터, 보일러/온도조절기, 환기장치 |
| 청소 | 로봇청소기, 일반 청소기 |
| 영상·생활 | TV, 모니터, 프로젝터, 스피커/오디오, 조명, 스마트플러그, 전동커튼/블라인드 |
| 출입·기타 | 인터폰, 도어록, 기타 사용자 가전 |

서로 구별하기 어려운 종류는 사용자가 그림만 보고 고를 수 있는지 먼저 확인한다. 벽걸이/스탠드 에어컨, 드럼/통돌이 등은 처음부터 저장 종류를 무한 증식시키지 말고 필요 시 **표현 variant**로 설계한다. 기타 가전은 기본 그림+직접 이름 지정으로 등록을 막지 않는다.

## 구조와 작업 순서

- 공통 가전 그림 진입점은 category 기반으로 둔다. IconData를 역추적해서 종류를 판정하는 새 구조는 만들지 않는다.
- 종류 정의, 표시명, 지원 경로, 그림 렌더를 분리한다. category 확장은 폰·RPi5 모델·백엔드 허용값과 기존 저장 데이터 호환을 조사한 뒤 별도 단계로 적용한다. ESP32/HW 코드 변경 없음.
- 폰과 키오스크의 공통 원본은 저장소 내 공유 자산/패키지 중 빌드 제약을 확인해 결정한다. 두 앱에서 그림을 따로 재작성하지 않는다. SVG 등 외부 자산을 사용하면 출처·라이선스를 기록한다.
- 1단계: 현재 7종+기타의 전 화면 통일 → 2단계: 전체 후보 그림 미리보기/이름 정리 → 3단계: 합의된 새 종류 등록·저장 호환 → 4단계: 키오스크 적용.
- 작은 토큰은 20–28, 목록은 32–48, 큰 카드는 64–96 논리 px를 시안 출발값으로 검토한다. 작은 크기에서 구별 안 되면 그림만 키우지 말고 배치를 바꾼다. 터치 영역은 그림 크기와 별개로 확보한다.

## 완료 조건

- 종류 선택 → 등록 → 홈 → 상세 → 저장 동작 → 기록에서 같은 종류가 같은 그림이다.
- 새 후보 그림 전체를 한 장의 카탈로그로 검토하고, 실제 지원 종류와 표시만 준비된 종류를 구별한다.
- 밝음/어두움, 큰 글씨, 길고 같은 이름, 기타/알 수 없는 값, 다중 대상, 삭제된 대상, 연습/실제, 준비 필요/연결 끊김을 시험한다.
- 기존 색 상태·읽기 이름·선택 의미·승인·정지를 보존한다. 단순히 기존 아이콘 assertion을 지우지 말고 새 그림과 상태색을 검증한다.
- 결함 재현 테스트 → 구현 → 전체 비골든·analyze → 렌더 직접 확인 → 의도한 골든만 갱신 → 에뮬레이터 확인 순서로 진행한다.
