# 2026-09-30 — 사용자 루틴: 저장 구조 · 트리거 5종 · 승인 결속 · 여러 단계 순서

UI 확정([UI 확정](UI-확정-2026-09-30.md) §1)에서 "메뉴는 사용자가 만든다"로 정했다. "즉석밥" 같은 고정 명령
버튼 대신 **사용자가 만든 루틴**이 메뉴가 되고, 기존 대표 명령은 템플릿 속 예시로만 남는다. 이번에 서버 쪽
저장 구조·API·트리거를 넣고, 기존 제안(승인 카드)·시나리오 실행 규칙에 연결했다.

> **모의까지다.** 실행 확인은 모의 전자레인지(눌림 L1 `press_confirmed`, `execution_mode=mock`)와 모의 ThinQ
> 공기청정기로만 했다. 실제 L3(전류)로 "끝났다"를 본 적이 없고, 레이더·폰 귀가 신호·음성 출력도 실물이 아니다.
> 폰·키오스크 화면은 이번에 바꾸지 않았다(Flutter 제외).

## 1. 원칙

- **승인 없는 실행은 없다.** 트리거는 제안 카드(실행 방식 `approve`) 또는 알림(`notify`)만 만든다. 루틴 코드에는
  실행 진입점이 없고, 실행은 `POST /suggestions/{id}/approve` 하나로만 일어난다. 테스트가 이를 고정한다
  (트리거 5종을 모두 울려도 실행 0건, 순서기는 `ApprovedCommand`만 받음, 루틴 코드에 직접 실행 호출 없음).
- **알림만(`notify`)은 어떤 경우에도 실행하지 않는다.** 보호자 알림함에 `routine_notice`로 남긴다.
- **승인은 그 순간의 단계에 묶인다.** 카드의 `scenario_id`는 `routine:<루틴ID>@<단계 지문 12자리>`다. 지문은
  단계 전체(안내·기다리기 포함)와 실행 방식으로 만든다. 카드가 뜬 뒤 단계를 고치거나, 루틴을 끄거나 지우거나,
  '알림만'으로 바꾸면 승인은 409(재승인)이고 카드는 내려간다. 이름·아이콘·트리거만 바꾸면 기계가 할 일이 같아
  승인은 그대로다.
- **복약 안내는 시간 알림까지다.** 약·건강 상태를 판단하지 않는다. 안내 문장은 사용자가 적은 그대로 남긴다.

## 2. 데이터 모델

```
Routine {
  id: "rt-xxxxxxxxxx", name(≤30자), icon(선택, ≤24자),
  steps[1..10], trigger, conditions[0..4],
  mode: "approve" | "notify", enabled: bool,
  created_at, updated_at, schema_version: 1
}
```

| 단계 `kind` | 필드 | 뜻 |
|---|---|---|
| `press_sequence` | `appliance_id`, `buttons[]`(사진 조작부의 버튼 ID 또는 이름), `note?` | 물리 누름. 저장할 때 그 가전의 등록 버튼에 있는지 검사하고, 실행 명령은 버튼 **이름**으로 만든다(ID `BT-08` → `즉석밥`) |
| `thinq_command` | `appliance_id`, `action`, `args` | U1 명령 계약 그대로. 저장할 때 가전의 허용 동작·값 범위를 검사 |
| `announce` | `text`(≤80자) | 알림함에 `routine_announce`로 남김. **음성 출력은 아직 연결 전** |
| `wait_until_done` | `appliance_id` | 앞 단계의 확인 결과를 보고 다음으로 넘어갈지 정함(§4) |

| 트리거 `kind` | 필드 | 근거 |
|---|---|---|
| `time` | `days`(0=월…6=일), `time`("HH:MM") | 그 시각부터 10분 안에 한 번(같은 날·같은 시각). 서버가 그때 꺼져 있었으면 놓친다 |
| `approach` | `zone`: `arrival`(폰 귀가 신호) · `room`(방 안) · `near`(가전 앞), `appliance_id?` | 공간 상태 기계의 **전이 기록**을 5초마다 본다. 노드가 하나라 가전별 구역은 아직 없다 |
| `after_done` | `appliance_id` 또는 `routine_id` | 가전: 실제 실행이 L3·상태 확인으로 끝나면 일반 카드, 모의 성공은 시연 카드, 그 밖(L1만·보고만)은 무시. 루틴: 그 루틴 실행이 성공으로 끝나면 |
| `event` | `event`(예: `wash_complete`), `appliance_id?` | ThinQ 이벤트. 모의 이벤트면 시연 카드 |
| `manual` | — | 앱의 '지금 실행'. 카드를 만들 뿐이다 |

조건 `kind`: `time_window {start, end}`(자정을 넘는 구간 가능) · `environment {temperature_at_least?, humidity_at_least?}`
(적은 기준 중 **하나라도** 넘으면 만족 — "28°C 이상 또는 습도 70% 이상"). 온습도를 못 읽으면 불만족이다.
조건이 안 맞으면 카드도 알림도 없고 트리거 기록(`GET /routines/log`)에만 남는다. '지금 실행'은 조건을 보지 않는다.

저장: `SIMPLELAY_DB_PATH`가 있으면 SQLite 표 `routines(routine_id, document, schema_version, updated_at)`, 없으면
메모리. 초안 표(열 두 개)는 기동 때 ALTER로 열을 더하고, 형식 0 문서(`mode`·`conditions`·`enabled` 없음,
`weekdays`, 단계 `type`)는 읽을 때 지금 형식으로 올린다. 읽을 수 없는 행은 건너뛰고 로그만 남긴다.

## 3. API (폰 팀용)

모든 경로는 기존 API 키 의존성 아래에 있다. 검증 오류는 **422**이고 `detail`은 화면에 그대로 보여도 되는
한국어 문장이다(예: `'전자레인지' 조작부 사진에 없는 버튼이에요: 순간이동`).

| 메서드·경로 | 요청 | 응답 |
|---|---|---|
| `GET /routines` | — | 루틴 목록. 각 항목 = §2 문서 + `when`(예: "평일 07:30") + `mode_label`("승인 후 실행"/"알림만") |
| `POST /routines` | 루틴 본문(`id`·시각 제외) | 201 + 저장된 루틴 |
| `GET /routines/{id}` · `PUT /routines/{id}` · `DELETE /routines/{id}` | PUT은 전체 교체 | 404 = 없는 루틴 |
| `POST /routines/{id}/enable` | `{"enabled": true\|false}` | 바뀐 루틴 |
| `GET /routines/next?limit=3` | — | "다음 실행" 카드: `[{routine_id, name, icon, at(ISO), when, mode, mode_label}]` — 켜진 **시각** 루틴만 |
| `GET /routines/templates` | — | 추천 템플릿(`is_template: true`, **사용자 데이터 아님**): `morning`·`outing`·`visitor`·`homecoming`·`wash_then_dry`. 저장하려면 사용자가 가전·버튼을 고친 뒤 `POST /routines` |
| `POST /routines/{id}/trigger` | — | '지금 실행'. 승인 루틴 → `{"kind":"suggestion","suggestion":{…카드…}}`, 알림 루틴 → `{"kind":"notice",…}`. 409 = 지금 못 만듦(꺼짐·가전 준비 안 됨·부재·쉬는 중) |
| `GET /routines/runs` · `GET /routines/runs/{run_id}` | — | 실행 기록(최근 20건, 메모리). `run_id`는 승인 응답의 `job_id`와 같다. `steps[]`에 단계별 `status`·`confirmation`·`execution_mode`·`detail` |
| `POST /routines/runs/{run_id}/stop` | — | 남은 단계를 보내지 않음. 누르는 중이면 긴급 정지도 보냄. 409 = 진행 중 아님 |
| `GET /routines/log` | — | 트리거 기록(카드 만듦·알림·조건 불만족·못 만듦), 최근 50건 |

제안 카드(`GET /suggestions`)에 `routine_id`·`routine_name`이 붙었다. 있으면 **화면은 `purpose` 대신
`routine_name`을 제목으로** 쓴다. 루틴 카드는 `time_band: "루틴"`, `reason`은 "루틴 '아침 데우기' · 평일 07:30
시각이에요"처럼 **루틴 이름 + 트리거 근거** 한 줄이다. 승인은 기존과 같이 `POST /suggestions/{id}/approve` →
`job_id`이고, 진행은 `/status`(구간별 job) 또는 `GET /routines/runs/{job_id}`로 본다.

습관 제안: 패턴 카드의 버튼 순서와 **똑같은 단일 단계 루틴**이 있으면 `reason`이 "평소처럼 '아침 데우기'
할까요? 최근 …"으로 시작하고 `routine_name`이 붙는다. 실행 내용(버튼 순서·승인 결속)은 종전 그대로다. 여러
단계 루틴(안내·기다리기 포함)은 고르지 않는다 — 습관 카드는 버튼만 누르므로 이름만 빌리면 본 것과 할 일이
달라진다. 맞는 루틴이 없으면 종전 문구 그대로다.

## 4. 여러 단계 실행

승인하면 순서기(`rpi/routines/runner.py`)가 단계를 구간으로 나눈다. 이어진 장치 단계는 한 번의
`execute_approved`(다가전 시나리오와 같은 게이트, 앞 단계가 확인되지 않으면 뒤 단계 미전송, 정지 요청이면
남은 단계 미전송)이고, 첫 구간은 승인 요청 스레드에서 제출해 바쁨(409)·준비 안 됨(412)이 그대로 승인 응답이
된다. 안내는 알림함 기록, 기다리기는 앞 결과를 본다.

| `wait_until_done` 판정 | 결과 |
|---|---|
| 그 가전의 마지막 결과가 성공 + `operation_confirmed`(L3) 또는 `state_confirmed` | 통과 |
| 성공 + `execution_mode=mock` | **시연 통과**("시연: 모의 실행이라 실제 완료를 확인한 것은 아니에요"), 실행 기록 `is_demo` |
| 그 밖(L1 눌림만·보고만·미확인·실패) | 루틴 멈춤 + 알림함 `routine_stopped` |

뒤 구간은 같은 승인의 연속이라 카드 유효 시간(15분)으로 끊지 않는다(세탁처럼 긴 대기). 명령 지문 대조와 실행
직전 재검사(대상·경로·동작 범위·준비 상태)는 구간마다 한다. 구간 사이에 다른 작업이 60초 넘게 안 끝나면 멈춘다.

| 시각 트리거 | 서버 재시작하면 "오늘 이미 냈다" 기억이 사라져 10분 창 안이면 다시 낼 수 있다(카드일 뿐 실행 아님) | 필요하면 설정 표에 기록 |
