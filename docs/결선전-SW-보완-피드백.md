# 결선 전 SW 보완 피드백

작성일: 2026-10-17

이 문서는 결선 직전 소프트웨어의 우선순위를 정리한다. 새 기능을 늘리기보다
실물 통합 흐름을 안전하게 실행하고, 실패했을 때 무엇이 일어났는지 설명할 수
있는 상태를 만드는 것을 목표로 한다.

## 현재 판단

- 승인 지문, 정지 단계, 비상정지 래치, 자동 실행 중복 방지, 조용한 시간,
  ThinQ 대상 검증 등 핵심 안전 계약은 이미 코드와 시험으로 상당 부분 고정되어 있다.
- RPi5에서 ThinQ 실가전 연계를 확인했다. 공기청정기가 22:00에 켜지고
  다음 날 07:00에 꺼지는 시각 자동 루틴과 자동 실행 결과를 실제로 확인했다.
- 남은 가장 큰 위험은 기능의 부재가 아니라 `CoreXY 실제 버튼 누름 → CT
  가열 시작·종료 감지 → 자동 실행 → ThinQ 상태 확인`을 같은 설치 환경에서
  반복했을 때의 관측성·복구성이다.

## 우선순위

### 1. 실물 통합 실행 기록

하나의 실행을 `run_id` 또는 이에 준하는 식별자로 묶어 다음 단계가 같은
기록으로 이어지게 한다.

1. 버튼 누름 요청·실제 누름 확인
2. CT 가열 시작 감지
3. CT 가열 종료 감지
4. 자동 실행 판단과 방해금지(조용한 시간) 판정
5. ThinQ 명령 전송과 상태 재조회
6. 최종 결과와 실패 이유

각 단계에는 허브 시각, 결과, 근거, 실패 원인을 남긴다. 앱·키오스크·서버
로그가 서로 다른 실행을 섞어 보여 주지 않아야 한다.

### 2. 결선 환경 보안

기능 보안은 API 인증, RPi5↔RPi4 링크 HMAC·nonce·sequence 검증, 승인 지문,
비상정지 래치, 자동 실행 정지 세대 등으로 상당 부분 갖춰져 있다. 다만
결선망에서 다음 통신 보안은 별도로 확인해야 한다.

| 위험 | 현재 의미 | 결선 전 조치 |
|---|---|---|
| 휴대폰↔RPi5 HTTP 평문 | 공유 Wi-Fi에서 `X-API-Key`가 도청될 수 있음 | 가능하면 HTTPS 또는 WireGuard/mTLS 적용. 적용 전까지 결선 전용 폐쇄망 사용, API 키 교체·보관, 개발용 HTTP 주소 금지 |
| 페어링 결과의 장기 API 키 전달 | 페어링 응답이 탈취되면 보호된 API를 호출할 수 있음 | 페어링 키·API 키를 영상·로그에 노출하지 않음. 사용 후 키 교체. 장기적으로는 짧은 수명의 1회용 부트스트랩 토큰으로 교환 |
| RPi5↔RPi4 TCP 7000 평문 | HMAC은 위조·재전송을 막지만 생활 패턴 도청은 막지 못함 | `SIMPLELAY_LINK_ALLOW_FROM`을 RPi5 주소로 제한하고, 포트 노출을 결선망으로 제한. 장기적으로 WireGuard/mTLS 적용 |
| 개발용 노출면 | API 문서, 개발자 실물 조작, 무인증 설정이 남으면 조작면이 커짐 | 결선 전 `/docs`·`/openapi.json`·`/redoc`, 개발자 모드, 무인증 환경 변수를 끄고 `/health` 외 보호 경로 인증을 점검 |

보안 점검 결과는 다음 네 가지를 기록한다.

1. 결선망에서만 보드가 서로 통신하는가
2. API 키·링크 키·ThinQ 자격 증명이 화면·로그·영상에 노출되지 않는가
3. 휴대폰·키오스크·보드의 보호 경로가 인증 없이 실행되지 않는가
4. 키를 교체해도 정상 페어링·실행·정지가 복구되는가

근본적으로는 휴대폰↔RPi5와 RPi5↔RPi4 모두 암호화된 인증 채널을 사용해야
한다. HMAC만으로는 명령 위조와 재전송은 줄일 수 있지만 통신 내용의 도청은
막을 수 없다.

### 3. 예외 처리의 완성

예외 처리는 `try/catch`의 개수가 아니라 다음 네 가지가 모든 실패 경로에
있는지를 기준으로 확인한다.

1. 안전한 상태로 멈추는가
2. 성공으로 잘못 표시하지 않는가
3. 원인과 확인 수준이 기록되는가
4. 사용자가 다음에 할 일을 알 수 있는가

결선에서 반드시 재현할 경로:

| 상황 | 기대 결과 |
|---|---|
| CoreXY가 버튼을 누르지 못함 | 성공 표시 금지, 누름 확인 불가 기록, 재시도 여부를 명확히 안내 |
| CT 가열 시작 미감지 | 가열 종료 자동화로 진행하지 않음 |
| CT 가열 종료 미감지 | 자동 실행하지 않음, 가열 종료 미확인 기록 |
| ThinQ 응답 지연·연결 끊김 | 결과 확인 불가로 기록, 근거 없는 재전송 금지 |
| 조용한 시간과 실행 시각이 겹침 | 실행하지 않고 조용한 시간으로 건너뜀 기록 |
| 자동 실행 중 정지·비상정지 | 아직 보내지 않은 동작 차단, 정지 수준을 실제 확인 단계까지만 표시 |
| RPi5 재시작 뒤 오래된 사건 수신 | 이전 사건을 새 사건으로 오인하거나 중복 실행하지 않음 |
| 키오스크가 이전 실행 결과를 표시 | 새 실행의 `job_id`·이벤트 순번을 기준으로 화면 전환 |

### 3. CT 결과 문구와 근거

현재 CT만으로 정상 종료, 취소, 문 열림 종료를 구분하지 못한다. 따라서
코드·앱·키오스크·발표 문구에서 `조리 완료`라고 단정하지 않고 다음 표현을
사용한다.

> 가열 종료를 감지했어요. 조리 완료인지는 확인하지 못했어요.

CT 이벤트에는 가능하면 감지 종류, 관측 구간, 감지 시각, 입력 근거를 함께
남긴다. 정상 종료와 취소·문 열림을 구분할 수 있게 되기 전까지는 자동
실행 정책의 한계도 기록에 남긴다.

### 4. 자동 실행 상태 설명

자동 실행 규칙 카드와 기록에는 다음 상태를 구분해 보여 준다.

- 켜짐
- 이번 실행은 조용한 시간이라 건너뜀
- 연결 불가 또는 결과 확인 불가
- 대상 가전이 바뀌어 다시 허용 필요
- 마지막 실행 결과와 다음 실행 시각

특히 조용한 시간에 건너뛴 사건은 시간이 지난 뒤 자동으로 재실행하지 않는다는
점을 화면과 기록에서 일관되게 말한다.

### 5. 루틴 저장과 자동화 허용의 분리

사용 기록에서 만든 루틴 초안은 저장만 하며, 저장했다고 자동 실행되지 않는다.
사용자가 별도로 자동 실행 내용을 확인하고 허용해야 규칙이 켜진다. 화면 문구도
다음 두 단계를 분명히 구분한다.

- `루틴으로 저장`: 저장만 하며 아직 자동 실행하지 않음
- `다음부터도 자동으로`: 조건·대상·동작을 확인한 뒤 승인 없이 실행

CoreXY 물리 버튼 누름은 자동 실행 대상이 아니며, 매번 사용자 승인이 필요하다.
자동 실행은 허용된 낮은 위험도의 ThinQ 동작에 한정한다.

## 결선 전 검증 묶음

### 정상 흐름

- 실제 설치 환경에서 버튼 누름 확인
- CT 가열 시작·종료 감지
- 허용된 자동 실행 규칙 실행
- ThinQ 상태 재조회로 결과 확인
- 앱·키오스크·기록에서 같은 실행이 같은 결과로 보이는지 확인

### 실패 흐름

- 버튼 누름 실패
- CT 시작·종료 미감지
- ThinQ 응답 지연·상태 재조회 실패
- 조용한 시간과 겹치는 시각 실행
- 실행 중 정지와 비상정지
- RPi5 재시작 뒤 중복 사건
- `실행 → 정지 → 다음 실행` 연속 동작

각 항목은 영상만 남기지 말고 다음 표로 함께 기록한다.

`시각 | run/job 식별자 | 입력 | 기대 결과 | 실제 결과 | 화면 문구 | 복구 방법`

## UI·접근성 보완

UI는 이미 승인 전 확인, 정지 버튼 고정, 확인 수준별 색·문구, 큰 글씨
대응을 갖추고 있다. 결선 전에는 새 화면을 늘리기보다 다음 문제를 실제
기기에서 재확인한다.

| 영역 | 보완 기준 |
|---|---|
| 승인 화면 | 360×780dp·글꼴 2.0에서도 대상 가전, 할 일, `지금 실행`이 하단 고정 영역에 가려지지 않음 |
| 자동 실행 | `켜짐`, `조용한 시간으로 건너뜀`, `결과 확인 불가`, `다시 허용 필요`, `다음 실행`을 색만이 아니라 문장과 아이콘으로 구분 |
| 루틴 후보 | `루틴으로 저장`은 저장만 하고 자동 실행하지 않는다는 안내를 저장 버튼 주변에 유지 |
| TalkBack | 루틴 설명과 `편집`·`실행하기`가 같은 루틴 단위로 읽히고, 버튼 이름에 루틴명이 포함됨 |
| 오류 복구 | 연결 끊김·CT 미감지·ThinQ 결과 미확인 때 원인과 다음 행동이 한 화면에 보임 |
| 키오스크 연속 실행 | `실행 → 정지 → 다음 실행`, `실패 → 닫기 → 새 제안`에서 이전 결과 화면이 남지 않음 |
| 문구 일관성 | `조리 완료` 대신 `가열 종료 감지`, `성공` 대신 실제 확인 수준을 앱·키오스크·기록에서 동일하게 사용 |
| 영상 촬영 | 타임랩스 화면만 믿지 않고, 버튼 누름·CT 이벤트·자동 실행 결과의 일반 속도 근접 영상 또는 로그를 함께 남김 |

UI 검증은 화면 캡처만으로 끝내지 않는다. 실제 폰·키오스크에서 큰 글씨,
스크린리더 순서, 오류 발생 뒤 복귀 경로, 실행 중 정지 버튼의 위치를 확인하고
동일한 문장이 서버 기록과 일치하는지 대조한다.

## 우선순위가 낮은 작업

새로운 AI 기능, 새로운 루틴 종류, 장식적인 UI 변경은 위 통합 흐름과 실패
복구 검증이 끝난 뒤로 미룬다. 결선 직전에는 “더 많이 한다”보다 “실패해도
안전하고, 무엇이 확인됐는지 증명한다”가 중요하다.
