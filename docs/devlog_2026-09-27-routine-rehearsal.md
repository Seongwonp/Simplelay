# 다가전 저녁 휴식 모의 시나리오

후속: [앱·키오스크 공용 모의 화면 연결](devlog_2026-09-27-routine-flutter.md). 아래 독립 브라우저 리허설의 계약을 별도 Flutter 모의 화면에도 연결했다. 기존 자연 제안 목록이나 실제 실행기 통합은 아니다.

## 사용

`python -m rpi.simulator_main --port 8768` 실행 후 `http://127.0.0.1:8768/simulator/routine`을 연다. 통신 리허설 첫 화면에서도 이동할 수 있다.

1. 공기청정기·선풍기 선택 후 '선택한 구성 미리보기'.
2. 선풍기를 제외하면 승인 버튼이 잠긴다. 다시 미리보기를 저장하고 별도로 승인한다.
3. 진행 중인 가전에 성공·실패·응답 유실을 한 번씩 주입한다. 첫 성공 후 두 번째 실패도 확인한다.
4. 전체 정지 요청은 후속 실행을 취소하고 현재 가전은 확인 대기로 둔다. 별도의 정지 확인 또는 응답 유실을 주입한다.

## 계약과 한계

- 합성 이력·가상 기기 2개의 독립 리허설이다. 자연 패턴 학습, 실제 앱·키오스크 제안 목록, 기존 실행 API 및 모터 실행기에 연결되지 않았다.
- 실제 SimulatorController일 때만 경로를 제공한다. 보통 서버에서는 404다. 가전 식별자는 고정된 모의 ID만 허용한다.
- 세션·판 번호가 바뀐 이전 미리보기의 승인은 409로 거절한다. 조회나 화면 폴링은 실행을 진행시키지 않는다.
- 선택 제외는 현재 세션에만 적용한다. 새 시나리오는 두 가전을 다시 선택한다. 영구 선호나 사용 이력에 기록하지 않는다.
- 결과는 가전별 succeeded/failed/unconfirmed/stopped/cancelled/excluded로 구분한다. 첫 가전 성공을 두 번째 실패나 정지 요청으로 덮지 않는다.
- 명령 발송만으로 접수를 단정하지 않는다. 응답 유실은 확인 불가이며 자동 재시도하지 않는다. 실패 이후 남은 가전은 발송하지 않는다.
- 전체 정지는 완료한 가전의 동작을 되돌리는 의미가 아니다. 실제 시스템의 일괄 정지는 기기별 정지 능력과 별도 명령·결과 계약이 필요하다.
- 진행/정지 확인 대기 중 새 세션이나 구성 수정은 거절한다. 모의 종료 후에만 새 시나리오를 시작한다.

## 확인

새 상태/API 테스트 11개 및 기존 정지·보관 API와 합쳐 21개 통과. 벤더 dbus_fast 경로를 포함한 전체 백엔드 테스트는 1,573개 통과(기존 경고 2개). 브라우저에서 선풍기 제외 → 미리보기 → 승인 → 공기청정기 성공 → 선풍기 제외 유지까지 직접 확인했다.

다음은 이 모의 모델에서 검증한 선택·승인·가전별 결과 계약을 앱과 키오스크의 공용 다가전 제안 모델로 옮기는 것이다. 실물 제어 전에 각 가전의 준비 상태, API/물리 경로, 부분 실패 시 후속 처리 정책을 연결해야 한다. 이후 Flutter 연결 변경과 함께 사용자 요청으로 커밋·푸시한다.
