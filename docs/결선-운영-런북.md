### 1-2. 예비 SD 이미지

- 본선 1주 전(10/30 전후) 리허설을 통과한 상태로 RPi5·RPi4 SD 카드를 통째로 복제한다. 라벨에 날짜와 커밋을 적는다.
- 기기 env 파일(API 키 등 비밀)이 이미지에 들어 있다. **예비 SD는 저장소나 공용 저장소에 올리지 않는다.**
- 복제한 카드로 한 번 부팅해 §3-2~§3-4를 통과하는지 확인한다. 확인하지 않은 예비는 예비가 아니다.

### 1-3. 무대 배치 (150×55cm ×2)

리허설 때 실측해 이 칸에 그림을 붙인다. 【리허설 때 기입】

- 키오스크 패널은 관객 쪽으로 세운다. 패널 가장자리에 손이 닿지 않게 둔다(§5-1).
- 갠트리는 관객 쪽 3/4 각도로 둔다. Z 누름이 옆에서 보이게 한다.
- 비상정지 버튼은 발표자 손이 닿는 곳에 둔다. 【HW 대기】 회로가 아직 없다.
- ThinQ가 모의라면 ThinQ 실물 가전은 무대에 두지 않는다(시나리오 v2 §5).

## 2. 네트워크 계획

시연장 Wi-Fi는 쓰지 않는다. 전용 공유기 하나에 모든 것을 붙이고 **고정 IP**를 준다. 공유기의 DHCP 예약으로 고정한다.

| 장치 | 연결 | 주소(예시 — 실제 값은 공유기 설정과 기기 env에만) | 쓰는 포트 |
|---|---|---|---|
| 전용 공유기 | — | `<GW>` (예: 192.168.50.1) | — |
| RPi5 | LAN | `<RPi5>` (예: .10) | 8000(백엔드) |
| RPi4 | LAN | `<RPi4>` (예: .11) | 7000(LAN 시험 배선일 때만) |
| 운영 노트북 | LAN | `<OPS>` (예: .20) | — |
| 시연 폰 | Wi-Fi | `<PHONE>` (예: .30) | — |
| ESP32 콘센트 모듈 | Wi-Fi | `<OUTLET>` (예: .40) | 【HW 대기】 |

- **주소를 바꾸면 고칠 곳이 셋이다.**
  1. RPi5 env의 `SIMPLELAY_UART_PORT=socket://<RPi4>:7000`(LAN 배선일 때만)
  2. 폰 허브 주소
  3. 여러 네트워크에 붙은 허브라면 `SIMPLELAY_PAIR_HOST=http://<RPi5>:8000`
- 집에서 쓰는 주소와 시연 주소가 다르면 리허설 한 번을 반드시 시연 주소로 한다.
- 실제 UART 선을 쓰면 RPi5↔RPi4 실행 경로는 LAN에 기대지 않는다. LAN은 폰과 노트북용으로만 남는다. 【HW 대기】 UART 선이 아직 없다.
- 공유기 SSID와 비밀번호는 시연용으로 새로 만든다. 다른 사람의 단말이 붙지 않게 한다. `SIMPLELAY_ALLOW_UNAUTHENTICATED=1`은 시연에서 **절대 쓰지 않는다**(시나리오 v2 §4-7).
- 인터넷은 ThinQ 실물과 날씨에만 필요하다. 인터넷이 없으면 키오스크는 인사말만 보여 준다(설계). 인터넷 없이도 시연이 끝까지 가는지 리허설에서 한 번 확인한다.

## 3. 설치 30분 체크리스트 (순서대로)

운영 노트북에서 상태를 확인한다. 기기 셸에는 `curl`이 없을 수 있다(BusyBox). PowerShell 예시는 이렇다.

```powershell
$B = "http://<RPi5>:8000"; $H = @{ "X-API-Key" = "<키 — 기기 env에서 읽음, 문서에 적지 않음>" }
Invoke-RestMethod "$B/health" -Headers $H
```

### 3-1. 배치와 전원 (0~8분)

- [ ] 책상 두 개를 배치하고 가전·갠트리·패널을 고정한다(양면테이프).
- [ ] 멀티탭을 나눈다(가전용, 보드·패널용).
- [ ] 공유기 전원을 켜고, LAN을 RPi5·RPi4·노트북에 꽂는다.
- [ ] 패널 케이블 세 개를 꽂는다: micro-HDMI(영상), **USB-C 데이터(터치)**, PD(전원).
- [ ] RPi4 → RPi5 순서로 전원을 넣는다(§3-4 참고).

### 3-2. RPi5 백엔드 (8~12분)

RPi5는 전원만 넣으면 백엔드 컨테이너가 뜬다(`--restart unless-stopped`, 재부팅으로 확인함).

- [ ] `GET /health`에서 `ok: true`를 본다. `act_mode`는 등급별로 다르다.
  - 실물·부분 실물: `uart`
  - 전부 모의: 시뮬레이터 서버
- [ ] `GET /status`에서 `developer_mode: false`를 본다(시연 날 기본값, 실행계획 §3-8).
- [ ] 응답이 없으면 운영 노트북에서 SSH로 `docker ps`와 `docker logs --tail 50 simplelay-backend`를 본다.
  - 기동 로그의 "API 인증: …" 줄로 키가 설정됐는지 확인한다.
  - `qrcode` import 실패면 이미지가 낡은 것이다(`6f3380c` 이전). 이미지를 다시 만든다.
- [ ] **페이싱을 확인한다.** `deploy/run_backend.sh`는 `SIMPLELAY_DEMO_PACING=1`을 항상 켠다. 시나리오 v2 §4-18은 실물·부분 실물에서 이 값을 끄라고 한다. 등급에 맞는지 확인한다(§8 결정 대기).

### 3-3. 키오스크 앱 (12~15분)

- [ ] 부팅 뒤 15초 안팎에 키오스크가 패널에 뜨는지 본다. 감시 컨테이너(`deploy/run_kiosk_watchdog.sh`)가 플랫폼 앱 관리자에게 상태를 묻고, 꺼져 있으면 시작한다.
- [ ] 뜨지 않으면 다음 순서로 원격 시작한다.
  1. 운영 노트북에서 RPi5에 SSH로 들어간다.
  2. 감시 로그를 본다: `docker logs --tail 20 simplelay-kiosk-watchdog`.
  3. 앱 관리자 호출이 실패하면 감시 컨테이너를 다시 시작한다: `docker restart simplelay-kiosk-watchdog`.
  4. 그래도 안 되면 플랫폼 앱 관리자의 시작 명령을 직접 보낸다. 명령과 앱 ID는 **비공개 로컬 메모**에 있다. 저장소에는 없다.
- [ ] 옛 키오스크 앱(같은 이름으로 보일 수 있음)이 아니라 새 앱 ID의 최신 버전(현재 1.4.0)인지 확인한다.
- [ ] 화면 위쪽에 실행 환경 표시가 보이는지 확인한다. 모의면 "모의 실행 · 실제 조작 아님"이 보여야 한다. 모의 표시를 가리지 않는다.
- [ ] 터치를 확인한다. 화면 가운데 버튼 하나를 누른다. 반응이 없으면 USB-C 데이터 선부터 본다.
- [ ] 연결 아이콘 세 개(와이파이, 누름 장치, 플러그)의 상태를 본다. 플러그는 "설치 안 됨"이 정상이다. 【HW 대기】

### 3-4. RPi4 실행기와 RPi5→RPi4 연결 (15~19분)

- [ ] **RPi4는 루트 파일시스템이 읽기 전용이다.** 그래서 도커 자동 기동을 설정할 수 없다. 부팅 뒤 SSH로 `systemctl start docker`를 먼저 하고, `docker ps`에서 `simplelay-act`가 `Up`인지 본다.
  - 없으면 `sh <데이터 경로>/run_act.sh`를 실행한다(`deploy/run_act.sh`. LAN 배선이 기본이고, UART 선이면 `LINK=uart`).
- [ ] RPi5를 RPi4보다 먼저 띄웠다면 RPi4 연결이 엇갈릴 수 있다. 이때는 `simplelay-act`가 스스로 재시작한 뒤 RPi5 쪽 `docker restart simplelay-backend`를 한 번 더 한다(LAN 배포 로그 §3).
- [ ] **연결을 확인한다.**
  1. `GET /connections`의 누름 장치 항목이 정상(회색)인지 본다.
  2. `docker logs --tail 20 simplelay-act`에 연결 로그가 있는지 본다.
- [ ] **전부 모의·LAN 모의 모션:** 안전한 시험 가전으로 `POST /execute`를 한 번 한다.
  - `/status`가 `succeeded / success / mock / physical / reported`면 통과다(9/30 실기기 확인 형태).
- [ ] **부분 실물:** 【HW 대기】 실행 전에 확인할 것이 있다.
  - RPi4 env에 `SIMPLELAY_MOTION_MODE=serial`과 `SIMPLELAY_MOTION_PORT`가 있는지 본다.
  - 기구 값 `SIMPLELAY_MOTION_*`이 있는지 본다. 없으면 누름을 거절한다(시끄러운 실패).
  - 원점 복귀를 확인한다.
  - 원시 기록기 `SIMPLELAY_RECORDER_PATH`에 파일이 생기는지 본다.

### 3-5. 폰 (19~22분)

- [ ] 릴리스 APK인지, 폰 "데모 모드"가 꺼졌는지 확인한다(시나리오 v2 §4-1).
- [ ] 허브 연결과 API 키를 확인한다. 둘 중 한 방법을 쓴다.
  - **짝짓기:** 키오스크 설정 → 폰 연결하기. 5분짜리 6자리 코드와 QR이 뜬다. 폰 설정 → 허브 → 코드로 폰 연결하기 → 키오스크에서 승인한다. 【미확인】 QR 카메라 인식과 두 기기 LAN 연결은 실기기에서 확인하지 않았다.
  - **직접 입력:** 폰 설정 → 허브에서 주소 `http://<RPi5>:8000`과 키를 넣는다. 9/30 에뮬레이터에서 확인한 방법이다.
- [ ] 홈 상단 칩이 "허브 연결됨"이고 연결 경고가 없는지 본다. 401이면 키가 다른 것이다.
- [ ] 개발자 탭이 보이지 않는지 본다(`developer_mode: false`).

### 3-6. ThinQ 모드 (22~24분)

- [ ] `GET /thinq/devices`가 200이고 `mode`가 등급에 맞는지 본다.
  - 부분 실물·전부 모의: `mock`
  - 실물: `real`. 단 **`RealThinqClient`가 아직 없어 지금은 이 등급이 불가능하다**(시나리오 v2 §2, G7).
- [ ] 404면 `SIMPLELAY_THINQ_MODE`가 빠진 것(기본 off)이다. 이 상태면 장면 ②·④가 에러 없이 사라진다(시나리오 v2 §4-5).
- [ ] `GET /readiness/air_purifier`가 `route: thinq, state: operable`인지 본다.
- [ ] `GET /demo/thinq/fault`에서 모든 기기가 `normal`인지 본다. 아니면 `POST /demo/thinq/fault {"device_id":…,"mode":"normal"}`로 되돌린다.
- [ ] 키오스크와 폰의 ThinQ 가전 이름에 "(모의)"가 보이는지 본다. 가리지 않는다.

### 3-7. 시연 데이터 정리와 실패 주입 해제 (24~27분)

- [ ] `DELETE /demo/inject-failure` → `{"ok":true}`(남은 주입 제거, 시나리오 v2 §4-17)
- [ ] `GET /wellness-pause` → `paused:false`. 아니면 `DELETE`
- [ ] `GET /presence` → 부재가 남아 있지 않은지 본다. 필요하면 `POST /presence {"present":true}`
- [ ] `GET /suggestions` → 앞 리허설의 카드가 남았으면 `POST /suggestions/<id>/reject {"mute":false}`로 치운다.
  - 주의: 치우는 것도 이벤트 기록에 남는다. 기록을 비우려면 시연 전용 DB로 시작한다. 방법은 【결정 대기 §8】
- [ ] `POST /demo/alert {"kind":"danger_sound","raised":false}` → 위험 경보 해제(모의·시뮬레이터 모드 전용, uart면 404)
- [ ] 전원 경로를 확인한다. 전자레인지 문은 닫고 안은 비운다. **가열하지 않는다.**
- [ ] 키오스크가 평소 화면으로 돌아왔는지 본다.

### 3-8. 직전 확인 (27~30분, 대기 중 5분마다 반복)

- [ ] 키오스크가 평소 화면이다. 연결 아이콘에 "!"가 없다(플러그 "설치 안 됨"은 예외).

## 4. 장면별 진행/중단 판정

등급 정의는 시나리오 v2 §2를 따른다. **실물** 등급은 `RealThinqClient`가 없어 현재 불가능하다. 실제로 고를 수 있는 것은 **부분 실물**(하드웨어 + ThinQ 모의)과 **전부 모의**뿐이다.

**판정 규칙.**
- 설치 끝(15:20)에 아래 "진행 조건"을 하나라도 못 채운 장면은 한 단계 아래 등급으로 내린다. 모든 등급에서 못 채우면 백업 영상으로 돌린다.
- 장면 도중에 등급을 올리지 않는다.

| 장면 | 실물 (현재 불가) | 부분 실물 【HW 대기】 | 전부 모의 | 중단 신호 → 대체 |
|---|---|---|---|---|
| ① 선제 제안 → 물리 실행 | 부분 실물 조건 + ThinQ 실물 | 원점 복귀 성공, 리허설 3회 연속 누름 성공(직전 30분), `/health.act_mode=uart`, RPi4 `MOTION_MODE=serial` | 시뮬레이터 서버 응답, 트윈 열림 | 원점 실패나 누름 실패 2회 → 전부 모의로 내리고 "오늘은 모의로 보입니다"라고 먼저 말한다 |
| ② 조리 확인 → 공기청정기 | L3 실물 판정 필요(G2, 센서 드라이버 없음) | 물리 결과가 `reported`라 자동 카드가 뜨지 않는다 → 운영자가 `POST /demo/scenario/cook_then_air` | ①이 성공하면 카드가 자동으로 뜬다 | `/thinq/devices` 404나 readiness 412 → ② 생략, ④를 물리 단독으로 줄인다 |
| ③ 실패 주입 → 재시도 | — | RPi4 주입 전달 확인, 갠트리 재누름 리허설 통과 | 트윈에 "재시도 1회째" | 재시도 뒤 안전 정지가 나면 ⑤의 안전 정지 설명으로 돌린다 |
| ④ 저녁 휴식(ThinQ + 물리) | — | ThinQ 모의, 선풍기 노드가 없으면 서버 쪽 모의 선풍기 | 둘 다 모의 | 1단계가 확인되지 않으면 2단계를 보내지 않는다(설계대로). 그대로 보여 준다 |
| ⑤ 긴급 정지 | 콘센트 모듈 릴레이 차단 【HW 대기, 회로 미제작】 | 키오스크 정지, `/stop` 응답 확인 | 키오스크나 트윈 정지 | 정지 뒤 갠트리가 계속 움직이면 **갠트리 전원 멀티탭 스위치를 끈다**(§5-4) |
| ⑥ 사용자 통제 | — | 운영자가 수동으로 `POST /presence` | 같음 | `PRESENCE_GATING`이 꺼져 있으면 "넘기기"만 보인다 |

**전환 순서.** 부분 실물 → 전부 모의 → 백업 영상. 전부 모의로 내릴 때는 운영 노트북에서 시뮬레이터 서버를 띄운다(약 1분). 그리고 키오스크·폰 주소를 그쪽으로 돌린다. 【미확인】 RPi5 키오스크 앱을 노트북 서버로 돌리는 절차는 시험하지 않았다. 지금 확실한 대체는 노트북 브라우저 `/kiosk/` 웹 빌드다. 단 로컬 `kiosk-web/`은 9/27 빌드라 재빌드가 필요하다(시나리오 v2 §4-10).

## 5. 대체 스위치와 복구 절차

### 5-0. 대체 스위치

| 무엇을 | 어떻게 | 효과 |
|---|---|---|
| ThinQ 실물 → 모의 | RPi5 env `SIMPLELAY_THINQ_MODE=mock` → `docker restart simplelay-backend` | 장면 ②·④가 모의 가전으로 진행. "(모의)" 이름을 그대로 읽는다 |
| 물리 실행 → 모의 모션 | RPi4 env `SIMPLELAY_MOTION_MODE=mock` → `docker restart simplelay-act` | 갠트리가 움직이지 않고 실행기는 모의 결과를 보고한다. 화면 실행 환경 표시를 확인한다 |
| 전체 → 시뮬레이터 | 노트북: `SIMPLELAY_THINQ_MODE=mock SIMPLELAY_PRESENCE_GATING=true .venv/Scripts/python.exe -m rpi.simulator_main --host 0.0.0.0 --port 8775` (+ `SIMPLELAY_API_KEY`) | DB·센서·노드가 꺼진 독립 서버다. 트윈 `/simulator/twin`이 있다 |
| 부재 철회 켜기 | `SIMPLELAY_PRESENCE_GATING=true` | 장면 ⑥ 부재 철회. 끝나면 `present:true` |
| ThinQ 장애 연출(질의응답용) | `POST /demo/thinq/fault {"device_id":"air_purifier","mode":"offline"\|"unconfirmed"\|"lost"}` | 끝나면 반드시 `"normal"` |
| 페이싱 | `SIMPLELAY_DEMO_PACING` 끄기 또는 켜기(`run_backend.sh`가 강제로 켬, §8) | 실물에서 켜 두면 이중으로 느려진다 |

### 5-1. 가장자리 스와이프로 키오스크가 닫혔을 때

- **원인.** 창 관리자가 화면 가장자리에서 시작한 터치를 스와이프로 읽어 앱을 닫는다. 앱에는 48px 안전 여백을 두었다.
- **복구.**
  1. 감시 컨테이너가 확인 간격(`SIMPLELAY_KIOSK_CHECK_S`, 기본 10초) 안에 다시 시작한다. **10~15초 기다린다.** 그동안 발표자는 폰이나 트윈으로 말을 잇는다.
  2. 20초가 지나도 안 뜨면 §3-3의 원격 시작 순서를 따른다.
- **예방.** 패널 테두리를 손이 덜 닿게 두고, 발표자는 화면 가운데만 누른다.

### 5-2. 백엔드를 다시 시작할 때

1. RPi5에서 `docker restart simplelay-backend`를 하고 약 5초 기다린다.
2. 노트북에서 `/health`를 확인한다.
3. RPi4 실행기가 가상 시리얼 끊김으로 스스로 재시작한다(설계). 그 뒤 §3-4 연결 확인을 다시 한다. 엇갈리면 백엔드를 한 번 더 재시작한다.
4. **재시작하면 휘발성 상태가 사라진다.** 실패 주입, ThinQ 장애, 부재, 짝짓기 창, 노드 준비 상태가 모두 초기화된다. 노드 가전은 다시 준비 보고가 필요하다(시나리오 v2 §4-2). §3-6과 §3-7을 다시 한다.
5. 폰이 "허브에 닿지 않아요"면 앱을 다시 열고 연결 칩을 본다.

### 5-3. RPi4 연결이 끊겼을 때

- **증상.** 키오스크 누름 장치 아이콘에 "!"가 붙는다. 실행이 실패하거나 확인 불가로 끝난다. **결과를 잃으면 확인 불가로 두고 자동 재실행하지 않는다**(설계). 그대로 보여 주고 이유를 말한다.
- **복구.**
  1. LAN 케이블과 공유기 링크 LED를 본다.
  2. RPi4에 SSH로 들어가 `docker ps`를 본다. 도커가 없으면 `systemctl start docker`, 그다음 `run_act.sh`를 실행한다.
  3. 컨테이너가 떠 있으면 `docker restart simplelay-act`를 하고, RPi5 백엔드를 한 번 재시작한다.
  4. §3-4 연결 확인을 다시 한다.
- **2분 안에 안 되면** 전부 모의로 내린다(§4).

### 5-4. 모션 이상 (탈조·벨트 헛돎·원점 상실·이상 소음) 【HW 대기】

1. **즉시 정지.** 키오스크 정지를 누르거나 `POST /stop`을 보낸다.
2. 움직임이 멈추지 않으면 **갠트리 전원 멀티탭 스위치를 끈다.**
   - 콘센트 모듈 릴레이 비상정지는 회로가 아직 없다.
   - `/stop` 응답의 ACK는 물리 정지의 증명이 아니다(증거 대장).
3. 화면 결과는 "정지됨" 또는 "안전 정지"다. "장치를 확인해 주세요" 문구를 그대로 보여 준다.
4. 다시 하려면 갠트리 전원을 넣고, 원점 복귀를 한 뒤 시험 누름 1회를 한다. 시연 중이면 **다시 하지 않고** 전부 모의로 내린다. 하드웨어는 무대에 두고 "오늘은 모의로 보입니다"라고 먼저 말한다.
5. 벨트 헛돎은 엔코더 값과 실제 위치를 어긋나게 한다(10/5 메모). 리허설에서 누름 성공률을 실측해 진행 조건(§4)을 다시 정한다.

### 5-5. Wi-Fi가 끊겼을 때

- **폰만 끊긴 경우.** 키오스크만으로 진행하고 폰 장면은 말로 대신한다(시나리오 v2 §5). 정지는 키오스크에서 한다.
- **공유기 전체가 죽은 경우.**
  1. 공유기 전원을 다시 넣는다(약 1~2분).
  2. 그동안 RPi5 키오스크는 같은 기기 루프백이라 계속 동작한다.
  3. RPi4 LAN 배선이면 실행 경로도 끊긴다. 실제 UART 선이면 실행 경로는 유지된다. 【HW 대기】
- **인터넷만 끊긴 경우.** 날씨 안내가 인사말로 바뀐다(설계). ThinQ 실물이라면 ②·④를 모의로 돌린다. 물리 경로는 영향이 없다.

### 5-6. 그 밖에

| 증상 | 확인 |
|---|---|
| 카드는 보이는데 "지금 실행"이 잠김, 승인하면 412 | `GET /readiness/<id>`의 `reasons` |
| 즉석밥 성공 뒤 ② 카드가 안 뜸 | ThinQ 모드(§3-6), 부재 상태(§3-7), 부분 실물이면 원래 수동 트리거다 |
| 첫 실행부터 재시도나 안전 정지 | 남은 실패 주입. `DELETE /demo/inject-failure` |
| 폰 401 | 키 불일치. §3-5 |
| 한글 본문 curl에서 422 | 파일 본문이나 PowerShell을 쓴다(시나리오 v2 §4-19) |

## 7. 철수와 종료

1. `DELETE /demo/inject-failure`, ThinQ 장애 `normal`, `present:true`로 상태를 되돌린다. 다음 리허설에 남지 않게 한다.
2. 갠트리 전원 스위치를 끈다. Z가 올라간 상태인지 본다. 【HW 대기】
3. RPi4와 RPi5를 SSH로 `poweroff`해 정상 종료한다. SD 손상을 막으려고 **전원을 바로 뽑지 않는다.** LED가 꺼진 뒤 전원을 뺀다.
4. 패널과 공유기 전원을 끈다. 케이블은 묶어서 회수한다.
5. 가전 고정 테이프를 떼고 운반한다(벨트 장력 확인).
6. 운영 노트북의 리허설 로그와 원시 기록은 로컬에만 둔다.
