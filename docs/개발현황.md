## 1. 프로젝트 개요

기존 가전에 **AI 제어 레이어를 씌우는** 장치. 가전을 바꾸지 않고 버튼 위에 물리적 액추에이터를 얹어 음성 명령 · 패턴 학습 · 선제 제안으로 동작시킨다.

**핵심 가치**: Sense → Interpret → Act 3계층 + 폐루프 검증 (버튼이 실제로 눌렸는지 센서로 확인 후 자동 재시도)

### CoreXY 운동학 요약

두 개의 고정 모터 A, B와 벨트 교차 구조.

| 동작 | 모터 A | 모터 B |
|------|--------|--------|
| X+ | 정방향 | 정방향 |
| Y+ | 정방향 | 역방향 |
| 대각선 | 한 쪽만 | 정지 |

```
ΔX = ½(ΔA + ΔB)
ΔY = ½(ΔA - ΔB)
```

## 4. RPi Python 서버 (완성)

**경로**: `rpi/`  
**프레임워크**: FastAPI + uvicorn (port 8000)  
**의존성**: `fastapi`, `uvicorn`, `pydantic`, `anthropic` (또는 OpenAI 호환)

### 4-1. API 엔드포인트

| 메서드 | 경로 | 설명 |
|--------|------|------|
| GET | `/health` | 연결 확인 (ping) |
| POST | `/execute` | 자연어 → 버튼 시퀀스 해석 → 실행 |
| POST | `/execute-buttons` | 버튼 시퀀스 직접 실행 (의도 해석 우회 — 사용자 정의 가전용) |
| POST | `/execute-for-appliance` | 자연어 → 버튼 시퀀스 해석, 단 요청에 실린 버튼 어휘 기준(사용자 정의 가전용 음성 명령). LLM 미설정 시 503 |

### 4-2. 의도 해석 계층 (`rpi/intent/`)

**LLM 의도 해석** (`llm.py`, `dbus_internal_ai.py`):
- 응답 형식 강제: `{"sequence": ["버튼라벨", ...]}`
- 알 수 없는 버튼 포함 시 예외 → 폴백 진입
- 네트워크/파싱/검증 오류 모두 `UnknownIntentError` 단일 타입으로 표면화
- `LlmClient` 구현체가 두 종류(둘 다 `rpi/api/deps.py`가 환경변수로 명시적으로 선택,
  자동 폴백 없음):
  - `HttpLlmClient` — OpenAI 호환 chat-completions 엔드포인트 (`SIMPLELAY_LLM_BASE_URL`).
    데모 시 대체용 클라우드 API 경로
  - `Dbusinternal_aiLlmClient` — 온디바이스 에이전트 서비스 (`SIMPLELAY_LLM_MODE=dbus`).
    요청/응답이 비동기라(요청 즉시 request_id만 반환, 실제 답은 시그널 스트림으로
    옴) 프로세스 하나로 요청을 보내고 별도로 시그널 스트림을 구독해서 완료 표시까지
    문장을 이어붙이는 구조 — 실기기 검증 완료
- 둘 다 설정 안 하면 서버는 기본적으로 오프라인 동작(해당 기능만 503)

**사용자 정의 가전 음성 명령** (`execute_purpose_for_appliance`, `service.py`):
- 서버 고정 규칙이 아니라 요청에 실린 버튼 라벨 어휘로 `LlmIntentResolver`를 즉석에서
  구성 — 가전마다 다른 임의의 버튼 이름을 등록 시점에 정의만 하면 바로 음성 명령 대상이 됨
- BLE 릴레이(ESP32)는 의도 해석을 못 하므로 이 경로는 RPi5 HTTP 직통에서만 지원

**규칙 기반 폴백** (`rules.py`):
```python
DEFAULT_RULES = {"우유 데워줘": ("해동", "시간 90초", "시작")}
```

**온디바이스 벡터DB 유사도 매칭** (`dbus_vectordb.py`):
- `VectordbIntentResolver` — `com.platform.internal_aiVectordb1`로 미리 등록해둔 예시
  발화(`seed_examples()`, 명시적 1회 호출)와의 유사도 검색(top_k=1)으로 버튼
  시퀀스를 찾음. `RuleBasedIntentResolver`(정확일치)와 `LlmIntentResolver`/
  `Dbusinternal_aiLlmClient`(느리지만 유연한 대화형) 사이의 중간 계층 — 빠르고
  오프라인이면서 규칙보다는 유연함
- 유사도 임계값 미달·메타데이터 파싱 실패 모두 `UnknownIntentError`로 표면화돼
  `TieredIntentResolver`에 그대로 얹힘
- **CAUTION**: `AddText`/`SearchText`의 실제 internal_gpio 출력 텍스트 포맷은 아직
  실기기로 확인 못 함(작업 시점에 RPi5가 꺼져 있었음) — 파싱 함수를 독립된
  순수 함수로 분리해뒀으니 실기기 확인 후 그 부분만 교체하면 됨. 리졸버 자체
  로직은 fake client로 완전히 검증됨

**선제 제안** (`suggestions.py`):
- `PatternDetector`가 감지한 반복 패턴을 바탕으로 제안 생성
- 제안은 `PENDING → APPROVED` 1회 게이트 (승인 전 실행 불가)
- 승인 시 기존 `intent → controller` 폐루프 연계

**패턴 감지** (`patterns.py`):
- 시간대·목적 기반 반복 횟수 집계
- 임계값 이상이면 제안 후보로 반환

### 4-3. 폐루프 컨트롤러 (`rpi/controller/`)

```
ClosedLoopController.execute(buttons)
  for button in buttons:
    for attempt in 1..max_attempts:
      grbl.press(button, correction)   # 좌표 보정 (재시도 시)
      result = verifier.verify(button)
      if result.pressed: break
    if failed:
      safety.stop(reason)              # 긴급 정지
      alerts.notify_failure(button)
      return SAFETY_STOPPED
  return SUCCEEDED
```

### 4-4. 센서 퓨전 검증 (`rpi/verifier/`)

전류 센서 + 음향 센서 2채널 가중 합산:

```
현재 가중치 설정 (FusionConfig):
  current_weight: 0.7   (전류 신호가 더 신뢰성 높음)
  audio_weight:   0.3
  confidence_threshold: 0.5

진리표:
  전류✅ 음향✅ → pressed=True,  confidence=1.0
  전류✅ 음향❌ → pressed=True,  confidence=0.7
  전류❌ 음향✅ → pressed=True,  confidence=0.6
  전류❌ 음향❌ → pressed=False, confidence=0.0
```

**위험소리(화재·가스 경보음) 감지** — `DangerSoundDetector`(`rpi/verifier/danger_sound.py`):
버튼음 검증(단발 프레임)과 달리 여러 프레임에 걸친 상태를 갖는다. 대역 에너지 비율
(기본 2800~4200Hz, 피에조 경보기 대역 추정치 — 실측 필요) + 온셋 주기성 검사로 판정하며,
최소 반복 횟수(`min_cycles`)를 요구해 전자레인지 완료음 같은 유한 반복과 구분한다.
감지되면 RPi4의 `ActExecutor.report_danger_sound()`가 엣지 트리거로 RPi5에 UART
`alert`/`alert_cleared` 메시지를 즉시 푸시한다(승인 절차 없음, `docs/protocol.md`).
RPi5 쪽 수신 클라이언트(`rpi/services/act_client.py`의 `ActClient`, `on_alert`
콜백)도 구현·테스트 완료. `SIMPLELAY_ACT_MODE=uart`로 켜면 `SimpleLayService`가
실제로 이 클라이언트를 통해 RPi4에 연결되고, 수신한 alert는 일단 로그로만
남긴다(전용 UI 표면화는 아직, `docs/roadmap.md` M2 참고). 기본값은 여전히 로컬
mock 컨트롤러 — 오프라인 우선 원칙 유지.

| ESP32 | BLE ↔ Wi-Fi 브릿지 | 보유 |
| Arduino Uno | 모터 PID 제어 (커스텀 펌웨어) | 보유 |
| ACS712 전류 센서 | 버튼 눌림 검증 | 조달 예정 |
| 마이크 모듈 | 음향 검증 | 조달 예정 |
| 7인치 터치스크린 | RPi 5 디스플레이 | 보유 |

**GRBL 사용 안 함**: DC 기어드 모터와 호환 불가. 대신 Arduino에 커스텀 PID 펌웨어.

## 8. PPT 스크린샷 촬영 계획

### 앱 스크린샷 (Flutter — 시뮬레이터 or 실기기)

| 화면 | 시나리오 | 포인트 |
|------|----------|--------|
| 홈 화면 | 제안 1개 도착 상태 | 슬라이딩 카드, 가전 Chip |
| 제안 확인 | 전자레인지 "우유 데우기" | 버튼 맵 그리드 하이라이트 강조 |
| 실행 중 | 2단계 완료, 3단계 진행 중 | 단계 체크 + 센서 차트 |
| 설정 | RPi 연결됨 상태 + 전자레인지 선택 | 연결 상태 뱃지 |

### RPi 터치스크린 스크린샷 (내일 구현 후)

| 화면 | 시나리오 |
|------|----------|
| 대기 화면 | 정상 상태 |
| 제안 화면 | 버튼 맵 + 승인 버튼 크게 |
| 실행 중 | 단계 진행 + 긴급 정지 |

### 시뮬레이션 캡처 방법
1. `python -m pytest rpi/tests/ -v` → 폐루프/패턴 감지 테스트 통과 화면
2. `curl -s localhost:8000/execute -d '{"text":"우유 데워줘"}'` → JSON 응답
3. Flutter 데모 모드 → 제안 시뮬레이션 → 승인 → 실행 상태 화면 순서
