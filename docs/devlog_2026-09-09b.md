## R1 · 실행 대상 가전 검증을 모든 진입점이 공유 (`5f02c6a`)

게이트가 **라우터의 직접 실행 3개 경로에만** 있었다. 제안 승인은
`approve_submit → submit_purpose → _controller_for`로 곧장 내려가 검사를 지나쳤다.

    선풍기 제안 생성 → 선풍기 삭제 → 남은 제안 승인
    → 노드 없음 → 로컬 기본 컨트롤러 폴백 → **전자레인지 갠트리가 움직인다**

라우터에 검사를 하나 더 붙이면 진입점이 늘 때마다 같은 구멍이 다시 생긴다.
대상을 고르는 **한 곳**(`SimpleLayService._controller_for`)에서 거절한다 —
동기 3 · 비동기 3, 여섯 진입점이 모두 여기로 합류한다.

- `UnknownApplianceError`는 `LookupError`다. `RuntimeError`(=409 "다른 작업이
  실행 중")와 섞이면 "잠시 후 다시 시도하세요"로 안내되는데, **기다려도
  영원히 안 되는 상황**이다. `main.py`에서 404로 한 번만 매핑한다.
- 가전 삭제 시 그 가전의 pending 제안도 내린다. 억제 목록에는 넣지 않는다 —
  사용자가 "그만 추천해"라고 한 게 아니라 대상이 사라진 것이다.
- 폰: 대상 가전을 모르면 현재 선택 가전으로 **바꿔 그리지 않고** 실행 버튼을
  내걸지 않는다. 무엇이 눌릴지 말할 수 없으면 실행을 권하지 않는다.

거절의 기준은 하나로 고정했다: **mock 컨트롤러 호출 0.**

### 곁가지 둘

- **1회용 승인 게이트가 실패한 승인까지 소비하고 있었다.** 404든 409든 카드만
  사라지고 아무 일도 일어나지 않았다 — "끝난 뒤 다시 시도하세요"라는 안내를
  받는데 정작 다시 시도할 카드가 없다. 실행 제출 **전에** 거절된 경우 게이트를
  되돌린다(제출은 executor 호출의 마지막 단계라 이중 실행이 되지 않는다).
- **테스트 격리 결함.** 가전 레지스트리 픽스처가 `dependency_overrides`로
  라우터 쪽 간선만 바꿔서, 게이트를 서비스로 옮기자마자 "방금 등록한 가전이
  실행 시점엔 없는 가전"이 됐다. 캐시를 비워 라우터와 서비스가 같은 인스턴스를
  잡게 했다.

## R2 · 모의 실행은 실제로 아무것도 보내지 않는다 (`c0ed947`)

어제 만든 데모 게이트(B7)가 막은 것은 **BLE 가짜 센서 주입뿐**이었다. HTTP
실행은 그대로 서버로 나갔다. 데모 모드를 켜고 제안을 승인하면 **실제 갠트리가
움직이는데 화면은 "실제 조작이 아닙니다"라고 말했다.** 폐루프의 존재 이유가
"눌림을 확인했는가"인데 그 확인을 화면이 뒤집는 셈이다.

문구가 아니라 **전송 경로**에서 갈랐다.

- `SimulatedExecutionService` — execute 3종·승인·**그 job의** `status`만
  흉내내고, 제안 목록·가전·이력·센서·`stop()`은 실제 서버에 위임한다.
  데모를 켜기 전에 시작한 진짜 작업을 멈출 수단이 사라지면 안 된다.
- BLE 확인 응답·음성 BLE 폴백도 막는다. HTTP만 막으면 BLE로 붙은 실기기가
  실제로 움직인다. 거절은 물리 동작이 아니므로 그대로 보낸다.
- `ExecutionStatus.isDemo` — 실행 모드를 **시작 순간에 job에 새긴다.** 화면이
  매번 전역 토글을 보면 진행 중 토글 한 번으로 표시가 뒤집힌다.
- 실행 중에는 토글을 잠근다. 모드를 갈아타면 실행 경로가 통째로 바뀌어 진행
  중이던 작업이 추적을 잃는다 — 평가가 지적한 "진행 중 토글 변경" 문제를
  근본에서 없앤다.
- 데모 센서 프레임에 `sequence_id` 추가. 없으면 4초 뒤 도착한 데모 값이 그 사이
  시작된 **진짜 실행**의 진행을 덮어썼다(가드는 있었는데 재료가 없어 통과했다).

곁가지: 데모 설정 읽기 실패가 이제 실행 시작 경로에 있어서, 못 읽으면 실행
자체가 깨졌다. 감쌌다 — 설정 하나 못 읽은 것이 조작을 막으면 안 된다.

## R3 · 동기화가 다른 폰의 가전을 지우지 않는다 (`792958a`)

'키오스크와 다시 동기화'가 **"폰이 원본"** 이라는 가정 위에 있었다. 서버에
있는데 이 폰에 없는 커스텀 가전을 전부 유령으로 보고 지웠다.

    폰 A에 선풍기, 폰 B에 가습기 등록 → A에서 동기화
    → **B의 가습기와 그 노드 등록이 사라진다**

서버 목록에만 있다는 것은 "지워도 된다"가 아니라 **"이 폰이 아직 못 받았다"**
는 뜻이다. 두 방향을 갈랐다.

- **올리기**: 이 폰의 가전을 서버에 upsert (종전과 같음).
- **내려받기**: 서버에만 있는 가전은 지우지 않고 이 폰 목록에 더한다.
  로컬 사진 경로는 그 폰의 데이터이므로 덮지 않는다.
- **지우기**: 사용자가 이 폰에서 지운 것만. 전송이 실패하면 기기에 남겨
  두었다가(`pending_appliance_deletes`) 다음 동기화가 다시 보내고, **성공한
  것만** 대기열에서 뺀다. 아직 못 지운 가전은 도로 내려받지 않는다.

무차별 삭제는 사실 "삭제 전송 실패"의 복구 수단이었다. 그래서 그것만 걷어내면
복구가 사라진다 — tombstone이 그 자리를 대신한다.

- 목록 조회 실패를 빈 목록과 구분(`null`). 뭉개면 다른 폰의 가전을 "없는 것"
  으로 취급해 판단이 통째로 뒤집힌다.
- 동기화 버튼 조건을 "커스텀 가전 존재"에서 "밀린 삭제 포함"으로. **마지막
  가전을 지우다 실패하면 버튼까지 사라져** 복구할 길이 없었다.
- 결과 안내를 올림·새로 받음·삭제 반영으로 나눈다. "실패"만 알리면 사용자가
  무엇을 다시 해야 하는지 알 수 없다.

**남은 것**: 같은 id의 upsert/delete 순서 보존, 동시 편집 충돌 규칙.

## R4 · 알림함의 못 불러온 것과 없는 것 (`ef978aa`)

목록을 한 번도 못 받은 화면이 "아직 알림이 없어요"라고 단언했다. 이 알림함이
다루는 것은 실행 실패·위험 신호음·안부 신호다 — 통신이 끊겨 못 본 것을
"아무 일 없다"로 읽게 두면 이 기능이 존재하는 이유가 무너진다.

- `CareInboxStatus`(loading·ready·failed·unconfigured) + 마지막 **성공** 확인
  시각. 서버 주소가 없는 것은 실패가 아니라 물어볼 곳이 없는 것이다.
- 실패해도 보던 목록은 유지하고 "새 알림을 확인하지 못했어요 · 다시 불러오기"를
  얹는다. 빈 목록에서도 당겨서 새로고침이 되게 스크롤을 남긴다.
- 목록 끝(또는 빈 상태)에 **"HH:MM 기준"** — 언제 확인한 것인지가 곧 이 화면을
  얼마나 믿어도 되는지다.
- 겹쳐 부른 새로고침이 **진행 중인 요청의 완료를 기다린다.** 전에는 즉시
  반환해서, 화면 진입 시 읽음 처리가 아직 비어 있는 목록 위에서 돌았다.
- 서버 이벤트 id가 되감기면 읽음 기준도 되감는다. DB를 새로 만들면 id가 1부터
  다시 시작하는데, 예전 `lastSeenId`(예: 50)를 두면 **새 알림 전부가 영구히
  읽음**이 되어 배지가 영영 안 뜬다.

## R5 · 추천 근거에서 "최근"을 뺀다 (`2e13adf`)

패턴 감지에는 기간 창이 없다. 시간대만 맞으면 그 목적의 **전체 이력**을 센다
(`rpi/intent/patterns.py`). 그런데 어제 넣은 문구는 "최근 저녁 시간에 4번
하셨어요"였다 — 화면이 집계 범위를 실제보다 좁게 말한 것이고, 안부 신호의
14일 창과도 혼동된다.

폰·키오스크 공통으로 **"저녁 시간에 4번 하셨어요."** 로. 어느 시간대인지는
남긴다(그건 실제 집계 기준이다). 기간 창이 제품 규칙으로 필요해지면 서버
집계에 넣고 응답에 기간을 실어 보낸 뒤 문구를 되살린다 — 기간 선택은 초기
사용자 기록을 보고 정할 일이라 지금 지어내지 않는다.
