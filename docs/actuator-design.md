# 액추에이터(구동부) 설계 확정 사항

> **현재 기준(2026-10-14) — 이 문서의 9/27 이전 내용보다 우선한다.**
> - 모션 MCU는 **ESP32**(`firmware-motion-corexy/`, 팀원 Touch Bridge CoreXY 펌웨어를 옮김), XY는 FIT0482 ×2 + JMOD-MOTOR-1.
> - Z 누름은 **솔레노이드**(GPIO → MOSFET, 시간 기반 누름)다. 아래 §1의 "FIT0482 ×3, 세 번째 모터를 Z에 배정"과 §1 끝의 "PID는 Arduino가 담당"은 **9/27 당시 기록**이며 폐기했다.
> - 실물: 시험대에서 모터 축 구동·엔코더·정지 확인까지(10/12~14). 벨트·캐리지 이동·솔레노이드 실제 누름은 제출 전 수행([제출 전 검증 과업](제출전-검증-과업.md) §0).
> - 보드 역할·결정 이력은 [하드웨어 방향 확정](하드웨어-방향-확정-2026-09-30.md)과 [재사용 경계](reuse-boundary.md)가 기준이다.
>
> 아래 본문(옛 머리말 포함)은 기구 방식(CoreXY)과 프레임 요구의 근거로 남긴 당시 기록이다.
>
> (당시 머리말) 하드웨어 설명이 여러 문서에 흩어져 있고 옛 구조(피니언/렉 레일) 설명도 섞여 있어서,
> 최종 확정된 구동부 방식만 이 문서에 모아 정리한다.

## 1. 기구 방식 — CoreXY

### 2026-09-27 사용자 정정 — 모터·드라이버 기준 (당시 기록 — Z는 10/10 솔레노이드로 바뀜)

사용자가 추가 제공한 전압·속도·전류·엔코더·외형 정보는 [FIT0482 제공 사양 기록](FIT0482-사용자제공-사양.md)에 정리했다. 엔코더 계수 기준과 스톨 전류는 여전히 미확인이다.

- **FIT0482 ×3 / JMOD-MOTOR-1 ×2**를 개발 구성 기준으로 사용한다. CoreXY A/B에 모터 2개, 독립 Z 누름에 같은 모델 1개를 배정한다.
- 이전 SwitchBot 분리 모터 재사용 계획은 이번 사용자 정정으로 대체한다.
- 드라이버 1장의 두 채널은 A/B, 다른 1장의 한 채널은 Z에 배정하는 SW 설계안이다. 실제 채널·핀 배선과 남은 채널 사용은 미확정이다.
- 아래의 기존 FIT0482 사양 기록은 Z에도 같은 모델 기준으로 참조한다. 제품 변형·실물 라벨, 실제 공급전압·전류, 엔코더 카운트 기준은 데이터시트·실측으로 대조해야 한다.
- **Z 회전량을 누름 거리로 바꾸는 기구**(리드스크루·캠·링크 등), 추가 감속비, 복귀/끝점 센서, 극성·누름 제한은 아직 미확정이다. 모델이 같아도 XY의 거리 환산을 Z에 그대로 쓰지 않는다.
- 구성 기준 확인은 수령·배선·실제 구동 검증 완료를 의미하지 않는다. 현재 CoreXY 화면은 예상 모션이며 모터 전류·엔코더·PID 동역학을 재현하지 않는다.

기존 피니언/렉 레일 구조를 버리고 CoreXY 갠트리 방식으로 확정.

> **(2026-10-10 팀원 확인)** 이 CoreXY 갠트리와 ESP32 모션 펌웨어는 팀원의 Touch Bridge와 **같은 것**이다(공유,
> [재사용 경계](reuse-boundary.md)). SimpleLay가 따로 설계한 기구가 아니다.

**버린 이유** (피니언/렉 레일의 문제):
- 레일 작동에 필요한 공간이 실제 제어 공간의 4배 이상
- Y축 모터가 Z축 모터+레일 무게까지 부담해서 속도가 점점 느려짐
- Z축 터치 시 모터가 튕기는 현상

**CoreXY 구성 요소**:
- 리니어 가이드 레일 × 3 (3D 자체 제작)
- 베어링(또는 아이들러 풀리) × 8 — 베어링 내장형 풀리를 구하지 못해, 베어링 겉에 고정하는 방식으로 대체
- 하단 구동 모터 2개 — **FIT0482 확보 완료** (6 V · 310 RPM · 50:1 · **엔코더 내장**)
- 모터 드라이버 — **JMOD-MOTOR-1 확보 완료** (2채널이라 A·B 두 모터를 1장으로 커버)
- 타이밍 벨트 (2GT 6mm)

> **엔코더 내장은 계획에 없던 이점이다.** 모터가 스스로 회전량을 돌려주므로 PID가
> 추측이 아니라 실제 위치로 닫힌다. 지금 폐루프는 "누르고 → 전류·음향으로 확인"인데,
> 여기에 **이동이 의도대로 됐는지**를 보는 채널이 하나 더 생긴다 — 누름 검증(기존)과
> 위치 검증(신규)이 분리되어, 실패했을 때 "못 갔다"와 "갔는데 안 눌렸다"를 구분할 수
> 있다. 보정 재시도의 근거가 그만큼 정확해진다.
>
> 전원 설계·정격은 [전력버짓.md](전력버짓.md) 참고. **6 V 모터에 12 V 입력**이라
> 강압 또는 듀티 제한이 필요하다 — 미해결 항목으로 그 문서에 정리해뒀다.

**운동 방정식** (모터 A, B의 이동량으로 X/Y를 유도):
```
ΔX = ½(ΔA + ΔB)
ΔY = ½(ΔA - ΔB)
ΔA = ΔX + ΔY
ΔB = ΔX - ΔY
```
두 모터가 항상 함께 구동되는 구조라, 한쪽만 움직여서 대각선 이동을 만든다. 모터 PID
제어는 RPi4가 아니라 별도 마이크로컨트롤러(Arduino, 커스텀 펌웨어)가 담당한다 — RPi4는
일반 리눅스라 실시간성이 부족해서, 두 모터의 타이밍이 어긋나면 대각선 이동이 틀어질
위험이 있기 때문. (자세한 보드 역할 분담은 `개발현황.md` 참고.)
(2026-10-14: 이 MCU는 Arduino가 아니라 **ESP32**로 정해졌다 — 위 머리말 현재 기준.)

## 2. 프레임 설계 — 가운데 개방형 + 홈 파킹 (신규 확정)

**문제 제기**: 액추에이터 프레임이 가전 조작 패널 전체를 덮으면, 자동 조작이 필요 없을 때
사용자가 손으로 직접 버튼을 누르고 싶어도 프레임에 가로막힌다.

**확정한 해결 방식**:
1. **가운데 개방형 프레임** — 프레임 중앙을 비워서, 사용자가 손을 넣어 패널에 직접 접근할
   수 있게 만든다.
2. **가전 운전 중 정지 버튼 위 대기** — 2026-09-27 사용자 요구. 시작 버튼까지 입력한 뒤
   Z를 복귀시키고, 캐리지를 해당 가전의 정지 버튼 좌표로 옮겨 대기한다. 대기 중에는
   버튼을 누르지 않는다. 여기서 '실행 중'은 버튼 시퀀스 입력 중이 아니라 가전 운전 중을
   뜻한다. 시퀀스 입력 중에는 다른 버튼을 눌러야 하므로 항상 정지 좌표에 있을 수 없다.
3. **가전 운전 종료 확인 후 가장자리 보관** — 버튼 입력 완료만으로 파킹하지 않는다.
   가전 종료/정지를 확인한 뒤 Z 복귀 확인 → 상단 또는 하단 보관 위치로 이동해 사용자의
   수동 조작 공간을 확보한다. 좌표 기준을 잡는 원점(home)과 보관 위치(park)는 구분한다.

### 정지 버튼 매핑·운전 대기 요구 (2026-09-27, 구현 전)

- 매핑 과정에서 일반 버튼 외에 **가전 정지 버튼을 명시적으로 지정·보정**한다. 이름에
  '정지'가 들어간다는 이유만으로 자동 선정하지 않는다. 가전별 정지 동작(1회 누름,
  길게 누름, 일시정지/취소 차이)도 실제 확인한다.
- 상단/하단 보관 좌표와 Z 복귀 위치를 별도로 설정한다. 위치·이동 범위·정지 버튼 접근을
  검증하기 전에는 이 자동 운전 대기 기능을 준비 완료로 표시하지 않는다.
- 가전 정지 요청은 일반 실행보다 우선한다. 정지 버튼 위에서 대기 중이면 Z 누름을
  요청하고, 이후 **정지 버튼 누름 확인과 가전 정지 확인을 별도로 기록**한다. 이동 중이나
  다른 버튼 위에서 요청되면 현재 위치·Z 복귀·구동 상태를 확인하는 별도 중단 절차가 필요하다.
- **가전 정지**(정지 버튼을 누르기 위해 모터 구동 필요)와 **구동부 비상정지**(모터 차단)는
  서로 다른 동작이다. 구동부 비상정지/고장 상태에서 정지 버튼을 누르려고 자동 재가동하지 않는다.
  앱의 기존 `/stop`이 가전 정지까지 수행한다고 가정하지 않는다.
- 운전 중에는 정지 버튼 위 대기 위치를 유지한다. 운전 종료 여부가 불명확하거나 통신이
  끊기면 완료로 간주해 파킹하지 않는다. 독립 정지 회로와 수동 접근은 HW와 함께 결정한다.
- 물리 확인 전에는 '즉시 정지 보장'이라고 표시하지 않는다. 요청→누름→가전 정지까지의
  지연, Z 걸림·복귀 실패, 시퀀스 도중 정지, 대기 중 정지, 운전 종료 후 파킹을 검증한다.
- 현재 통신 시뮬레이터에는 이 운전 대기·정지 버튼 누름·보관 상태 흐름이 **아직 없다**.
  기존 7개 통신 시나리오 통과를 이 요구의 검증으로 간주하지 않는다.

**아직 확인 필요한 것 (예솔님 검토 필요)**:
- [ ] 홈 포지션을 상단/하단 중 어느 쪽으로 할지 — 실제 버튼맵 배치를 보고 버튼이 적게
      몰린 가장자리로 정한다 (시작/취소 같은 자주 쓰는 버튼이 몰린 쪽은 피한다).
- [ ] 프레임 강성 — 가운데를 개방하면 벨트 구동 캐리지를 지지하는 뼈대가 줄어들어서
      진동/휨에 더 취약해질 수 있다. 폐루프 재시도(검증 실패 시 좌표 보정 후 재시도)가
      어느 정도 오차를 흡수하긴 하지만, 어느 수준까지 흔들려도 되는지는 실측 필요.
- [ ] Z축(당시 FIT0482 기준, 현재는 솔레노이드)의 누름 기구도 홈 복귀 시 패널 위에서
      완전히 비켜나는지 확인 — X/Y 캐리지만 파킹되고 Z축 몸체가 남아있으면 여전히 손이
      안 들어갈 수 있다.
