# Touch Bridge 안전 계약 → SimpleLay 적용 보고 (2026-10-15, 보고서 — 코드 수정 전)

같은 팀의 한이음 프로젝트 **Touch Bridge**(시각장애인용 가전 입력 대행)의 안전 계약 논문이 ACK 2026 포스터로 게재 확정됐다
(게재가, 심사 8점 — "안전 계약 구조화는 우수하나, 물리적 제어를 다루면서 실물 하드웨어 검증이 없다").
SimpleLay와 갠트리·모터·모션 펌웨어 제어 핵심을 같이 쓰므로, 세 계약을 SimpleLay 코드에 대 보고 두 프로젝트 공통의 첫 실물 정지 시험을 설계했다.

- 방법: SimpleLay 코드 읽기 + 저장소 밖 재현 스크립트 1회(실제 서비스 객체에 가짜 실행기). Touch Bridge 쪽은 문서·작업 기록·블로그를 읽기만 했다.
- **이 문서의 '빠짐·일부만' 판정은 코드·재현 기준이다. 실물로 확인한 정지는 모터 축 시험대(벨트·솔레노이드 없음)의 이동 중·누름 중 단일 정지뿐이다**
  ([10/13](devlog/devlog_2026-10-13-desktop-board.md) 10회, [10/14](devlog/devlog_2026-10-14-desktop-board.md)). 다단계 시퀀스 중간 정지·루틴 정지·Wi-Fi 끊김·보내기 전 정지는 **실물 미검증**이다.
- 코드 수정은 이 보고를 확인받은 뒤에 한다.

## 0. 요약

| 계약 | SimpleLay 상태 | 가장 큰 빈칸 |
|---|---|---|
| ① 확인 기반 피드백 | 정지 단계(보냄·모션 보드 응답·멈춤 확인)와 엄격한 짝짓기는 **이미 지킴** | 승인·루틴 경로에서 링크가 끊기면 **결과 안내 없이 조용히 끝남**(G1). 일부 화면 문구가 확인 없이 '멈췄어요/눌림 확인'을 씀(G6) |
| ② 정지 전파 | 정지 우선 경로·MCU 큐 비우기·정지 뒤 재홈/재누름 금지는 **이미 지킴**. 토큰 대신 **공유 플래그를 매번 다시 읽는 구조** | **접수 뒤·보내기 전 정지가 사라져 전 시퀀스가 실행되고 '성공'**(G2, 재현). 루틴 구간 사이 정지가 다음 구간으로 이어짐(G3) |
| ③ 보수적 해석 | 규칙은 전체 일치만(이미 지킴), 승인 카드가 많은 경로를 대신 막음 | **텍스트·홈 음성의 "멈춰"·"그만"이 전자레인지 '취소' 버튼 누름으로 해석됨**(G7) — 정지어 우선 판정이 서버에 없다 |

논문의 결함 유형 (a)누름 중 정지·(b)버튼 사이 정지·(c)전송 시작 전 정지·(d)실행 중 끊김이 SimpleLay에서도 **(a)는 실물로 막힘을 확인, (b)(c)(d)는 구조적 빈칸이 있음**(아래 G2·G3·G1·G5).

## 2. 빈칸 — 안전 영향 순 (수리 후보, 아직 고치지 않음)

| # | 영향 | 논문 유형 | 내용 | 수리 방향(제안) |
|---|---|---|---|---|
| **G1** | 높음 | (d) + 거짓 성공 | 승인 카드·루틴·시나리오의 물리 단계에서 링크가 끊기면 예외가 로그로만 남고 **결과·이력·보호자 알림 없이 끝난다**. `/status`에는 이 job 번호에 **직전 실행의 결과**가 붙는다(`service_commands.py:371-377, 502-508`). 시연의 '첫 조리 승인'이 이 경로다. **재현함** | 물리 단계 예외를 '수신 불명·미확인' 결과로 바꿔 기록·안내·보호자 알림까지 보낸다 |
| **G2** | 높음 | (c) | 접수 뒤·보내기 전에 온 정지가 사라진다 — RPi5는 abort만 보내고 기록만 세우고, RPi4는 아직 쉬는 중이라 abort를 버리며, 뒤이어 온 실행 요청을 **전부 실행하고 '성공'**. **재현함**(정지 뒤 버튼 3개 전송, succeeded) | RPi5가 실행 요청을 보내기 직전에 정지 기록을 확인하고, RPi4는 실행 시작 전에 받은 abort를 다음 실행 요청과 짝지어 거절 |
| **G3** | 중상 | (b) | 루틴 구간 사이 정지가 다음 구간으로 이어질 수 있다 — `/stop`이 루틴 취소를 맨 마지막에 세우고(`router.py:978-986`), 루틴은 대기 뒤 다시 보지 않으며(`runner.py:446-455`), 다음 실행 시작이 정지 기록을 지운다(`service.py:688-692`) | `/stop`에서 루틴 취소를 먼저, 대기 뒤 재확인, 실행 시작 리셋이 루틴 정지를 지우지 않게 |
| **G4** | 중 | (a) | 어댑터가 정지 확인 → 동작 잠금 대기 → 이동 전송 사이에 정지를 다시 보지 않는다. MCU는 쉬는 중 정지 뒤 원점을 유지하므로 그 이동을 실행할 수 있다(최대 워치독 2 s) — 사용자에겐 이미 '멈춤 확인' 보고 뒤. **추정, 재현 안 함** | 잠금을 얻은 뒤 정지 재확인. 펌웨어: 쉬는 중 정지에도 이동 허가를 끊는 방안 검토(Touch Bridge v2는 정지마다 원점 폐기) |
| G5 | 중 | (d) 변형 | Wi-Fi가 조용히 끊기면 RPi4가 남은 버튼을 계속 누를 수 있고(연결 감지까지 약 11 s 추정), RPi5는 '완료하지 못했어요'로 단정. **추정** | 실행 중 RPi5→RPi4 생존 신호, 끊기면 RPi4가 스스로 정지. RPi5 문구는 '미확인' |
| G6 | 중 | ① | 정지 결과가 사용자에게 가지 않는 화면(폰 실행 중 정지 결과, 키오스크 정지 실패, 폰 수동 조작 확인 문구) | 키오스크 계획과 묶어서 |
| G7 | 중 | ③ | 텍스트·홈 음성 "멈춰"가 '취소' 버튼 누름. 쉬는 중이면 실제로 누른다 | 서버 해석 맨 앞에 정지어 판정 → `/stop` 의미로. 고정 시험 수정 |
| G8 | 낮음~중 | ② | 쉬는 중 끊김에 MCU 원점 유지, RPi4 재시작 뒤 그대로 믿음(추정) | 재시작 뒤 원점 재확인 요구 검토 |
| G9 | 낮음 | ② | RPi4 hold 해제 대기 중 abort 처리 지연(추정 최대 3 s) | 읽기 루프를 막지 않게 |
| G10 | 기록 | ② | hold 중 정지는 이동·누름을 일으킨다(가전 정지 버튼). 논문의 '정지 뒤 복구 이동 없음'과 다름 | 설계 차이로 문서에 명시(가전을 멈추는 동작이라 의도된 것) |
| **G11** | 중상 | ① | **엔코더가 죽어도 '멈춤 확인(verified)'이 뜬다** — 10/13 발견 6: 엔코더 선 접촉 불량으로 0만 읽는 상태에서도 "멈춘 것을 확인"이 떴다. '값이 안 변함'만으로 멈춤을 판정하기 때문(하드웨어 검토 10/15 지적) | 정지 전 이동 구간에서 엔코더가 실제로 변했는지(살아 있음)를 확인한 경우에만 `verified`, 아니면 `mcu_ack`에 머문다. 엔코더 단선 감지 시 '확인 불가' |

**수리 순서 제안:** G2·G1(시연 경로) → G3 → G7 → G4·G5 → 나머지. 각 수리는 **고치기 전 재현 시험이 실패하는 것을 먼저 확인**한다.

## 3. 두 프로젝트 공통 첫 실물 정지 시험 (PS-1)

논문 결론의 향후 과제("실제 제어기에 같은 정지 시나리오를 주입하여 대기 명령의 폐기 여부와 모터 정지까지의 응답 시간을 측정")와 심사평의 '실물 미검증'에 바로 답하는 시험이다.
**같은 기계·같은 판정 기준, 전송 경로는 각자.**

### 3-1. 전제와 차이

| 항목 | SimpleLay | Touch Bridge |
|---|---|---|
| 전송 | 폰·키오스크 → RPi5(HTTP) → RPi4(Wi-Fi) → USB 시리얼, 줄 단위 JSON | 폰 → BLE → ESP32, 규약 v2 JSON(또는 레거시 G-code) |
| 펌웨어·보드 | `firmware-motion-corexy`(원작 제어 핵심 + SimpleLay 규약, BLE·v2 제거)를 올린 **SimpleLay용 ESP32** | 원작 펌웨어 v3를 올린 **Touch Bridge용 ESP32** — 갠트리·모터는 같은 1대이고 **ESP32만 프로젝트별로 다르다**(사용자 확인 10/15). 펌웨어를 바꿔 올릴 필요 없이 **보드만 바꿔 끼워** 같은 기계에서 두 시험을 한다 |
| 정지 응답 | 진행 중 명령 `{"id":n,"ok":false,"error":"stopped"}` + 정지 `{"id":s,"ok":true}` | 같은 commandId의 `STOPPED`(규약 v2: 1초 안) |
| 정지 뒤 원점 | 동작 중일 때만 버림 | 규약 v2: 언제나 버림 |
| 끊김 | 호스트 워치독 2 s(동작 중이면 원점 버림) | 규약 v2: homed=false(펌웨어 구현 여부 확인 필요) |

**안전 준비:** 벨트 장착 전에는 모터 축만(1단계), 장착 뒤 캐리지·솔레노이드(2단계). 실제 가전 대신 **골판지 더미 패널**. 손이 닿는 곳에 전원 차단(물리 E-STOP 또는 전원 스위치) — 소프트웨어 정지가 실패하면 바로 끊는다. 한 사람은 기록, 한 사람은 차단 담당.

### 3-2. 기록 장치

- **호스트 쪽 전송 기록:** SimpleLay는 RPi4 어댑터가 시리얼로 쓴 줄과 받은 줄을 시각과 함께 남긴다(세션 기록 `SIMPLELAY_SESSION_LOG_PATH` + 어댑터 송수신 기록). Touch Bridge는 앱의 BLE 쓰기 기록(논문의 가상 전송 계층 자리에 실제 전송 기록).
- **제어기 쪽 수신:** MCU가 정지 뒤 받아들인 동작 명령 수 — 정지 뒤 이동·누름 요청에 대한 MCU 응답(`ok`/거절)으로 센다. 가능하면 펌웨어 시험 빌드에 '받은 명령 카운터'를 상태에 싣는다(시험 전용, 결정 필요).
- **엔코더:** 위치 사건(a·b 카운트)을 10 Hz 이상으로 기록. **멈춤 = 0.1 s 간격 두 번 연속 a·b 변화 없음**(SimpleLay `verified`와 같은 정의).
- **영상:** 폰 카메라 고속 촬영(가능하면 240 fps)으로 갠트리와 화면을 한 프레임에. 사람이 정지 뒤 움직임 유무를 판정하는 근거.
- **시계:** 구간 시간은 **같은 기기 시계** 안에서만 잰다(RPi4: 정지 전송~MCU 응답~엔코더 정지). 폰·RPi5가 끼는 구간은 SimpleLay 시계 기준점(`clock_ref`)으로 환산하고 환산했다고 적는다.

### 3-3. 시각 정의

| 기호 | 뜻 | 측정 기기 |
|---|---|---|
| t0 | 사용자가 정지를 누름(앱·키오스크 기록) | 폰·키오스크 |
| t1 | 정지가 제어기로 나감(시리얼 쓰기 / BLE 쓰기) | RPi4 / 폰 |
| t2 | 제어기 정지 응답 받음 | RPi4 / 폰 |
| t3 | 엔코더 멈춤 첫 확인 시각 | RPi4(엔코더 사건) |
| t4 | 화면·음성에 결과 표시 | 폰·키오스크 |

보고 값: **응답 t2−t1**, **정지 시간 t3−t1**, **전체 t4−t0**(환산 표시), **정지 뒤 호스트 전송 줄 수**, **정지 뒤 MCU가 받아들인 동작 수**, **사람 관찰 정지 뒤 움직임**.

### 3-4. 시나리오

| # | 시나리오 | 논문 대응 | 주입 방법 | 반복 | 비고 |
|---|---|---|---|---|---|
| S1 | 이동 중 정지 | — | 버튼 3개 시퀀스, 첫 이동 중간 | 10 | SimpleLay 모터 축은 10/13 확인 — 캐리지로 다시 |
| S2 | 누름 중 정지 | (a) | 솔레노이드 켜진 동안(2단계) | 10 | 1단계는 누름 신호만 |
| S3 | 버튼 사이 대기 중 정지 | (b) | 첫 버튼 끝난 직후 대기 구간 | 10 | 다음 버튼 이동·누름 0이어야 |
| S4 | 전송 시작 전 정지 | (c) | 승인 직후 첫 명령이 나가기 전(SimpleLay: 승인 → 0.2 s 안 정지) | 10 | **SimpleLay 현재 코드는 실패 예상(G2)** — 수리 전 기준선으로 기록 |
| S5 | 실행 중 연결 끊김(정지 없음) | (d) | SimpleLay: RPi4 Wi-Fi 끄기 / USB 뽑기, Touch Bridge: BLE 끊기 | 5 | 제어기가 워치독 안에 멈추는지, 화면이 '미확인/끊김'인지 |
| S6 | 루틴 구간 사이 정지 | (b) 변형 | SimpleLay 전용: 두 장치 루틴 첫 구간 끝 직후 | 5 | **실패 예상(G3)** |
| S7 | 쉬는 중 정지 뒤 새 명령 | — | 정지 → 바로 이동 명령 | 5 | 원점 처리 차이(G4·G8) 관찰 |

**하드웨어 검토(10/15)로 더한 시나리오:**

| # | 시나리오 | 왜 |
|---|---|---|
| S0 | 보드 교체 직후 점검 — 축마다 방향, 10 mm 이동 카운트(보드별 환산 계수), 부팅·정지 직후 브레이크/풀림(손으로) | 핀·엔코더 배율·STBY 처리가 펌웨어마다 다를 수 있음 |
| S8 | **물리 E-STOP(전원 차단) vs 소프트웨어 정지의 정지 거리** | TB6612는 전원이 살아 있으면 쇼트 브레이크, 끊으면 브레이크 없이 미끄러질 수 있어 **최후 수단이 더 늦게 멈출 수 있음**(추정) |
| S9 | 원점 복귀(스톨 홈) 중 정지 | — |
| S10 | 큐가 찬 상태에서 정지 → 큐가 비워지는지(Touch Bridge 32칸) | 큐 크기 차이 |
| S11 | 연속 정지, 정지 직후 다시 실행 | — |

**측정 보강:** 엔코더 A/B를 **로직 분석기**에 분기해 두 보드에 같은 장비로(시험 대상 보드가 스스로 '멈춤'을 보고하는 것에 의존하지 않음 — G11). 정지를 받는 순간 ESP32가 **LED/GPIO 토글** → 240 fps 영상 한 프레임에 LED와 캐리지를 함께 찍어 같은 시계로 비교. 회차마다 **모터 전원 전압** 기록, 두 보드는 같은 날 같은 전원으로 연달아. 두 펌웨어의 PID·가속도 값 표를 결과에 같이 싣는다.

**합격 기준은 시간보다 정지 거리(mm)를 우선:** 예 — 정지 뒤 캐리지 이동 < 버튼 최소 간격의 절반, 정지 뒤 솔레노이드 작동 0회. 시간 기준은 캐리지를 단 상태 10회의 최대값에 여유를 두어 확정(규약 v2의 1 s는 위쪽 한계로만).

**순서:** 1단계(모터 축) S0·S1·S3·S4·S5·S7 → 벨트·솔레노이드 장착 뒤 2단계 전체 + S8~S11.

**솔레노이드 단 뒤 먼저 볼 것(공통 기구 — 한 번 재면 두 프로젝트 공통 사실):**
누름 유지 중 정지·전원 차단·ESP32 리셋(플래시·브라운아웃) 때 플런저가 풀리는 시간과 최대 켜짐 시간 — 최대 켜짐 시간이 가전의 '길게 누름' 기준보다 짧아야 한다. HW 확인: MOSFET 게이트 **풀다운 저항**, **플라이백 다이오드**, 솔레노이드가 **스프링 복귀형**인지, 솔레노이드 돌입 때 로직 전압 최소값(브라운아웃).
세로 설치 시 쉬는 중 출력 해제로 캐리지가 **중력으로 처지는지**도 실측(원점 유지 정책 G8과 연결). 각 시나리오는 **같은 펌웨어·같은 커밋**으로 묶어 실행하고 SHA를 적는다.

### 3-5. 기록 양식 (한 줄 = 한 회)

| 날짜·시각 | 프로젝트 | 커밋/펌웨어 | 시나리오·회차 | 주입 시점 | t2−t1(ms) | t3−t1(ms) | t4−t0(ms, 환산) | 정지 뒤 호스트 전송 줄 | 정지 뒤 MCU 수락 동작 | 영상상 정지 뒤 움직임 | 화면 문구 | 단계(sent/mcu_ack/verified) | 원점 상태 | 비고 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|

원본 기록(시리얼·BLE·엔코더·영상)은 저장소 밖에 두고 파일 이름만 적는다. 기존 [실측 기록표](실측-기록표.md)에 PS-1 절로 옮긴다.

### 3-6. 합격 기준 (값은 실측 후 확정)

| 항목 | 기준 |
|---|---|
| 정지 뒤 호스트 전송 동작 줄 | **0** (모든 회) — 계약 정의 |
| 정지 뒤 MCU가 받아들인 동작 | **0** (모든 회) — 계약 정의 |
| 영상상 정지 뒤 새 움직임 | **0회** (감속 중 관성 이동은 별도 기록) |
| 정지 응답 t2−t1 | 중앙값 ≤ [실측 후 확정] ms, 최대 ≤ [실측 후 확정] ms (Touch Bridge 규약 v2 상한 1 s 참고) |
| 정지 시간 t3−t1 | 중앙값 ≤ [실측 후 확정] ms, 최대 ≤ [실측 후 확정] ms |
| 화면 문구 | 실제 단계와 **100% 일치**(보냄을 멈춤으로 말한 회 0) |
| 끊김(S5) | 제어기 스스로 멈춤 ≤ [실측 후 확정] s(워치독 2 s 설계값), 화면은 '미확인/끊김' — '완료·성공' 0회 |

**보고 방식:** 표는 회차 전부. 실패 회는 숨기지 않고 원인(G 번호)과 함께. "앱 쪽 0줄"과 "제어기 쪽 0줄"과 "영상상 정지"를 따로 말한다 — 논문이 구분한 것과 같다.

### 3-7. 논문·포스터에 쓸 때

**SimpleLay 실측 인용 범위(하드웨어 검토 10/15):** "같은 갠트리·모터·드라이버·엔코더를 쓰는 연계 프로젝트에서, 다른 ESP32·펌웨어로 모터 축 시험대(벨트·캐리지·솔레노이드 미장착)에서 이동 중 정지 10회 — 모션 보드 응답 6~18 ms, 정지 명령 → 엔코더 멈춤 확인 중앙값 약 160 ms"까지. 단서: 개발자 조그 경로·5 mm 이동 시작 88 ms 뒤 정지·무부하, 10/14은 시험대 빌드, 엔코더 판정은 단선 시 거짓 확인 가능(G11).
**쓰면 안 되는 말:** "Touch Bridge 정지가 실물 검증됨", "정지 후 0줄이 실물에서도 확인됨", "심사평 지적 해소", 조건 없는 "정지 응답 약 10 ms".


- 진행: 같은 갠트리에 **SimpleLay ESP32 → Touch Bridge ESP32 순서로 보드만 바꿔 끼우고** 같은 시나리오를 돈다. 보드를 바꿀 때마다 배선·엔코더 방향 확인(S0: 원점·짧은 이동 1회)부터.
- Touch Bridge 포스터에 쓰려면 **Touch Bridge 보드·펌웨어·앱 경로(BLE)로 잰 회차만** Touch Bridge 결과로 말할 수 있다. SimpleLay 경로 결과는 '같은 기계에서 다른 전송 경로' 결과로 따로 적는다.
- 포스터에 넣을 수 있는 최소 결과: S1·S3·S4를 Touch Bridge 경로로 각 10회 → 정지 뒤 수락 0·정지 시간 분포. 발표일 전에 못 하면 "계획"으로만 적는다.
