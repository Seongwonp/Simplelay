# U1-a — 명령·결과·승인 계약 설계 (2026-09-22, 구현 전)

[ThinQ 연동 검토](ThinQ-연동-검토-2026-09-22.md) §7·§8 기준. **코드는 바꾸지 않았다.** 아래 §5의 충돌은
구현 전에 팀이 정한다. 현재 코드 위치는 대조용이며, 인용한 동작은 2026-09-22 `39a9b9f` 기준이다.

## 1. 세 축 (독립)

| 축 | 값 | 누가 정하나 |
|---|---|---|
| 실행 환경 `ExecutionMode` | real / mock / unknown (기존 그대로, cloud 추가 없음) | 실행 대상(어댑터)이 스스로 선언 |
| 제어 경로 `ControlRoute` (신규) | physical / thinq | 명령을 만들 때 대상 가전 등록 정보로 확정 |
| 확인 수준 `Confirmation` (신규) | accepted / state_confirmed / operation_confirmed / unconfirmed | 어댑터가 결과에 기록. 실행 환경과 무관 |

- 모의 ThinQ 서버는 `mock` + `state_confirmed`가 가능하고, 실제 클라우드도 `real` + `unconfirmed`가
  가능하다. 상태 변경 확인 여부로 실행 환경을 정하지 않는다(§8).
- 물리 경로의 확인 수준: L1 통과 = `state_confirmed`(눌림을 센서로 확인), L3 통과 = `operation_confirmed`,
  L3 미판정 = 그대로 `state_confirmed`. 기존 `ExecutionResult`에서 계산해 채운다.

## 2. 명령 계약

```
Command (frozen)
  target_id        가전 ID (기존 appliance_id)
  route            ControlRoute
  action           동작 이름. physical: 버튼 라벨 순서를 buttons에 둠 / thinq: 프로필 동작(예: power, fan_speed)
  args             {이름: 값}. physical은 빈 dict. 값은 str|int|float|bool만
  buttons          physical만. 기존 tuple[str, ...] 그대로
  fingerprint      route·target_id·action·정렬한 args·buttons를 정규 JSON으로 만든 sha256
```

- physical은 **기존 `execute(buttons)` 경로를 그대로** 쓴다. Command는 그 위를 감싸는 기록·승인용
  봉투다. 컨트롤러 프로토콜은 바꾸지 않는다.
- thinq는 새 프로토콜 `CommandController.execute_command(cmd) -> CommandResult`. `execute(buttons)`에
  동작명을 문자열로 밀어 넣지 않는다(§7).
- 상한: physical은 기존 `_validate_resolved_sequence`(개수·바이트). thinq는 동작 1개/명령, args 바이트
  상한, 허용 인자 이름·범위는 U1-b의 프로필 검사에서.

## 3. 결과 계약

```
CommandResult (frozen)
  status          succeeded / failed / stopped / unconfirmed
  confirmation    Confirmation
  execution_mode  ExecutionMode (어댑터 선언)
  route           ControlRoute
  requested_at, accepted_at, confirmed_at   (없으면 None)
  provider_ref    클라우드 메시지 ID 등. 없으면 None
  detail          사람이 읽을 한 줄 (확인 못 한 이유 포함)
  buttons         physical만: 기존 tuple[ButtonResult, ...]
```

- `unconfirmed`는 실패가 아니다. 접수는 됐는데 정해진 시간 안에 상태 변경을 못 봤다는 뜻이다. 자동으로
  다시 보내지 않는다(중복 실행). 화면은 "보냈지만 확인 못 함"으로, 다시 조회 버튼을 준다.
- 클라우드 성공을 "버튼 조작을 마쳤어요"로 보이지 않는다. 확인 수준별 문장은 §6.
- 확인 대기 상한(초)은 설정값이며 실측 전 기본값은 추측이다. 구형 기기 5분 갱신은 상한 안에 못 들어오므로
  그 기기는 `unconfirmed`가 정상 결과일 수 있다 — 프로필·모델별로 기록한다.

## 4. 승인 계약

```
ApprovedCommand (frozen)
  command          Command (위)
  approval_id      승인 1건의 ID
  approved_at, expires_at
  shown_summary    사용자가 본 문장(예: "공기청정기 풍량 강")
```

규칙:
1. **승인은 명령에 붙는다.** 승인 뒤 목적 문자열을 다시 해석하지 않는다. 실행기는 `ApprovedCommand`의
   command를 그대로 실행한다.
2. **실행 직전 재검사**는 한다(§8): 대상 존재 → 경로별 준비 상태(U1-b) → 동작 지원·인자 범위(프로필) →
   상황 유효성(기존 approval_guard: 부재·환경 근거 소멸·완료된 행동). 하나라도 어긋나면 실행하지 않고
   `approval_invalid`로 카드를 되돌린다.
3. **내용이 달라지면 재승인.** 재검사 중 현재 해석(가전 정의 `functions`나 프로필)이 승인한 command와
   fingerprint가 다르면 `ApprovalMismatch`로 거절하고 새 카드를 만든다. 예: '풍량 약' 승인 후 '풍량 강'
   실행 금지.
4. 만료: `expires_at`(패턴 제안은 시간대 끝, 환경·데모는 생성 15분 — 기존 만료 규칙 재사용).
5. 직접 명령(`/execute` 음성·수동 버튼)은 사용자의 발화 자체가 승인이므로 해석 뒤 실행한다. 단 폰의
   "이대로 실행할까요?" 확인 창이 **구체적 명령**을 보여 준 경우엔 그 명령을 그대로 보낸다(재해석 금지).

## 5. 기존 정책과의 충돌 — 구현 전 결정 필요

| # | 충돌 | 현재 코드 | 제안 |
|---|---|---|---|
| 1 | **승인 후 재해석 금지 vs 현재 승인은 재해석** | `approve()`/`approve_submit()`이 `execute_purpose(purpose, appliance_id)`로 목적을 **다시** 해석한다(`rpi/intent/suggestions.py`). 테스트 `test_approve_still_reresolves_independently_of_the_preview`가 이 동작을 고정 | 물리 경로도 승인 고정으로 통일. 제안 생성 시 미리보기가 아니라 확정 command를 만들고, 승인 시 fingerprint 재검사. 테스트는 "재해석하지 않고 어긋나면 재승인"으로 바꿈. **경로별로 정책을 둘로 두지 않는다** |
| 2 | **결과 표시** | 앱·키오스크는 `last_status == succeeded`면 "버튼 조작을 마쳤어요"(`app/lib/providers/execution_status_provider.dart`, 키오스크 `done_view.dart`). `ButtonStep{button, success}`뿐 | `StatusResponse`에 `route`·`confirmation`·`last_steps[].kind` 추가(하위 호환: 기존 필드 유지). 앱·키오스크 문구 분기 §6. 폰·키오스크 골든 갱신 필요 |
| 3 | **상태 enum** | `ExecutionStatus`는 succeeded/safety_stopped/failed. `unconfirmed`가 없어 접수 뒤 미확인을 failed로 기록하게 됨 | `ExecutionStatus.UNCONFIRMED` 추가. 이력·앱 매핑(실패 아님, 재조회 안내) 같이 |
| 4 | **학습 조건** | `_run_buttons`·`patterns._evidence`·`completed_actions`가 REAL+DIRECT+SUCCEEDED만 본다. `UsageRecord`에 확인 수준이 없다 | `UsageRecord`·`job_history`에 `route`·`confirmation` 열 추가(SQLite ALTER, 옛 기록은 unknown). 학습 조건: 기존 + **thinq는 `state_confirmed` 이상**. 승인 기록은 계속 SUGGESTION으로 제외 |
| 5 | **정지 의미** | `emergency_stop_report()`는 `NodeRegistry`의 노드에만 `request_stop`을 뿌리고, 결과를 받음/미확인 둘로 나눔 | 클라우드 어댑터 `request_stop()`은 **미전송 대기 명령 취소**만 보장. 이미 전송한 명령은 취소하지 않고 `sent_uncancellable`로 보고. 가전 운전 정지 명령은 자동으로 보내지 않는다(별도 승인 행동). `EmergencyStopReport`에 `cloud_uncancellable` 추가. 클라우드 등록소도 정지 순회에 포함 |
| 6 | **실행 락** | 서버는 한 번에 실행 1건(`_running`·ControlArbiter). 클라우드 확인 대기가 락을 오래 잡으면 물리 실행이 막힘 | 클라우드 job은 **접수 + 짧은 확인 대기(상한)**까지만 락을 잡고, 그 안에 확인 못 하면 `unconfirmed`로 job을 끝낸다. 늦게 온 상태 변경은 job을 되살리지 않고 별도 조회 결과로만 보인다 |
| 7 | **준비 상태 게이트** | `_require_ready`는 4축 전부 또는 `runs_locally` 예외 | U1-b에서 경로별로. U1-a에서는 명령에 route가 있어야 U1-b가 분기할 수 있다는 것만 확정 |
| 8 | **감사 이벤트 문구** | `_record_care_outcome`이 "'{label}' 실행이 완료되지 못했어요" | `unconfirmed`는 "보냈지만 확인 못 했어요"로 분리 |

## 6. 화면 문구 (확인 수준별)

| route | confirmation | 문장 |
|---|---|---|
| physical | state_confirmed | 버튼 조작을 마쳤어요 (기존) |
| physical | operation_confirmed | 버튼 조작을 마쳤고 가전 동작도 확인했어요 |
| thinq | accepted | 명령을 보냈어요 — 아직 상태를 확인하지 못했어요 |
| thinq | state_confirmed | 명령을 보냈고 상태가 바뀐 것을 확인했어요 |
| thinq | unconfirmed | 보냈지만 확인하지 못했어요 — 가전을 직접 확인하거나 다시 조회해 주세요 |
| any | stopped | 실행을 멈췄어요 (기존, 장치 정지 단정 안 함) |

## 7. U1-a에서 만들 것 / 안 만드는 것

만든다: `ControlRoute`·`Confirmation`·`Command`·`CommandResult`·`ApprovedCommand` 자료형과 fingerprint,
`CommandController` 프로토콜, 결과→확인 수준 매핑(물리), 스키마·이력 열, 문구 표, 위 충돌 1·3·4·8의 수리.
테스트는 계약 위반(재해석·불일치·미확인을 성공으로 표시)이 먼저 실패하는 것부터.

안 만든다: 실제 ThinQ 호출, PAT 처리, 프로필 검사(U1-b), 모의 서버(U1-c), 앱 화면 개편(문구만).
