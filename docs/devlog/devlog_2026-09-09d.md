## 문제

R3에서 **삭제**는 기기에 남겨 두었다가 다시 보내게 했다. 그런데 **업로드
실패는 스낵바에서 끝났다.**

    서버가 꺼져 있을 때 가전 등록 → "서버 연결 후 다시 저장하면 돼요" 스낵바
    → 사용자가 잊음 → 폰에만 있는 가전이 됨 → 키오스크는 영영 모름

그리고 대기열이 `Set<String>`(id만)이라 **로컬에서 지운 뒤의 재전송을 복구할
수 없었다** — 보낼 내용이 어디에도 없기 때문이다.

## 대기열

순서 있는 operation 목록으로 바꿨다. 각 항목에 `op_id` · `appliance_id` ·
종류(upsert/delete) · **payload 스냅샷** · 생성 시각.

- **payload가 있어야** 로컬에서 지운 뒤에도 재전송할 수 있다. 이게 id만
  저장하던 방식과의 결정적 차이다.
- **FIFO.** 같은 가전의 `upsert → delete`가 뒤집히면 지운 가전이 되살아나고,
  `delete → upsert`가 뒤집히면 방금 만든 가전이 사라진다. 앞의 작업이
  실패하면 **같은 가전의 뒤 작업도 보내지 않는다.**
- **single-flight.** 연타해도 한 번만 나간다.
- **로딩을 기다린다.** 대기열도 서버 주소도 기기에서 비동기로 올라온다. 앱을
  열자마자 누르면 예전에는 "보낼 게 없다"고 판단해 저장분을 덮어쓰거나,
  주소가 설정돼 있는데도 "주소를 먼저 설정해 주세요"가 떴다.
- **부분 성공은 성공한 것만 뺀다.** 이미 지워진 항목의 404는 성공으로 본다 —
  되돌려 놓으려던 상태(그 가전이 없음)가 이미 성립했다. 실패로 치면 대기열에서
  영영 안 빠진다.
- 가전 편집기 저장도 이 경로를 탄다.

**복구용 진입점**(`resendAll`)을 따로 뒀다. 대기열은 "이 폰이 한 변경"만
담는데, 서버가 꺼져 있던 시절에 등록했거나 대기열이 생기기 전 버전에서 만든
가전은 대기열에 없다. 설정의 '키오스크와 다시 동기화'가 그 수단이다.

## 충돌 — 조용히 덮어쓰지 않는다

폰이 둘이면 같은 가전을 각자 편집할 수 있다. 지금까지는 나중에 저장한 쪽이
그냥 이겼다(last-write-wins). **진 쪽 사용자는 자기가 방금 한 편집이 사라진
것도 몰랐다.**

가장 작은 규칙으로 막았다. 서버가 가전마다 판 번호를 세고, 클라이언트가 "내가
본 판은 3이었다"고 밝히면서 저장한다. 그 사이 누가 4로 올려놨으면 **409로
거절하고 서버 내용을 유지한다.** 자동 병합도, 자동 덮어쓰기도 하지 않는다.

- 판 번호는 **재시작에도 남는다.** 매번 1로 돌아가면 검사가 의미를 잃는다.
- 판을 밝히지 않은 저장은 종전대로 통과시킨다 — 최초 등록과 구버전 폰의
  경로다.
- 충돌한 작업은 대기열에서 뺀다. 다시 보내도 같은 충돌이 반복될 뿐이다.
- 사용자에게는 **"다른 기기에서 변경되어 서버 내용을 가져왔어요."**

## 최소 상태 UI

카드·배지·통계 타일을 늘리지 않았다. 한 줄이다.

| 상황 | 표시 |
|---|---|
| 평상시 | **아무것도 없음** |
| 대기 중 | `키오스크에 반영할 변경 2건` |
| 실패 | `변경 1건을 보내지 못했어요` + `다시 시도`(48px 이상) |

늘 떠 있는 상태 표시는 읽히지 않고, 정작 문제가 생겼을 때도 눈에 안 들어온다.

사용자 문구에 `upsert`·`tombstone`·`revision`·`409` 같은 내부 용어를 쓰지
않는다 — 테스트가 그걸 고정한다.

## 고정한 이음매

1. 앱 시작 직후 outbox 로딩 전에 눌러도 저장된 작업이 유실되지 않는다
2. upsert 실패 후 앱을 종료·재실행해도 payload가 남아 재전송된다
3. 같은 id의 `upsert → delete` / `delete → upsert`가 뒤집히지 않는다
4. 부분 성공 시 성공한 것만 제거한다
5. 연타해도 중복 실행·순서 역전이 없다
6. 재전송이 멱등이다 — 이미 지워진 항목의 404는 성공
7. 병합이 로컬 사진 경로를 덮거나 업로드하지 않는다
8. 충돌 시 어느 쪽도 조용히 덮어쓰지 않는다

R3 시절 테스트 파일(`appliance_sync_test.dart`)은 여기에 흡수했다. 같은 것을
다른 어휘로 두 번 검증하면 한쪽이 썩는다.

## 곁가지

- `http.Response(String, ...)`는 본문을 **latin-1로** 인코딩한다. 한글 detail을
  담은 409 픽스처가 인코딩 단계에서 던져, 테스트에서 409가 통신 실패로
  둔갑했다. 실제 서버는 utf-8 charset을 붙이므로 픽스처도 그렇게 맞췄다.
- 위젯 테스트는 **가짜 시계** 위에서 돈다. 기기 저장소 읽기 같은 진짜 비동기를
  그냥 await 하면 영원히 끝나지 않는다 — `tester.runAsync`로 감싼다.
