## 1. 온디바이스 의도 해석을 D-Bus 직접 호출로 전환 (dbus-fast)

실기기 정찰 결과, 우리 백엔드는 플랫폼 위에 **파이썬 컨테이너**로 올라간다. 컨테이너
안에는 기존에 쓰던 D-Bus CLI 바이너리가 없다. 그래서 시스템 버스 소켓만 마운트하고
파이썬에서 D-Bus를 직접 부르는 경로로 바꿨다 — 이 경로가 실기기에서 실제로 붙는 것을
확인했다.

- `DbusFastVectordbClient` — 기존 CLI 클라이언트와 같은 `VectordbSearcher` Protocol.
  resolver는 그대로 끼워진다. **반환값이 타입으로 와서** CLI 텍스트 파싱의 불확실성이
  사라진다(그 출력 포맷은 실기기로 확정된 적이 없어 CAUTION이 붙어 있었다).
- 호출을 invoker로 주입 — 기존 subprocess runner와 같은 철학. 테스트는 버스 없이 가짜
  invoker로 로직을 고정한다. dbus-fast가 없어도 import되게 실제 연결 시에만 지연 import.
- `SIMPLELAY_DBUS_TRANSPORT`로 native(기본)/cli 선택. pyproject에 `[dbus]` extra.

우리 D-Bus 클라이언트가 기대하는 인터페이스가 실기기 시그니처와 맞는 것도 확인했다
(요청/응답 시그니처, 시그널 형태). 몇 달 전에 짜둔 배선이 추측이 아니라 실제로 맞았다.

## 2. 네이티브 앱으로 빌드 — 실기기 첫 컴파일

키오스크(rpi5-touchscreen-app)를 플랫폼 SDK로 네이티브 빌드했다. 첫 실기기 빌드에서

표면이었는데, 오늘 통째로 확인됐다.

## 3. 화면이 안 뜨던 진짜 이유 — 지급받은 터치 디스플레이 불량

배포는 다 됐는데 화면이 검게 남았다. 파고든 결과 컴포지터가 부팅 중 크래시하고 있었고,
코어덤프 백트레이스로 원인을 정확히 특정했다(로컬 문서에 기록).

그리고 대회 사무국 공지가 이걸 확정해줬다: **"검정 케이스 7인치 터치 디스플레이가
라즈베리파이5에서 펌웨어 문제로 터치 미동작. 마우스 사용 시연 권장."** 우리도 검정
케이스 수령.

- 그 터치 디스플레이를 분리하고 **일반 HDMI 모니터 + USB 마우스**만 남기니 컴포지터가
  크래시 없이 정상 기동 → **키오스크가 화면에 떴다.**
- 우리 백트레이스가 사무국 공지와 정확히 일치했다. 즉 화면 문제는 우리 앱·배포와
  무관한 **지급 하드웨어(불량 펌웨어 터치패널)** 문제였다.

**시연 구성 확정:** 일반 HDMI 모니터 + 마우스(사무국 안내대로). 터치 픽스는 대기.

## 오늘 해소한 프로젝트 최대 리스크 두 개

1. **"백엔드를 어디서 돌리고 온디바이스 AI와 어떻게 잇나"** — 컨테이너 + D-Bus 직접
   호출로 실증. 별도 서버 불필요.
2. **"화면이 왜 안 뜨나"** — 지급 터치 디스플레이 펌웨어 불량으로 확정(사무국 공지 +
   우리 백트레이스 일치). 일반 모니터 + 마우스로 정상.

발표에서 "실기기 배포 완료, 화면 표시 확인(스크린샷), 남은 터치 이슈는 플랫폼 하드웨어
문제(사무국 확인)"라고 근거와 함께 말할 수 있다.

## 저녁 추가 — 백엔드를 실기기 컨테이너로, 키오스크가 "연결됨"으로

오전에 화면을 띄웠고, 저녁엔 오늘의 최대 리스크였던 **"백엔드를 어디서 돌리나"** 를
실증까지 끝냈다. 백엔드를 실기기 위 **파이썬 컨테이너**로 올렸고, 키오스크가 거기에
붙어 실제 상태를 받는 것을 확인했다.

### 한 것
- `deploy/backend.Dockerfile` — python:3.12-slim 기반, 런타임 의존성만 명시 설치,
  `rpi/`·`rpi4/`만 COPY, uvicorn으로 `0.0.0.0:8000` 서빙. arm64로 빌드.
- `deploy/run_backend.sh` — 이미지를 기기에서 `docker load` 후 실행. 시스템 D-Bus
  소켓과 데이터 볼륨을 마운트하고 `--restart unless-stopped`.
- `.dockerignore` — 이미지엔 `rpi/`·`rpi4/`만. NDA 로컬 자료·대용량은 전부 제외.
- 기기 docker 데몬을 부팅 시 자동 기동하도록 설정(재부팅에도 백엔드가 따라 올라옴).

### 드러난 버그 하나 (고침)
- `httpx`가 코드에선 **최상위 import**(ESP 노드 HTTP 전송)인데 `pyproject`엔 test
  extra에만 있었다. test 의존성을 안 까는 컨테이너에서 기동 즉시 `ModuleNotFoundError`.
  → base 의존성으로 옮기고 이미지에도 포함. **커밋 2d82bd3.**
  (SDK 버전 차이·의존성 누락처럼, 정적 검사로 안 잡히고 실기기/컨테이너에서야 드러나는
  부류. 오늘만 세 번째 같은 패턴 — activeThumbColor, 그전 펌웨어, 이번 httpx.)

### 확인
- 컨테이너 `/health` = `{"ok":true,"actuator_ready":true,"act_mode":"local"}`.
- 백엔드 로그에 **호스트(키오스크)에서 오는** `/status`·`/suggestions`·`/alerts` 폴링이
  찍힘 → 키오스크가 실제로 붙어 있음.
- 키오스크 화면: 앰버 "기기 연결이 필요해요" → **"화면을 눌러 가전 조작"** + 상태 점
  초록. 대기화면 터치 게이트(b9cc094)와 맞물려 두 상태가 모두 맞게 동작:
  연결 안 되면 터치해도 안 넘어가고, 연결되면 조작판으로 진입.

### 남은 것
- 지금 백엔드는 mock 모드(오프라인 우선 기본값). 온디바이스 D-Bus 실호출(dbus-fast)로
  실제 의도 해석을 붙이는 건 vectordb 서비스 활성화 확인 후.
- 마우스 상호작용 시연 리허설, rpi4(Act 보드) 연결.

## 밤 추가 — 제품 3건 (코스 현실화 · 데모 페이싱 · "다시 추천 안 함")

실기기가 붙어 있는 김에 데모 완성도를 세 가지 올렸다. 모두 폰·키오스크·백엔드
동기화 + 테스트 + 실기기 배포·확인까지 끝냈다.

### 1. 전자레인지 코스를 실사용 빈도로 (커밋 0d5d48d)
"우유·자동조리" 타일이 어색하다는 지적 → 실제 자주 쓰는 **즉석밥·냉동식품·라면**으로
교체. 버튼맵은 UI가 아니라 액추에이터가 누를 물리 버튼의 거울이라 다섯 진실원천
(매니페스트·키오스크·폰·버튼라벨맵·자연어 규칙)을 함께 맞췄다. "가전엔 버튼 십수 개지만
이 사용자가 쓰는 것만 남긴다"는 단순화 논지를 그대로 보여주는 큐레이션.

### 2. 데모 페이싱 (커밋 46cbc76)
mock 액추에이터는 즉시 끝나 "즉석밥 눌렀더니 순간 완료"로 보였다(실 모터 미연결).
`SIMPLELAY_DEMO_PACING`(기본 꺼짐)이 켜지면 단계마다 잠깐 멈춰 **폐루프**(누름→검증→
다음)가 화면에 보인다. 지연만 주고 진행 이벤트는 그대로라 로직·테스트 불변. HW 붙으면
끄고 실 모터 시간으로 대체. 실기기에서 "즉석밥(0/2)→시작(1/2)→완료"가 ~2.4초에 걸쳐
흐르고, 각 단계의 센서 검증·시도횟수가 표시되는 것을 확인.

### 3. "다시 추천 안 함" (커밋 7a8eec9)
제안 거절이 지금까진 카드만 없애는 dismiss라, 이력이 남아 패턴이 같은 걸 또 띄웠다
(실제로 테스트 노이즈로 "즉석밥"이 계속 뜨는 걸 겪음). "싫다는 걸 기억하는 것"도
공감지능이라, 거절을 **버튼 2개**로 나눴다:
- "이번만 넘기기" — 이번 카드만
- "다시 추천 안 함" — 그 루틴을 억제 목록에 넣어 패턴이 재생성하지 않음

백엔드에 SuppressionStore(SQLite 영속), 패턴 생성 시 스킵, `/suppressions`·unmute API.
폰 설정에 "다시 추천 안 하는 항목" + 개별 해제. 실기기에서 두 버튼 표시·억제·해제 확인.

백엔드 584 · 키오스크 43 · 폰 153 통과. 세 기능 모두 실기기 배포·화면/동작 확인.

## 밤 추가 2 — 온습도 기반 에어컨 선제 제안 (커밋 fd2a065)

패턴 제안이 "사용 이력"을 본다면, 이건 "지금 공간이 어떤가"(온습도)를 본다. 쾌적
범위를 벗어나면(기본 28°C·70%) **"에어컨 켤까요?"** 를 선제 제안한다 — 센서(공간 이해)와
선제 제안(공감지능)을 잇는 자리. 판단은 설명 가능한 임계값(AI 고도화가 아니라 배선).

- `EnvironmentalSuggester`: 주입된 센서 읽기로 냉방 후보 판단 + 근거 문구 생성.
  `ProactiveSuggestionService`에 배선 — DND·억제·중복 가드를 그대로 탄다.
- 에어컨 규칙: "에어컨 켜줘"→(전원,냉방) + 별칭(덥다·시원하게·틀어줘…).
- 제안에 `reason` 필드 → 폰·키오스크가 **"지금 31°C · 습도 72% — 더워요"** 표시.
- `POST /demo/environment`: 온습도 강제값으로 시연(센서 미연결 대비), `/sensors`도 반영.

**실기기 확인**: 강제로 31°C·72% → 키오스크에 "에어컨 켜줘, 지금 할까요? / 지금 31°C ·
습도 72% — 더워요 / 전원→냉방 / [이번만 넘기기][지금 실행] / 다시 받지 않기" 표시.

에어컨은 별도 물리 노드(ESP32)가 아직 없어 로컬 컨트롤러로 실행 — **2번째 물리 노드는
rpi4 붙일 때.** 지금은 "시스템이 공간의 여러 가전을 이해한다"까지 실증.
