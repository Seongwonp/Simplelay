# 2026-10-15 공기청정기 센서 공기질 제안 — '공기가 나빠요' → 강풍 (서버)

사용자 요청 건(10/15 동결 예외 '공기질(공기청정기 센서) 제안')이다. 공기청정기가 ThinQ로 알려 주는 **자기 센서의 등급**이 나쁨이면
'공기청정기를 강풍으로 바꿀까요?' 카드를 띄운다. 승인하면 ThinQ 한 단계(`set_wind_strength HIGH`)가 종전 승인·실행 경로로 나간다.
**서버(`rpi/`)만 바꿨다.** 폰·키오스크 코드는 바꾸지 않았다 — 기존 시나리오 카드 모양(시나리오 이름·질문·근거·할 일)을 그대로 쓴다.

> **검증 수준: 시험까지(모의).** 모의 ThinQ 클라이언트와 저장소 안 모의 클라우드(공식 SDK 경유)로만 확인했다.
> **실제 공기청정기에서 나쁨 등급으로 카드가 뜬 것은 아직 보지 않았다**(10/15 실물 상태는 좋음·보통만 봤다 — [ThinQ 실물 첫 연동](devlog_2026-10-15-thinq-real.md)).
> 폰·키오스크 화면에서 이 카드가 어떻게 보이는지도 에뮬레이터·실패널로 보지 않았다(서버 응답 모양이 기존 시나리오 카드와 같다는 것까지만).

## 1. 왜 이렇게

- 근거를 **공기청정기 자체 센서 하나**로 둔다. 우리 쪽 임계값(µg/m³ 경계)은 두지 않는다 — 실측 근거가 없고, 가전이 이미 매긴 등급이 있다.
- 센서 값이 없으면(공기청정기 꺼짐·켠 직후 센서 준비 중) 제안하지 않는다. 10/15 실물에서 꺼져 있으면 `airQualitySensor` 칸이 없고,
  켠 직후에도 잠시 비어 있었다(그때 풍량은 약으로 돌아간다). 값을 지어내거나 옛 값을 쓰지 않는다.
- 새 화면을 만들지 않고 **시나리오 카드**를 쓴다. 카드가 확정 명령(`commands`)을 들고 다니므로 승인이 그 명령에 묶이고(지문 대조),
  조용한 시간·잠시 쉬기·다시 받지 않기·부재 판정·대기 카드 하나 규칙을 제안 서비스가 다른 카드와 똑같이 적용한다.

## 2. 문구

| 자리 | 문구 |
|---|---|
| 시나리오 이름(`GET /scenarios` `name`, 화면의 '시나리오 · …') | 공기가 나빠요 |
| 질문(`purpose`) | 공기청정기를 강풍으로 바꿀까요? |
| 근거(`reason`) | 공기청정기 센서: 초미세먼지 42 · 나쁨 — 나쁜 칸 중 앞의 하나(초미세먼지 → 미세먼지 → 종합 공기질). 종합 공기질은 지수라 숫자 없이 '종합 공기질 · 나쁨' |
| 모의일 때 근거 끝 | (시연: 모의 센서 값이에요) — 카드도 시연 카드(`is_demo`) |
| 할 일(`commands[].summary`) | 공기청정기 풍량 강 (모의는 '공기청정기(모의) 풍량 강') |

- 등급 말: GOOD 좋음 · NORMAL 보통 · BAD 나쁨 · VERY_BAD 매우 나쁨(폰 상태 카드와 같은 말).
- 결과 문장은 새로 만들지 않는다. 실행 결과는 기존 확인 수준(`state_confirmed` '강풍으로 바꿨어요.' · `already_at_target` · 접수됨 등)으로만 말한다.
  **'공기가 좋아졌어요'·'깨끗해졌어요' 같은 말은 어디에도 없다**(시험이 카드 문장에서 확인).

## 3. 규칙

- **나쁨:** `PM2Level`(PM2.5) · `PM10Level` · `totalPollutionLevel` 중 하나라도 `BAD`·`VERY_BAD`. 모르는 등급 값은 판정에 쓰지 않는다.
- **값 없음 → 제안 없음:** 센서 칸 없음·빔, 전원이 `POWER_OFF`로 보임(칸이 남아 있어도 옛 값일 수 있어 쓰지 않는다), 아는 등급이 하나도 없음.
- **이미 강풍:** 풍량(`windStrengthDetail`, 없으면 `windStrength`)이 `HIGH`(또는 더 센 `POWER`)면 제안하지 않는다.
- **승인:** ThinQ 한 단계 `air_purifier` `set_wind_strength` `{wind_strength: HIGH}` — job 모델·확인 수준 그대로. 보내기 전 조회에서 이미 강풍이면
  보내지 않는다(기존 `already_at_target`).
- **자동 실행 없음:** 정의가 `auto_allowed=False`라 '다음부터도 자동으로' 제안(`auto_rule_offer`)이 없고 `approve-and-allow`는 422.
  자동 실행 허용 규칙(`rpi/routines/auto_rules.py`)의 범위는 바꾸지 않았다(가열 종료 → 공기청정기 하나 — [자동 실행 허용 규칙](devlog_2026-10-13-auto-rule.md)).
- **센서 값 없이 만들지 않는다:** 시연 트리거(`POST /demo/scenario/air_quality_high`)도 409.
- **대기 카드 하나:** 같은 시나리오의 대기 카드가 있으면 새로 만들지 않는다(제안 서비스 기존 규칙).
- **다시 알리기:** 카드를 만든 뒤에는 (1) 공기가 좋음·보통으로 돌아온 것을 **한 번 본 뒤에만**, 그리고 (2) 카드를 만든 뒤 **45분**(카드 유효 15분 + 30분)이
  지나야 다시 만든다. (2)는 카드가 언제 내려갔든(거절·실행·만료) 내려간 뒤 적어도 30분이라는 뜻이다. 값 없음은 '좋아짐'이 아니다.
- **조용한 시간·잠시 쉬기:** 다른 제안과 같다 — 조용한 시간, 잠시 쉬기 두 범위(`suggestions_and_auto`·이어받은 `suggestions_only`) 모두 새 카드를 만들지 않고,
  떠 있던 카드는 내린다. 막혀서 카드가 안 생겼으면 다시 알리기 상태를 그대로 두어, 끝난 뒤에도 나쁘면 그때 제안한다(환경 제안과 같은 모양).
  '다시 받지 않기'는 질문 문장으로 억제된다(기존 규칙).

## 4. 판독 스레드

- `SIMPLELAY_THINQ_MODE`가 mock·fake_cloud·real일 때만 서버 기동 때 전용 데몬 스레드(`air-quality-poll`)를 띄운다. off면 스레드가 없다.
  판독마다 ThinQ 공기청정기(가전 ID `air_purifier`, 환경 변수 또는 '찾은 가전 추가')가 있는지 먼저 보고, **없으면 ThinQ를 부르지 않는다.**
  (스레드 자체는 ThinQ가 켜져 있으면 뜬다 — 기동 뒤 사용자가 공기청정기를 추가할 수 있어서다. 그동안은 메모리 확인만 한다.)
- 주기 `SIMPLELAY_AIR_POLL_SECONDS` 기본 120초, 최소 60초(작으면 60), 최대 3600초. 기동 뒤 첫 판독은 30초 뒤.
- 건너뛰기: 다른 실행이 진행 중이면(확인 조회와 호출을 다투지 않게), SDK 경로에서 최근 1분 호출이 상한(`SIMPLELAY_THINQ_MAX_CALLS_PER_MINUTE`, 기본 30)의
  **절반 이상**이면(나머지는 사용자 명령 몫). 상한 자체(넘으면 보내지 않음)는 SDK 클라이언트가 그대로 지킨다. 조회는 최근 15초 조회 기억(`cached_status`)을 함께 쓴다.
- 판독 실패는 기록만 하고 이번 판독을 건너뛴다. 다음 주기까지 다시 읽지 않는다. 연달아 실패하면 경고는 첫 번째만.
- **정지와의 관계:** 판독은 이 스레드에서만 한다 — 이벤트 루프·공유 스레드 풀을 쓰지 않는다([재확인 2차 수리](devlog_2026-10-14-eval-recheck2-fix.md)·[재시작 직후 초기화](devlog_2026-10-14-startup-init.md)와 같은 원칙).
  lifespan은 스레드만 띄우고(환경 변수만 읽음) 싱글턴 생성·ThinQ 조회는 그 스레드 안에서 한다. 종료는 표시만 하고 판독을 기다리지 않는다.
- 로그에는 가전 ID만 쓴다(기기 ID·토큰 없음).

## 5. 리허설

`POST /demo/thinq/air-quality` `{"level": "GOOD"|"NORMAL"|"BAD"|"VERY_BAD"|"NONE", "pm2"?, "pm10"?, "forget_recent"?}` — 모의 센서 값을 넣고 판독을 **한 번 바로** 한다.
응답은 `execution_mode: "mock"`, 판독 결과 `check`(`offered`·`no_data`·`ok`·`already_strong`·`waiting_rearm`·`card_quiet`·`not_offered`·`skipped:…`), 떠 있는 공기질 카드.

- mock: 모의 클라이언트의 센서 칸을 바꾼다(전원이 켜져 있을 때만 상태에 실린다 — 모의 기본은 꺼짐). fake_cloud: 모의 클라우드의 `POST /__fake__/air`(이 기기 안 주소만)로 넣는다.
- **real 모드는 409**(실제 공기청정기 값 자리에 모의 값을 섞지 않는다). ThinQ가 꺼져 있으면 404.
- `NONE`은 센서 칸을 지운다(센서 준비 중 흉내). `forget_recent`는 다시 알리기 기억을 지운다 — 리허설을 되풀이할 때만.
- 순서(모의): `POST /thinq/command` 공기청정기 전원 켜기 → `POST /demo/thinq/air-quality {"level": "BAD"}` → 폰·키오스크에 '시나리오 · 공기가 나빠요' 카드 → 승인 → 실행 상태.

## 7. 시험

새 시험 `rpi/tests/test_air_quality_suggestion.py` **51개**(매개변수 포함): 나쁨·매우 나쁨 판정과 근거 문장, PM10·종합만 나빠도 판정, 좋음·보통 무시,
센서 칸 없음·빔·꺼짐(옛 칸 포함)·등급 없음 → 값 없음, 이미 강풍(두 풍량 칸), 주기 기본·최소·최대, 다시 알리기·45분, 막힌 제안 뒤 다시 준비,
판독 실패 기록·건너뜀·재시도 폭주 없음, 서버 경로(카드 하나·문구·모의 표시·보낸 것 없음, 좋음·보통 없음, 꺼짐·준비 중 없음, 이미 강풍 없음,
승인 → `set_wind_strength HIGH` 정확히 1회·`state_confirmed (mock)`, 자동 허용 없음·422·규칙 없음, 시연 트리거 409, 거절 뒤 다시 알리기,
조용한 시간·잠시 쉬기 두 범위·떠 있던 카드 내림·다시 받지 않기), ThinQ off면 스레드 없음, 공기청정기 없으면 조회 0회, 실행 중·호출 절반이면 건너뜀,
전용 스레드에서 조회, real 모드 주입 409(모드·실행 환경 두 갈래), ThinQ off 주입 404, 모의 클라우드(공식 SDK) 끝-끝,
**판독이 ThinQ 조회에서 멈춘 채 `/stop`**(lifespan 켠 Uvicorn) — 정지 진입 **72~102 ms**(6회, 상한 0.5초)·응답 200·서버 종료도 판독을 기다리지 않음(개발 PC, HTTP 요청 시작부터 Python 진입까지 — 모터 정지 시간이 아니다. 기동 직후 첫 요청이라 같은 PC의 기존 lifespan 정지 시험 37~63 ms와 비슷한 크기). 시험한 조건에서만 확인한 값이다.

## 8. 남은 것·위험

- **실물 미확인:** 실제 공기청정기가 `BAD`·`VERY_BAD`를 낸 상태에서 카드가 뜨는 것, 그 등급 문자열(`VERY_BAD`)이 실제로 그 철자인지(10/15에는 GOOD·NORMAL만 봤다),
  센서 준비 시간, RPi5 허브 real 모드(보드 인터넷 미연결).
- **화면 미확인:** 폰·키오스크에서 '시나리오 · 공기가 나빠요' 카드와, 승인 뒤 실행 상태 화면 제목(앱 규칙상 질문 대신 시나리오 이름 '공기가 나빠요'가 쓰인다)을 에뮬레이터·실패널로 보지 않았다.
- 카드가 떠 있는 동안 공기가 좋아져도 카드는 유효 시간(15분)까지 남는다(승인하면 강풍으로 바뀔 뿐 — 거짓 결과 문장은 없다). 내리는 규칙은 넣지 않았다.
- 호출 한도: 실제 클라우드 한도는 공개 문서에서 확인하지 못했다(분당 30은 우리 쪽 **추측** 상한). 판독은 2분에 1회(조회 1번) + 나쁨일 때 준비 확인이다.
- 45분·30분·120초는 정한 값이지 실측 근거가 아니다(**추측**).
