## 2. 동작 — 네 경우 (제어 요청 횟수와 문장)

| 경우 | status / receipt / confirmation | 제어 요청 | 서버 문장(`last_detail`) |
|---|---|---|---|
| 보내기 전부터 목표값 | `succeeded / not_dispatched / already_at_target` | **0회** | 이미 강풍으로 설정돼 있어요. 변경 명령을 보내지 않았어요. |
| 보내기 전 다른 값 → 보낸 뒤 목표값 | `succeeded / accepted / state_confirmed` | 1회 | 강풍으로 바꿨어요. |
| 보내기 전 조회 실패·값 없음 → 보낸 뒤 목표값 | `succeeded / accepted / state_confirmed_unknown_before`(새 값) | 최대 1회 | 강풍으로 설정된 것을 확인했어요. ('바꿨어요' 금지 — 원래 강풍이었을 수 있다) |
| 보낸 뒤 상태 확인 실패 | `unconfirmed / accepted / none` | 1회, **추가 전송 0회** | 명령을 보냈어요 — 설정이 바뀌었는지 확인하지 못했어요. 자동으로 다시 보내지 않아요 |

- 설정 이름은 `ThinqCapability.setting_phrase` — 풍량은 '강풍'·'약풍', 그 밖은 속성 이름을 붙인다('풍량 중'·'운전 모드 청정'·'운전 시작').
  자동 실행은 job을 만들 때의 사본(`value_phrase`)을 쓴다.
- **보내기 전 조회 실패의 동작이 바뀌었다:** 종전에는 조회 예외(오프라인 제외)면 '상태를 읽지 못해 보내지 않았어요'였다. 이제 원격 제어 확인이
  필요 없는 동작(공기청정기)은 **1회 보내고** 재조회로 판정한다. 세탁기 시작·일시정지(원격 제어 허용을 먼저 봐야 함)와 오프라인은 종전대로 보내지 않는다.
- 값 객체가 조합을 강제한다: `already_at_target`은 `succeeded`+`not_dispatched`만, `state_confirmed_unknown_before`는 `succeeded`+`accepted`만,
  둘 다 물리 경로 불가. `not_dispatched`의 성공은 `already_at_target`뿐.

### 정지·철회·전송권과의 순서

- '이미 목표값'도 **정지(미전송 취소) → 전송 직전 재판정(규칙 켜짐·지문·대상·사건 나이·정지 세대) → 전송권 확인**을 모두 지난 뒤에만 나온다.
  어느 하나에 걸리면 `failed / not_dispatched / none`이고 자동 실행은 `outcome: blocked`로 기록된다(성공 기록 없음).
- 보내지 않으므로 전송권 확인은 `commit(will_send=False)` — 검사만 하고 '전송 개시'로 표시하지 않는다. 그 뒤의 끄기·삭제가 '이미 보내기 시작했어요'(in_flight)로 알리지 않는다.
- 같은 사건 1회: 사건 키는 받을 때 처리 표시된다. 이미 목표값으로 끝난 사건을 다시 받아도 `duplicate`(시험).

### 기록 구분 `dispatch`

`/history`·`/routines/auto-rules/runs`·`last_auto_run`에 `dispatch`: `sent`(명령을 보낸 실행) · `state_only`(상태만 확인 — 이미 목표값) ·
`not_sent` · `unknown`. receipt·confirmation에서 유도한다(DB 열 추가 없음). 자동 실행 기록의 `reason`도 이미 목표값이면
'이미 목표 설정이라 변경 명령을 보내지 않았어요 — 이 사건은 처리했어요'로 바꿔, 제출 때의 '승인 없이 보냈어요'를 남기지 않는다.

### 집계·연쇄

- 사용 기록(제안 집계)은 세 성공을 모두 성공으로 센다(`Confirmation.reached_target`).
- 루틴 다음 단계의 '시작 확인'과 `after_done` 깨우기는 **종전대로 `state_confirmed`만**(`confirms_appliance` 그대로) — 이미 목표값·전 값 모름으로 다음 가전을 깨우지 않는다.

## 5. 남은 것

- **실제 클라우드·실가전:** 이미 강풍에서의 제어 요청 0회, 약풍→강풍 '바꿨어요', 실제 SDK의 조회 실패 형태(예외 종류)에서 1회 전송 — [절차 §5-1](../ThinQ-실물-확인-절차.md).
- 실제 클라우드에서 보내기 전 조회가 실패하는 빈도가 높으면 '설정된 것을 확인했어요'가 자주 나올 수 있다 — 실측 뒤 판단.
- 옛 폰·키오스크(이 커밋 전 빌드)는 `already_at_target`을 '보내지 않음' 칩·'명령을 보내지 않았어요' 기록으로 보일 수 있다 — **다음 배포 때 RPi5·폰·키오스크 같은 커밋.**
- 실패널·실폰에서 문장 길이(큰 글씨 줄바꿈)는 보지 않았다(골든은 기존 장면만 — 이미 목표값 장면 골든은 새 화면 금지에 따라 만들지 않았다).
