## 1. 서버: 시작 게시와 요청 중복 방지

- `DevApiState.start_lock`으로 **세션 생성 → 소유권 게시 → 현재 세션 확인**을
  직렬화했다. 겹친 시작은 기다렸다가 실행하지 않고 409 `session_starting`으로
  거절한다. 정지는 이 락을 사용하지 않아 게시 중에도 처리할 수 있다.
- 게시 중 A가 정지되면 A 시작 요청은 410이다. B는 A 게시가 끝난 뒤 새로
  요청해야 한다. 따라서 늦은 A의 `bind()`가 이미 열린 B의 소유권을 덮지 않는다.
- 중복 기록을 최근 64건 deque에서 **세션 수명 동안 유지하는 set**으로 바꿨다.
  최대 4096건에 도달하면 429 `request_capacity_reached`로 닫으며, 오래된 ID를
  버리지 않는다. 정지는 한도 밖이고 새 세션부터 기록을 초기화한다.
- ID 예약 시에도 세션 ID를 대조한다. 이전 세션의 지연 요청이 새 세션의
  중복 기록을 변경할 수 없다. ID가 생략된 요청도 서버가 발급한 ID를 기록한다.
- 이 계약은 **중복 실행 방지(at-most-once dispatch)**다. 같은 ID의 재전송은
  결과 재전달이 아니라 409이며, 이전 요청의 성공을 뜻하지 않는다. 원래 요청이
  거절됐거나 응답이 유실된 경우에도 같은 ID를 자동 재실행하지 않는다.

추가 API 테스트 4건: 66건 후 첫 ID 재전송, 용량 한도/정지 예외/새 세션/옛 세션
거절, 게시를 게이트에 멈춘 상태의 정지·새 시작 경합, 유휴 정지 실패≠fault.

## 2. 폰: 화면 수명과 응답 수명 분리

- UI 세대 번호와 API 인스턴스를 함께 확인한다. 정지·종료·앱 숨김·dispose·
  서버/토큰 변경 시 이전 세대를 무효화한다. 늦은 성공뿐 아니라 오류와
  `finally`도 새 세션의 상태·안내·busy를 변경하지 못한다.
- 세션 **시작 요청 중** 숨김/이탈/정지가 발생해도 무효화한다. 이후 성공 응답이
  오면 heartbeat를 켜지 않고, 그 세션을 만든 **원래 서버에 세션별 종료**를
  보낸다. 전역 stop으로 다른 세션을 건드리지 않는다.
- hidden 뒤 이어지는 paused는 중복 종료/무효화하지 않는다. 현재 lifecycle도
  처음에 읽는다. inactive만으로는 종료하지 않는 기존 정책은 유지한다.
- 상태 조회에도 읽기 순번을 붙여 이전 조회가 새 명령/정지 상태를 덮지 못한다.
- 설치 가전·버튼 목록이 변경되면 드롭다운의 사라진 선택값을 사용하지 않는다.
  현재 대상이 없어지면 명령을 잠근다(대상을 임의의 다른 가전으로 바꾸지 않음).

## 3. 정지 응답과 최종 정리 완료 구분

`confirmed`는 **이번 stop 호출의 확인**이다. 기존 응답 필드는 유지하되 API
모델 주석과 폰 소비 계약을 명확히 했다. `state.phase`가 우선이다.

| 응답 상태 | 화면 처리 |
|---|---|
| stopping | 남은 동작 정리 중이라고 안내, 완료 문구 금지 |
| fault | 정지 미확인·새 조작 잠금을 안내 |
| confirmed + idle | 정지 확인 안내 |
| 그 외(유휴 정지 실패 포함) | 완료를 확인하지 못했다고 안내, fault를 추측하지 않음 |

정리 중에는 이전 조회가 끝난 뒤 500ms 간격으로 최대 20회 조회한다(요청 오버랩
없음). 응답 지연 때문에 **총 10초 제한이라는 뜻은 아니다**. 한도에 도달하면
자동 조회를 끝내고 사용자가 `상태 새로고침` 또는 `정지`를 누를 수 있다.
화면 숨김/이탈은 조회 타이머를 취소하고, 복귀 시 상태를 다시 읽는다.

네트워크 오류는 “요청이 닿지 않았다”가 아니라 **“응답을 확인하지 못했다”**로
표현한다. 응답 유실만으로 서버 수신 여부나 물리 정지를 단정할 수 없다.

## 4. heartbeat 정책

- 일반 HTTP 호출 기한은 5초로 유지했다. heartbeat만 TTL의 1/3(최대 1초)을
  응답 기한으로 사용한다. 기본 TTL 2초일 때 약 667ms다.
- 유지 요청은 겹쳐 보내지 않는다. **첫 확인 실패부터 조작을 닫고 heartbeat를
  중단하며 세션 종료를 시도**한다. 뒤늦은 heartbeat 응답으로 세션을 재개하지
  않는다. 만료 응답은 상태 조회로 넘어간다.
- 이 선택은 연결 유지율보다 보수적인 종료를 우선한다. 지연이 큰 네트워크에서
  세션이 자주 종료될 수 있고, 단말/현장 지연 측정 뒤 정책을 조정해야 한다.
  타임아웃을 늘려 TTL 만료를 가리는 방식으로 변경하지 않는다.

## 6. 보장 범위와 다음 인계

**완료는 재현한 mock/API/위젯 시나리오까지다.** 스레드 인터리빙 전체를 증명한
것도, 실제 모터 정지를 확인한 것도 아니다.

- 요청이 HTTP 기한을 넘겨 완료되면 세션 비밀값을 못 받아 종료 요청을 보낼 수
  없는 경우가 남는다. 그때는 서버 TTL/watchdog에 의존한다. 늦은 요청 자체를
  네트워크에서 취소하거나 물리 정지 시각을 보장한다고 표현하지 않는다.
- 단일 워커 전제, 메모리 fault의 프로세스 재시작 경계, 토큰의 평문 HTTP 전송은
  그대로다. 공유망이나 실물 제어로 범위를 넓히기 전에 별도 검증/설계가 필요하다.
- **다음: H0~H1** — 장치 도착 후 부팅/연결 확인, 한 가전의 실제
  누름→센서 검증→실패 주입→보정 재시도→정지 흐름을 측정하고 로그를 남긴다.
- 개발자 실물 모드는 **H3·H4 실측 + 접근 제한/전송 보호 + 교차 확인** 뒤 별도
  승인 단계다. 이번 종료를 `allow_real_adapter` 활성화 근거로 쓰지 않는다.
- 장치가 없으면 신규 기능을 늘리기보다 폰 실단말의 화면 이탈/복귀·접근성·현장
