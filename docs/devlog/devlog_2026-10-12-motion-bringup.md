# 2026-10-12 데스크톱 — CoreXY 모션 실물 첫 시험(개루프·엔코더)

하드웨어(갠트리·모터·TB6612 드라이버·ESP32)를 받아 처음으로 실물 모터를 돌렸다. 펌웨어는 [`firmware-motion-corexy/`](../../firmware-motion-corexy/README.md)의 `esp32dev_bringup` 빌드(사람용 텍스트 명령)다.

**검증 수준:** 개루프 PWM 구동과 엔코더 계수까지 실물로 확인했다. 폐루프 위치 이동(`G`), 원점 복귀(`H`), 솔레노이드, RPi4 연결, 줄 단위 JSON 빌드는 **아직 실물 미검증**이다. 버튼 누름은 여전히 0건이다.

## 확인한 것

| 항목 | 결과 |
|---|---|
| 업로드 | ESP32-D0WD-V3(rev 3.1, CH340 USB) — 115200bps로 성공 |
| 모터 A(왼쪽 아래) | `M 0.3 0 600` → 엔코더 A +891, 역방향 −909. B 엔코더 변화 없음 |
| 모터 B(오른쪽 아래) | `M 0 0.3 600` → 엔코더 B +1003, 역방향 −1012. A 엔코더 변화 없음 |
| 두 모터 같은 방향(+X 의도) | `M ±0.3 ±0.3 1100` → A·B 약 ±1,550~1,760 카운트(설정상 약 45mm) |
| 캐리지 방향 | **판정 못 함.** 레일이 헐거워 벨트·캐리지가 헛돌았다. 모터·엔코더는 정상 |

- 모터 A=왼쪽, B=오른쪽이 팀원 README와 일치함을 사람이 눈으로 확인했다.
- 엔코더 부호: PWM 양수일 때 카운트도 양수다(두 모터 모두).
- 같은 명령에서 A·B 카운트가 최대 약 150 차이 났다. 개루프라 차이가 있을 수 있고, 레일을 조인 뒤 다시 본다.

## 문제와 해결

1. **첫 ESP32 보드 플래시 실패:** CH340·rev 1.0 보드는 어떤 속도에서도 "Failed to communicate with the flash chip"으로 실패했다. 보드 불량으로 보고 팀원 보드로 바꿨다. 고속 업로드에서 끊기는 일이 있어 `upload_speed = 115200`으로 고정했다(`841a9bf`).
2. **모터 전원:** AA 6V 팩을 드라이버 VM에 연결했다(VSEL 점퍼를 빼고 가운데 핀으로 연결, GND 공통). LED는 전원 표시용이지만 접촉 불량으로 꺼져 있어도 모터가 돌았다. 배터리를 뽑아서 모터가 멈추는 것으로 전원 경로를 확인했다.
3. **모터 B가 안 돎:** 모터와 엔코더를 서로 바꿔 꽂아 보니 모터 B는 A 채널에서 돌았고, 모터 A는 B 채널에서 돌지 않았다. 원인은 **B 제어선 접촉 불량**(ESP32 32·33·13 → PWMB·BIN1·BIN2)이었고, 선을 다시 꽂아 해결했다. 펌웨어는 대칭이었다. 그 사이에 넣은 PWM 채널 명시와 실패 시 기동 거절(`e26bfb9`)은 원인이 아니었지만 안전 개선이라 남겼다.
4. **시험 중 손으로 축을 돌리면** 엔코더 값이 섞인다. 시험 중에는 기구를 만지지 않는다.

## 남은 것

- 레일·캐리지 유격 조정(HW) → 캐리지 방향 시험 다시 하기(+X=오른쪽, +Y)
- 그다음 `Z` → `G 20 0` → `G 20 20` → `G 0 0` 작은 폐루프 이동 → `H` 원점 복귀
- 실제 풀리 잇수와 이동 범위(설정은 20T·2mm·200×200mm, 측정 필요), STBY·솔레노이드 풀다운 확인
- 그 뒤 `esp32dev` 빌드, RPi4 시리얼 연결, 개발자 모드 실물 조이스틱 확인
- 첫 동작 영상은 로컬에만 둔다(커밋하지 않음)

## 저녁 — 폐루프 이동과 폰 → RPi5 → RPi4 → ESP32 실물 경로

### 폐루프 이동(bring-up 빌드, 데스크톱 USB)

| 명령 | 도착 | 엔코더 (A, B) |
|---|---|---|
| `Z` → `G 10 0` → `G 0 0` | (10.01, 0.01) → (0.00, 0.00) | (351, 350) → (0, 0) |
| `G 40 0` → `G 0 0` | (40.03, 0.00) → (0.00, 0.03) | (1401, 1401) → (1, −1) |

- **모터 축 기준으로는 폐루프 이동이 정확했다.** 알람은 없었다.
- **캐리지는 거의 움직이지 않았다.** 모터 톱니를 벨트를 잘라 만들어서 벨트와 맞물리지 않는다. HW 할 일: 아이들러 풀리를 제대로 끼우고, 캐리지에서 벨트를 더 당겨 다시 고정하기.
- 그래서 스톨 원점(`H`)은 시험하지 않았다. 벨트가 미끄러지면 스톨을 못 잡아 벽을 계속 민다.

### 시험대 빌드 `esp32dev_benchhome`(`0f95ed7`)

- `home`이 움직이지 않고 **현재 위치를 원점으로 삼는다.** 배너 fw는 `firmware-motion-corexy-benchhome`다.
- 경로 확인 전용이며 시연 보드에는 올리지 않는다.

### 실물 경로 (처음)

- ESP32(CH9102 USB)를 RPi4에 꽂으니 `/dev/ttyACM0`로 잡혔다.
- RPi4 env:
  - `SIMPLELAY_MOTION_MODE=serial`
  - 기구 값은 config.h와 같게: 1400·20T·2mm, 범위 0~50mm
  - 줄 기록 `SIMPLELAY_MOTION_LOG_PATH`
- RPi5 env: `SIMPLELAY_DEV_MODE`·`SIMPLELAY_DEV_REAL_MOTION`, 조그 상한 5mm.
- 두 보드에 HEAD(`83ecc7e`)를 배포했다. RPi4 로그에 "developer motion ops accepted"가 남았다.
- `/dev/state`: `motion_target=real`, `real_motion_ready=true`.
- 에뮬레이터 개발자 도구에 **'실제 장치'** 배지가 떴다. 폰에서 연 세션으로 아래를 확인했다.
  - **홈**: MCU에 `home` 전달, 응답 `homed:true`
  - **x+ 1mm**: `move a=35 b=35`, 엔코더 35, 0.18 s
  - **정지**: RPi4 `dev motion stop` → MCU `stop` 전달
- 개발자 API 스크립트(같은 경로)로 보낸 5mm 조그:
  - x+5 → 엔코더 (175, 176)
  - y+5 → (350, 0)
  - y−5 → (175, 175)
  - 세션 종료: "정지를 확인했습니다"
  - 사람이 모터가 도는 것을 눈으로 확인했다.

### 발견한 것

1. **원점을 범위 경계 0에 두면 엔코더 1카운트 차이로 반대 방향 조그가 거절된다.** x−5가 `soft_limit`(y = −0.014 mm)로 거절됐다. 시험대에서는 X/Y 최소를 음수로 조금 내리거나, 원점에서 몇 mm 나간 뒤 시험한다. 실제 원점은 후퇴 3mm 뒤라 해당이 없다.
2. **RPi4가 MCU `stop`의 응답 줄을 기록하지 않는다.** 정지를 쓰기만 하고 읽지 않는 구조로 보인다. 펌웨어는 항상 응답한다. 다음 명령 때 버려지는지, 짝이 어긋나지는 않는지 확인이 필요하다.
3. 폰 조그가 1mm 고정이라 눈으로 보기 어려웠다. **방향 패드와 이동량 선택(1·2·5mm, 서버 상한 이하)으로 바꿨다**(`bd09528`). 앱 백그라운드 시험이 다른 애니메이션 프레임에 기대 우연히 통과하던 것도 고쳤다.
4. 개발자 탭 입구 문구가 아직 "모의 제어 — 실제로 움직이지 않습니다"로 고정돼 있다. 화면 안 배지는 서버 기준으로 바르게 나온다. 입구 문구를 고쳐야 한다.

### 보드 상태(변경)

- RPi5 env에 개발자 모드 실물 값 4줄을 더했다. 백업은 `env.bak-20261012`이고, 끄려면 `SIMPLELAY_DEV_REAL_MOTION`을 지운다.
- RPi4 env를 모션 serial로 바꿨다. 백업은 `env.bak-20261012`(빈 파일)이다. **ESP32가 빠지면 실행기를 세우지 않는다**(run_act.sh 장치 검사). 모의로 돌리려면 env를 비운다.
- 개발자 토큰은 저장소 밖 로컬 파일에만 있다.

- 폰 **580** 통과(골든 제외, 579 + 1), analyze error·warning 0
- 펌웨어 세 빌드 컴파일 성공
- 저장소 가드 5 통과

## 밤 — RPi4 무선 전환(랜선 없음)

제품 구조는 허브(RPi5)가 거실에 있고 RPi4+ESP32 세트가 가전 옆에 붙는다. 그래서 둘 사이를 무선으로 바꿔 확인했다.

- **방법:**
  - RPi4를 connman으로 집 Wi-Fi에 연결했다. 비밀번호는 사용자가 직접 입력했다.
  - RPi5 env `SIMPLELAY_UART_PORT`를 RPi4의 Wi-Fi 주소(같은 대역)로 바꿨다.
  - **RPi4 랜선을 뽑았다**(`eth0 carrier=0`). RPi4에는 전원과 ESP32 USB만 남았다.
  - 코드 변경은 없다. 연결이 원래 IP(TCP)라 매체만 바뀌었다.
- **RPi5↔RPi4 왕복 지연(ping 5회):** 평균 108 ms, 최소 99 ms, 최대 122 ms. 유선보다 느리고, 정지 지연 측정에 포함된다.
- **사용자가 에뮬레이터 방향 패드로 직접 조작했다.**
  - 홈, 5mm 이동 13회(x+·y+·x−·y−), 모두 `ok`, 거절·알람 0.
  - MCU 이동 하나 약 0.33 s, 모터 축 엔코더 오차 2카운트 이내.
  - 원점에서 +쪽으로 먼저 움직여 −방향 거절은 없었다.
- **정지(폰):**
  - RPi5 `POST /dev/stop` 200 → RPi4 `dev motion stop (emergency_stop)` → MCU `stop` 전달.
  - MCU 응답 줄은 기록되지 않았다(발견 2와 같음).

### 무선에서 발견한 것

5. **반쯤 끊긴 연결이 남으면 RPi4가 새 연결을 받지 못한다.**
   - 백엔드를 재시작해 주소를 바꿨더니, RPi4 쪽 socat이 예전 연결을 붙잡고 있어 `act_link_unavailable`이 계속됐다.
   - RPi4 실행기를 다시 띄우자 붙었다.
   - Wi-Fi에서는 이런 반쯤 끊긴 연결이 흔하다. TCP keepalive를 켜거나, 새 연결이 오면 예전 연결을 끊고 넘겨받게 고쳐야 한다(미수리).
6. **RPi5↔RPi4 연결에 인증이 없다.** 같은 Wi-Fi의 누구나 RPi4 7000번으로 실행 프레임을 보낼 수 있다.
   - 랜선 두 개일 때는 범위가 좁았지만, 집 Wi-Fi에서는 문제다.
   - 시연은 우리 공유기(WPA2)로 1차 차단한다.
   - 제품은 허브 주소 제한과 페어링 키 서명이 필요하다(미수리).
7. 랜선을 연결한 채 Wi-Fi를 켜면 같은 대역에 주소가 두 개 생긴다. 이때 데스크톱에서 유선 주소로 SSH가 안 됐다(경로가 엇갈린 것으로 추정). 운영에서는 한쪽만 쓴다.

### 대회장 구성(제안)

- 여행용 공유기를 "우리 집 Wi-Fi" 역할로 가져간다.
- 폰·RPi5·RPi4 모두 무선으로 붙고, 선은 전원뿐이다.
- 공유기 DHCP 예약으로 RPi4 주소를 고정한다.
- 대회장 Wi-Fi에는 의존하지 않는다. 날씨처럼 인터넷이 필요한 기능은 공유기 상위 연결(폰 핫스팟 등)이 있을 때만 쓴다.

### 페어링 키 인증(`d0d5cb0`)

- hello와 응답은 긴 키로 서명한다. 세션 키는 HMAC(K, cn|sn)이다.
- 이후 모든 프레임에 `seq`와 `mac`을 싣는다. 서명이 없거나 틀리거나 옛 순번이면 답하지 않고 버린다.
- 정지와 abort도 서명 대상이다. RPi4는 받은 cn 4096개를 기억해서, 옛 hello를 다시 보내 세션을 빼앗지 못하게 한다.
- 한쪽에만 키가 있으면 링크가 닫힌다. 이때 RPi5는 '인증 실패' 이유를 보이고 실행을 412로 막는다. 두 보드 모두 키가 없으면 종전과 같고 경고만 한 줄 남긴다.
- 한계: 암호화는 아니라 내용은 보인다. 방해(재밍)도 막지 못한다.
- 인증 구현은 Opus 서브에이전트가 했고, 검토하고 다시 실행한 뒤 커밋했다.
- 시험: 20건을 새로 넣었다. 수정 전 코드에서 16건 실패, 4건 오류를 확인했다.

### 배포·확인

- 두 보드에 `3d26afc`를 배포했다. 새 `run_act.sh`(keepalive)도 함께 올렸다.
- 키 64자리를 RPi5에서 만들어 RPi4로 그대로 넘겼다. 화면에 출력하지 않았고, 해시 앞자리로 둘이 같은지 확인했다. env 파일 권한은 600이다.
- RPi4 로그에 "link auth on"과 "new session"이 남았다.
- 인증된 링크로 개발자 세션의 상태 조회, 홈, 종료가 정상이었다. 모터 배터리를 뺄 예정이라 이동은 하지 않았다.
- **백엔드만 재시작했을 때 5 s 안에 다시 붙었다**(`actuator_ready=true`). 이번에는 RPi4 실행기를 재시작할 필요가 없었다.
- 이미지를 Wi-Fi로 옮기는 데 수 분이 걸렸다. 유선보다 훨씬 느리다. 다음에는 RPi4 랜선을 잠시 꽂거나 RPi4에서 직접 빌드한다.
