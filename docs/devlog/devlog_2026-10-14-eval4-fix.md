## 3. 설계와 경계

### H-N2 — 정지 경로가 기다리는 것

- 서비스 잠금 안의 실행 게이트는 **메모리 사본만** 읽는다. 사본은 통째로 바꿔 끼우므로(파이썬 속성 읽기 한 번) 읽기에 잠금이 없다.
- 규칙 DB 쓰기는 `_persist_lock` 안에서만, 그 잠금을 잡은 채 다른 잠금을 기다리지 않는다(메모리 잠금은 사본·판 번호를 읽는 순간만).
  늦게 끝난 쓰기가 새 상태를 옛 상태로 덮지 않게 늘 그때의 가장 새 사본을 쓰고 판 번호로 건너뛴다.
- 서비스의 다른 DB 사용(실행 기록 등)이 멈추는 경우는 이번 범위 밖이다 — 이번에 고친 것은 '규칙 저장소 잠금 → 서비스 잠금 → 정지' 사슬이다.

### M-N3 — 응답과 영속화, 내구성 경계

- `/stop`의 규칙 끄기: 세대 올림(`halt`, 이미 있음) → 메모리에서 끔(목록·판정 즉시 '꺼짐') → 응답. DB 쓰기·알림함 기록은 뒤의 스레드(실패하면 1초 간격 3회).
- **세션 표시** `auto_rules_session = {"open", "session"}`: 규칙 저장소를 열 때 지난 표시가 **열린 채 다른 프로세스 것**이면(정상 종료가 아님) 켜진 규칙을
  끈 채 시작하고(이유 "허브가 정상 종료되지 않아(전원 끊김·강제 종료 등) 자동 실행을 멈췄어요 — 다시 켜려면…") 표시를 이 프로세스 것으로 연다.
  서버 종료(`main.py` lifespan)는 남은 규칙 쓰기를 5초 안에 마쳤을 때만 표시를 닫는다.
- **보장하는 것:** 정지 뒤 규칙 끄기가 DB에 닿기 전에 프로세스가 죽거나(전원·강제 종료), DB 쓰기가 끝내 실패·지연되면, 다음 기동은 규칙을 꺼진 채 시작한다.
- **대가(정직하게):** 정지가 없었어도 **비정상 종료 뒤에는 늘** 자동 실행이 꺼진 채 시작한다(다시 허용 필요). `sudo reboot`·`systemctl restart`처럼
  lifespan 종료를 거치면 유지된다. 시연 중 전원을 뽑아 다시 켰다면 루틴 탭에서 '다시 허용'이 필요하다.
- **보장하지 않는 것:** 표시가 아예 없던 DB(이 커밋 전에 만든 DB의 첫 기동)는 지난 종료를 모르므로 그대로 믿는다. 같은 프로세스 안에서 엔진을 다시 만드는 경우(시험)는
  재시작으로 보지 않는다. 세션 표시 쓰기 자체가 실패하면 기록만 남긴다(다음 기동은 앞 표시를 본다).
- 폰: `/stop` 응답 실패는 '정지가 안 갔다'가 아니다. 같은 job 결과를 이미 받았으면 그 문장을 지키고, 시간 초과는 '전달 여부 모름'으로 말한다. 정지 판정은 종전대로
  `/status` 폴링이 한다. 키오스크는 `/stop` 응답으로 완료 화면을 만들지 않아 바꾸지 않았다.

### H-N1 — 전송권

- 순서: 최종 재판정(조회를 마친 뒤, 메모리) → controller 잠금 안에서 정지 취소 확인 → **전송권 확인**(`_send_lock` 안에서 재판정을 한 번 더 하고 `_sending`에 표시) → `dispatched` → POST.
- 철회(끄기·값 바꾸기·삭제·비상정지의 규칙 끄기)는 같은 `_send_lock` 안에서 메모리를 바꾼다. 그래서 '재판정 반환 → 철회 완료 → POST 시도'면 전송권 확인에서 걸리고,
  '전송권 확인 → 철회'면 철회가 `_sending`을 보고 '이미 보내기 시작함'을 응답한다. 둘 사이 다른 상태는 없다.
- 잠금은 메모리 판정 동안만(입출력·네트워크 없음). POST·확인 조회 동안 잡지 않는다. 정지(`request_stop`)는 controller 잠금을 잠깐 기다릴 수 있지만 그 안의 일은 메모리 판정뿐이다.
  > **범위 주석(2026-10-14 HIGH 재확인):** 이 문장은 당시 **규칙 저장소 경로**에만 맞았다. 뒤에 붙은 조용한 시간 판정(`QuietHours.settings`)이 DB 저장 동안
  > 잡힌 잠금을 기다려, 시작 게이트·전송권 확인 안에서 정지가 800 ms 넘게 막혔다(H-R1). 조용한 시간·잠시 쉬기·완료 기록·노드 목록을 불변 사본 읽기로 바꾼 뒤의
  > 현재 범위와 남은 예외는 [재확인 수리](devlog_2026-10-14-eval-recheck-fix.md) §3을 본다.
- `_sending`은 job이 끝나면(완료 이벤트) 지운다. 전송을 시작한 명령은 되돌리지 않는다 — 공기청정기를 원래대로 돌리거나 끄지 않는다.
- 폰은 `in_flight_notice`를 아직 화면에 띄우지 않는다(서버 응답까지). 실행 결과는 종전대로 기록·알림함에 남는다.

### M-N1 — 기준점 유효 기간·드리프트

- 옮긴 끝 시각 = `L0 + (x − R) − 드리프트 상한 × |x − R|`. 기준점 나이(`지금 − L0`)가 유효 기간을 넘거나, 불확실성(`상한 × |x − R|`)이 한계를 넘으면 None(보류).
- 상대 드리프트가 상한 안이면 나이를 실제보다 짧게 잡지 않는다(왕복 지연은 종전대로 나이를 길게 하는 쪽). 상한 500ppm은 리눅스 NTP 최대 보정 속도 수준의 **설계값**이다 — 두 보드
  사이 실제 드리프트·왕복은 아직 재지 않았다. 기본값에서 최대 불확실성은 600초 × 500ppm = 0.3초.
- 환경 변수: `SIMPLELAY_EVENT_CLOCK_REF_MAX_AGE_S`(600)·`SIMPLELAY_EVENT_CLOCK_DRIFT_PPM`(500)·`SIMPLELAY_EVENT_CLOCK_MAX_UNCERTAINTY_S`(1)·`SIMPLELAY_EVENT_CLOCK_REFRESH_S`(60). 잘못된 값이면 기동 거절.
- 전송 직전 재검사는 여전히 **나이 재검사**다 — 받은 뒤 링크가 끊기거나 기준점이 바뀌어도 받을 때 옮긴 값을 계속 쓴다('받은 당시 기준점으로 확인한 과거 사실은 유효').
  전송 때도 지금 링크·기준점이 유효해야 한다는 더 강한 정책은 택하지 않았다.

### M-N2 — 허용 경계

- 같은 프로세스: 허용 순간의 허브 단조 시각(메모리)과 사건 끝 시각(같은 축)을 비교. 벽시계 보정과 무관하다.
- 재시작 뒤 DB에서 불러온 허용: 이 프로세스의 사건 시계가 시작한 순간(`main.py` lifespan에서 만든다)이 경계 — 그 전에 끝난 가열은 허용 뒤의 사건인지 단정하지 않고 보류.
  재시작 뒤에 끝난 가열은 저장된 허용으로 보낸다. `allowed_at`(벽시계)은 표시용으로만 남는다.
