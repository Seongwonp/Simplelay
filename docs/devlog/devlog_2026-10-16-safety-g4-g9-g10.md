# G4·G9 정지 경계 수리 / G10 의미 고정 (2026-10-16)

기준: `main`의 `fc650ee` 위 작업 트리. 커밋·push·브랜치·stash 없음. CLAUDE.md·폰·키오스크·펌웨어·제출 초안 본문은 변경하지 않았다.
**검증 수준: 메모리 링크·가짜 MCU·모의 검증기를 쓴 시험 조건만. 보드 미배포, 실제 기구·누름·CT 미검증.**

## 1. 항목별 결과

| 항목 | 재현 / 변경 | 확인 범위 |
| --- | --- | --- |
| G4 | 동작 확인 이후 동작 잠금 대기 / 송신 함수 진입 직전 / 실제 쓰기 잠금 대기를 멈춰 두고, 별도 스레드의 `request_stop()` 완료 후 진행하면 옛 home·move가 stop 뒤에 전송됐다. 실제 쓰기 잠금 안에서 home·move·press의 정지 플래그를 다시 검사한다 | 공개 home·move_to·press 진입점 × 3경계 9건, 이동 뒤 Z 전송 직전 1건, 정지 뒤 상태 조회 및 명시적 재준비 1건 |
| G9 | 실제 `ActExecutor.run()` 수신 루프에 execute→abort를 넣었다. 이전 hold의 이동 응답을 지연시키면 hold 해제/join 때문에 abort가 늦어졌다. 준비부터 실행 자리를 예약하고 대기를 실행 task로 옮겼다 | appliance/drive abort가 join 3초를 기다리지 않고 MCU에 도착. 대기 중 정지 뒤 새 버튼 0개. 중복 execute는 busy, 준비와 실행을 같은 task로 기다리고 종료 상태 정리 |
| G10 | 실행 중 / hold 중 / 비상정지의 기존 동작을 유지했다. [안전 보고](../안전계약-적용-보고-2026-10-15.md) §2-1에 표로 분리 | 실행 중 정지는 구동부 중단. hold 일반 정지는 등록된 취소 누름 후 보관. drive·비상정지는 추가 누름·보관 이동 없음. 6건은 수정 전에도 통과 |

G9의 비상정지 호출은 콘센트 콜백 진입점으로 직접 넣었다. **기존 코드에서도 그 구동부 정지 요청은 지연되지 않았고, 최종 비상정지 회귀 시험은 수정 전에도 통과한다.** 기존 `error / estop_latched` 응답을 유지한다. 일반 abort 수신 지연 재현과 섞지 않는다.

G4는 정지 줄이 쓰인 뒤 옛 동작 줄이 이어지는 순서를 차단한다. 이미 쓰기 경계에 진입한 전송을 취소하거나, 막힌 transport 쓰기를 선점하는 기능은 아니다. G9도 shutdown·운영체제·스레드 풀의 모든 지연을 없앴다는 뜻은 아니다. 0.8초는 개발 PC 시험의 관측 한도이며 실물 정지 성능 수치가 아니다.

## 5. 배포와 남은 확인

`rpi/controller/serial_motion.py`는 RPi4에서도 쓰는 모션 어댑터이며 `rpi4/services/act_executor.py`도 바뀌었다. **RPi4 재배포 필요. RPi5·RPi4는 검토 후 같은 커밋으로 배포하고 설치 SHA를 기록한다.** 메시지 형식은 바꾸지 않았지만 옛 RPi4에는 G4·G9 결함이 남는다.

보드 날에는 실제 hold 이동 중 새 실행→정지, 잠금 대기 뒤 잔여 이동·누름 없음, 일반 hold 취소와 drive/비상정지의 차이를 확인한다. 신호·모터 축·캐리지·버튼·CT 중 어디까지 관측했는지 따로 남긴다. 솔레노이드·벨트 장착 후 PS-1을 진행하기 전 안전 전달표부터 채운다. 평가 설정 변경·실물 조작·자동 재누름 정책 변경은 이번에 하지 않았다.
