# 2026-09-21 — 공감지능 첫 수리: 다시 묻기·만료·키오스크 반복 안내

사용자가 기능·UI 계획의 구현 시작을 요청했다. 이번 범위는 제안의 수명과 넘김 처리다. 최근 기록 기반 학습·홈/제안 디자인 개편은 다음 단계다.

## 변경

- 패턴 제안을 넘기거나 승인하면 **해당 시간대 종료까지** 같은 가전·목적·시간대의 자동 재제안을 차단한다. 승인 제출 자체가 실패하면 차단을 풀고 카드를 복원한다.
- 기한은 서버 시계로 계산하며 자정을 넘는 시간대와 하루 전체 시간대를 처리한다.
- DB 설정이 있는 배포에서는 기존 SQLite settings에 다시 묻기 기한을 저장한다. DB 없는 개발 구성은 메모리 한정이다. 저장 실패를 넘김/실행 성공으로 응답하지 않는다.
- 패턴 제안은 시간대 끝에, 환경·데모 카드는 생성 15분 후 만료한다. 목록 조회와 승인/거절에서 검사하므로 만료된 카드는 실행하지 않는다.
- 환경 제안은 카드 유효기간까지 다시 묻지 않는다. 명시적인 데모 트리거는 생활 습관의 일시 차단에 섞지 않는다. 영구 숨김과 DND는 기존 계약을 유지한다.
- 제안 ID에 서버 인스턴스별 UUID를 넣어 재시작 전 카드 ID가 새 카드의 승인으로 해석되지 않게 했다.
- 키오스크 무응답은 거절로 보내지 않는다. 화면 세션에서 이미 자동 표시한 pending ID는 반복 표시·발화하지 않는다. 서버 목록에서 사라진 ID는 정리한다. 키오스크 재시작까지 노출 기록을 영속화한 것은 아니다.
- 제안 화면도 서버 목록을 확인해 다른 기기에서 처리됐거나 만료된 카드를 내린다.
- 넘김 응답을 기다리고, 실패하면 카드와 재시도 수단을 남겨 안내한다. 넘김 전송 중 승인/중복 넘김을 막는다. API는 401·500을 성공으로 삼키지 않으며, 이미 사라진 카드의 404는 멱등 넘김으로 처리한다.
- 영구 숨김 저장과 생성 판정을 같은 서비스 락으로 보호하고, 느린 미리보기 동안 시간대가 종료되면 새 카드를 만들지 않는다.

## 검증

- 수정 전 새 백엔드 회귀 테스트: **6 실패·1 통과**. 재제안·만료·자정 경계·재시작 ID 결함을 먼저 확인했다.
- 수정 후 **백엔드 전체 1,264 통과**, 의존성 deprecation 경고 2건.
- **키오스크 127 통과(골든 제외)**. 새 테스트 7건: 무응답 반복 방지, 새 카드 표시, 원격 처리/만료 반영, 넘김 실패 후 재시도, HTTP 200/404/401/500 처리.
- 백엔드 추가 검증: DB 재오픈 후 차단 유지, 저장 실패 시 실행 0회, 환경 제안의 가전별 차단, 동시 승인 1회 실행, 느린 미리보기의 시간 경계.
- Flutter analyze: 오류·경고 0. 기존 `settings_overlay.dart`의 `activeColor` deprecation info 1건 유지.
- 화면 레이아웃을 개편하지 않았으므로 골든 비교는 재실행하지 않았다. 폰 소스는 변경하지 않았고 폰 테스트도 이번에는 실행하지 않았다.
- RPi5에 배포하거나 실제 터치패널·모터를 구동한 결과가 아니다. 기존 RPi5 화면 표시 성공은 사용자 확인 사항이다.

## 검증 환경

- 프로젝트 `.venv`에 Python 테스트 의존성을 준비했다.
- Windows의 dbus-fast wheel 빌드가 인코딩 오류로 실패했다. 공식 PyPI의 2.46.4 소스를 `.venv/vendor`에 풀고 `src`를 PYTHONPATH에 지정해 변경 없이 실제 라이브러리를 로드했다. 가짜 Variant나 테스트 skip으로 대체하지 않았다.
- Flutter 3.47.5 / Dart 3.13.4를 `.venv/flutter`에 준비했다. `pub get --enforce-lockfile`을 사용했고 프로젝트 lockfile은 변경하지 않았다.
- Windows 한글 경로에서 shader compiler·analysis server·test isolate 오류가 발생했다. 영문 junction과 영문 TEMP/TMP/PUB_CACHE로 해결했다. 초기 충돌의 불완전한 테스트 산출물은 build 안에서 이름을 바꿔 보관한 뒤 새로 생성했다.

1차 완료 당시 최근 기간·서로 다른 사용일·별칭 정규화·학습 출처 분리는 미적용이었다. 최근 기간·사용일·출처 분리는 아래 2차에서 반영했다. 수동으로 같은 일을 끝낸 경우의 재제안 억제, 공간 상태/환경 변화에 따른 즉시 후보 철회, 노출/거절 통계도 별도 후속이다. 이번 수정으로 이 기능들이 완성됐다고 표시하지 않는다.

## 2차 — 습관 학습 근거 정비

- 기본 후보 조건: 최근 28일 안의 성공 기록, 서로 다른 사용일 3일 이상, 기존 최소 실행 횟수 충족. 28일/3일은 제품 기본값이며 사용자 실험으로 검증한 최적값은 아니다. `PatternConfig`로 조정할 수 있다.
- 같은 날 반복 실행은 횟수에는 남지만 사용일을 늘리지 않는다. 미래 기록은 제외하고, 자정을 넘는 시간대는 시작한 날을 같은 사용일로 센다. 시간대 판정은 서버 시계의 지역 시간 기준이다.
- 가전 ID와 목적을 함께 묶는다. 가전 A의 2일과 가전 B의 1일을 3일 습관으로 합산하거나 마지막 가전으로 몰아주던 동작을 제거했다.
- 실행 이력에 `execution_mode`(real/mock/unknown), `source`(direct/suggestion/demo/unknown)를 저장한다. 동기·비동기 실행 모두 실제로 선택한 컨트롤러의 모드를 기록하며, 추천/데모 승인 출처는 작업 스레드까지 전달한다. HTTP 요청에서 임의로 실제 실행 여부를 지정하지 않는다.
- 자연스러운 습관 후보에는 real + direct 성공 기록만 사용한다. 추천을 승인한 기록으로 같은 추천의 횟수가 계속 부풀어 오르는 것을 막는다. 모의·추천·데모 기록 자체는 삭제하지 않는다.
- SQLite는 열을 추가해 이전 DB를 유지한다. 기존 기록은 unknown으로 읽고 실제 사용이었다고 소급 표시하지 않는다. 따라서 모의 실행만으로는 자연 습관 카드가 생기지 않는다. 수동 데모 제안 기능은 유지한다.
- 서버 `reason`에 “최근 28일 동안 아침 시간에 3일 사용하셨어요.”처럼 근거를 보낸다. 앱·키오스크의 기존 reason 표시 경로를 사용하며 이번 차수에는 화면 배치를 변경하지 않았다.

검증: 백엔드 전체 **1,293 통과**, 의존성 deprecation 경고 2건. 새 회귀 테스트 29건으로 기간 경계·미래/오래된 기록·사용일·자정/시간대·가전 분리·모의/추천/데모 제외·DB 이관/재오픈·동기/비동기 출처 전달을 확인했다. 기존 테스트의 학습용 표본에는 실제/직접 사용이라는 전제를 명시했다. 다른 가전 기록 합산을 기대하던 테스트는 새 요구사항에 맞게 반대로 검증한다.

이번 차수는 Python 로직 변경이므로 Flutter 테스트를 반복 실행하지 않았다. RPi5 배포·실물 모터 검증은 하지 않았다.

남은 작업: 별칭/정규 목적 통합(사용자 정의 기능과 충돌하지 않도록 실행 의미까지 확인 필요), 수동 실행 직후 재추천 억제, 학습 상태 UI, 공간 상태에 따른 후보 철회, 노출/거절 통계. 현재 구현은 통계 기반 습관 감지이며 AI 모델을 지속 재학습하는 구현은 아니다.


## 3차 — 표현 통합과 학습 상태 화면

- 기본 규칙이 실제로 해석한 버튼 순서와 일치할 때만 `햇반 데워줘`/`밥 데워줘`/`즉석밥 데워 줘!`를 대표 목적으로 기록한다. 일반 실행 이력에는 원래 요청을 유지하고, 습관 학습용 이력에 대표 목적을 기록한다. 과거 이력을 일괄 변경하지 않는다.
- 사용자 정의 기능으로 실행한 목적은 원래 이름을 유지한다. 대표 이름이 사용자 정의 기능과 충돌해도 통합하지 않는다. LLM 재호출이나 의미 추측 없이 첫 결정론적 규칙 계층이 확인한 표현만 통합한다. 자유 발화 전체의 의미 통합은 아직 아니다.
- 알려진 별칭을 과거에 추천 숨김한 경우에도 대표 목적이 그 선택을 우회하지 않는다. 숨김 해제는 기존 설정 목록에서 원래 저장한 항목을 해제하는 방식이다.
- 읽기 전용 `/learning` API 추가. 최근 기간, 최소 사용일/횟수, 가전·시간대별 날짜/횟수, 습관 확인 여부, 숨김, 방해 금지를 전달한다. 실제 후보 생성과 같은 근거 집계를 공유하지만 현재 시간대 밖의 미완성 습관도 보여준다. 조회가 추천 생성이나 실행을 일으키지 않는다. 운영 라우터의 기존 API 키 인증을 적용한다.
- 앱 설정의 제안 영역, 키오스크 설정에 **생활 습관 알아가기** 진입 추가. 기록을 먼저 보여주고 기준 설명은 **어떻게 기억하나요?**에 접었다. 학습할 기록 없음, 연결 없음, 조회 실패를 구분하며 새로고침/닫기를 제공한다. 오래된 서버의 404도 빈 이력으로 표시하지 않는다.
- 키오스크는 로컬 설정 화면 안에서 열고 닫아 KioskCanvas 확대와 큰 글씨 설정을 유지한다. 앱은 다이얼로그로 표시한다. 습관 확인을 즉시 추천/자동 실행과 동일하게 표시하지 않는다.

검증:

- 백엔드 전체 **1,302 통과**(새 테스트 9건), 의존성 deprecation 경고 2건.
- 키오스크 비골든 전체 **131 통과** 후, 확대 유지/설정 복귀 통합 테스트 1건을 추가해 새 화면 5건 + 렌더 2건을 최종 통과했다.
- 앱 학습 화면 4건 + 기존 설정 화면 20건 통과. 수정 후 학습 화면 4건과 렌더 2건 재검증. 앱 전체 테스트를 실행한 것은 아니다.
- 390×844 앱, 800×480 키오스크에서 일반/1.6배 글씨 렌더 이미지 4장 생성 및 확인. 큰 글씨에서 설명 때문에 사용 기록이 밀리던 배치를 수정했다. 실물 터치패널 검증은 아니다.
- 정적 분석 오류/경고 없음. 기존 info는 앱 5건, 키오스크 1건이며 신규 null-aware 안내는 수정했다.

렌더: `app/test/goldens/learning_1.0.png`, `learning_1.6.png`, `rpi5-touchscreen-app/test/goldens/learning_1.0.png`, `learning_1.6.png`. 스크린샷 테스트는 기존 프로젝트 방식처럼 Windows 맑은 고딕을 사용하고 `FLUTTER_ROOT` 또는 로컬 `.venv/flutter`에서 아이콘 폰트를 읽는다.

다음: 수동으로 완료한 일을 곧바로 다시 권하지 않기, 공간/환경 변화로 무효해진 후보 철회, 학습 상태와 데모 시나리오 연결. RPi5 배포와 모터 실구동은 아직 하지 않았다.


## 4차 — 직접 완료한 조작의 재추천 억제

- 실제 컨트롤러에서 성공한 직접 조작을 별도의 `CompletedActions`에 남긴다. 같은 가전·같은 목적은 현재 습관 시간대가 끝날 때까지 다시 제안하지 않는다. 자정을 넘는 시간대도 하나로 취급한다. 환경 제안은 직접 조작 완료 후 15분간 쉬며 정확히 15분이 지나면 다시 후보가 될 수 있다. 이 값은 제품 기본 정책이다.
- 음성/목적 실행은 검증된 대표 목적으로 비교한다. 이름 없는 수동 버튼 실행은 **한 번의 실행 요청에서 전체 버튼 순서가 제안의 알려진 순서와 일치할 때만** 완료로 본다. 단일 버튼 요청 여러 개를 합치거나 알 수 없는 사용자 정의 동작을 추측하지 않는다. 수동 버튼 기록으로 습관 학습 횟수를 만들지 않는다.
- 제안 생성 직전에 재검사하고, pending 조회 때 완료된 카드를 제거한다. 앱·키오스크는 기존 폴링을 통해 다음 조회에서 반영한다. 이미 보이던 카드의 승인은 404로 거절되어 실행하지 않는다.
- 승인 확인 이후 의도 해석 중 직접 조작이 끝날 수 있으므로, 실제 실행 서비스의 시작 락 안에서 완료/만료를 다시 검사한다. 이 검사와 실행 점유 사이에 다른 직접 실행이 끼지 않는다. 동기·비동기 승인 모두 적용한다.
- 실패·모의/불명 실행·데모·추천 승인·사용자 정지 실행은 직접 완료 이력에서 제외한다. 사용자 정지 요청이 있었는데 컨트롤러가 성공을 반환한 경우에도 습관 로그를 성공으로 쌓지 않는다.
- 최근 완료 이력은 DB 설정에 저장하고 재시작 때 복원한다. 저장할 때 이틀보다 오래된 항목을 정리한다. 저장 실패 시 실제 성공을 실패로 바꾸지 않고 오류를 기록하며 현재 메모리의 억제는 유지한다. 이 예외에서는 재시작 후 유지까지 보장하지 못한다.
- 완료 추적은 업데이트 이후 실행부터 적용한다. 이전 실행 이력을 조작 완료로 소급 변환하지 않는다. 여기서 완료는 서버가 확인한 버튼 조작 성공이며, 가전 자체의 가열/세탁 같은 전체 운전 완료를 뜻하지 않는다. 명시적인 데모 카드 생성/승인은 유지한다.

검증: **백엔드 전체 1,329 통과**, 새 회귀 27건. 같은/다른 가전·목적, 전체/부분/역순 버튼, 실제/모의/실패/정지/데모 구분, 재오픈, 자정·시간대 시작·15분 경계, 미래 시각, 저장 실패, 미리보기/승인 해석 중 완료와 만료, 비동기 수동 조작을 검증했다. 의존성 deprecation 경고 2건 유지. `git diff --check` 통과.

이번 차수는 Python과 문서만 수정해 Flutter 테스트는 반복하지 않았다. 배포·물리 모터 시험은 하지 않았다. 다음 단위는 공간/환경이 달라져 더 이상 유효하지 않은 추천의 철회다.


## 5차 — 공간·환경 변화로 무효해진 추천 철회

- 공간 감지 게이트가 연결된 구성에서는 명시적 부재가 확인되면 기존 자연 추천도 철회한다. 생성·목록 조회·승인·실행 접수 직전까지 검사한다. 사람 감지 자체를 새로 구현한 것은 아니며 `SIMPLELAY_PRESENCE_GATING=true` 배선이 필요하다. 기존 정책대로 감지기 없음/TTL 만료의 unknown은 허용한다. 명시적인 데모 카드는 이 게이트의 예외다.
- 온습도가 제안 기준 아래로 내려가거나 센서가 없음/실패/유효하지 않은 값을 반환하면 환경 카드를 철회한다. 목적이나 대상 가전이 바뀌어도 이전 카드 ID를 재사용하지 않는다. 환경이 다시 제안 조건을 만족하면 새 ID로 생성한다. 철회는 사용자 거절이나 영구 숨김으로 저장하지 않는다.
- 값만 달라져 같은 환경 제안이 유효하면 ID·생성 시각·만료 기한을 유지하고 근거 문구만 갱신한다. 키오스크는 새 근거를 반영하면서 TTS나 카운트다운을 재시작하지 않는다. 앱은 기존 reason 갱신 경로를 사용한다.
- 센서 I/O는 제안 상태 락 및 실행 시작 락 밖에서 수행한다. `/suggestions` 조회도 작업 스레드로 이동했다. 실행 시작 게이트에서는 마지막 확인 후 **15초 미만**인 환경 스냅샷만 사용하며, 긴 의도 해석으로 오래된 근거가 된 경우 실행하지 않는다. 이 유효기간은 제품 기본 정책이다. 센서 확인 직후부터 물리 동작 전체 동안 환경이 고정됨을 보장하는 기능은 아니다.
- 승인 도중 상태가 무효해진 카드는 실패 복구 시 pending으로 되살리지 않는다. 방해 금지 중 목록 조회에서도 부재로 무효해진 자연 카드를 정리한다. 이미 접수되어 실행 중인 작업을 환경 변화만으로 자동 긴급 정지시키지는 않는다.
- NaN/무한대/비수치 온습도, 0~100% 밖의 습도를 근거에서 제외한다. 온도는 정상이고 습도만 무효라면 정상 온도만 사용한다. 습도만 높은 상황의 이유는 ‘더워요’ 대신 ‘습해요’로 표시한다.

검증: **백엔드 전체 1,356 통과**(새 회귀 27건), 의존성 deprecation 경고 2건. 부재/복귀/unknown, 온습도 정상화·손실·오류·갱신, 대상 변경, 생성/승인 도중 변화, 오래된 스냅샷, 잠금 중 센서 I/O 금지, 데모 예외, DND 중 철회 등을 검증했다. **키오스크 비골든 전체 133 통과**, 새 회귀는 근거 갱신 시 TTS·표시 시간 반복 방지다. `git diff --check` 통과. 화면 구조 변경이 없어 새 골든을 만들지 않았고, 앱 소스·폰 테스트는 이번 차수에 변경/실행하지 않았다.

반영은 서버의 다음 조회/생성/승인 검사 시점이며 센서 상태를 즉시 푸시하는 구현은 아니다. RPi5 배포, 카메라 감지 프로세스 연동, 실제 센서·모터 시험은 아직 하지 않았다. 다음 후보는 거절/철회/승인 이유의 기록과 본선 시연 시나리오 검증이다.

## 6차 — 피드백 사유 기록과 오프라인 본선 리허설

- 생성·승인 요청·접수·건너뛰기·숨김·만료·시스템 철회를 구분하는 이벤트 기록을 추가했다. 이유, 생성 근거, 가전, 출처, 작업 ID를 함께 남긴다. 반복 조회나 환경 문구 갱신을 새 노출로 세지 않으며 시스템 철회를 사용자 거절로 취급하지 않는다.
- 인증된 읽기 전용 `/suggestions/events` API 추가. 최근 2,000건을 메모리와 SQLite에 보관하고 조회는 최대 200건이다. DB 재오픈 복원을 검증했다. 저장 실패는 기록 상태에 표시하고 이미 접수한 실행이나 성공한 건너뛰기를 되돌리지 않는다. 실패한 기록의 재시작 복원은 보장하지 않는다.
- 비동기 `submitted`는 작업 접수이며 물리 성공이 아니다. 원시 예외 문자열은 피드백에 저장하지 않는다. 사용자별 선호도 모델이나 이벤트 조회 UI를 추가한 것은 아니다.
- 시연 온습도에 ‘시연 데이터’ 표시를 추가하고 이벤트 및 승인 이력을 demo로 분리했다. 실제 센서로 돌아오면 같은 조건이어도 이전 시연 카드 ID를 철회한다. 시연 환경의 쿨다운은 실제 환경 제안과 별도로 저장한다.
- 합성 사용 이력·가상 시계·테스트 컨트롤러를 사용하는 API 리허설 추가. 학습 근거 → 건너뛰기 → 다음 시간대 승인 → 중복 차단 → 직접 완료 억제 → 부재/복귀 → 숨김 → 시연 환경 철회 → 명시적 데모 승인 → 이벤트 추적을 연결했다. 테스트의 REAL 분기는 실물 측정이 아니다.

검증: **백엔드 전체 1,377 통과**, 새 피드백 회귀 20건과 통합 리허설 1건. 기존 의존성 deprecation 경고 2건. Python과 문서만 수정하여 Flutter 검증은 반복하지 않았다. 실물 동시 조작·센서·모터 시험은 별도다. 발표 순서, 기록 해석, 재실행 방법과 미검증 범위는 `본선-시연-검증-2026-09-21.md`에 정리했다.


## 7차 — 앱·키오스크 실행 추적 및 복구 점검

- 키오스크가 새 실행 접수를 기다리는 동안 이전 job ID를 유지해 이전 성공을 새 작업 완료로 오인할 수 있었다. 실행 화면 진입 시 추적 ID와 재시도 콜백을 초기화하고, 다른 단말 작업을 관찰할 때만 그 ID를 명시적으로 전달한다. 접수 응답 전에는 상태 폴링 결과를 실행 근거로 사용하지 않는다.
- 상태 응답과 완료 연출의 지연 콜백은 현재 화면 단계와 job ID를 다시 검사한다. 앱도 늦게 도착한 이전 작업의 오류/응답이 현재 작업의 연결 유효 시각이나 추적 상태를 바꾸지 않도록 보완했다.
- 키오스크의 연결 유실·서버 재시작 후 작업 유실은 ‘실행 상태를 확인할 수 없어요’로 표시한다. 연결이 살아 있어도 작업 기록이 사라질 수 있으므로 단순히 연결이 끊겼다고 단정하지 않는다. 음성도 같은 기준을 사용한다. 일반 실패와 서버가 보고한 safety_stopped를 구분하고, 후자에만 실행 정지 안내를 사용한다. 물리 모터 정지를 보증하는 문구는 아니다.
- 새 회귀 3건: 이전 작업 완료 직후 두 번째 접수 지연, 서버 재시작으로 작업 유실 후 대기 화면 복귀·다른 단말 작업 관찰, 확인 불가 화면이 정지를 단정하지 않는지. 두 번째 접수 테스트에서 실제 safety_stopped 응답의 화면 사유도 검증했다. 복구 경로는 명령을 재전송하지 않는다.

검증: **키오스크 비골든 전체 136 통과**, **앱 관련 40 통과**(작업 추월·재시작 복원·실행 상태·제안 provider 및 화면), **백엔드 관련 12 통과**(동시 승인/승인·거절 경쟁 각 50라운드, API 리허설, 정지, 서비스 생명주기). 백엔드 소스는 이번 차수에 바꾸지 않았다. 정적 분석 오류/경고 없음, 기존 info 앱 5건·키오스크 1건 유지. 이번 앱 전체 테스트와 실물 Wi-Fi/터치/모터 검증은 수행하지 않았다.

접수 응답 유실 시 해당 job ID를 모르는 문제 자체를 복구하는 요청 멱등키 프로토콜은 이번 범위에 포함하지 않았다. 확인 불가를 성공이나 정지로 바꾸거나 자동 재실행하지 않는다. 실제 두 단말 동시 조작 및 대표 흐름 20회 연속 실물 리허설은 여전히 남아 있다.
