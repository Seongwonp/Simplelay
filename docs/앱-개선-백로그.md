# 앱 개선 백로그

교차 리뷰(2026-09-08)에서 나온 항목 중 **아직 안 한 것**과, High 6건을 처리하면서
**의도적으로 남긴 것**을 모아둔다. 주차별 계획은 [결선로드맵](결선로드맵.md)에 있고,
여기는 "무엇을 왜 남겼는가"를 파일 단위로 기록해 다음 세션이 바로 집게 하는 용도다.

> 우선순위 원칙: **HW(폐루프 물리 조작)가 1순위**다(지도교수 방침 + 차별점).
> 아래 항목은 HW 브링업 사이사이에 넣는다. 화려함보다 단순함이 논지이므로,
> "정보를 더 넣는" 방향의 개선은 채택하지 않는다.

## A. 리뷰 Medium — 아직 안 한 것

### A1. 홈을 '연결 관리'에서 '지금 할 일' 화면으로
`app/lib/screens/home_screen.dart`

연결 칩·서버 카드·예비 BLE 카드가 함께 있어, 실제로 실행 가능한 상황에서도
"뭔가 더 연결해야 하는 앱"으로 보인다.

- 상단: 현재 가전명 + 조작 가능 여부 / 본문: 지금 확인할 제안 / 하단: 말·버튼 조작
- 서버·BLE 세부는 **'연결 상세'** 안으로
- **문구 과장 정정**: 서버 `ping()` 성공만으로 "AI 추론 · 제안 · 실행 준비 완료"를
  선언한다. 확인한 것이 서버 연결이면 **"기기와 연결됐어요."** 까지만 말해야 한다.
  (온디바이스 추론 계층은 아직 켜지 않았다 — [inference-boundary](inference-boundary.md))

### A2. 'AI 느낌'을 만드는 화면 조합 걷어내기
카드가 같은 중요도로 반복되고 주요 행동이 뒤로 밀리는 **정보 구조**가 원인이다.
둥근 카드를 각지게 바꾸는 식의 표면 변경으로는 해결되지 않는다. 팔레트는 유지.

| 화면 | 문제 | 변경 |
|---|---|---|
| `suggestion_screen.dart` | 가운데 정렬 제목·설명·지도·목록을 쌓아 설명 페이지처럼 보임 | 왼쪽 정렬로 가전명 → 실행 질문 → 순서. 장식 여백 축소 |
| 〃 버튼 지도 | 복잡한 실제 패널을 다시 크게 보여줘 단순화 이점이 약함 | 기본은 순서 목록, 지도는 **'실제 버튼 위치 보기'** 로 접기 |
| 〃 단계 목록 | 지도에서 본 내용을 카드로 반복 | 카드 테두리 제거, 하나의 번호 목록으로 |
| `voice_screen.dart` 파형 | 실제 음량이 아니라 정해진 반복 애니메이션 — 잘 듣고 있다는 인상을 과장 | 삭제하거나 실제 입력에 연동 |
| `status_screen.dart` 차트 | 면적이 크고 의미·시간축이 불분명해 개발 도구처럼 보임 | 기본은 현재 동작·확인 결과, 차트는 상세로 |
| `settings_screen.dart` | 스위치마다 별도 패널이라 중요도가 평평함 | 일상 설정은 구분선 목록, 노드·주소·동기화는 '설치 및 연결 관리'로 |
| `onboarding_screen.dart` | '환영합니다 + 기능 3개'는 흔한 앱 소개. 사용법보다 네트워크 용어를 설명 | **"가전 버튼을 대신 눌러드려요."** → '말하기 → 확인 → 실행'. `.local` 설명은 설치 도움말로 |
| `theme/app_theme.dart` | 본문 18인데 하단 탭 11 — 큰 본문과 작은 길찾기가 따로 설계된 느낌 | 탭 14 안팎, 보조 설명 16 기준 |

> 이 표의 "하단 버튼 폭" 항목은 완료(`a009721`) — 1:2 배분이라 '이번만 넘기기'가
> 단어 중간에서 줄바꿈되던 문제를 키오스크와 같은 3:4로 맞췄다.

### A3. '왜 추천했는지'와 '안 받기'의 결과를 분명하게
`app/lib/providers/suggestion_provider.dart`, `app/lib/screens/settings_screen.dart`

- HTTP 응답의 `time_band`·`occurrences`를 앱 제안으로 옮길 때 **버린다**. 환경 제안의
  `reason`은 표시되지만(완료) 사용 패턴 근거는 약하다 →
  **"최근 저녁 시간에 4번 사용했어요."** 처럼 한 문장으로.
- BLE 제안에서는 '이번만 넘기기'와 '다시 받지 않기'가 결국 같은 `approved: false`
  메시지다. 영구 억제를 약속해놓고 그 경로에서는 전달하지 못한다 →
  **영구 억제를 지원하는 제안에만** 그 버튼을 보이기.
- 억제 직후 **"이 제안은 앞으로 표시하지 않아요. 되돌리기"** 제공.
- 억제 목록의 **로딩·조회 실패를 빈 목록과 구분**("불러오지 못했어요. 다시 불러오기").

### A4. 이력·알림을 읽은 뒤 할 수 있는 행동
`app/lib/screens/history_screen.dart`, `care_events_screen.dart`

- 이력 상세에 **성공한 단계 / 확인하지 못한 단계 / 시도 횟수** 표시.
- 실패 결과에 작은 회복 동선(기기 연결 확인 · 버튼으로 조작 · 도움 요청 문구 복사).
- 알림함: 최초 조회 실패를 '알림 없음'과 구분, 마지막 확인 시각 표시.
- **앱 재시작 후에도 진행 중 job을 다시 확인**하도록 마지막 job_id·대상 가전 보존.

### A5. 실제 위젯 색 대비 (토큰 쌍이 아니라 실제 조합)
작은 일반 텍스트 기준 WCAG AA는 4.5:1.

| 위치 | 조합 | 측정 |
|---|---|---|
| `suggestion_screen.dart` 순서 배지 | 라이트 강조색 위 검정 | 약 3.78:1 |
| `settings_screen.dart` 억제 빈 상태 | 크림 배경 위 `Colors.grey` | 약 2.38:1 |
| `home_screen.dart` 알림 배지 | 다크 빨강 위 흰 작은 숫자 | 약 3.63:1 |

## B. High 처리하면서 의도적으로 남긴 것

### B1. 패턴 제안은 대상 가전을 모른다 ★가장 큰 잔여
`rpi/intent/models.py`(UsageRecord), `rpi/services/persistence.py`

제안↔가전 결합(`0b87bd3`)으로 **환경 제안**은 대상을 들고 다니지만, **사용 이력에
가전이 기록되지 않아** 패턴 제안은 대상을 모른다. 현재는 클라이언트가 현재 선택
가전으로 폴백한다(대개 맞다 — 그 가전에서 쓴 이력이므로).

완전히 닫으려면 `UsageRecord`에 `appliance_id`를 추가하고 SQLite 스키마·기록 경로·
패턴 후보 생성까지 이어야 한다. 여러 가전을 실제로 함께 쓰기 시작하면 필요해진다.

### B2. 가전 삭제를 선택 칩에서 분리
`app/lib/screens/settings_screen.dart`

파괴적 동작이 선택 칩 안의 작은 ×에 붙어 있다. **확인 대화상자로 보호되고 있어
위험은 낮아** 이번엔 히트박스만 다뤘다. 정석은 가전 상세의 '가전 삭제' 버튼으로 분리.

### B3. 음성 실패 화면 자체의 대체 경로
`app/lib/screens/voice_screen.dart`

홈에서는 두 경로를 항상 보이게 했지만(`d696325`), 음성 화면에서 인식이 실패하면
여전히 스낵바 안내 위주다. 실패 화면에 **"다시 말하기 · 버튼으로 조작"** 을 남기면
같은 시도를 반복하지 않는다.

### B4. 골든이 환경을 탄다
`app/test/goldens/`, `rpi5-touchscreen-app/test/goldens/`

다른 환경에서 생성된 골든이 이 머신에서 미세하게 어긋났다(테두리 안티에일리어싱·
아이콘 글리프, 0.06~0.31%). 내용 회귀가 아니라 래스터화 차이다. 반복되면 **허용
오차 비교자(tolerance comparator)** 도입을 검토한다.

### B5. 온디바이스 추론 계층이 아직 꺼져 있다
`rpi/api/deps.py`, [inference-boundary](inference-boundary.md)

규칙 → 온디바이스 의미검색 → 온디바이스 LLM의 3계층 중 **1계층(규칙)만 켜져 있다.**
2·3계층은 코드가 준비돼 있고 연결도 확인했지만 실기기 활성화를 확정하지 못했다.
발표에서는 **"경계를 설계하고 연결을 검증했다"** 까지가 정직한 선이다.
켜는 작업은 HW 폐루프가 굳은 뒤에 한다(어려운 것 두 개를 동시에 디버깅하지 않는다).

### B6. 15인치는 프리뷰로만 확인
`rpi5-touchscreen-app/lib/widgets/kiosk/kiosk_canvas.dart`

설계 캔버스 비율 확대(`09cb76c`)는 위젯 테스트와 프리뷰 골든으로 검증했다.
**실기기 육안 확인은 장비 수령 후**(터치 정확도·가독성).

### B7. 데모 실행 주입이 `kDebugMode`에만 걸려 있다
`app/lib/screens/suggestion_screen.dart`

BLE 승인 경로에서 `kDebugMode`만으로 데모 실행 흐름(가짜 센서)을 주입한다.
**실기기 디버그 실행에도 가짜 센서가 섞일 수 있다** — 진짜 실행을 성공처럼
보이게 만들 수 있어 위험하다. 명시적인 데모 세션(env·설정 플래그)에서만
동작하게 바꿔야 한다. 리뷰가 안티패턴으로 지목한 항목이기도 하다.

## C. 권장 순서

1. **HW 브링업** — 시리얼선·전류센서·좌표 캘리브레이션 (별도: 로드맵 W3/W5)
2. **B1** 사용 이력에 가전 기록 (여러 가전 데모를 하려면 선행)
3. **A3 + A5** — 근거 문장과 색 대비. 둘 다 작고 심사 기준(접근성)에 직결
4. **A1 + A2** — 화면 인상 개선. 전면 재설계 없이 정보 구조만 정리
5. **B7** 데모 주입 게이트 정리 (작지만 위험도가 있다)
6. **A4, B2, B3** — 회복 동선·세부
7. **B5** 온디바이스 계층 활성화 (HW가 굳은 뒤)

## 하지 않기로 한 것 (리뷰 안티패턴)

- 실패 화면에 '전체 다시 실행' 버튼 — 일부 버튼은 이미 눌렸을 수 있다
- '되돌리기'로 반대 버튼 자동 누르기 — 물리 조작은 취소 연산이 아니다
- 센서 숫자·신뢰도·차트 늘리기 — 필요한 것은 "눌림을 확인했는가"다
- 모든 동작에 확인창 — 확인은 대상·순서가 불확실한 실행에 집중
- 앱에서 못 받는 데이터를 데모 센서 값으로 보충
- 새 모델·클라우드 추론·복잡한 보호자 플랫폼 신설
