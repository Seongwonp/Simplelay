# 실측 기록표 (원가 · 설치 시간 · 대안 비교 · 성공률 · 정지 지연 · CT 조리 판정)

작성 2026-09-14. **빈 표와 측정 방법만 둔다.** 실측하지 않은 숫자는 채우지 않는다 —
발표·질의응답에 쓰는 숫자는 이 표에 기록된 측정에서만 가져온다.

측정 순서와 원시 데이터 수집 도구는 [하드웨어 연결 설계](하드웨어-연결-설계.md) §6을 따른다.

## 공통 규칙

- 칸마다 **측정일·측정자·조건**이 추적돼야 한다. 조건이 바뀌면 새 행으로 쓴다.
- 원시 데이터(CSV·영상)는 저장소에 올리지 않는다. 이 문서에는 **요약 수치와 원시 파일 이름**만 적는다.
  - 센서 원시값: `python -m rpi.bench.raw_recorder` → `data/bench/` (git 무시 경로)
  - 실행 이력: 서버의 실행 이력 CSV 내보내기(작업 ID·결과·버튼별 시도 수·정지 지연)
- 추정·조사값은 실측과 섞지 않는다. 쓸 때는 비고에 `추정` 또는 `조사(출처)`를 붙인다.
- 빈칸은 "아직 모름"이다. 0이나 "-"로 메우지 않는다.

## 4. 성공률

**측정 방법**

- 대상: 전자레인지 버튼 3개부터. 버튼마다 목표 반복 수를 정하고 시작 전에 적는다.
- **사람 판정이 기준이다.** 가전 표시창 변화·버튼음을 영상으로 남기고, 누름이 실제로
  들어갔는지 사람이 판정한다. 센서 판정은 사람 판정과 비교하는 대상이다.
- 실패 주입(리허설 기능)을 쓴 시도는 따로 표시하고 자연 성공률 합산에서 뺀다.
- mock 모션 실행은 기록하지 않는다(실행 이력의 실행 모드로 확인).

### 5-1. 모션 보드 정지 응답 — 시험대 실측(10/13~14)

**조건:** 벨트·솔레노이드를 달지 않은 시험대(모터 축·엔코더만). 위 표의 t0(사람이 누른 순간)·③(캐리지 물리 정지)는
아직 재지 않았다 — 아래는 **소프트웨어가 정지를 보낸 뒤** 모션 보드가 답한 시간과 엔코더로 멈춤을 확인한 시간이다.
원기록: [10/13 보드 날](devlog/devlog_2026-10-13-desktop-board.md) §2, [10/14 마감](devlog/devlog_2026-10-14-desktop-close.md).

| 구간 | 경로·조건 | 표본 | 값 |
|---|---|---|---|
| A. 보냄 → 모션 보드 응답(`mcu_ack`) | 개발자 경로, 5 mm 조그 시작 약 88 ms 뒤 정지 | n=10 | 중앙 **10.95 ms** |
| B. 보냄 → 멈춤 확인(`verified`, 엔코더 두 번) | 같은 조건 | n=10 | 중앙 **160 ms** |
| A | 폰 실행 상태 화면 정지(일반 실행 중) | 1 | 16.7 ms(화면 "모션 보드 응답 18 ms") |
| A | 폰 정지 — 이동 중(`move` 34 ms 뒤) | 1 | 10.1 ms, MCU 이동 `error: stopped` |
| A·B | 루틴 실제 경로 이동 중 정지(0.2 s 뒤, 10/14) | 1 | `verified`, 응답 18 ms, 누름 없음 |
| A·B | 누르는 도중 정지(`press_start` 70 ms 뒤, 10/14) | 1 | `verified`, 응답 15 ms |

- 화면의 ms는 기록 간격보다 0~1.3 ms 크다(측정 지점 차이).
- 이 값은 **정지까지 걸린 시간이 아니다.** 캐리지 물리 정지(③)는 벨트 장착 뒤 영상·엔코더로 위 표에 적는다(측정 필요).

## 6. CT 가열 판정 (전자레인지 가열 시작·가열 종료 감지, 2026-10-13 추가 — 종료 감지는 조리 완료가 아닐 수 있음)

[시연 계획 v4](본선-시연-계획-v4.md) 선행 조건 ②. 가열 종료 감지 → 공기청정기 자동 실행의 조건이 이 판정이라,
**가열이 아직 진행 중인데(전력 감소·팬만 도는 구간) 종료로 잡지 않는지**(B·D)가 핵심이다. 버튼 누름 완료는 가열 종료로 치지 않는다.
아직 한 번도 재지 않았다.

> **정책(10/14 사용자 확정, 3차 평가 L1):** 가열 종료가 감지되면 취소·문 열림이어도 제안·자동 실행이 일어날 수 있다 — 공기청정기 풍량 변경은 낮은 위험 동작이라 허용하고, 화면·문서에 '조리 완료가 아닐 수 있음'을 명시한다. 그래서 **C1·C2는 실패 판정이 아니라
> 가열 종료 감지·제안·자동 실행이 일어났는지와 그 지연을 기록**한다. 문구 정책이지 취소 판별이 생긴 것이 아니다.

> **지금 판정의 한계(2026-10-14 코드 확인):** `rpi/verifier/cycle_end.py`는 'CT 전력이 운전(≥ `run_min_w`)을 `min_run_s` 넘게
> 지난 뒤 대기(≤ `standby_max_w`)로 `settle_s` 머묾'만 본다. **취소 버튼이나 문 열림으로 가열이 끝나도 전력 모양이 같아서
> 정상 종료와 구분하지 못한다.** 그래서 화면·카드·기록은 '가열 종료 감지(조리 완료가 아닐 수 있음)'라고만 말한다.
> 아래 C1·C2에서 구분 근거(예: 종료음·남은 시간·문 스위치)를 찾기 전까지 이 표현을 올리지 않는다.

시각은 영상(조작부·표시창·종료음이 함께 보이게)과 실행 이력·콘센트 모듈 원시 기록을 맞춰 적는다.

| 시각 | 뜻 | 측정 방법 |
|---|---|---|
| **실제 시작** | 마그네트론·조명·팬이 켜진 순간 | 영상 프레임 |
| **시작 판정** | 서버가 가열 시작(L3 `operation_confirmed`)을 낸 시각 | 실행 이력 |
| **실제 종료** | 표시창 0·종료음 | 영상 프레임·마이크 |
| **완료 판정** | 서버가 가열 종료(`heat_complete`)를 낸 시각 | 실행 이력 |

경우(각 3회 이상):

- **A 정상 짧은 가열** — 30초 가열 그대로 끝까지.
- **B 가열 중 전력 감소** — 출력 단계를 낮추거나 출력이 주기적으로 꺼졌다 켜지는 구간. 이 감소를 완료로 잡으면 실패.
- **C1 중간 취소(취소 버튼)** — 가열 중 취소 버튼. 정책상 **실패가 아니다** — 가열 종료 감지가 났는지, 카드·자동 실행이 일어났는지,
  취소 → 감지 → 실행까지의 지연을 기록한다. 지금 판정으로는 **정상 종료와 같게 나올 것으로 예상**(위 한계) — 구분 근거(취소 때와 정상 종료 때의
  전력·종료음 차이)가 보이면 함께 적는다. 화면·기록이 '조리 완료가 아닐 수 있음'을 밝혔는지도 본다.
- **C2 중간 문 열림** — 가열 중 문을 연다(가열이 멈추고 조명은 켜질 수 있다). C1과 같은 기록(실패 아님). 문을 연 채 둘 때와 바로 닫을 때를 나눠 적는다.
- **D 종료 후 팬 동작** — 가열이 끝난 뒤 냉각 팬만 도는 구간. 팬 전력을 가열로 보거나 팬이 멈출 때까지 완료가 끌려가는지 본다.
