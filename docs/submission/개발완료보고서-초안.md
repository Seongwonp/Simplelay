## 1. 개요

### 1-1. 작품 한 줄

**기존 가전은 그대로 두고 위에 얹어 버튼을 대신 눌러 주는 부착형 장치**다. 여기에 사용 습관에 따라 먼저 제안하고, 사용자가 승인해야만 실행하며, 눌렸는지 스스로 확인하는 지능 계층을 더했다. 버튼식 가전은 XY 갠트리로, 스마트 가전은 ThinQ Connect 경로로 다룬다. 두 경로는 **하나의 승인·실행·확인 흐름**에 묶인다. 결선 시연은 버튼식 가전 세 가지(전자레인지·세탁기·인터폰)를 "한 사람의 하루"로 엮어 보인다.

### 1-2. 배경 문제

1. **가전 교체 비용.** 스마트 가전은 비싸고, 집에 있는 저가 가전은 원격 제어 기능이 없다. 【가격 비교표 — 출처를 붙여 기입】
2. **조작 부담.** 버튼이 작고 메뉴가 깊은 가전은 어르신이나 손이 불편한 사람에게 어렵다. 같은 조작을 매일 같은 시간에 반복한다.
3. **"눌렀다"와 "됐다"는 다르다.** 기존 버튼 누름 로봇은 누르고 끝난다(반응형). 버튼이 덜 눌리거나 가전이 받아들이지 않아도 사용자는 모른다.
4. **자동화와 통제의 균형.** 알아서 켜 주는 자동화는 가열 기기처럼 위험한 가전에서는 오히려 불안하다.

### 1-3. 목표

| 목표 | 이번 결선 범위 |
|---|---|
| 버튼식 가전을 교체 없이 원격·음성으로 조작 | CoreXY 갠트리와 Z 누름. 【HW 대기】 갠트리 조립 중 |
| 눌렸는지·가전이 동작했는지 스스로 확인 | 폐루프 L1~L3 설계·구현, **모의 검증** |
| 습관 근거로 먼저 제안하되 승인 뒤에만 실행 | 구현, 시연·테스트 데이터로만 확인(실제 사용 이력 없음) |
| 버튼 가전과 스마트 가전을 한 흐름에 | 물리 경로와 ThinQ 경로 공통 계약. **ThinQ는 모의** |
| 여러 가전에 같은 흐름(사용자 루틴) | 전자레인지·세탁기·인터폰 루틴 4개(아침 데우기·외출 전 세탁·방문자 문 열기·세탁 끝 알림), **모의**. 실물은 전자레인지 갠트리 1대를 먼저, 세탁기·인터폰은 조작부 모형 |
| 가전이 끝난 것을 알아채 다음 행동으로 | 세탁 완료 = 콘센트 CT 전력 하강 + 종료음 교차 확인, **가짜 콘센트 모듈·합성 음 수준**, 기준값 측정 전 |
| 화면과 무관한 비상정지 | 콘센트 모듈 버튼 → 가전 전원 차단·래치·사람 확인 해제. 펌웨어 **컴파일**, 래치·해제 흐름 **모의**, 회로 미조립 |

## 2. 시스템 구성

### 2-1. 전체 구조

```
폰 앱 ─Wi-Fi(HTTP)─┐
키오스크(RPi5 화면) ┤
                   ▼
            RPi5 허브 ──인터넷──▶ ThinQ 클라우드 ─▶ 스마트 가전 (현재 모의)
         (해석·제안·승인 게이트·이력)
                   │ 줄 단위 JSON (UART 설계, 현재 LAN 위 시험 배선)
                   ▼
            RPi4 실행기 (폐루프 L1·L2, 정지, 재시도)
                   │ USB 시리얼 (모션 규약 home/move/press/stop/ping/limits)
                   ▼
            모션 MCU ─▶ 모터 드라이버 ─▶ FIT0482 ×2 (CoreXY) + Z 누름
            ESP32 콘센트 모듈 ─ CT 전력(USB 시리얼) ─▶ RPi4 (L3 판정·세탁 완료 판정) · 버튼 → 릴레이 비상 차단
            마이크 ─▶ RPi4 (비프음·종료음·위험 소리)
```

## 4. 핵심 기술

### 4-1. 층별 폐루프 검증 L1~L3

누른 뒤 세 층으로 나눠 확인하고, 층마다 복구 방법을 다르게 둔다.

| 층 | 확인하는 것 | 근거 신호(설계) | 실패 시 |
|---|---|---|---|
| L1 눌림 | 버튼이 물리적으로 눌렸는가 | 모터 전류 변화 | 위치·깊이를 보정해 재누름. 버튼당 최대 3회, 그래도 안 되면 안전 정지 |
| L2 수용 | 가전이 입력을 받았는가 | 비프음(마이크). 카메라 표시창 비교는 후보 | 같은 입력을 1회 다시 넣는다 |
| L3 동작 | 가전이 실제로 동작하는가 | CT 전력: 기준선 대비 상승·유지, 대기 전력 복귀 | **자동 재시도 없이** 안전 정지 |

- 판정기는 꽂아 쓰는 구조다. 판정기가 없으면 L1만 동작한다.
- 실행 결과에 버튼별 시도 수, 실패 층, 보정 내용이 실린다(`button_results`).
- **검증 수준.** 판정 로직, 재시도, 보정 요청은 **모의** 입력으로 검증했다. L3 실물 경로(`SIMPLELAY_L3_MODE=real`)는 콘센트 모듈 포트가 설정됐을 때만 배선되고, 없으면 기동을 거절한다. 콘센트 모듈은 가짜 출력으로만 시험했다. 임계값은 추측이며 `【실측 후 기입】`이다.
- 시연에서는 햇반을 실제로 데워 L3(전력 상승)와 잔여 전류 꼬리를 실측할 계획이다. 빈 상태 가열 금지·조리 시간 상한·비상정지 동작 확인을 설치 체크리스트로 둔다([운영 런북](../결선-운영-런북.md) §3-7).
- 측정 계획: 버튼 3개 × 30~50회로 누름 성공률과 정지 지연을 잰다.

| 지표 | 값 |
|---|---|
| 1회 누름 성공률 | 【실측 후 기입】 |
| 재시도 포함 성공률 | 【실측 후 기입】 |
| 정지 요청 → 모터 정지 시간 | 【실측 후 기입】 |
| CT 켜짐/꺼짐 판정 정확도(전자레인지) | 【실측 후 기입】 |
| 완료 → 대기 전력 복귀 시간 | 【실측 후 기입】 |
| 세탁 완료 판정(전력 하강·종료음 일치율) | 【실측 후 기입】 |

### 4-2. 승인 결속

- 제안 카드에는 실행할 명령(대상·경로·동작·인자)의 **지문**이 들어 있다.
- 승인하면 서버가 정의로부터 명령을 다시 만들고, 그 지문이 카드와 같을 때만 실행한다. 카드를 띄운 뒤 정의가 바뀌었거나 다른 명령이 끼어들면 실행하지 않는다.
- 여러 단계 루틴은 승인 한 번에 묶은 명령만 실행한다. **앞 단계가 확인되지 않으면 다음 단계를 보내지 않는다**(예: 아침 데우기의 복약 안내는 데우기 시작 확인 뒤).
- 가열 기기는 승인 없이 실행하지 않는다. 음성으로는 시작할 수 없고, 정지만 할 수 있다(설계).

### 4-3. 실행 출처와 확인 수준 표시

화면은 서버가 보고한 것만 성공으로 보인다.

- **실행 환경.** 실제 장치인지 모의인지를 키오스크 상단과 폰 배너에 표시한다. 모의 가전 이름에는 "(모의)"를 붙인다.
- **경로.** 물리 버튼인지 ThinQ인지 표시한다.
- **확인 수준.** "접수됨 / 접수 불명 / 상태 확인됨 / 실행기 보고만 받음"을 나눈다. "상태 확인됨"일 때만 성공으로 적는다.
- 결과를 잃으면 "확인 불가"로 두고 **자동 재전송하지 않는다.** 중복 가열을 막기 위해서다.
- "정지됨"(사용자가 멈춤)과 "안전 정지"(확인 실패로 멈춤)를 다른 문구로 알린다. 둘 다 "장치를 확인해 주세요"를 붙인다.

### 4-3-1. 세탁 완료 판정 — 전력 하강 + 종료음 교차 확인

- **전력.** 콘센트 모듈 CT 전력이 운전 하한 이상으로 일정 시간 돈 뒤 대기 상한 이하로 내려와 머물면 "사이클 끝"으로 본다. 담금·헹굼 사이의 짧은 하강은 끝으로 보지 않는다. 끊긴 구간은 대기로 세지 않는다.
- **소리.** 위험 소리 감지 신호처리를 재사용해, 몇 번 울리고 조용해지는 종료음 묶음을 찾는다. 계속 반복되면 경보로 보고 종료음이 아니라고 본다.
- **융합.** 두 입력이 시간 창 안에서 맞으면 "세탁이 끝났어요", 하나면 "끝난 것 같아요 — 확인해 주세요"로 말을 낮추고 루틴의 안내 문장을 읽지 않는다. 출처(실물/모의/주입)를 함께 기록하고 화면 문장에 붙인다.
- 세탁기는 기동 전류가 커서 콘센트 릴레이로 끊지 않고 **CT로 재기만** 한다.
- **검증 수준.** 가짜 콘센트 모듈과 합성 음으로 RPi4 판정 → RPi5 루틴 안내까지 시험했다(릴레이 명령 0건 확인). 실제 세탁기·CT·마이크는 0건이고 기준값(운전·대기 W, 대기 유지 시간, 종료음 대역·개수)은 **전부 추정**이다. 무대 세탁기는 물을 돌리지 않으므로 시연은 표시된 주입으로 보인다.

### 4-3-2. 비상정지 래치와 사람 확인 해제

- 콘센트 모듈은 버튼을 매 틱 보고 **호스트와 무관하게** 릴레이를 열어 가전 전원을 끊는다. 래치는 모듈(재부팅 보존)과 RPi4 양쪽에 걸린다.
- 래치가 걸리면 모든 실행을 거절하고, 키오스크 위쪽 띠와 폰 배너로 알린다. 버튼을 풀고 화면에서 확인해야 풀리며, 버튼이 눌린 채면 해제를 거절한다. 자동 해제는 없다.
- 릴레이가 끊는 것은 **가전 전원**이지 모터 전원이 아니다. 모션 이상 때 갠트리 전원은 개별 스위치로 끊는다.
- **검증 수준.** 펌웨어 컴파일, 래치·해제 흐름은 가짜 모듈·시뮬레이터 모의, 회로 미조립. 버튼 → 차단 지연은 `【실측 후 기입】`.

### 4-4. 하이브리드 제어 — 물리 버튼 + ThinQ

- 전문가 의견(9/29)에 따라 물리 버튼 경로 옆에 ThinQ Connect 경로를 두었다. 같은 명령 계약(대상+경로+동작+인자, 지문, 확인 수준)을 쓴다.
- ThinQ 명령은 보낸 뒤 상한 시간 안에 상태를 다시 읽어 바뀐 것을 확인한다.
- 이미 보낸 클라우드 명령은 취소를 보장할 수 없다. 그래서 정지 화면에 그렇게 표시하고, 가전 전원 끄기를 자동으로 보내지 않는다.
- **검증 수준: 모의.** 실제 ThinQ 클라이언트는 미구현이다. 등록 가전과 PAT를 확보해야 한다. 속성 이름은 추측이며 확인이 필요하다.
- 결선 시연 본 장면은 버튼식 가전 세 가지로 하고, ThinQ 경로는 질의응답에서 모의 장애 주입으로 보인다.

### 4-5. 공간·습관 제안

- **습관.** 최근 28일의 실제·직접·성공 사용만 가전과 시간대별로 센다. 시연·모의·제안 승인 기록은 학습에서 뺀다. 서로 다른 3일 이상이 기준이다.
- **절제.** "건너뛰기"(이번만)와 "숨김"을 구분한다. 같은 시간대에 반복해서 권하는 것을 제한한다.
- **철회와 거절을 따로 기록.** 사용자가 직접 끝낸 조작, 명시적 부재, 환경 근거 소멸로 시스템이 거둔 제안은 "거절"로 배우지 않는다.
- **공간.** 재실 보고로 부재 중 제안을 보류한다(설정으로 켬). 레이더 같은 공간 감지 하드웨어는 없다. 재실은 수동 보고나 시연 입력이다.
- **날씨.** 보조 조건으로만 쓴다. 날씨를 받지 못하면 실내 기준만 쓰고 "날씨 정보 없음"을 근거에 적는다.
- 모든 판단은 통계·규칙 기반이다. 개인 식별이나 학습형 선호 모델은 없다(지도교수 방침: AI 고도화보다 하드웨어).

### 4-6. 온디바이스 우선 추론 경계

목적 → 버튼 시퀀스 → 실행 → 검증의 핵심 경로는 **인터넷 없이 끝난다.** 의도 해석은 다음 순서로 시도한다.

1. 규칙
2. 기기 안 유사도 매칭(선택)
3. 기기 안 대화형 해석(선택)
4. 외부(기본 꺼짐)

모두 실패하면 "모르겠다"고 실패한다. 아무 버튼이나 누르지 않는다. 자세한 내용은 [inference-boundary.md](../inference-boundary.md)에 있다.

### 4-7. 접근성

[사용자 편의 체크리스트](../사용자편의-가이드-체크리스트.md)를 기준으로 했다(KS X 3253, KS X 9211, 고령층 친화 키오스크 표준).

- 큰 글씨, 음성 안내(TTS), 터치 영역 48dp 이상, 색만으로 상태를 말하지 않기(문구·아이콘 병행), 깜빡임 1초에 1회 이하
- 사용자 말 문구. 예: "플러그 연결이 약해요 · 끝났다는 알림이 늦을 수 있어요"
- 키오스크 가장자리 48px 안전 여백. 실기기에서 가장자리 터치가 앱을 닫는 것을 발견하고 넣었다.
- **미확인:** TalkBack 완주, 실제 패널에서 글자 크기 실측, 당사자 평가

## 5. 플랫폼 활용

- RPi5와 RPi4는 **LG 제공 임베디드 SW 플랫폼** 이미지 위에서 동작한다. 우리 백엔드와 실행기는 플랫폼 위 컨테이너로 올렸다.
- 키오스크는 플랫폼 앱으로 설치했고, 플랫폼 앱 관리자를 통해 부팅 자동 실행된다.
- 플랫폼이 제공하는 기기 안 기능(유사도 검색, 대화형 해석, 맥락 정보)은 선택 계층으로 배선했다. 꺼져 있거나 실패해도 핵심 경로는 동작한다.
- 가산점 (1) "하드웨어 3종 연동"은 RPi5(해석·제안·키오스크), RPi4(실행·검증, 안내문 예시의 RPi Zero 자리 — 2026-10-05 확정), ESP32(전력·비상 차단)로 대응한다.
  - **증거 상태:** 보드별 앱 계정 최소 호출과 실제 시연 연동 기록은 모두 미측정이다. 실측 뒤 표를 채운다([가산점 증거 대장](../가산점-증거-대장.md)).
- 가산점 (2) 멀티모달: 음성, 전류, 음향, 영상 후보, 전력, 날씨를 상황 판단에 쓰는 설계다. 그중 세탁 완료 판정은 **전력 + 종료음 융합을 구현**했다(모의·합성 음 수준, §4-3-1). **융합 효과 비교는 미측정이다.**

| 항목 | 보드 | 상태 |
|---|---|---|
| 해석·제안 서비스 최소 호출 | RPi5 | 【실측 후 기입】 |
| 실행·검증 서비스 최소 호출 | RPi4 | 【실측 후 기입】 |
| 전력 계측·콘센트 통신 | ESP32 ↔ RPi4 | 【실측 후 기입】 |
| 제안 → 승인 → 실행 → CT 검증 시연 연동 | 3보드 | 【실측 후 기입】 |

### 8-1. 보드 역할을 바꾼 이유

- 15.8형 키오스크(1920×1080)와 기기 안 추론을 한 보드에서 돌리려면 RPi5 성능이 필요했다.
- RPi4는 센서 ADC, 폐루프 여유, USB 모션 연결을 맡기에 충분했고, 실시간 제어 자리(안내문 예시의 RPi Zero)를 맡는다.

## 9. 한계와 향후 과제

**한계 (2026-10-06).**
1. 모터·센서 실물 검증 0건. 누름 성공률, 정지 지연, CT 판정은 모두 미측정이다.
2. 물리 비상정지는 펌웨어(컴파일)와 래치 흐름(모의)까지이고 회로가 없다. 릴레이는 가전 전원을 끊을 뿐 모터 전원은 끊지 않으며, 물리 정지 확인(엔코더 속도 0)도 없다.
3. 실물로 준비하는 갠트리는 전자레인지용 1대다. 세탁기·인터폰은 조작부 모형이고 누름 경로가 미정이다.
4. 세탁 완료 판정 기준값은 추정이다. 코드는 CT 2채널(전자레인지·세탁기 동시 계측)을 받지만 펌웨어 컴파일·가짜 모듈 수준이고, 두 번째 CT는 구매 중이라 배선·채널별 보정은 하지 않았다. 인터폰 호출 감지는 없다.
5. ThinQ는 모의다. 실제 클라이언트 구현과 속성 확인이 남았다.
6. 실제 사용 이력이 없다. 제안 근거는 시연 데이터다.
7. 공간 감지 하드웨어(레이더)가 없다. 재실은 수동 보고다.
8. 다이얼식 조작부는 지원하지 않는다(실행 거절).
9. 당사자 사용성 평가를 하지 않았다.

**향후 과제.**
- 실측 결과로 판정 임계값 확정
- 콘센트 모듈 회로 조립과 비상정지 실물 확인, 두 번째 CT 채널
- 세탁기 표준 코스 전력·종료음 실측으로 완료 판정 기준값 확정
- ThinQ 실물 연동과 원복 제안
- 세탁기·인터폰 조작부에 누름 장치 적용(모형 → 실물)
- 당사자 평가와 접근성 실측
- 모션 MCU 확정에 따른 펌웨어 통합
