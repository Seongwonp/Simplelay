## 1. U1-a 구현 (하드웨어 없이 가능)

각 항목은 **실패 테스트 → 수정 → 통과** 순서. 파일 위치는 설계 §5 참고.

- [ ] 1-1 자료형: `ControlRoute`, `Confirmation`, `Command`(fingerprint 포함), `CommandResult`, `ApprovedCommand`.
      물리 `ExecutionResult` → 확인 수준 매핑(L1 통과 = state_confirmed, L3 통과 = operation_confirmed).
      테스트: fingerprint가 args 순서에 무관, 인자 하나 다르면 다름.
- [ ] 1-2 `ExecutionStatus.UNCONFIRMED` 추가. 이력·`/status`·앱 매핑에서 실패로 취급하지 않음.
- [ ] 1-3 `UsageRecord`·`job_history`에 `route`·`confirmation` 열(SQLite ALTER, 옛 기록 unknown).
      학습 조건: 기존(REAL+DIRECT+SUCCEEDED) + thinq는 state_confirmed 이상. 승인 기록은 계속 제외.
      테스트: accepted만 있는 클라우드 성공은 습관에 안 들어감.
- [ ] 1-4 승인 고정(결정 1): 제안이 확정 command를 들고 다니고, `approve()`/`approve_submit()`은 재해석 대신
      fingerprint 재검사 → 다르면 `ApprovalMismatch`(카드 되돌리고 새 카드). 실행 직전 재검사(대상·준비·상황)는 유지.
- [ ] 1-5 `StatusResponse`·`HistoryEntryResponse`에 `route`·`confirmation` 추가(기존 필드 유지).
- [ ] 1-6 `_record_care_outcome`: unconfirmed는 "보냈지만 확인 못 했어요"로 분리.
- [ ] 1-7 앱·키오스크 문구 분기(설계 §6 표). 화면 배치는 안 바꿈. 골든 갱신 후 이미지 직접 확인.
- [ ] 1-8 `EmergencyStopReport`에 `cloud_uncancellable` 자리만 추가(어댑터는 U1-c). 정지 순회에 클라우드 등록소 포함할 자리 표시.

완료 기준: 백엔드·폰·키오스크 전체 통과, 골든 비교 통과, analyze error·warning 0, 가드 통과.
개발현황·CLAUDE.md 검증 수치 갱신, devlog 기록.

## 2. U1-b 경로별 준비 상태 (U1-a 뒤)

- [ ] 준비 상태를 **route·요청 동작** 기준으로. physical은 기존 4축 유지. thinq는 인증·대상 접근·동작 지원·인자 범위·동작별 실행 조건.
- [ ] `_require_ready`의 `runs_locally` 예외 경로가 클라우드에 적용되지 않게.
- [ ] 확인 못 한 필수 조건은 조작 가능으로 두지 않음(테스트).
