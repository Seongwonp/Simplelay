# 장애 복구 결과표 (2026-10-07, 인계 노트북-3 §F)

상황마다 **자동 재전송·자동 재개가 없는지**와 **무엇이 막히는지**를 모의로 시험했다. 배선은 운영과 같다 — RPi5 `open_uart_act_controller`(재연결 포함)·`SimpleLayService`·API, RPi4 `rpi4.act_main._run`(실행기·콘센트 모듈 배선). `socket://`(socat)만 메모리 중개자로, 모터·콘센트 모듈·모션 MCU·센서는 가짜(모의 모터·`fake_outlet`·`FakeMcu`·가짜 ADS1115/마이크 모듈)로 바꿨다. **전부 모의 수준이다. 실물 정지 지연은 측정하지 않았다(미측정).**

## 시험이 찾은 결함과 수리

- **모션 MCU가 누름 중 재부팅했을 때 `SIMPLELAY_MOTION_AUTO_HOME`이 켜져 있으면 같은 실행이 스스로 재홈하고 다시 눌렀다**(실행 결과 `succeeded`). 폐루프가 어댑터 오류(`MotionReset`)를 L1 재시도로 넘기고, 재시도의 `press()`가 auto_home으로 원점 복귀부터 했기 때문이다. 수리(`rpi/controller/serial_motion.py`): 동작 중 재시작을 본 뒤에는 새 실행(`reset_stop`)이나 명시적 `home()` 전까지 auto_home을 쓰지 않고 누름을 거절한다. 수정 전 `[auto_home_on]`이 실패(`'succeeded' != 'succeeded'`)하는 것을 확인했다. 기본값(auto_home 꺼짐)은 수정 전에도 재누름이 없었다.

## 한계

- 실물 정지 지연(비상 버튼 → 모터 정지, 링크 끊김 → RPi4 정지)은 **미측정**이다. 시험은 '멈추라는 요청이 나가고 남은 버튼을 누르지 않는다'까지다.
- 링크 끊김은 RPi4가 EOF를 볼 때만 RPi4가 멈춘다. 소켓이 반쯤 끊겨(FIN 없음) RPi4가 모르면 RPi4는 시퀀스를 끝까지 누르고, RPi5는 이미 실패로 적었다 — 결과 유실과 같이 사람이 가전을 확인한다.
- 결과 유실·링크 끊김 뒤 '실패' 기록은 '안 눌렸음'이 아니라 '모름'이다. 화면 문구는 그대로다.
- FakeMcu는 원점 복귀 전 이동을 받는다 — 시험에서 펌웨어(`motion_refusal`의 `not_homed`)처럼 거절하게 바꿔 끼웠다. 실물 펌웨어 동작은 보드 확인 전이다.
