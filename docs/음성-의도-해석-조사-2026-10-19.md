# 음성 의도 해석 조사 (2026-10-19)

**질문:** 폰 음성 → RPi5 본체가 '가전이 할 수 있는 동작 목록' 중 하나로 해석 → 확인 카드 → 실행. 지금 해석은 **정확 비교 + 띄어쓰기·끝 문장부호 무시**(`rpi/services/thinq/bindings.py`의 `command_for_purpose`, 10/19 실기기에서 '공기 청정기 켜 줘'가 거절되던 것을 고친 단계)다.
이것을 **인터넷 없이 본체 안에서, 새 AI 시스템 없이(지도교수 방침 'AI 고도화 금지', 사용자 결정 '기존 기능 고도화만')** 무엇으로, 얼마나 가볍게 보강할 수 있는지 웹 자료로 조사했다.

**전제(바꾸지 않는 것):** 해석 결과는 **닫힌 목록(가전별 등록 동작 수~수십 개) 중 하나 또는 '모름'**. 목록 밖 짐작 금지, 실행 전 사람 확인 필수. 외부 클라우드 해석은 기본 꺼짐 선택지로만.

**읽는 법:** 모든 출처는 2026-10-19 확인. 수치는 출처가 잰 조건의 값이며 SimpleLay 본체에서 잰 값이 아니다 — 본체 값은 모두 `추측/측정 필요`. 상용 비서는 공개 설계 지침만 인용하고 성능 비교는 하지 않는다. 본체 사양은 RPi5(Cortex-A76 4코어 2.4 GHz, RAM 1~16 GB 판매)이며 **우리 보드의 RAM 용량은 확인 필요**([Raspberry Pi 5 제품 페이지](https://www.raspberrypi.com/products/raspberry-pi-5/)).

## 1. 닫힌 명령 집합 의도 분류 — 가벼운 방법 비교

| 방법 | 정확도 경향 | RPi급 CPU 지연 | 메모리 | 오프라인 | 설명 가능성 | '모름' 처리 |
| --- | --- | --- | --- | --- | --- | --- |
| A. 규칙 + 정규화 + 별칭(동의어) 사전 | 사전에 있는 말은 확실, 없는 말은 전부 실패 | 마이크로초 수준(추측/측정 필요) | 무시할 수준 | 예 | 가장 높음 — "'공청기'는 '공기청정기'의 별칭" | 일치 없으면 그대로 '모름' |
| B. 퍼지 문자열 매칭(편집 거리, 한글 자모 분해) | 오타·STT 한두 글자 오류에 강함, 뜻이 다른 비슷한 말(켜/꺼)에 위험 | 수십 개 후보면 밀리초 미만(추측/측정 필요) | 수 MB 미만 | 예 | 높음 — 점수와 가장 가까운 후보를 보여 줄 수 있음 | 점수 하한(cutoff) 미만이면 '모름' |
| C. 문장 임베딩 최근접(다국어 소형 모델, ONNX/CPU) | 바꿔 말하기에 강함, 짧은 반대말 구분은 약할 수 있음 | 출처 측정: 인텔 노트북 CPU에서 문장당 약 49 ms — RPi5는 측정 필요 | 모델 약 1.2억 매개변수, int8 ONNX 있음(파일 수백 MB급, 추측/측정 필요) | 예 | 중간 — 유사도 값만 설명 근거 | 유사도 하한 + 1·2위 차이로 '모름' |
| D. 소형 분류기(few-shot, 예: 임베딩 + 분류 머리) | 예문 몇 개로도 쓸 만하다는 보고 | C와 비슷 | C와 비슷 | 예 | 낮음~중간 | 확률 하한(보정 필요) |
| E. 소형 LLM + 선택지 제한 문법(llama.cpp GBNF) | 문맥 이해 가장 넓음, 근거 설명 어려움 | 출처 측정: RPi5에서 1~1.5B 4비트 모델 생성 약 10~11.5 토큰/초(프롬프트 처리 별도) | 1.4~2.4 GB RAM | 예 | 낮음 | 문법에 '모름' 선택지를 넣어야 함, 확률 보정 어려움 |

근거:

- **A·B(규칙·별칭·퍼지):** 오픈소스 스마트홈 허브의 로컬 의도 인식은 문장 틀(대안 단어 `(a|b)`, 선택 단어 `[..]`)과 일치시키는 방식이다([Home Assistant 개발 문서 — intent recognition](https://developers.home-assistant.io/docs/voice/intent-recognition/), [hassil](https://pypi.org/project/hassil/1.5.3)). 사용자 커뮤니티의 주된 불만은 STT 결과가 틀과 정확히 같아야 한다는 엄격함이고, 그 위에 퍼지 매칭을 얹는 외부 통합이 따로 나와 있다([hass-closest-intent 소개 글](https://deddit.petersanchez.com/g/selfhosted@lemmy.world/p/RLd3yH5Bjmtg3XTscn-I-created-hassclosestintent-Fuzzy-intent-matcher)). SimpleLay의 지금 상태(정확 비교)와 같은 문제·같은 보강 방향이다.
- **B(퍼지 라이브러리):** RapidFuzz `process.extractOne`은 `score_cutoff`를 넘는 후보가 없으면 `None`을 돌려준다 — '모름'과 바로 대응된다([RapidFuzz GitHub](https://github.com/rapidfuzz/RapidFuzz), [배치 처리 문서 요약](https://tessl.io/registry/tessl/pypi-rapidfuzz/files/docs/batch-processing.md)). 3.0부터 기본 전처리를 하지 않으므로 정규화는 직접 해야 한다(같은 문서).
- **B(자모):** 글자 단위 편집 거리는 한글 음절 하나가 받침 하나만 달라도 통째로 다른 글자로 센다는 한계가 문서화돼 있다([ParadeDB 퍼지 문서](https://docs.paradedb.com/documentation/full-text/fuzzy)). 자모 분해 도구는 파이썬에 여럿 있다([jamo](https://python-jamo.readthedocs.io/), [hgtk](https://pypi.python.org/pypi/hgtk/0.1.1), [jamolib](https://pypi.org/project/jamolib/)). 다만 표준 라이브러리 `unicodedata.normalize('NFD', …)`만으로도 음절을 자모로 풀 수 있어 새 의존성 없이 가능하다(추측 — 구현 시 확인).
- **C(임베딩):** multilingual-e5-small은 약 1.18억 매개변수·384차원, fp32/fp16/int8 ONNX 변형이 공개돼 있다([ONNX 모음](https://huggingface.co/usama99athar/multilingual-embedders-onnx-coreml), [Xenova ONNX](https://huggingface.co/Xenova/multilingual-e5-small)). 지연 측정은 인텔 노트북 CPU 기준 문장당 49 ms뿐이고 Pi 측정은 찾지 못했다([OpenVINO 모델 카드](https://huggingface.co/seminse/multilingual-e5-small-openvino-npu-static)). paraphrase-multilingual-MiniLM-L12-v2는 12층·384차원·어휘 25만, 최대 128토큰([config](https://huggingface.co/sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2/blob/main/config.json)).
- **D(few-shot):** SetFit은 문장 임베딩 모델을 예문 쌍으로 대조 학습한 뒤 분류 머리를 붙이며, 클래스당 8개 예문으로도 전체 학습에 견줄 만했다는 보고가 있다([arXiv 2209.11055](https://arxiv.org/abs/2209.11055v1), [HF 블로그](https://huggingface.co/blog/setfit)). '학습 단계'가 생기므로 지도교수 방침상 새 AI 고도화로 읽힐 위험이 크다.
- **E(LLM + 문법):** llama.cpp GBNF 문법은 각 단계에서 허용 토큰만 남겨 출력을 선택지로 묶는다([llama.cpp GBNF 사용 안내](https://instagit.com/ggml-org/llama.cpp/how-to-use-grammar-files-with-the-gbnf-format), [llguidance 문서](https://huggingface.co/OpenTransformer/llama.cpp-prismml/blob/main/docs/llguidance.md) — 토큰 마스크 계산은 단일 코어 평균 약 50 µs). RPi5 실측 표: 1B급 4비트 모델 약 11.2~11.5 토큰/초·RAM 1.4~2.4 GB, 1.5B 약 10 토큰/초·1.8 GB, 3B 약 4.7~5.2 토큰/초([RPi5 LLM 성능 조사](https://stratospherelinuxips.readthedocs.io/en/develop/immune/research_rpi_llm_performance.html), 보드 RAM 미기재·단일 프롬프트 측정). 문법 제약 분류의 Pi 측정은 찾지 못했다. 선택지로 출력을 묶어도 **틀린 선택지를 고르는 것**은 막지 못한다.
- **'모름'은 어떤 방법이든 약점:** 150개 의도 평가 세트 연구에서 분류기들은 범위 안 문장은 잘 맞히지만 범위 밖 문장 거르기에 고전했다([Larson 외, EMNLP 2019, arXiv 1909.02027](https://arxiv.org/abs/1909.02027v1), [oos-eval](https://github.com/clinc/oos-eval)). 거절 임계값은 검증 데이터로 정하고, 0.5 같은 고정값이 최적이라는 보장이 없으며, 의도 수가 늘면 1위 확률 자체가 작아진다([arXiv 2202.05957](https://arxiv.org/pdf/2202.05957), [arXiv 2209.04944](https://arxiv.org/pdf/2209.04944), [arXiv 2405.19967](https://arxiv.org/pdf/2405.19967)). 임계값 선택은 잘못 받아들임과 다시 묻기의 비용 저울질이다([Genesys 글](https://www.genesys.com/en-sg/wp-json/wp/v2/blog/501936)).

## 2. 한국어 특화

- **자모 vs 음절:** 한국어 문장 분류(감성·의도 유형)에서 음절(글자) 단위 특징이 자모 단위보다 대체로 나았다(Cho 외, PACLIC 33, 2019, [arXiv 1905.13656](https://arxiv.org/abs/1905.13656)). 학습 모델의 입력 표현 이야기이고, **편집 거리 비교에서 자모 분해는 별개 문제**다 — 받침 하나 차이(예: '켜'/'켜줘'의 접합, '청정'/'청전')를 작은 거리로 잡는 용도.
- **STT 오류의 모양:** 한국어 음성 인식 오류는 주로 글자 단위 불일치라는 관찰이 있다([arXiv 1811.04231](https://arxiv.org/pdf/1811.04231)). 2026년 한국어 음성 질의응답 연구도 한 글자 STT 오류가 뜻을 바꾸는 별도 실패 경로라고 본다([arXiv 2605.17443](https://www.alphaxiv.org/abs/2605.17443)). 즉 퍼지 비교는 도움이 되지만, **한 글자 차이로 뜻이 뒤집히는 쌍(켜/꺼, 올려/내려)** 은 퍼지로 합치면 안 된다.
- **형태소·어미 정규화:** Kiwi(Apache 2.0, C++ 핵심·파이썬 래퍼, ARM64 빌드)는 웹 문장 약 87%·문어 약 94% 정확도, 줄당 약 1.9 ms 예시, 기본 메모리 약 278 MB, 오타 교정 켜면 약 694 MB·로드 9.4 s([Kiwi GitHub](https://github.com/bab2min/Kiwi)). 수십 개 명령 목록에는 과하다 — 어미('해 줘/해줘/해 줄래/좀')는 짧은 접미 규칙 목록으로 떼는 편이 가볍고 설명 가능하다(판단, 측정 필요).
- **음성 표현 보강 연구:** 음소열과 STT 결과를 함께 쓰는 방식이 STT 오류에 강하다는 연구가 있으나([PhonemeBERT arXiv 2102.00804](https://arxiv.org/pdf/2102.00804), [arXiv 2203.12067](https://arxiv.org/pdf/2203.12067)) 모델 학습이 필요해 SimpleLay 범위 밖이다.
- **데이터셋:** 3i4K는 한국어 짧은 발화 약 6.1만 개를 7개 의도 유형(명령·질문 등)으로 나눈 것으로(CC BY-SA 4.0), 가전 동작 분류가 아니라 문장 유형 분류다([TFDS kor_3i4k](https://www.tensorflow.org/datasets/community_catalog/huggingface/kor_3i4k?hl=tr)). 공개 한국어 스마트홈 가전 명령 데이터셋은 이번 검색에서 확인하지 못했다(국가 데이터 포털 직접 검색 필요). **SimpleLay는 시험 세트를 직접 만드는 것이 현실적**(§5).

## 3. 음성 비서 공개 설계 지침 — 실패 시 대처·확인 대화

- **확인의 세 단계:** 결과가 큰 동작은 명시 확인(사용자가 승인해야 진행), 실수가 드물고 가벼운 동작은 암시 확인(들은 말을 되말하되 묻지 않음), 위험이 낮고 빠른 흐름은 맥락 확인([Alexa Haus — Be trustworthy](https://developer.amazon.com/en-US/alexa/alexa-haus/design-principles/be-trustworthy), [음성 설계 용어집](https://developer.amazon.com/fr/designing-for-voice/glossary/)). SimpleLay는 물리 기기를 누르므로 **모든 실행이 명시 확인(확인 카드)** — 이미 그렇게 돼 있고 바꾸지 않는다.
- **못 알아들었을 때:** 원래 질문을 그대로 반복하지 말고 짧게 사과 + 줄인 질문, 막히면 선택지·예시·화면 정보를 더하고, 사용자를 탓하지 않으며, 연속 실패는 2~3회에서 끝내고 다른 방법을 안내([Google 대화 설계 — Errors](https://developers.google.cn/assistant/conversation-design/errors), [Dialogflow 재질문](https://developers.google.com/assistant/df-asdk/reprompts?authuser=9) — 플랫폼은 종료됐으므로 원칙만). 사용자는 무엇을 말해야 하는지 볼 수 없으니 힌트를 주라는 지침도 있다([Alexa 블로그 — 슬롯 안내](https://developer.amazon.com/en-US/blogs/alexa/alexa-skills-kit/2019/07/guiding-users-with-successful-alexa-prompts-for-custom-slots)). → SimpleLay의 '모름' 화면은 **"이렇게 말해 보세요" 예시 2~3개 + 버튼으로 고르기**가 맞다.
- **고령자 실사용 연구:** 고령자 15명 4주 가정 연구에서 대화 턴의 약 24.8%가 오류, 가장 많은 것은 의도 인식 실패, 바로 다음 시도에서 풀린 것은 약 25.5%, 4주 동안 오류율이 줄지 않았다. 사용자가 반복·바꿔 말하기로 복구를 시도한 경우가 대부분이었고, 비서가 먼저 복구를 이끈 경우는 드물었지만 성공률이 더 높았다. 정해진 명령어 대신 자연스러운 말('고마워' 등)로 멈추려다 실패하는 사례도 보고됐다(Mahmood·Wang·Huang, ACM Transactions on Accessible Computing 19(1), 2026 — [서지](https://api.crossref.org/works/10.1145%2F3796236), [arXiv 2403.02421](https://arxiv.org/html/2403.02421v3)). 고령자 대상 음성 비서의 대체 응답(fallback) 원인으로 모호한 요청·지원 안 되는 기능·오작동 깨우기·전사 오류가 정리돼 있다([arXiv 2608.30738](https://arxiv.org/pdf/2608.30738), 게재처 미확인).
  → **설계 시사점:** (1) '모름'이 나오면 시스템이 먼저 가까운 후보·예시를 보여 줘야 한다(사용자 재시도에 맡기지 않기). (2) 멈춤 말은 넓게 받는다(이미 G7 정지어 '멈춰·그만·정지' — 발화 전체 일치 규칙은 유지). (3) 익숙해지면 나아진다고 가정하지 않는다.

## 4. 안전 — 물리 기기 조작에서 오인식 줄이기

- **민감 동작 추가 확인:** 음성 비서 업계는 문 열기·보안 카메라 끄기 같은 동작에 명시 승인 또는 PIN 확인을 둔다([Google Home — Secondary User Verification](https://developers.home.google.com/cloud-to-cloud/enhancements/secondary-user-verification)). 사용자 인터뷰 연구(16명)는 소리 내어 말하는 PIN을 신뢰하지 않으며 상황(장소·옆 사람)에 따라 요구가 다르다고 보고했다(Ponticello 외, [SOUPS 2021](https://www.usenix.org/conference/soups2021/presentation/ponticello)). → SimpleLay는 음성 승인 대신 **화면 확인 카드**로 승인하므로 이 우려를 피한다. 유지.
- **거절 선택지와 임계값(§1 마지막 항):** 범위 밖 문장 거르기는 분류기들의 공통 약점이고, 임계값은 검증 세트로 정해야 하며, 잘못 받아들임의 비용이 크면 임계값을 높여 '모름'을 늘린다. 물리 기기는 잘못 받아들임 비용이 크다.
- **SimpleLay에 대입:** 퍼지·임베딩이 만든 결과는 **"혹시 이것인가요?" 후보**로만 쓰고, 정확 일치와 똑같이 확인 카드를 거친다. 확인 카드에는 해석된 동작 이름을 크게 쓴다(사용자가 원래 말과 다른 것을 알아볼 수 있게). 반대 뜻 쌍은 퍼지로 넘나들지 못하게 막는다.

## 5. SimpleLay에 권하는 것

### 5-1. 얹을 방법 (가벼운 순, 둘 다 '규칙 계층 보강'이지 새 AI 아님)

**① 정규화 규칙 + 별칭 사전 (먼저, 거의 비용 없음)**
- 지금(띄어쓰기·끝 문장부호 무시)에 더해: 어미·군말 떼기 목록('좀', '해 줘/해줘/해 줄래/해 주세요/해라', '줘/줄래/주라') → 동사 원형으로, 가전 별칭 사전('공청기'·'공기 청정기' → 공기청정기), 동작 별칭('틀어'→'켜', '꺼 줘'→'꺼').
- 사전은 데이터 파일 한 곳에 두고 시험이 읽는다(가전별 등록 동작 목록 옆). 일치 이유를 그대로 기록할 수 있어 설명 가능성 최고.
- 예상 지연: 마이크로초~1 ms 미만(추측/측정 필요), 메모리 무시할 수준.

**② 자모 분해 편집 거리로 "혹시 이것?" 후보 1개 (①로 못 찾을 때만)**
- ① 정규화 뒤 남은 문장을 자모로 풀어(표준 라이브러리 NFD로 가능, 추측) 닫힌 목록과 정규화 편집 거리 비교. **점수 하한 미만 또는 1·2위 차이가 작으면 '모름'**.
- 결과는 바로 실행 후보가 아니라 **"'공기청정기 켜기'를 말씀하셨나요?"** 확인 카드 문구로(정확 일치와 구분되는 표시). 반대 뜻 쌍(켜/꺼, 올려/내려, 열어/닫아, 시작/정지)은 서로 다른 동사 묶음이면 퍼지 점수와 상관없이 후보에서 뺀다.
- 하한값은 §5-2 시험 세트로 정하고 문서에 근거를 남긴다(실측 전에는 `추측/측정 필요`).
- 예상 지연: 동작 수십 개 × 짧은 문장이면 1 ms 안팎(추측/측정 필요, RPi5에서 순수 파이썬 기준), 메모리 수 MB 미만(추측).

문장 임베딩(C)은 ①② 결과를 시험 세트로 재 본 뒤에도 바꿔 말하기 실패가 많을 때만 다음 후보로 검토한다(모델 파일 수백 MB급·RPi5 지연 측정 필요·설명 가능성 낮음).

### 5-2. 시험 방법

- 가전별 등록 동작마다 기대 결과(동작 ID 또는 '모름')를 붙인 한국어 변형 문장 세트를 시험 데이터로 둔다. 지표: **잘못 받아들임 0건 필수**(다른 동작으로 해석), 그다음 '모름' 비율을 줄인다. 퍼지 후보는 '후보' 표시가 붙었는지도 검사.
- 하한값을 바꾸면 세트 전체를 다시 돌리고 결과를 devlog에 남긴다. 수정 전 코드에서 실패하는 문장을 먼저 확인한다(커밋 게이트).

예시 20개(공기청정기 기준, 기대 결과는 ①② 적용 뒤 목표):

| # | 발화(STT 결과 가정) | 기대 |
| --- | --- | --- |
| 1 | 공기청정기 켜 줘 | 켜기 (정확·띄어쓰기) |
| 2 | 공기 청정기 좀 켜줘 | 켜기 (① 군말) |

### 5-3. 하지 말 것

- 퍼지·임베딩 결과로 **확인 카드 없이 실행**하지 않는다. 정확 일치든 후보든 같은 확인 카드.
- 반대 뜻 동사(켜/꺼 등)를 편집 거리로 넘나들게 두지 않는다. 부정('~지 마', '안 ~')을 무시하고 일치시키지 않는다.
- 닫힌 목록 밖 동작을 만들어 내는 생성형 해석(LLM 자유 출력)을 넣지 않는다. 소형 LLM은 문법으로 묶어도 '틀린 선택지'는 막지 못하고 RPi5에서 1~2 GB RAM과 초 단위 지연(추측/측정 필요)이 든다 — 지도교수 방침과도 어긋난다.
- 학습 단계가 있는 분류기(few-shot 미세조정 포함)를 결선 전에 넣지 않는다(새 AI 고도화로 읽힘·시험 범위 폭증).
- 측정 없이 하한값·지연을 문서나 화면에 사실로 쓰지 않는다. '정확도가 상용 비서보다 낫다' 같은 비교를 하지 않는다.
- 형태소 분석기를 이 용도만으로 들이지 않는다(수백 MB 메모리, 수십 개 명령엔 과함).
